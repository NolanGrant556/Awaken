# 消息输入与编辑 · 实现方案

本文说明代码职责、数据与接口、异常恢复和验证方法。功能范围及用户操作见[需求文档](需求文档.md)。

### `SlashProvider`

provider接收 `workspaceRootForRun`，只负责取数、可见性、action 和可选 token。palette只负责 active、hover preview、键盘和选择；runtime只消费认识的 token type。

当前 App 与定时任务 Agent 编辑器都为 `/` 注册排除 plugin 来源的 Skill provider。Workbench `@` 注册 Deep Research workflow token、内置 Computer Use capability provider 与已启用 Plugin provider；定时任务 Agent 编辑器的 `@` 只注册 Computer Use 与 Plugin，不注册 Deep Research。file/prompt/connector 仍是扩展类型，不是已支持产品能力。`SlashAction.type = "workflow"` 当前只用于 Workbench `@deep-research` / `@研究` token，见 [16 深度研究](../../../README.md#16_深度研究)；token 选择后必须再输入研究问题才能提交，提交后绑定研究意图并由主 Agent 组队调研、审稿、按问题发布 Office 或 Markdown。不得把 `/` Skill、plugin Skill 或同名用户 Skill 写成深度研究。定时任务选择 Computer Use 只持久化同一个 capability token，不提前授予工具权限，也不允许无人值守自动通过 review、handoff、系统授权或其它安全 gate。

## 提交与运行边界

`useThreadComposerDraft.clearForSubmission(ownerKey)` 清空本次 owner 的草稿并登记内存提交标记，返回绑定该 owner 和标记的恢复函数。正文/token/附件/placement 的后续修改、显式清空或再次提交会使旧标记失效；selection 更新不会。恢复使用同一 React 状态的函数式更新检查标记，失败只能回填仍属于本次提交的空草稿，不依赖调用时的当前会话或过期闭包。标记不进入 Core、journal 或持久化。

`useRunSubmission` 在 startRun 失败时先调用该恢复函数，再用 ThreadSession generation 判断是否向当前视图发出失败状态。`useRunSubmission.test.ts` 覆盖切走后失败回填与迟到成功隔离；`useThreadComposerDraft.test.tsx` 在 StrictMode 中覆盖完整草稿、光标更新、后续编辑/清空/重提以及编辑后又删空。真实 Desktop 草稿切换证据见 [A 草稿](../../../apps/desktop/test-fixtures/runtime-consistency/desktop-draft-A.png)、[B 草稿](../../../apps/desktop/test-fixtures/runtime-consistency/desktop-draft-B.png)及[源码摘要与范围](../../../apps/desktop/test-fixtures/runtime-consistency/manifest.json)。实际窗口验证 A/B 来回切换后各自草稿保留；startRun 迟到失败及较新编辑保护由上述隔离回归覆盖，本次没有在真实 Desktop 注入这两类失败。

`toRunInputAttachment()` 移除 renderer-only previewURL。run input：

- image可携带 base64、mime、尺寸，作为视觉输入；
- file携带绝对路径、mime、大小和显示名；
- runtime把文件加入 attached-files/TaskScope后，Agent按需用工具读取；
- 附件事实不拼进用户正文；
- provider capability不在 renderer硬拦图片，真实不支持由运行错误/降级表达；
- 不能把附件路径本身视为授权写入边界。

## 耐久历史与恢复

### Append-only marker

物理 journal 不截断或覆盖。成功改写追加一个无可见 AG-UI 帧的 `thread_rewound`：

```json
{
  "kind": "thread_rewound",
  "thread_id": "thread_...",
  "payload": {
    "rewind_id": "rewind_...",
    "target_run_id": "run_...",
    "previous_active_head_run_id": "run_...",
    "mode": "undo"
  }
}
```

读取层按 semantic sequence 折叠 active run lineage：marker 使 active lineage 中从 `target_run_id` 到当时头部的所有 run 失效；marker 自身不进入模型消息或 Workbench narrative。后续新 run 正常追加，因此编辑表现为“rewind 后追加 replacement run”。

所有下列路径必须消费同一 active lineage：

- `messagesFromSemanticRecords()` 的模型 conversation 恢复；
- `RestoreThread()` 的内存 Agent/thread 重建；
- `GetThreadTranscript()` 与 Desktop replay；
- `ThreadSnapshot.RunID` 和侧栏 preview 投影。

rewind 成功后 Runtime 丢弃该 thread 的内存 sessions/thread；下一次运行必须从折叠后的耐久历史重建，不能携带失效后缀的 conversation 或 provider opaque state。metadata 的 latest run/preview 是投影；首轮撤销时必须显式清空，不能因空值合并规则保留旧头部。

### 并发与失败

- `RewindThread` 持有排他的 thread/project mutation 边界，和 `StartRun` 互斥。
- 请求的 `expected_head_run_id` 必须等于当前 active head，且 target 必须仍在 active lineage；否则返回 `THREAD_HISTORY_CONFLICT`。
- journal marker append + flush 成功后才更新 metadata 和丢弃内存状态。
- Core 提交失败时 Desktop 保留原回复与编辑内容。
- 当前编辑发送由 `rewind` 与现有 `StartRun` 两步组成：若 rewind 已提交而新 run 创建失败，旧后缀保持失效，修改后的结构化草稿恢复到 Composer 供用户修正或重试，不伪造 replacement run。

## 接口

### Core HTTP

```text
POST /v1/threads/{thread_id}/rewind
Content-Type: application/json
```

请求：

```json
{
  "target_run_id": "run_被撤销的用户轮次",
  "expected_head_run_id": "run_当前有效头部"
}
```

成功响应：

```json
{
  "thread": { "thread_id": "thread_...", "run_id": "run_前驱或空" },
  "target_run": { "run_id": "run_...", "input": "..." },
  "removed_run_ids": ["run_...", "run_后续..."]
}
```

`target_run` 是 Core 在改写前读取的 canonical run，用于恢复正文、附件、token 和文件评论；客户端不能从已渲染 DOM 反推耐久输入。`removed_run_ids` 是回执，不是 Renderer 本地 splice 的 authority；UI 必须重读 canonical transcript。

稳定错误：

| HTTP | code | 含义 |
|---|---|---|
| 400 | `INVALID_REWIND_TARGET` | thread/target/head 缺失 |
| 404 | `THREAD_NOT_FOUND` | 会话不存在 |
| 409 | `THREAD_BUSY` | 会话有活动 run 或正在删除 |
| 409 | `THREAD_HISTORY_CONFLICT` | target/head 已不是当前有效谱系 |
| 409 | `THREAD_REWIND_UNSUPPORTED` | v1、归档、定时或 ACP 会话 |
| 503 | `PERSISTENCE_UNAVAILABLE` | 无耐久 journal |

### Desktop bridge

Renderer 只通过 `RuntimeClient.rewindThread()` 调用 typed Preload/Main bridge。Main 对 path segment 编码并映射 wire DTO；Renderer 不获得 journal 路径、FileStore 路径或模型凭据。新回复仍通过既有 `startRun()`，Main 继续负责完整模型配置和 secret 边界。

## Composer 形态与高度的实现

### 会话模型与推理强度

- 模型弹层选择支持 effort 的模型后进入二级面板；当前模型按钮、模型列表与二级面板标题复用同一枚供应商 Logo。档位通过 Codex 式单行离散轨道选择，不显示 `Effort`、Apply 或档位文字；最低档直接落在轨道左端且不重复画圆点，其余真实档位圆点始终保留在中性轨道层，最高档提示点在右端内侧留出间距，而选中最高档后的白色滑块仍到达轨道右端。彩色光流从上层覆盖已经过的点，白色圆形滑块覆盖当前点，只让滑块右侧尚未选择的中性灰点露出。往回拖时光流裁切边界后退，被覆盖的档位点自然重新出现，不通过隐藏节点模拟。左侧为增强线宽、亮度和局部辉光的连续光流填充，右侧为无彩色的中性轨道；普通档复用 `AwakenMemoryLightFlow` 的紧凑绿色光流，最右 `max` 档使用同一绘制器的红色色调；Composer 只持有档位状态和交互，光流 primitive 不读取 thread preference；
- 模型菜单打开时由 Design System 让底部模型触发按钮执行同一套 240ms 横向伸展动效：右端保持稳定，胶囊从当前内容宽度向左拉长到当前模型槽宽度，内容随胶囊居中，宽态 Chevron 同步旋转并在关闭时反向收回；模型列表卡片保持原有尺寸和定位，不参与伸展。模型槽占用工具栏第三列，上限 `16.25rem`，长模型名在槽内省略；展开宽度不得超过该槽，不得按 `100vw` 或视口比例侵入 `+` / 插件入口。`center` 首页与 `dock` 对话页共享实现，只在点击时读取一次按钮宽度，不新增计时状态、运行时订阅或持续循环，`prefers-reduced-motion` 下直接显示展开后的按钮并停用 Chevron 过渡；
- 模型菜单仍锚定在 ComposerBar 当前层级内：`center` 优先向下、`dock` 优先向上；首选方向空间不足且另一侧空间更大时自动翻转，并按可用高度内部滚动。菜单打开期间窗口缩放或祖先滚动必须重新计算，不得把某一形态永久固定成向上或向下；
- Composer 自身可用宽度不超过 `440px` 时，Design System 通过容器查询把模型触发按钮收为只显示供应商 Logo 的 32px 圆形胶囊，隐藏可见模型名与 Chevron；完整 `模型名 · effort` 继续作为按钮 accessible name 与 hover title，菜单内仍显示完整模型信息。宽度恢复后文字与 Chevron 自动恢复。右侧栏打开导致 Composer 变窄时，先截断模型名再必要时收为 Logo 胶囊，不读取 Inspector 状态、不新增 Renderer 尺寸状态；
- 指针按下和拖动期间，滑块及填充边界使用轨道内的精确指针位置；松手、取消、键盘选择或面板重开后收敛到当前 capability 档位圆点。`max` 只在进入轨道最右区域并跨过像素回差后触发，反向拖回使用对称回差防止抖动。点击、拖动或 Arrow/Home/End 只能落在 capability 真实存在的档位并立即写入 thread preference；单纯悬停或移动不变更档位；`prefers-reduced-motion`、页面隐藏、离屏和卸载时沿用光流 primitive 的静态/停绘策略；
- 不支持 effort 的模型直接选择，不显示空入口；MiniMax thinking 开关不作为 effort；
- 应用后标签为 `模型名 · effort`，无档位模型只显示模型名；
- 有历史消息时只在模型与推理强度二级面板内显示“切换模型或推理强度会重建对话缓存，下次发送消息时生效”的说明，不再触发全局提示条；
- run busy 时模型与 effort 控件禁用，选择只影响下一次 run；
- 已有 thread 通过 typed model-preference IPC 立即持久化；未建 thread 的 center 草稿在首次 run 时原子写入；
- profile 失效或档位变化时回退有效 default，并只提示一次，不批量改写历史 thread。

## 键盘与 IME的实现

统一 token editor 以浏览器 DOM 为编辑期事实源，但不把 React children 当作受控正文。非 composition 的 `input` 把每个 token 前的文本回传为该 token 的 `leadingText`，最后一个 token 后的文本回传为 `composerValue`；composition 期间不向 DOM 回写。外部 draft 真正变化时才重建 DOM，并用“正文 UTF-16 offset + 每个原子 token 计 1”的逻辑位置恢复 selection。该逻辑位置不包含 token label，也不写入持久化数据。selection listener 必须通过稳定 callback/ref 读取最新上层回调；上层 render 产生的新函数 identity 不能重新注册 listener 或立即回写一份等价 selection，draft owner 对逻辑位置和 caretRect 都相同的更新返回原 state。

## 行内排版与说明浮层

`AwakenComposerBar.css` 和 `AwakenUserPromptBlock.css` 的 token 使用 `inline-flex`、`vertical-align: baseline` 与 `align-items: baseline`，由文字标签提供共享基线；图标单独 `align-self: center`，保持 16px，正文与标签保持同一 14px/20px 字号与行高。不能只把外层改成 baseline 而仍让第一个图标参与容器基线计算。center、dock、embedded 和 Prompt bubble 使用同一规则，不改动原子节点、leadingText、逻辑光标或持久化格式。

主 palette 通过 `computePosition` 把光标矩形作为虚拟锚点，并用 input 作为 contextElement 观察弹窗滚动；异步测量按请求版本提交，关闭或更新后的旧结果不回写。`AwakenComposerSlashPreview` 以真实候选按钮为锚点，使用 Floating UI 的 autoUpdate、flip、shift 与 size，测量说明的实际尺寸并限制在窗口和 clipping ancestors 的交集内。浮层仍挂在 Composer palette 内，不转移到全局 overlay，不提高层级绕过弹窗滚动职责。定位完成前隐藏；滚动列表或移出列表后关闭旧说明。`/` 与 `@` 复用此组件。

运行 `npm run test:composer-layout` 会构建真实组件，在独立 Electron 进程与临时 userData 中检查三个 Composer 形态、消息气泡、重启提示，以及弹窗左右边界的说明浮层。测试不连接用户 Core、调用 LLM 或访问用户数据；真实 Desktop 验收仍按下节入口执行。通过 `AWAKEN_LAYOUT_BASELINE=<提交>` 可用旧源码运行同一夹具，确认回归能识别缺陷；`AWAKEN_LAYOUT_RESULTS=/tmp/result.json` 可保留测量结果。只测窗口坐标函数不足以证明弹窗内浮层可见，必须检查实际渲染边界。

macOS 当前证据见[排版与浮层验证记录](../../../apps/desktop/test-fixtures/composer-visual-layout/verification.json)。记录区分隔离 Electron 几何、真实 Desktop 输入/选择/消息回读与未执行的故障注入；截图不扩大为其他平台通过证明。

## Trigger 与过滤的实现

```text
/(?:^|\s)\/([^\s/@]*)$/
/(?:^|\s)@([^\s/@]*)$/
```

- `/` 只显示当前可调用且 `sourceOrigin != "plugin"` 的普通 Skill；Workbench `@` 显示 Deep Research workflow、内置 Computer Use capability action 及已启用 Plugin；定时任务 Agent 编辑器的 `@` 显示 Computer Use 与已启用 Plugin，但不含 Deep Research。即使 Plugin 目录为空，Computer Use 仍保持可选；
- `@` 查询对 Computer Use 与 Plugin 使用同一过滤；两类结果都无命中时显示“没有匹配的能力或 Plugin”，不得把仍可用的 Computer Use 误报成空 Plugin 目录；
- `@` palette 按来源显示两个连续分区：`内置` 只包含宿主拥有的 Deep Research 与 Computer Use（定时任务只显示其中的 Computer Use），`插件` 包含其余已启用 Plugin；分区只改变目录层级展示，不改变 action 顺序、过滤、键盘导航、token identity 或运行时复验；
- `AwakenComposerBar.css` 的 textarea placeholder 与 inline editor 空态伪元素统一使用 `--aw-text-tertiary`，textarea placeholder 的 opacity 固定为 1；禁用状态仍由输入组件自己的 disabled 行为处理，不改变高度、光标或提交。
- Workbench 与定时任务 Agent 输入提示都把 `@` 描述为选择“内置功能或插件”，不能继续把整个入口写成只选择 Plugin；
- `/doc` 过滤；
- `@computer`、`@电脑` 可过滤到 Computer Use；
- `/doc`、`@computer`、`你好 /doc`、`中文123 @computer` 可触发；`你好/doc`、`中文123@computer`、`我们/`、`我们@` 不触发；把光标放在 query 后时，marker 后已有后续正文也不妨碍当前 caret 对应的 trigger；
- 先输入整句、再把光标移回句中补空格后输入 `/`、`@`，与从左到右顺序输入使用同一规则；只补 marker 而没有空格不触发；非 collapsed selection 不触发；
- Escape 或选择只删除当前光标对应的 trigger，保留前文和光标后的正文；选择 action 后 token 插入 trigger 原位；
- filter 匹配 label、description、preview description/path、keywords，不区分大小写；
- provider 的完整过滤结果都必须保留；palette 只通过最高 210px 且受裁切容器约束的可视窗口、内部滚动和后续可选的虚拟化控制渲染成本，不得用固定条数截断能力目录；
- Core 对 Skill Registry 或 Plugin Store 的成功 mutation 递增 composer catalog revision 并通过 `/v1/composer-catalog/events` 发布失效事件。Desktop 常驻订阅，palette 保持打开时按当前 marker、workspace 和 revision 重新读取对应 provider；旧异步请求卸载或 revision 变化后不能覆盖新结果。每次重新打开仍直接读取当前目录，不依赖事件没有丢失。

## Skill provider 当前规则的实现

Skill token payload：

```ts
{
  skillId: string;
  sourceOrigin: string;
  skillFilePath: string;
  rootDir?: string;
}
```

### Plugin mention provider

```ts
{
  pluginName: string;
  pluginDigest: string;
}
```

### 项目路径 token

```ts
{
  path: string;
  entryKind: "file" | "directory";
  projectId: string;
  folderPath: string;
  relativePath: string;
}
```

### 项目路径 token

Desktop 先用 typed Main IPC 对当前 active project、精确绑定文件夹、lexical/realpath containment、存在性、条目类型与 symlink 做校验，再把返回 identity 插入当前逻辑 selection。token label 只使用 basename，绝对路径不进入 editing host 或复制出的可见正文。StartRun 时 Core 必须按当前 `projectId` 与精确 `ReadableRoots` 再校验相对路径、真实路径和类型；项目切换、文件夹解绑、删除、类型变化或 symlink 都使旧 token 结构化失败。成功后 Core 才在 model-facing effective input 的原 token 位置写入绝对路径，持久化的 display input 与 prompt bubble 仍只显示名称 token。

## Token 顺序与删除的实现

统一 editor 中的正文 segment 可重新定位和编辑。每次结构化回调按当前 token 顺序更新 durable `leadingText`，最后 segment 更新 `composerValue`；React 普通 rerender 不重建 editing DOM，因此光标不会因为状态同步跳到末尾。

## 附件选择与粘贴的实现

### 文件选择

{
  id;
  kind: "image" | "file";
  path?;

  dataBase64?;
  displayName?;

## UI 投影的实现

- `leadingText`、原子 token、token 间正文与最后尾文共同位于一个 `contenteditable="plaintext-only"` editing host，不得使用多个 DOM 编辑区、独立 flex 文本块或 textarea 拼接；
- 长前缀换行后，token 和后续输入在剩余宽度允许时继续同一行，光标紧跟尾文，不能把编辑面整体推到 token 下方；
- token 边界使用 Design System 视觉间距，不得通过改写 `composerValue` 或最终 prompt 注入空格；
- token 内部使用 `16px` 线性图标、`5px` 图标/label 间距和 `8px` token 后间距；整个 token 通过 `14/20px` 行盒的几何中心与相邻中英文、英文和数字对齐，不应用图标下沉，也不得按 token 类型各自补偏；
- token DOM 使用稳定 `data-composer-token-id` 与 `contenteditable="false"`；token label、Skill 路径、Computer Use 隐藏引导和 caret 辅助字符均不得进入可见正文或复制结果；项目路径与 capability token 的 identity 会结构化持久化，但只有复验后的绝对路径或固定 capability 引导进入 model-facing effective input，不回写 display input；当前实现不使用 zero-width caret sentinel；
- composition start/update/end 期间浏览器独占编辑 DOM；composition 完成后再同步结构化状态。外部 draft restore 可重建 DOM，但必须恢复逻辑 selection；
- 无 token 时继续使用原生 textarea；移除最后一个 token 后恢复其 `leadingText` 并回到普通文本输入面。

- 位于 ComposerBar 输入 surface 之后，只在 `variant="center"` 且父级传入 `projectPicker` 时显示；
- 当前项目名称直接从 `options[].selected` 派生，不在组件内保存第二份选中项目；
- 菜单选项和「创建项目」只触发父级回调，组件不读取 workspace、FileStore 或 Electron；
- 低栏不是输入正文、附件条、metaItems、overlay 或 dock stack，不参与 run payload。
