# 中间区域设计不足诊断

## 1. 结论摘要

基于当前需求包、架构契约、历史切片和 `main` 上真实实现的静态调研，可以得出一个明确结论：

**当前中间区域的结构壳设计基本成立，但交互系统设计不足以稳定覆盖整个中间区域。**

这意味着：

- `RunStage -> ExecutionFeed -> ComposerDock` 作为结构骨架是对的；
- turn 叙事、底部 composer、overlay、marker rail 的分层方向也是对的；
- 但 scroll、anchor、sticky、follow、prompt 折叠、approval 高度变化、overlay 恢复入口、work packet 聚合等交互没有被统一设计成一个完整系统；
- 结果就是：局部补丁可以暂时修复某个现象，但很容易破坏另一个已经成立的行为。

所以，当前中间区域频繁出现 BUG，以及“修一处、另一处又坏”，根因更接近于：

**设计覆盖不足和交互建模不完整，导致实现层长期在同一套脆弱事实之上叠补丁。**

## 3. 当前设计已经足够的部分

以下部分目前可以判断为“设计方向成立”：

### 3.1 结构主骨架成立

当前中间区域已经形成了清晰的结构骨架：

```text
WorkbenchShell
  -> RunStage
    -> ExecutionFeed
    -> ComposerDock
    -> overlay
```

这套骨架至少解决了三个大问题：

- 中间区域有唯一滚动容器；
- narrative、composer、overlay 有明确挂载层；
- 运行态与空态可以共用同一主舞台，而不是分裂成两套页面。

这部分设计不足以解释当前的大多数连锁 BUG。

### 3.2 narrative 与非 narrative 的分层方向正确

当前契约明确要求：

- `ExecutionFeed` 只承载 turn / narrative；
- composer 通过 `RunStage` 的 composer slot 挂载；
- marker rail、toast、未来 return affordance 通过 overlay 挂载。

这个边界本身是健康的，因为它避免了：

- 在 feed 内混入输入和控制面板；
- 在 composer 内混入不该参与布局测量的浮层；
- 在 `RunStage` 外再造新的 fixed 容器。

### 3.3 turn 作为叙事单元的设计方向正确

需求包和当前实现都已经收敛到同一个核心事实：

- prompt 属于 turn；
- prompt 下方的 thinking / tool / approval / file change / answer 属于同一 turn 叙事；
- marker、sticky header、anchor 都应围绕 turn，而不是围绕单条 message 或纯滚动位置。

这说明产品语义主轴已经清楚，不需要推翻。

## 4. 当前设计不足的部分

真正不足的是下面这些“交互系统层”的设计。

### 4.1 缺少统一的中间区域交互状态机

需求包已经明确提出，后续算法至少要显式建模：

- `currentTurn`
- `latestTurn`
- `pendingPromptAnchor`
- `followLatestOutput`
- `pausedByUser`
- `resumeIntent`
- `composerInset`
- `promptBubbleMode`
- `programmaticScroll`
- `returnToLatestAffordance`
- `workPacketMode`

但当前 `main` 上被真正统一建模的，主要只有：

- pending prompt anchor
- latest output follow
- paused / resume intent
- programmatic scroll
- active turn
- composer inset

而且这些状态并不是被组织成一个正式状态机，而是分散在：

- `ref`
- `ResizeObserver`
- `useLayoutEffect`
- DOM 测量
- CSS 变量
- 组件内部本地状态

中间区域已经不是“一个滚动算法”能解释清楚的规模了，但目前的设计仍偏向用局部规则把它拼起来。

这会直接导致：

- 某个状态的变更边界不清楚；
- 某个被动布局变化容易被误判成用户意图；
- 某个新增交互很难找到唯一归属层。

### 4.2 用户意图与被动布局变化的边界设计不够稳固

需求包已经把这条原则说得很清楚：

- 用户主动滚动、点击 marker、阅读历史，是“用户意图”；
- markdown 增高、ThoughtTrace 增高、approval card 出现、composer 多行增高，是“被动布局变化”；
- 后者不应被误判为前者，也不应反向触发恢复 follow。

但当前设计里，这条边界还没有被上升为清晰的系统模型，而更多依赖：

- wheel / touch / scrollTop 方向判断；
- near tail 判断；
- at scroll bottom 判断；
- 少量 resume intent 标记。

这对 P0 主链够用，但对真实复杂交互不够稳：

- prompt 展开导致高度变化时怎么办；
- approval stack 出现或消失时怎么办；
- multiline composer 高度变化时怎么办；
- 未来 return-to-latest 按钮出现时怎么办。

只要这些变化继续沿着“额外判断条件”叠加，而不是被纳入统一意图模型，就会越来越脆。

### 4.3 多种行为共享同一套布局事实，耦合过高

当前中间区域有一条很关键但也很脆弱的共享事实链：

- composer 实际占用高度
- output gap
- latest turn min-height
- sticky header 可读空间
- marker rail bottom
- near tail 判定
- native scroll bottom

这些行为都依赖同一个底部空间事实，但目前的设计缺少更高层的“唯一语义定义”。

于是问题就变成：

- 改 dock 高度测量，会影响 final output 避让；
- 改 latest turn min-height，会影响 prompt 锚定和滚动尾部；
- 改 overlay 位置，会影响按钮是否压到 composer 或 narrative；
- 改 approval/runtime panel 的挂载方式，会影响 composer inset 和 follow。

也就是说，现在并不是某个点写错了，而是很多行为共用同一根骨架，却没有被完整制度化。

### 4.4 交互责任过度集中在 Desktop renderer 编排层

设计系统层当前是“被动壳”，这是合理的；但代价是 Desktop renderer 层承担了过多跨域职责。

当前中间区域相关职责同时集中在：

- `App.tsx`
- `useRunStageScrollController.ts`
- `workbenchPresentation.ts`

这里面混杂了：

- narrative 渲染
- approval 渲染与去重
- runtime panel 栈
- turn marker rail
- thread replay 与恢复
- scroll / sticky / follow
- composer 生命周期
- DOM 测量与 CSS 变量写入

这种设计会让局部改动天然带有“跨域回归风险”，因为：

- UI 层改一个挂载位置，可能影响 scroll controller；
- narrative 层改一个 DOM wrapper，可能影响 marker 和 anchor；
- approval 层改一个展示策略，可能影响 composer inset。

这也是典型的“可以继续做功能，但越来越难稳定”的信号。

### 4.5 关键交互状态仍被藏在局部组件内部

有些行为已经是正式产品交互，但状态仍不是中间区域系统状态的一部分。

最典型的是 prompt bubble 折叠 / 展开：

- 当前它已经不是纯视觉细节；
- 它会影响 prompt 高度、sticky header、anchor 位置和 turn body 可视空间；
- 但它仍主要是 `AwakenUserPromptBlock` 的组件内部状态。

这意味着：

- scroll controller 看不到一个正式的 `promptBubbleMode`；
- layout 系统也没有统一消费这个模式；
- 未来任何围绕 prompt 高度的修复，都容易只修到局部而不是修到系统。

### 4.6 已确认的中间区能力仍未完整落地

需求包定义的一些能力，当前还没有真正进入系统：

- return-to-latest affordance 仍未落地为正式 overlay 能力；
- collapsed work packet 仍未形成正式 narrative 模型；
- 长工具 / 文件 / 执行日志仍缺少统一的高层摘要载体。

这件事的影响不是“少了几个功能”这么简单，而是：

- 用户缺显式恢复入口时，只能继续把恢复逻辑压在滚动启发式上；
- work packet 不存在时，主叙事要么过细、要么过空；
- 设计上没有第一等对象，实现层就会继续用临时兼容逻辑填补。

### 4.7 当前中间区域更像“切片叠加结果”，而不是完整交互系统

从历史切片可以看出，这个区域是按阶段长出来的：

- 先做 workbench 壳；
- 再做 prompt / planning；
- 再做 stop / follow-up；
- 再做 exploring；
- 再做 approval / file change；
- 再做 replay 恢复。

这种演进方式本身没有问题，但如果缺少一次中途的系统化收束，就会留下两个后果：

- 局部组件都合理；
- 整体交互却没有统一的状态与事件总图。

这正是当前中间区域最核心的设计债。

## 5. 为什么这里会频繁出现“修一处坏一处”

综合来看，当前连锁 BUG 的产生路径大致是这样的：

1. 某个现象暴露出来，例如 sticky header、final output 避让或按钮位置不对。
2. 实现层在现有 ref / effect / CSS 变量链上增加一条局部规则。
3. 这条规则会改变共享布局事实或事件链。
4. 另一个原本依赖同一事实的行为随之被破坏。
5. 新一轮修复再次以补丁方式叠加，系统越来越难推理。

最容易互相牵连的几组行为是：

- prompt 高度、sticky ownership、latest turn min-height
- composer 高度、bottom inset、final output gap
- marker 点击、active turn、follow pause / resume
- approval / runtime panel stack、高度测量、dock safe area
- transcript replay、turn 分组、active turn 恢复

所以这里的高频 BUG，不应被理解为“工程师不够小心”，而应被理解为：

**当前设计没有给这些高耦合交互提供足够清楚的系统边界。**

## 6. 现阶段最需要补的是设计，而不是继续叠补丁

如果只从“修当前 bug”出发，这个区域还可以继续往下补；
但如果目标是降低后续回归率，当前最值得补齐的是以下设计层内容：

### 6.1 中间区域状态总图

要明确：

- 哪些状态是第一等状态；
- 哪些是派生状态；
- 哪些状态只能由用户事件改变；
- 哪些只能由布局事实改变；
- 哪些需要在 thread switch / replay / rerun 时复位。

### 6.2 中间区域事件总图

要明确：

- 用户事件：submit、wheel、touch、pointer、marker click、prompt expand、return click
- 被动事件：body grow、markdown ready、approval show/hide、composer grow、viewport resize
- 系统事件：run requested、run created、run finished、thread switched、replay restored

否则后续所有“为什么这里恢复了 follow / 为什么那里 sticky 交接了”都会继续靠追 effect 链定位。

### 6.3 唯一布局事实定义

需要把以下语义正式化，而不是靠多个函数默契维持：

- 什么叫 latest output tail
- 什么叫 native scroll bottom
- 什么叫 composer inset
- 什么叫 latest turn bottom reserve
- 哪个空间是按钮可以悬浮但不能占位的空间

### 6.4 第一等交互对象补齐

下列对象应被当作正式交互对象，而不是局部技巧：

- prompt bubble mode
- return-to-latest affordance
- collapsed work packet
- active turn ownership handoff

这些对象如果没有进入系统模型，未来还是会重复出现“单点修复”。

## 7. 对后续工作的建议

本诊断不提供具体实现方案，只给设计推进建议。

建议按以下顺序推进：

1. 先补“状态 / 事件 / 转换”设计稿，不直接写实现。
2. 把 `promptBubbleMode`、`returnToLatestAffordance`、`workPacketMode` 正式纳入中间区域模型。
3. 明确“用户意图”和“被动布局变化”的边界，不再继续靠零散启发式外扩。
4. 明确唯一布局事实，避免 output gap、inset、tail、safe area 各算各的。
5. 每次只改一个行为轴，并用真实 Desktop 做对应 AC 验收。

## 8. 最终判断

最终判断可以收敛为一句话：

**当前中间区域不是“局部算法还差一点”，而是“结构设计已成型，但交互系统设计仍未完整成型”。**

因此：

- 它可以继续承载当前一部分能力；
- 但它还不足以稳定覆盖整个中间区域；
- 在没有补齐交互系统设计之前，继续直接修 bug，仍会较高概率出现新的连锁回归。
