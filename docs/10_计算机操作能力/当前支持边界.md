# 计算机操作能力当前支持边界

## 1. 权威范围

本文唯一拥有 Awaken 当前是否具备原生 Computer Use、哪些现有能力不能与其混同，以及把目标能力迁入“当前支持”所需的证据。未来实现分别由本目录的目标契约拥有。

选择 CUA 作为首个 Driver 是已经确认的**目标设计**，不表示当前产品已经接入 CUA。

## 2. 当前产品事实

截至当前代码，Awaken 没有原生 Computer Use。用户不能通过 Awaken 自有受控运行时观察整个桌面、定位窗口或 accessibility 元素、发送鼠标键盘输入、批准高风险 GUI 动作、接管/交还控制权，或回放 GUI 轨迹。

当前代码不存在：

- `src/computer` 或等价 Computer domain/runtime；
- `LaneComputer`、`ComputerExecutor` 或 run-scoped `ComputerSession`；
- `computer_observe`、`computer_act`、`computer_verify`；
- CUA 依赖、构建、签名、打包、启动或 readiness 接线；
- Computer session、lease/fence、action review、takeover 或 unknown-outcome 恢复；
- Computer 专属 SemanticJournal 记录、控制 route、AG-UI 投影和 Desktop 控制面；
- 对 Computer 截图实施加密、保留期和访问审计的媒体策略。

因此产品文案、Agent prompt、设置页和工具清单都不能宣称“可操作任意本机应用”“可看屏幕并点击”或“已支持 CUA”。

## 3. 当前可复用底座

以下能力已存在，但只是 Computer 实现的基础，不构成 Computer Use：

| 当前能力 | Computer 实现应如何复用 |
| --- | --- |
| `ToolDefinition` v2、工具 catalog 与 run 固定快照 | Computer 工具进入同一注册与暴露链，不建立第二套 registry |
| `ExecutionIntent`、`executors.Router` 和现有 execution lanes | 新增 `LaneComputer` 与 `ComputerExecutor`，不从 Renderer 或 provider adapter 旁路 |
| `ExecutionOutcome.ModelContent`、`ToolResultStore` 和 provider 图像投影 | 截图复用现有 tool-result media 链；补充 Computer 的加密、保留和访问策略 |
| `SemanticJournal` 与 live/replay 共用 projector | 结构化 Computer 事实写入 Journal，大媒体只写受控引用 |
| `RuntimeIdentity`、`ControlToken`、`/v1/control/*` 与 Desktop Main control client | 用户 review/takeover route 复用现有控制身份，不把 bearer token 交给 Renderer |
| `ask_user`、`interaction_required`、ACP permission 的 typed wait 范式 | 只借鉴等待、取消和恢复方式；Computer review 必须是独立语义 |

当前仍没有统一 `supports_tools` 模型能力位，现有 `ToolResultStore` 也不是加密的 Computer 证据库。两者都是实现准入缺口。

## 4. 邻近能力不是 Computer Use

| 当前能力 | 为什么不能上升为 Awaken 原生 Computer Use |
| --- | --- |
| MCP 浏览器/自动化 server | 每个 server 自带合同；Awaken 没有统一 Computer session、fence、review、takeover 和轨迹真相 |
| Connector | Connector 只管理 MCP/CLI 来源与生命周期，不授予 OS 全局观察和输入能力 |
| Bash | 当前是登录用户的命令执行面，不提供窗口/AX/截图/action digest/checked perform，也可能成为 GUI 自动化旁路 |
| typed 文件与 Office 工具 | 只操作明确文件或应用合同，不等于控制桌面 |
| Electron Desktop 自身 | 能显示 UI、打开 artifact，不等于 Agent 能控制其他应用 |
| Codex 或测试使用的 Computer Use | 属于开发验收基础设施，不在 Awaken 产品 runtime 内 |

若某个 MCP server 自带截图或点击，只能表述为“通过该 MCP server 调用其工具”。

## 5. 当前正确降级

任务需要未被 typed tool、MCP 或 Connector 覆盖的 GUI 时，当前必须明确报告缺少能力，并让用户手动完成或安装有明确合同的扩展。不得：

- 静默用 Bash、AppleScript、`xdotool` 或坐标脚本模拟 Computer Use；
- 把浏览器 MCP 描述成整个 OS 的统一控制层；
- 让模型输出坐标后交给未受策略、租约和审计约束的脚本；
- 复活通用 ApprovalCard 来掩盖 Computer review/runtime 尚不存在；
- 把目标契约中的 route、状态或事件写入当前 API 清单。

## 6. 当前验证

### 6.1 静态检查

```bash
rg -n "LaneComputer|ComputerExecutor|computer_observe|computer_act|computer_verify" src apps/desktop
rg -n "ComputerSession|computer_observation|computer_action|computer_control_transfer" src apps/desktop
rg -n "trycua|cua-driver|CuaDriver" go.mod go.sum package.json package-lock.json src apps
```

预期没有生产实现命中。未来即使命中类型名，也必须继续核对注册、运行绑定、控制 route、Desktop UI、打包和测试，不能据此单独宣称已支持。

### 6.2 真实 Desktop

按根 README 的正式入口打开 Awaken，只读确认工具、Connector、Skill、Workbench 和设置中没有原生 Computer 控制入口。外部测试代理能操作 Awaken 窗口不能作为产品能力证据。

## 7. 迁入“当前支持”的门槛

只有同时满足以下条件，才能修改本文结论：

1. CUA 已按目标架构进入锁定依赖、构建、签名、打包、启动和 readiness 链；
2. Computer Tool/Runtime、session、policy、review、lease/fence、takeover 和持久化真实存在；
3. 能力暴露不会被 Bash、原始 CUA MCP/CLI 或其他 GUI 自动化面旁路；
4. 聚焦自动化、相关 Go/Desktop 构建与故障注入在本次工作区通过；
5. 正式打包 Desktop 完成真实任务、TCC、取消、接管、崩溃恢复和重启验收；
6. 01/02/03/04/09 域的当前权威同步更新；
7. [目标测试与准入门](./目标测试与准入门.md) 的发布门全部有可追溯证据。
