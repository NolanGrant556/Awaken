# 上下文窗口与压缩

## 1. Request envelope

模型上下文由稳定 system prompt、结构化历史、attachments、inline SkillContextBlocks、runtime snapshot 和 tool schemas 组成。runtime snapshot 记录 workspace/cwd、模型、tool snapshot ID、environment ID 和 Skill summary；tool schemas 来自本 run 固定可用性快照。

RequestBuilder 在 system prompt 的最后追加稳定、host-owned `conversation_continuity` 块：最终请求中当前 user 输入之前的 user/assistant/tool 消息都是当前同一个 Awaken 任务的历史轮次；跨日期、Desktop/Core 关闭、重启或重新打开不会把这些已恢复历史变成另一个独立会话。只要当前输入之前存在消息，用户使用“上一个对话”“上一轮”“刚才”或“之前”等指代，模型必须默认解析到当前任务中最近的相关历史并直接回答，不得声称系统未提供；只有用户明确说另一个任务/独立会话时才按跨任务不可见处理。该块不复制历史正文，不把数量、thread/run/session ID、时间戳、message origin 或内部 message/turn identity 下发为供应商私有字段，也不允许模型声称看到了请求之外的其他任务或编造未提供的时间。它的 Context Epoch 与缓存身份由[提示词缓存、上下文用量与成本治理](提示词缓存与成本治理.md)统一定义。

Skill 不在估算前与 tools 求交。目录只暴露统一 `skill` 工具及有预算的 Skill catalog；调用后的 inline 正文才进入上下文。

## 2. 预算

上下文窗口由 model window、output reserve、effective window、warning/auto-compact threshold 和 compact target 决定。当前 `awaken_leaf_v4` 从 provider-visible projection 生成 `ContextUsageSnapshot`，按 typed prompt/message/tool provenance 统计分类并保证分类和等于总估算。它仍是版本化本地估算，不是 provider tokenizer 的精确输入量。

`ContextActualTokens`、最近响应的 input/output/total 和 cached usage 都不能替代 Core 的窗口估算或压缩安全判断。Desktop 的“上下文窗口”汇总在 provider/model identity 兼容且主调用 usage 完整时优先显示最近 provider `total_tokens`（缺失时按 input/output 分项恢复）的当前累计值，并把与六项 typed 本地分类的差额按“对话”优先规则 reconciliation；没有实际值时回退 local estimate。打开旧 thread 时，Desktop 以当前可运行 profile 请求 Core 从耐久历史与当前工具/Skill/Memory 重建 v4 snapshot；provider/model/protocol、compact 等不兼容 Context Epoch 边界不复用旧实报，重启或工具定义更新产生的 `tool_schema_changed` epoch 仍保留同一供应商和模型最近实报。无法重建且旧记录没有 breakdown 时才显示已有汇总和“暂无分类明细”。完整口径见 [提示词缓存、上下文用量与成本治理](提示词缓存与成本治理.md)。

Skill catalog 预算约窗口 1%；inline Skill 压缩内容预算为单 Skill 最多约 5,000 tokens、合计最多约 25,000 tokens，最近调用优先。例如 6 个满预算 Skill 只保留最新 5 个。截断必须保留 Skill ID、锚定路径和可精确交给 `Read` 的原始路径。

## 3. 压缩与耐久边界

压缩保留最新用户意图、未完成工具配对、active gate、canonical tool outcome、artifact/change identity、最近 Skill 上下文和必要恢复事实。超过 32 KiB 的文本 tool result 已在首次 model admission 前写入 thread-owned `0600` blob，压缩和恢复只消费带 digest/字节数/preview/storage key 的稳定 projection，不重新截断；failed/unknown side effect 不能被改成成功。

压缩成功产生完整 post-compact messages 和唯一 `compact_boundary_id`。Runner 的提交顺序固定为：

```text
计算压缩结果
  -> append context_compacted
  -> flush journal
  -> 替换内存 conversation messages
  -> 压缩已调用 Skill 上下文
  -> 发出 compact finished
```

append/flush 任一步失败都视为压缩失败，压缩前消息和旧 Context Epoch 继续作为 authority；不能只更新内存导致重启后退回旧上下文。服务重建按 03 域契约用合法 `context_compacted.messages` 替换此前历史，再追加边界后的记录；只有成功持久化的 boundary 才以 `compact_succeeded` 建立新 epoch，因此重启后模型看到的上下文必须与 live 压缩结果一致。

fork body 属于 child 上下文，不纳入父压缩；父只保留 child result/identity。child 自己的 compaction record 带 agent identity。attachments 与 tool result media 通过 runtime storage key 恢复，不重复持久化 image/PDF base64。

## 4. 主动与被动压缩

- 接近 auto-compact threshold 时执行 proactive compact；
- 除此之外，`ContextWindowState.ShouldAutoCompactByActualUsage` 作为并行主动触发：当 `LastAPIUsageTokens > 0` 且 `LastAPIUsageTokens + EstimatedDeltaTokens >= AutoCompactThreshold` 时也触发 proactive compact。它与 v4 `EstimatedTokens` 触发是 OR 关系，不替换 `EstimatedTokens`，也不修改 `awaken_leaf_v4` 估算口径——`ContextActualTokens`、最近 provider total/output 仍不参与当前窗口估算。`LastAPIUsageTokens` 在同一 run 的连续请求中优先取 provider `total_tokens`，因为下一请求会重新纳入上一条 assistant 输出；provider 未返回 total 时回退 `input_tokens`。它只补 v4 estimator 在 prefix 命中、tool result 体积差和媒体能力差异上的偏差，避免 provider 真实 continuation usage 已经接近窗口但本地估算仍低于阈值的过晚压缩。`LastAPIUsageTokens + EstimatedDeltaTokens` 溢出时直接触发压缩作为防御。成功压缩后 governor 把 `lastAPIUsageTokens` 重置为 0，因为下一次请求是基于 compact 后的新 prefix，上一条 provider-reported usage 不再对应其 input，避免 stale-trigger 循环；
- provider 返回上下文过长且仍可安全重试时执行 reactive compact；
- 同一 governor 的失败计数和 circuit breaker 防止无限压缩循环；
- summary 请求使用 `compact_summary` purpose、独立 affinity 和 8192 token 上限；按 provider 辅助模型策略选择模型，无法安全映射时复用主模型并记录 fallback；
- summary model 失败可使用明确标记的本地 fallback，失败或中断不切 epoch；
- 无法安全裁剪 tool pair 或最新用户意图时 block，而不是静默丢失。

provider/tool snapshot 只保存 ID/摘要；压缩后不能重新选择当前 registry implementation。Skill 正文截断必须提示重读锚定路径。

## 5. 当前不支持与缺口

- per-model tool-support capability 尚未统一；
- catalog/Skill token 预算是估算，不是 provider tokenizer 精确值；
- bare unit Runner 没有 recorder 时只做内存压缩；产品 `RunService` 路径必须始终持久化；
- Windows/Linux 的大路径、非 ASCII attachments 与真实重开压缩尚无本轮实机证据；
- 当前没有多个 Core 实例并发写同一 thread 的产品级 session lease。
