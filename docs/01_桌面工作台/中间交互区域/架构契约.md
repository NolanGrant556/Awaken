# Awaken Desktop Workbench Contract

## 范围与目标

本契约限定 Awaken Desktop 渲染进程（`apps/desktop/src/renderer/`）中**中间工作区**（Workbench Main Area）的现有设计与交互边界。

覆盖的主链路：

```
AppShell -> WorkbenchShell -> RunStage -> ComposerDock / ExecutionFeed
```

对应实现入口：

- 页面编排：`apps/desktop/src/renderer/App.tsx`
- 纯决策函数：`apps/desktop/src/renderer/workbenchPresentation.ts`
- 结构组件：`@awaken/design-system` 中的 `AppShell`、`WorkbenchShell`、`RunStage`、`ExecutionFeed`、`ComposerDock`、`ComposerBar` 等
- 单元测试：`apps/desktop/src/renderer/App.test.ts`（已覆盖 workbench presentation 的多项决策函数）

本契约的目的是：把当前中间区域已经成型、且被确认为产品意图的交互，**正式固化为不可随意破坏的架构边界**。后续任何改动如果触碰这些边界，必须同步更新本契约，并附真实运行验收证据。

## 当前结构

中间区域的挂载和布局由 `RunStage` 组件统一承载。在 `App.tsx` 中，`RunStage` 被使用为：

- `scrollRef` / `onScroll`：滚动容器的引用和滚动事件；
- `overlay`：用于挂载 turn marker rail 等悬浮导航；
- `composer`：用于挂载底部 dock 形态的 composer；
- 子内容：
  - 空态时渲染 `run-stage-center-composer`（视觉中心位置的 center composer + `TaskWelcome`）；
  - 运行态时渲染 `ExecutionFeed`，内部按 turn 分组展示 `UserPromptBlock` 及 narrative items。

`RunStage` 是中间区域**唯一的滚动、定位、overlay、composer 容器**。任何需要在中间区域新增悬浮层、吸底元素、固定面板、额外 composer 的行为，都必须通过 `RunStage` 的现有插槽解决，而不是绕过它创建新的独立容器。

## 架构分层

中间区域由三层职责共同守护，后续改动必须明确自己属于哪一层，不得越层：

| 层级 | 代表 | 职责 | 不可做的事 |
|------|------|------|-----------|
| 设计系统 | `@awaken/design-system` | 提供结构壳、视觉 token、可复用组件、布局约定 | 不内联业务逻辑；不直接感知 runtime 状态 |
| 交互编排 | `App.tsx` | 页面级编排：runtime 订阅、DOM 滚动、wheel/touch 事件、active marker 同步、`scrollPromptToAnchor()`、sidebar/inspector 折叠、composer 生命周期 | 不引入与中间区域无关的全局状态；不绕过 `RunStage` 插槽新增布局元素 |
| 纯决策 | `workbenchPresentation.ts` | 可测试的纯函数：center/dock 形态判断、turn marker rail 采样、anchor 位置计算、latest turn min-height 计算、scroll 意图判断 | 不直接操作 DOM；不引入副作用 |

## 核心契约

以下五条是中间区域的正式产品契约，任何改动都不得在未更新契约的情况下破坏它们：

1. **中间区现有交互是正式产品契约**
   - 空态：视觉中心位置的 `center` composer + `TaskWelcome`；
   - 运行态：底部 `dock` composer + `ExecutionFeed` + 达到显示条件时的 turn marker rail + 最新 turn 自动 follow / 用户滚动暂停 / 恢复；
   - 这些行为不是临时实现，而是产品意图。

2. **`RunStage` 是唯一滚动 / 定位 / overlay / composer 容器**
   - 所有中间区域的悬浮、吸底、overlay、composer 都必须通过 `RunStage` 的 `overlay` / `composer` / 子内容插槽挂载；
   - 禁止在 `RunStage` 外部新增 `position: fixed` 或 `position: absolute` 的中间区域元素。

3. **`ExecutionFeed` 只承载 narrative / turn**
   - 它的内部只应包含 turn section（当前 DOM 类名为 `execution-turn-section`）、`UserPromptBlock` 和 narrative items；
   - 禁止在 `ExecutionFeed` 内添加业务控制面板、输入框、通知横幅、操作按钮等非 narrative 控件。

4. **composer 形态目前只承认 `center` 和 `dock`**
   - 空态使用 `variant="center"`；
   - 运行态使用 `variant="dock"`；
   - 如果未来需要第三种形态，必须先更新本契约，并通过真实运行验收。

5. **任何影响中间区布局、滚动、marker、composer 的改动，必须先过 workbench contract + 截图 / 真实运行验收**
   - 涉及上述区域的 PR 必须附带：
     - 改动前后的真实运行截图或录屏；
     - 如果修改了 `workbenchPresentation.ts`，必须同步补充或更新对应单元测试；
     - 如果修改了本契约，必须在 PR 中明确说明变更理由。

## 禁止事项

为降低“修一个功能破坏原有设定”的风险，以下行为在默认情况下被禁止：

- 在 `RunStage` 外部新增独立定位的中间区域容器；
- 在 `ExecutionFeed` 内添加非 narrative 的业务控件；
- 在 `App.tsx` 中内联新增与中间区域布局/滚动相关的硬编码计算；
- 新增或修改第三种 composer 形态而不更新本契约；
- 修改 `workbenchPresentation.ts` 中的纯决策函数而不更新或补充单测。

## 样式边界

`apps/desktop/src/renderer/styles/workbench.css` 承载 Workbench 中间区域样式边界。以下类名前缀属于该边界；无论它们出现在 `workbench.css` 还是其他 Desktop renderer 样式文件中，修改这些选择器时都默认触发本契约与 `docs/01_桌面工作台/中间交互区域/复核清单.md`：

- `.aw-run-stage-*`
- `.run-stage-*`
- `.execution-feed`
- `.execution-turn-*`
- `.execution-prompt-*`
- `.composer-*`
- `.turn-marker-*`
- `.narrative-*`

这些样式覆盖 RunStage 滚动容器、空态 composer、底部 composer dock、turn 分组、prompt header、turn marker rail 以及 narrative item 的视觉边界。若改动涉及 `@awaken/design-system` 已拥有的结构类或 token，先确认 ownership：通用结构和 token 优先在设计系统内演进，Desktop renderer 只保留产品编排和场景级覆写。

## 测试策略

中间区域已有以下测试层次，后续应保持并强化：

1. **纯函数单元测试（已存在）**
   - 位置：`apps/desktop/src/renderer/App.test.ts`
   - 覆盖：`shouldUseCenterComposer`、`turnMarkerRailDisplay`、`scrollTopForPromptAnchor`、`latestTurnMinHeightBottomReserve` 等决策函数；
   - 要求：任何对 `workbenchPresentation.ts` 的修改，必须同步补充或更新对应测试。

2. **真实运行截图 / 录屏（必须新增为 PR 验收）**
   - 涉及中间区域布局、滚动、marker、composer 的改动，PR 必须附带：
     - 空态（center composer）截图；
     - 运行态（dock composer + `ExecutionFeed` + turn marker rail）截图；
     - 如有滚动/锚定相关改动，必须附录屏或关键帧截图。

3. **轻量视觉回归护栏（VRT）**
   - 当前提供 `npm run capture:workbench:vrt`，复用真实 Desktop 窗口截图，按 center / dock / marker 产出截图和汇总 manifest；
   - 当前 baseline 位于 `docs/01_桌面工作台/中间交互区域/验收基线/`，包含 `center.png`、`dock.png`、`marker.png`；
   - 该脚本先作为 PR 级对比截图护栏，不做复杂像素级平台化；
   - 后续如升级为自动化像素比对，必须继续覆盖 center / dock / marker 状态，并保留真实运行验收证据。

## 变更流程

本契约不是静态文档，而是跟随产品演进的规则。修改流程如下：

1. 在 PR 中明确说明哪些契约条款被修改、新增或移除；
2. 提供真实运行截图 / 录屏作为验收证据；
3. 如果修改了 `workbenchPresentation.ts`，同步更新 `App.test.ts`；
4. 将契约变更与代码变更放在同一 PR 中，便于 reviewer 统一 review；
5. reviewer 使用 `docs/01_桌面工作台/中间交互区域/复核清单.md` 检查是否遗漏边界。
