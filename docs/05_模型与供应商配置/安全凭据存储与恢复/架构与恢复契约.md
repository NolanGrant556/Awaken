# 安全凭据存储与恢复契约

## 目标

Awaken 必须在 macOS、Windows 与后续支持的平台上通过同一套产品语义保存模型 API key：优先自动恢复，无法恢复时只在 Awaken 内引导用户重新录入，不把系统钥匙串、凭据管理器或命令行操作暴露为常规产品步骤。

安全存储不可用时禁止降级为明文文件、环境变量回写或日志输出。任何迁移都必须先完成新密文写入，再原子替换旧密文；旧密文在新写入成功前不得删除。

## 已确认的根因

原实现直接使用 Electron 同步 `safeStorage`，并以 `isEncryptionAvailable()` 作为前置开关。这个模型把系统安全存储的临时认证失败压成一个永久布尔值，导致运行、余额、保存和测试四条路径泄露同一条笼统英文异常。

历史上模型凭据先于 `app.setName("Awaken")` 上线。macOS 的 Safe Storage service 由应用名称派生，因此本机同时存在旧的 `@awaken/desktop Safe Storage` 与当前的 `Awaken Safe Storage`。这说明凭据身份曾发生变化，但现有文件没有版本、身份或迁移元数据。

Electron 42.4.1 的异步 `safeStorage` 与既有同步密文兼容，并能表达 `temporarily unavailable` 与 `shouldReEncrypt`。它仍依赖 macOS Keychain 或 Windows DPAPI，不能绕过操作系统永久丢失的主密钥，但可以避免主线程阻塞并提供正确的恢复状态。

## 不变量

1. 模型 API key 只允许出现在 Electron 主进程内存和系统安全存储保护的密文中。
2. Renderer、日志、错误事件、余额结果和模型摘要不得包含明文 key 或底层系统错误详情。
3. 新写入只使用异步安全存储；不得调用 `setUsePlainTextEncryption(true)`。
4. `isAsyncEncryptionAvailable()` 不是操作前置条件。读取和写入必须直接执行，并按结果分类。
5. 临时不可用时保留旧密文；不得把它改写成缺少 key，也不得自动生成替代密钥覆盖它。
6. 只有新密文成功生成并持久化后，才允许替换旧密文。
7. macOS 应用名称、bundle ID 与签名身份，以及 Windows application ID 与 `userData` 路径，属于持久化凭据身份，发布后不得随显示文案修改。
8. 模型 API key 是 Awaken 全局配置，不提供进程内或 workspace 级临时凭据降级。

## 凭据状态机

```text
missing
  -> secure_write -> ready
  -> secure_store_temporary -> relaunch_required

ready
  -> decrypt_ok -> ready
  -> should_reencrypt -> rotate_pending -> ready
  -> temporary_unavailable -> relaunch_required
  -> permanent_or_corrupt -> reentry_required

relaunch_required
  -> controlled_relaunch -> ready | reentry_required
```

同一 Electron 进程会复用已经初始化的 async encryptor；当 provider 以临时空密钥初始化后，同进程内反复重试通常不会重新查询 Keychain 或 DPAPI。因此 UI 的“重试”应执行受控 relaunch，而不是循环调用同一个 decrypt。

## 存储格式与迁移

现有 `model-profiles.json` 顶层格式继续兼容 version 1。凭据对象新增独立 envelope 版本：

```json
{
  "encryptedApiKey": "base64 ciphertext",
  "last4": "1234",
  "version": 2,
  "scheme": "electron-safe-storage"
}
```

缺少 `version` 的记录视为 legacy v1。异步 decrypt 成功后：

1. 立即把明文仅保留在当前调用栈内；
2. 若为 legacy v1 或返回 `shouldReEncrypt=true`，调用异步 encrypt 生成 v2 replacement；
3. replacement 成功后原子写回同一 profile；
4. replacement 失败时仍可完成本次已成功的读取，但保留旧密文，后续再次迁移；
5. legacy identity 无法由当前应用身份解开时，不删除数据，进入应用内重新录入流程。

## 跨平台边界

- macOS：底层为 Keychain。系统更新、登录钥匙串认证状态、应用名称或签名身份变化都可能影响读取。
- Windows：底层为 DPAPI。用户身份、登录密码的管理员重置、用户目录或 Local State 丢失可能造成永久不可恢复。
- 两个平台统一输出产品状态，不在常规错误中显示 Keychain、DPAPI、错误码或系统操作说明。
- 操作系统永久拒绝或丢失主密钥时，任何本地应用都无法安全还原旧 key。正确恢复是保留非敏感模型配置，让用户在 Awaken 内重新录入；不是明文回退。

## 用户体验契约

- 运行前发现临时不可用：显示“模型密钥暂不可用”，提供“重新启动 Awaken”。
- “重新启动 Awaken”执行受控 Desktop relaunch，重新初始化系统安全存储 provider。
- macOS 开发态必须通过 README 的 `open:desktop` 托管入口重建 screen、renderer、Electron 与 core；打包版使用 Electron 原生 relaunch。
- 确认为不可读时：“在 Awaken 中恢复”打开已配置模型列表，由“更新 API key”进入原 profile 的编辑区。
- 用户重新输入后必须成功写入系统安全存储才算保存完成；安全存储仍不可用时保留原配置并明确提示重试。
- 余额面板只显示一个全局凭据状态，不为每个 provider 重复底层异常。
- 设置页区分“已安全保存”“安全存储暂不可用”“需要重新输入”和“未配置”。

## 验收要求

1. 旧同步密文可由异步路径读取。
2. 临时不可用不会删除或覆盖现有密文。
3. `shouldReEncrypt` 只在新密文生成成功后写回。
4. 保存、测试、余额、运行统一使用同一凭据层和错误分类。
5. IPC 不再向 Renderer 传递 `Error invoking remote method` 原始文案。
6. 安全写入失败时，新 key 不写入 `model-profiles.json`、日志或 transcript，已有密文保持不变。
7. macOS 与 Windows contract tests 使用相同状态机；平台差异只存在于 provider 适配层。
8. 最终按根 README 从真实 Awaken Desktop 完成保存、重启、余额与真实 prompt 验收。
