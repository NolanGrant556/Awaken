# 认证、持久化与恢复边界

## 1. 当前支持

stdio server 可使用 MCP config 中显式 env/args；HTTP/SSE 可使用 headers 与 OAuth。部分 provider 把不可拆分的访问 key 作为固定 endpoint URL 的 query 参数；这类完整 URL 属于 MCP config，随 user/project 配置以 `0600` 保存，并按敏感配置处理，不进入日志、提示或验收截图。它不转换为 OAuth token source。OAuth token source 由 `PersistentCredentialStore` 分层保存：

```text
~/.awaken/auth/connector-accounts.json
  scope + server name + canonical endpoint hash
              -> credentialRef、state、server/auth/token/redirect URL、
                 client ID、scopes、updatedAt、expiresAt

系统 secrets backend（macOS Keychain / Windows Credential Manager / Linux secret service）
  service=awaken-mcp, user=<credentialRef>
  -> access token、refresh token、client secret 与完整 StoredTokenSource
```

metadata 文件不保存 access token、refresh token、client secret、Authorization header 或 secret env value。所有 metadata mutation 先取得同目录跨进程锁，再读取最新完整文件并通过 FileStore 原子 replace 写入，目录保持 `0700`、文件保持 `0600`；损坏 JSON fail closed，不当作空 accounts 覆盖。

Desktop/Core 正式使用 `AWAKEN_HOME=~/.awaken`。测试必须注入隔离根与 fake secret backend；没有任何根的独立调用使用临时目录，不隐式触碰真实用户 metadata。

## 2. 保存、更新与删除

保存前必须先完整读取并校验 metadata。credential identity 由 effective scope、server name 与 canonical endpoint 共同确定；同一 identity 的更新复用已有 `credentialRef`，首次保存生成 UUID。secret 写入成功后才原子发布 metadata；metadata 写失败时恢复此前 secret，首次写入则删除未被引用的新 secret。回滚失败与原失败合并上报，不能宣称保存成功。

删除先读取旧 secret 作为回滚值，再删除 secret 和 metadata；metadata 写失败时恢复旧 secret。成功后该 scoped endpoint identity 不再有 credential ref。管理面删除 server、builtin Connector disconnect 或修改 endpoint 时清理旧 identity；删除 project override 不得清理其下方同名 user identity。删除只操作当前 metadata 中该 identity 的 ref，不能按显示名清理其他 scope/endpoint 的秘密。外部直接编辑或删除配置文件不会触发主动清理，但新 identity 无法读取旧 token；加载到 metadata 的 `serverUrl` 与当前 canonical endpoint 不一致时也会 fail closed 并清除该条 metadata/secret。

由于系统 secrets backend 与 JSON 文件不存在共同事务，进程崩溃仍可能发生在两者调用之间；启动只信任已发布 metadata，无法从 keyring 枚举结果发明 account。没有 metadata 的孤立 secret 不获得产品 authority。

## 3. 认证与运行边界

- `connected` 只由当前 Manager session snapshot 证明，不能由“曾认证”或 metadata 存在证明；
- metadata state `authorized|needs_reauth` 是恢复提示，不证明当前 token 可读、未过期或业务权限充足；
- server `needs_auth` 时 tool provider readiness 为 `needs_auth`，当前 run 返回 next action，不发起业务 transport；
- OAuth 完成只证明认证流程已完成，不证明 provider tool 的 recipient 语义、业务权限、可恢复删除或副作用安全；MCP tool 不要求这些 Awaken per-tool contract，实际保证由 server 自身提供；
- builtin Connector 的 persisted user MCP config 携带稳定 provider identity；重启时 Registry 只据此恢复 active owner，再以当前 Manager snapshot 投影卡片状态。手工同名配置不能被认作 builtin owner；local/dynamic owner 不持久。

## 4. 异常与恢复

- metadata 缺失：该 server 未保存认证；不扫描 keyring 猜 ref；
- metadata 损坏/version 不支持：读写失败并保留原文件；
- credential ref 对应 secret 缺失/不可读：返回 credential not found 或 secrets backend 错误，进入 needs-auth/恢复路径，不用空值覆盖；
- connected call 收到 401：当前没有完整透明 refresh/retry 闭环；有副作用调用不能盲重试；
- refresh 或调用出现 unknown/partial side effect：先检查 provider 状态，再决定是否重试；
- 日志、AG-UI、journal 和 JSON metadata 只投影 ref/状态与非敏感连接事实，不投影 token、client secret、headers 或 secret env value。

## 5. 当前不支持与缺口

- 不支持把 OAuth access/refresh token、client secret、Authorization header 或 secret env 明文写入 `~/.awaken/.env`、`~/.awaken/config/mcp-servers.json`、`awaken.mcp.json` 或 connector metadata；provider 强制绑定在 endpoint query 中、无法拆分为 header/OAuth 的 opaque access key 只作为完整 URL 配置保存，仍按敏感值处理；
- 不支持从当前 metadata 和 secrets backend 之外自动导入 connector account；
- dynamic client registration、特殊 OAuth provider 与浏览器回调尚无完整全平台矩阵；
- WebSocket 认证不支持；
- 多 Desktop 实例/旧 Manager session 的统一 generation owner 未完成；
- 系统 secrets backend 与 metadata 的 crash-atomic transaction 不存在；
- Windows Credential Manager/Linux secret service 的发布验收不能从 macOS Keychain 推断。

## 6. Owner 与验证

- OAuth 流程：`src/mcpclient/auth.go`、`oauth_persistent.go`。
- metadata/keyring 协调：`src/mcpclient/credential_store_persistent.go`。
- 文件原子性：`src/filestore/atomic.go`。

自动化至少覆盖重启 round-trip、跨实例 mutation lock、JSON 不含三类 secret、0600、损坏 metadata 不覆盖、metadata 写失败恢复旧 secret/删除新 orphan、删除失败恢复 secret：

```bash
go test ./src/mcpclient ./src/filestore -count=1
```

真实 Desktop 需用专用 OAuth 测试账号完成授权、重启、工具调用、断开/清除和重新授权；检查 `connector-accounts.json` 只含非敏感字段，并确认日志、SemanticJournal 与 Renderer 无 token/client secret。平台 secrets backend 的真实验收必须分别执行。
