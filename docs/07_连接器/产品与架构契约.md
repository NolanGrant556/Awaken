# 产品与架构契约

## 1. 定位

Connector 是 MCP 与 CLI 两类 provider 的统一运行能力；顶层连接器目录只展示 `catalogPlacement=connectors` 的条目。definition 显式携带 `kind: mcp | cli`、`catalogPlacement: connectors | plugin_only`、可见名称、说明、类别、provider、auth type、trust/source、稳定 `providerId`、aggregate capabilities、dependencies 和 provider readiness。`plugin_only` 只改变用户入口，不删除 Registry definition、OAuth 或 MCP runtime；它由引用该能力的插件页面独占展示，避免同一功能在插件与连接器两个页面重复出现。只有 `kind=mcp` 可携带 MCP config factory/inline config 并进入 MCP Manager；`kind=cli` 的安装、配置、授权和启停由 Electron Main 的 `CliConnectorManager` 独立拥有，不生成 MCP config，也不调用 MCP connect/disconnect。需要宿主账号的 MCP Connector 由 Core `Connector Auth Broker` 统一拥有账号、PKCE 会话、Keychain 凭据和 token refresh；插件只能引用稳定 Connector ID 和读取 readiness，不能取得凭据。

CLI 连接器当前固定为 `dingtalk-workspace`（钉钉）与 `lark-cli`（飞书）。目录页使用紧凑的桌面信息密度：宽窗口保持两列、窄窗口降为单列，名称、说明、状态和标签形成克制的文字层级，说明或标签不得把单张卡片撑成大块面板。目录卡展示品牌标识、产品名与能力简介，不展示版本、安装来源或内部 readiness 枚举；整张卡与保留在右侧的「+」都只打开同一个连接详情弹窗，不直接执行安装。弹窗的 X 固定在右上角，保留无障碍关闭名称，鼠标悬停或键盘聚焦时不显示可见 tooltip 或原生 `title` 提示。弹窗拥有完整 onboarding：未安装时显示「安装」；安装中同步显示 Main 上报的阶段与百分比进度，按钮变为「取消安装」；CLI 与官方 Skill 都成功但没有已验证的当前用户身份时显示「重新授权」，不得回退为「安装」或把正常未登录显示成「CLI 操作失败」；授权完成后显示带勾的绿色「已连接」，鼠标悬停或键盘聚焦时切换为「取消登录」，点击调用官方 logout。受管安装同时把与固定 CLI 版本匹配、经过 SHA-256 校验的官方 Skill 安装到用户级 `~/.agents/skills`：DWS 使用官方稳定 mono 包 `dws`，Lark 安装当前官方仓库的全部 `lark-*` 包。已有 Awaken-managed CLI 在升级到本契约后，如果对应官方 Skill 整套尚未出现，会补装同版本官方 Skill，若用户或其他安装器已放入部分同名包则保留现场而不覆盖。登录由 Main 启动官方 CLI 并打开经过校验的官方 HTTPS 页面，用户只在官方网页完成操作；弹窗只显示等待/重试状态，不重复展示授权链接或二维码。DWS 只允许精确的 `https://login.dingtalk.com/oauth2/auth` 用户 OAuth 页面，必须拒绝同属钉钉域名但用于获取 client ID 的 `mcp.dingtalk.com/cli/clientId`、logout 和其他后台 endpoint。Lark URL 校验使用精确的 `accounts.feishu.cn`、`open.feishu.cn` 及 Lark 对应 hostname，并拒绝应用注册、device authorization、revoke 与 token 等服务端 API endpoint；CLI stdout/stderr 中出现这些后台地址时只按失败诊断处理，绝不交给系统浏览器。它们只负责把经过验证的官方命令暴露给现有本机执行环境。具体业务命令仍由 Skill/Bash 与中央 ToolRuntime 契约拥有，Connector 不形成新的任意命令执行旁路。

aggregate capability 用于目录发现和解释“这个 Connector 大体能提供什么”，不是具体 MCP tool 的授权来源。具体 tool 在 server connected/auth-ready 且输入 schema 有效时即可调用；standard annotations、tool `_meta` 和 capability 只改善模型选择、目录与诊断，缺失、无效或互相矛盾都不形成 transport 前 gate。远端消息、删除及其他副作用权限由 MCP server 自身负责。

Outlook 同样保持零宿主审批：发送、回复、转发、定时发送、移动、删除和退订工具在 connected/auth-ready 且 schema 有效时可以进入 provider，不增加 Core permission gate。Awaken 官方 Outlook Skill 负责模型侧低自由度编排：新邮件、回复、转发和定时发送默认先创建/读取草稿，展示发件邮箱、实际 To/CC/BCC、主题、附件、回复范围与发送时间；随后优先调用宿主提供的提问用户工具，若没有该工具则输出摘要并停止等待。只有用户确认当前摘要后才调用一次发送工具；摘要内容变化、批量范围变化或发送结果未知都不能沿用旧确认或自动重发。这是模型行为协议，不改变 MCP transport 的开放调用边界。

分类标签中 MCP 使用官方 MCP 标记，CLI 使用终端图标，两者共用 16px 请求尺寸与统一光学包围盒；所有 MCP 目录卡同样使用官方 MCP 标记，无论来自内置目录、用户自定义、project 还是任何运输模式，都不根据 server 名称生成字母或换成 server 图标；CLI 目录卡继续展示各自品牌标识。连接器一级导航恢复使用插头图标，不再与 Skill 共用六边形轮廓。

## 2. 当前来源

- builtin：五个顶层目录 MCP definition、两个 CLI definition，以及一个 `plugin_only` Outlook host Connector；MCP 连接时生成并持久化 user MCP config，CLI 不写 MCP config。`awaken.microsoft.outlook` 由首个 Awaken 内置插件「Outlook 邮箱」通过稳定 Connector ID 引用，不能出现在顶层连接器目录；
- local：本地定义，连接时通过 `InjectDynamic` 注入当前进程，不持久化 dynamic state。

内建 capability/dependency 目前包括：DingTalk/Lark 聚合 `message.send` 并分别依赖 `dws`/`lark-cli`，browser connectors 聚合 `browser.interact`，Context7 聚合 `web.search`，Outlook 依赖 Microsoft Graph 并通过本地 in-process MCP 暴露个人/共享邮箱的近期浏览、自由文本搜索、稳定分页、最多 20 封完整正文批量读取、递归文件夹名称/路径解析、文件夹与分类、附件、草稿生命周期、发送、回复/回复全部、转发、已读与分类专用更新、移动、删除、标准退订和本机定时发送。具体 tool annotation 与输入 schema 仍是 per-tool 事实。

## 3. UI 状态

Connector 列表显示 `catalogPlacement=connectors` 条目的 source、provider identity、capabilities/dependencies 和当前 readiness。只有当前 MCP server snapshot 可证明 connected/needs_auth/failed；点击过连接或 config 存在都不是 connected 证据。内置 MCP 连接后即使为了重启恢复而持久化为 user config，仍只保留在「Awaken 内置」原卡片中操作；Connector owner 认领的单个 server 一旦存在，原卡片右侧就显示该 server 的启停开关与设置入口，停用后仍留在原位并可重新开启。「用户安装」只列出未被任何 Connector owner 认领、且名称不以 `plugin__` 开头的独立 user/project MCP server，不重复投影 Connector 拥有的底层 server 或插件认领的 server。插件自带 MCP 的启停与详情只在插件页；插件通过 `host_connector` 使用的宿主 MCP 作为只读引用出现在插件详情，展示该插件实际依赖的 runtime 和工具。若宿主 Connector 为 `plugin_only`，其 setup、连接、审批等待、重连与退出登录入口也只出现在引用插件，连接器页不得再投影同一 MCP 或账号卡片。
`authType=oauth2` 且带 host OAuth definition 的用户入口是账号动作，不显示底层 in-process server 的普通配置/启停入口；目录可见 Connector 使用连接器卡片，`plugin_only` 使用引用插件的 setup item。插件整体关闭不属于账号动作，不得调用 Connector `Disconnect`、删除 token 或改变账号 readiness；只有用户在账号行明确选择“断开连接”才能退出账号。未连接时显示连接、授权等待时允许取消并提供“页面要求管理员审批”、等待审批时显示独立状态且允许批准后重新连接；已连接时显示独立账号行和“已连接”下拉，下拉提供强制重新连接与断开连接，不能取代引用插件自身的整体启停开关。强制重新连接即使已有有效账号也必须发起新的 PKCE session，并在新凭据交换成功前保留旧凭据；取消该 session 不得清除原账号。授权会话由 Core 跨窗口焦点和插件页挂载持有；Renderer 页面离开只停止观察，返回后按当前插件/setup/指纹重新认领活动会话，不因切到浏览器、其他窗口或 Awaken 页面自动取消。OAuth 回调在 `verifying` 阶段等待工具运行时就绪时，必须读取忽略账号投影的纯 MCP runtime 状态；不得用包含当前授权会话 `pending` 状态的综合 Connector status 等待自身完成，否则会形成循环依赖并产生虚假超时。Electron Main 取得 Core 的一次性 authorization URL，复用安全 URL 校验后调用系统浏览器并在返回 Renderer 前删除 URL；Renderer 只轮询脱敏 session。断开连接会同时清理共享账号凭据和该 Connector runtime，因此所有引用同一 Connector ID 的插件同步回到 `needs_auth`。
目录卡的辅助说明只有在提供标题之外的信息时才显示；provider 名称或其他文案与产品名等价时必须省略，但后端 definition 的 Description 与 provider identity 仍保留为目录元数据，不因 UI 精简而删除。MCP 配置弹窗使用「本地进程（stdio）」与「Streamable HTTP」两个模式按钮区分命令型和远程 URL 配置；按钮切换说明与安全示例，粘贴可明确判定的本地 JSON、远程 JSON 或裸 URL 时同步当前提示模式，但不取得 schema ownership，也不得在用户已经粘贴内容后静默覆盖或重写输入。用户安装卡片优先显示 Core snapshot 的 `displayName`，设置、启停和工具路由仍使用 canonical server identity。
用户 MCP server 的启停或配置重启只能更新卡片状态，不得改变其在当前目录中的安装顺序与网格位置，也不得因 Manager 重建或列表轮询而短暂清空「用户安装」并闪现空态。持久化启停在写完 config 后原地 Disable/Enable；`RestartWithConfig` 重建时 Snapshot 必须始终保留该 server 条目。

Desktop 的 MCP/CLI 展示分类只读取 Core `kind`，不得按名称或依赖关键字推断。CLI readiness 独立表达 activation、install、executable、configuration、authentication、overall、版本、ownership 与稳定安全错误；不得复用 MCP connected 状态。`ConnectorDefinition.Category` 仍是业务类别，不能与 kind 合并。

## 4. Ownership

| owner | 负责 | 不负责 |
| --- | --- | --- |
| Connector Registry | definition 合并、connect/disconnect、进程内 active owner 与 builtin provider identity 重启恢复 | MCP transport、tool schema/Outcome 与可选 Artifact bridge |
| Core `Connector Auth Broker` | host Connector 的 PKCE/state/callback、账号 readiness、refresh、Keychain ref、取消与退出登录 | 插件自带 OAuth、Renderer 浏览器调用、Microsoft Graph 业务语义 |
| Core Outlook runtime | 固定 Microsoft Graph endpoint、边界化邮件/草稿/附件/文件夹/分类操作、共享邮箱目标、本机定时队列、标准退订、in-process MCP schema 与明确 401 信号 | OAuth 凭据持久化、任意 Graph URL、后台 webhook/subscription、Awaken 退出后的常驻发送 |
| MCP Manager | server/session、snapshot、tools/Skills 注册 | Connector 产品分组 |
| Tool Catalog/Runtime | provider snapshot、决策、Outcome | Connector 安装 UI |
| Desktop Main `CliConnectorManager` | 固定 manifest、CLI 与官方 Skill 下载校验、安全解包、`~/.agents/skills` 中固定官方包的原子安装、绝对路径探测、配置/授权子进程、激活入口与非敏感 readiness | 任意 renderer command/argv/cwd/env、业务命令和 MCP session |
| Awaken Design System | `AwakenConnectors` 页面组合、连接器卡片/品牌/开关、`AwakenProductLogo` 官方方形产品标志、CLI 详情与 MCP 配置/设置弹窗的 UI-only 结构、视觉状态和回调契约 | runtime client、MCP/CLI 数据读取、安装/授权/配置副作用、凭据与持久化 |
| Desktop Renderer | 把 Core/Main 状态转换为 Design System props，处理连接、启停、刷新、配置、安装与授权回调，以及 Workbench `ExternalActionGate` | 重复实现连接器组件视觉；连接器 onboarding 授权链接/二维码、文件路径读取、CLI stdout/stderr、device code/token/secret、任意子进程参数或“选择 CLI”文件选择器 |

## 5. 产品动作与授权

连接器目录卡与其右侧「+」只负责打开连接详情弹窗。弹窗中的「安装」调用固定受管安装；Main 以 `CliInstallProgress` 事件投影真实阶段与单调百分比，安装期间同一按钮为「取消安装」，取消是正常终态并恢复到可重新安装，不显示失败残留。安装期间点击遮罩或关闭弹窗只隐藏详情，不取消安装；重新打开时必须继续显示同一 install session 的当前阶段、百分比和「取消安装」。CLI 与官方 Skill 均完成后，只要官方 `auth status` 尚未证明当前用户身份有效，弹窗就显示「CLI 与官方 Skills 已安装，当前未授权」和「重新授权」，直接调用 Main 的固定 provider 授权生命周期，不创建 thread、不提交 Agent 消息，也不要求 workspace。DWS 默认打开钉钉官方浏览器登录页；Lark 在首次使用时先打开官方应用配置页，配置完成后自动进入用户授权。授权期间弹窗显示「请在已打开的官方网页完成授权」，不展示链接或二维码，并且主按钮必须为可操作的「取消授权」；系统无法可靠感知用户关闭外部浏览器，因此不得把等待态做成无恢复动作的禁用按钮。授权等待期间点击「取消授权」、遮罩或关闭按钮都必须结束当前授权会话：Main 立即放弃 session、终止子进程、清理临时目录并恢复「重新授权」，迟到的子进程事件不得反写失败；再次打开详情不得继续显示「取消授权」。授权失败后仍显示「重新授权」，但可以同时展示经过清洗的具体失败原因。每个阶段完成后 Main 都以官方 `auth status` 重新验证并通过 CLI state 事件同步弹窗，只有验证成功才显示绿色「已连接」。Lark 必须同时满足 `identities.user.available=true` 与 `identities.user.verified=true`；顶层 `verified` 可能只表示 Bot 身份可用，不能证明用户已登录。已连接按钮悬停/聚焦显示「取消登录」，点击执行 provider 官方 logout 并重新探测 readiness；退出后即使应用配置和 Bot 身份仍可用，也必须恢复「重新授权」入口、清除账户展示，并且不得设置安装或普通 CLI 执行错误。

Agent 或业务 Bash 在执行具体业务命令时若收到官方 CLI 的结构化授权要求，仍由 Tool Runtime 进入通用 `interaction_required` 等待，Workbench 以 `ExternalActionGate` 展示安全 HTTPS 链接/受控二维码；用户完成后由 Core 验证并最多自动重放原调用一次。连接器 onboarding 与 run-bound 授权是两条独立入口，但共享同一安全边界：device code、token、secret、原始 stdout/stderr 与二维码本地路径不得进入模型、Journal、AG-UI transcript 或历史 replay。

Outlook 使用 Microsoft identity platform 的 Authorization Code + PKCE：Core 只监听随机 `127.0.0.1` 端口，redirect URI 使用该端口的 `http://localhost` loopback 地址；非 loopback authorization/token endpoint 必须为公共 HTTPS，DNS 解析到私网、link-local、multicast 或与声明 host 不一致的 loopback 必须拒绝。Awaken 发布方使用自有的 Microsoft 公共客户端 ID；该 ID 作为非凭据的发布元数据由 `scripts/build-binary.mjs` 提供默认值，并通过 Go ldflags 编译进 macOS/Windows 发布 binary。开发或私有发行可以用 `AWAKEN_MICROSOFT_CLIENT_ID` 覆盖构建值，运行中的开发 Core 也优先读取同名环境变量。它不是 secret，但不能由插件或 Renderer 覆盖，最终用户不需要填写。未配置时 Outlook 插件 setup 明确失败且不打开网页。当前 scope 固定为 `openid profile offline_access Mail.ReadWrite Mail.Send Mail.ReadWrite.Shared Mail.Send.Shared MailboxSettings.ReadWrite`；shared scopes 只服务 work/school 账号的共享/委托邮箱，用户还必须在 Exchange 中拥有目标邮箱的 Full Access 以及 Send As 或 Send on Behalf 等实际邮箱权限；`MailboxSettings.ReadWrite` 服务主分类的读取、创建、颜色更新和删除。Microsoft Graph 的分类 `displayName` 创建后只读，Awaken 不提供虚假的分类重命名参数。scope 指纹变化会要求既有账号重新连接，普通插件、Renderer 和用户输入不能修改 scopes。企业 Entra token 组合超过 macOS `go-keyring` 单条写入上限时，通用 Credential Store 按随机 revision 分片写入 Keychain 并以 SHA-256 manifest 验证重组；Token 分片与 manifest 均不进入磁盘 metadata。

账号 readiness 在 Core 内只缓存不含 token 的状态、OAuth contract fingerprint 和短期过期时间，避免插件 inventory 为同一 setup 绑定的多个组件重复读取 Keychain；授权成功、断开连接、凭据 contract 变化、明确 401 或重新认证标记都会立即失效或更新缓存。缓存不能提供 access token，也不能替代工具调用前的真实凭据解析与 Graph 鉴权。

Outlook Graph 收到明确 401 时，Core 把账号标为需要重新授权并将 `awaken-outlook` server 置为 `needs-auth`。Workbench 只对这个明确状态进入 `ExternalActionGate`，用户完成连接后原 tool call 以相同 identity 自动重放一次；第二次仍需要授权返回 `connector_auth_replay_exhausted`。Outlook Graph/OAuth 使用 03 域当前 network route；auto 策略下的 loopback 代理在 CONNECT/TLS 链路失败时，只有无副作用的 Graph 读请求会在代理冷却后按新 route 重试一次；OAuth 凭据 POST 先用无凭据 HEAD 预检隧道，真实 code/refresh POST 始终只发送一次。代理负责目标 DNS 时不把 fake-IP 当作 provider 私网地址；切到 direct 后固定经校验的解析地址并继续由 TLS hostname 校验服务身份。普通网络、代理或 timeout 错误只报告暂时不可用并保留 refresh token，不得伪造 `needs_auth`；provider 明确返回 `invalid_grant` 等重新认证错误时才将凭据标为需重连。Graph 写请求、普通断线、4xx/5xx 和结果未知不自动重放。共享邮箱的 403/`ErrorSendAsDenied` 是邮箱授权或 Exchange permission 不足，不改写为账号过期，也不退回个人邮箱执行。

前台邮件、草稿、附件、文件夹、分类和共享邮箱操作完全在本机 Core 到 Graph 的请求链路完成。附件上传使用小文件 Graph attachment API 或 3–150 MiB upload session；下载只写用户给出的绝对新文件路径，不创建父目录也不覆盖。`List-Unsubscribe` 只支持 RFC 8058 public-HTTPS one-click POST 与 `mailto:`，HTTPS 会做 DNS/私网阻断、固定解析、默认端口和 no-redirect；普通外部退订页面只诊断，不自动访问。

Outlook 的新邮件、草稿更新、回复草稿额外 CC、转发和定时新邮件输入把 `to`、`cc`、`bcc` 统一声明为邮箱地址字符串数组；Core 再转换为 Graph recipient 对象，不要求模型构造嵌套 `emailAddress` 或 `{address,name}`。`list_messages` 与 `search_messages` 只向模型返回稳定 `hasMore/nextCursor`，不暴露 Graph nextLink；cursor 是 Core 编码的同源、同 mailbox resource 不透明续页地址，后续调用必须原样复用，不能从页大小推算 `$skip`。Graph 把 `/mailFolders/inbox` 续页规范化成 `/mailFolders('inbox')` 时，Core 只把这两种 OData 资源写法视为等价；跨 origin、mailbox、folder 或 collection 仍 fail closed。`get_messages_batch` 使用 Graph batch 一次读取最多 20 个唯一 message ID，保留单项失败与 Retry-After 且不自动重试；`find_mail_folder` 对 `inbox`、`drafts`、`sentitems`、`deleteditems`、`archive` 等 locale-independent well-known 名称直接向 Graph 解析真实 ID，其他名称在最多 500 个已发现文件夹内递归匹配并按精确路径、精确名称、路径后缀、包含关系排序，多个强候选仍由模型展示而非猜测。`set_message_categories` 完整替换分类，清空时使用明确 `clear: true`，不依赖模型正确构造空数组，也不接受空字符串。定时发送先在 Outlook 创建草稿，本机 `AWAKEN_HOME/outlook/scheduled-mail.json` 只保存计划 ID、mailbox、draft ID、UTC 时间、状态和安全错误，不保存主题、正文、收件人或附件路径。同一 mailbox/draft ID 只能存在一个计划；计划存在时 MCP `send_draft` 拒绝立即发送，用户必须先取消计划并重新确认发送方式。取消计划时草稿已不存在按 `draftCleanup=already_absent` 成功收敛；其他草稿删除失败保留“计划已取消、草稿清理失败”的部分结果。Core 运行时发送到期草稿；退出或休眠期间不常驻，重启后处理已到期计划。只有明确的鉴权失效延后重试；断网、timeout、Graph 错误或结果未知一律收敛为 failed，不自动重放写操作，用户检查 Sent Items 后自行决定。后台订阅、Webhook、邮箱离线同步和系统级常驻调度当前不支持。

## 6. 当前缺口

- MCP builtin 连接会覆盖同名 user MCP config，当前没有通用的被覆盖副本/undo；DingTalk/Lark 旧内建 MCP 记录只在精确匹配退役工厂签名时迁移并先备份，修改过或手工同名记录保留并提示复核；
- builtin active owner 可由 canonical user MCP config 中匹配的 provider identity 重建；local/dynamic active owner 仍只在进程内；
- 通用 MCP OAuth/401/WS 边界沿用 06；Core-owned Outlook 已实现 PKCE、refresh、明确 401 后的交互恢复与一次性重放，但不代表任意 Connector 已自动获得同样的 provider adapter；
- aggregate capabilities 与依赖是声明；MCP readiness 来自 MCP connection/auth，CLI readiness 来自 Main 的绝对路径版本/config/auth 探测；`dws doctor` 仅作内部诊断，不得覆盖已验证的授权可用事实；
- CLI 当前支持 macOS/Windows manifest 条目，Linux 为 `unsupported`；当前固定受管版本为 DWS `1.0.32` 与 Lark CLI `1.0.71`，官方 Skill 与相同版本一并固定，不解析在线 latest，也不调用 CLI self-update；
- 真实 macOS/Windows 安装、授权、过期、取消、重启与卸载旅程仍需按验收规范逐项完成；自动化与 fake CLI 不能单独声明完成；
- Outlook 新增 shared scopes 后，work/school 共享邮箱与 personal Microsoft account 登录都必须分别做真实账号验收；自动化只能证明 scope、路径和 fail-closed，不得代替租户权限与个人账号兼容性；
- per-tool metadata 是可选目录/Artifact 扩展，不为 provider 执行后的诚信或可撤销性背书，也不授权或禁止 MCP 调用；
- 团队/远程 Connector source 如未接入真实 provider，不能以 UI placeholder 写成支持。
