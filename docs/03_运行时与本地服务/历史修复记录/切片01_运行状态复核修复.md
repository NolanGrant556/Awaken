## Proposed Changes

### 1. 修复 Bridge 错误信息脱敏

**文件：** [`apps/desktop/src/main/index.ts`](file:///Users/nolangrant/Awaken/apps/desktop/src/main/index.ts)

**What/How：**
- 保持 `requestRuntime` 不变，继续向上抛出可读错误（它用于 create-run / cancel-run 等场景，需要 body 信息）。
- 在 `ipcMain.handle("awaken:get-runtime-info", ...)` 内部用 `try/catch` 包裹 `requestRuntime` 调用。
- catch 后向 renderer reject 一个固定、不携带原始 body 的安全错误，例如 `Runtime unavailable` 或 `Runtime request failed`。
- 同时把原始错误输出到 main 进程日志（不暴露给 renderer），便于调试。

**Why：**
- 满足 Slice 1 spec "Bridge error 不得包含 API key" 的要求。
- 将脱敏逻辑集中在 bridge handler，而不是修改通用 `requestRuntime`，避免影响其他需要详细错误信息的 runtime 调用。

### 3. 补全 handleRuntimeInfo 的 500 序列化失败处理

**文件：** [`src/server/handlers.go`](file:///Users/nolangrant/Awaken/src/server/handlers.go)

**What/How：**
- 修改 `handleRuntimeInfo`：
  1. 判断 `provider == nil` 时返回 503（已有逻辑，保留）。
  2. 调用 `json.Marshal(provider.GetRuntimeInfo())`。
  3. 如果 `err != nil`，调用 `http.Error(w, "failed to serialize runtime info", http.StatusInternalServerError)` 返回。
  4. 成功时设置 `Content-Type` 并 `w.WriteHeader(http.StatusOK)`，再 `w.Write(data)`。
- 保持 `writeJSON` 不变，继续供其他 handler 使用（它们的 payload 不涉及 spec 的 500 要求）。

**Why：**
- 严格满足 spec 对序列化失败场景的行为定义。
- 避免在 `WriteHeader(200)` 之后再发生 encode error 导致无法改状态码。

### 4. 增强 BaseURLHost 精确断言

**文件：** [`src/server/server_test.go`](file:///Users/nolangrant/Awaken/src/server/server_test.go)

**What/How：**
- 在 `TestRuntimeInfoEndpointDoesNotLeakSecrets` 中，除了检查 body 不包含 secret，再增加：
  ```go
  var info RuntimeInfo
  if err := json.NewDecoder(rec.Body).Decode(&info); err != nil {
      t.Fatalf("failed to decode response: %v", err)

      t.Fatalf("expected base_url_host api.anthropic.com, got %q", info.BaseURLHost)
  ```

- 注意：因为 `rec.Body` 已被读取，测试前需要先保存 body 字符串或重新构造 reader。这里可以先 `io.ReadAll(rec.Body)` 得到 body 字符串，再用 `strings.NewReader(body)` 做 decode。

**Why：**
- 明确验证 `extractHost` 从 `https://api.anthropic.com/v1` 提取出 `api.anthropic.com`，而不仅仅是字符串包含。

## Assumptions & Decisions

1. **Bridge 脱敏不改动 `requestRuntime`**：该函数被 create-run、cancel-run、resolve-approval 等多个 handler 复用，那些场景仍需要把 runtime 错误信息带给 renderer。只在 `get-runtime-info` handler 做兜底脱敏，是最小侵入且符合 spec 的方案。
2. **不修复 renderer 轮询 in-flight guard**：review 中提到的“轮询可能重叠”属于 P3 低风险项。当前 3 秒间隔、本地 runtime 请求通常在毫秒级完成，重叠概率极低；修复它需要的 abort controller/request counter 会引入额外复杂度。本轮计划不做，留待后续如果观察到实际状态覆盖问题再处理。
3. **历史切片目录是否提交**：当时用户提供的 spec 路径位于 Trae 规格目录，属于项目计划文档，应随代码一起提交以便追溯。该规格现已迁入 `docs/03_运行时与本地服务/历史切片/切片01_运行状态/`。
4. **不主动运行 `git commit`**：用户记忆约束“Do not commit code changes”。本计划只执行 `git add` 到 staging，不执行 `git commit`。
