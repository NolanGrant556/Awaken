# Workbench 用户消息撤销与编辑设计契约

## 1. 权威范围与当前状态

本文是普通 Desktop Workbench 中历史用户消息撤销、原位编辑、有效历史裁剪和重新生成的唯一产品与工程权威。

**当前支持：** SemanticJournal v2 普通会话中的耐久用户消息可撤销或编辑。旧 v1 transcript、归档会话、定时任务专用会话、ACP 会话以及存在 `running | cancelling` run 的会话不支持历史改写。撤销/编辑只改变当前会话的有效对话谱系，不复原项目文件、Memory 或任何外部系统副作用。

Workbench 通用 ownership、输入结构、重放和协议边界分别见[架构契约](架构契约.md)、[输入、斜杠菜单与附件](输入、斜杠菜单与附件.md)、[叙事投影与重放](叙事投影与重放.md)、[SemanticJournal 与重放](../../03_运行时与本地服务/SemanticJournal与重放.md)和 [HTTP 与 SSE 接口契约](../../09_AGUI与A2UI协议/HTTP与SSE接口契约.md)。

## 2. 用户行为

### 2.1 消息操作栏

- 可改写的用户消息气泡下方显示「撤销、编辑、复制」操作栏，位于 turn header 内，不是 narrative item、overlay 或第三种 Composer。
- 撤销和编辑按钮分别以「撤销此消息」「编辑此消息」作为 Tooltip 与 accessible name；撤销使用 Design System 的 `undo` 概念（左指回弯箭头），编辑使用 `edit`。按钮支持 pointer、键盘聚焦及原生 button 的 Enter/Space 激活。
- run 执行或取消过程中按钮禁用。同一时刻最多编辑一条消息；编辑期间底部 Composer 保持原草稿但不可提交。
- 长消息的展开/收起、正文选择、附件显示和复制行为保持不变；点击操作按钮不触发气泡展开。

### 2.2 撤销

1. 用户点击「撤销此消息」后，Desktop 用 `AwakenDialog` 明确提示：该消息及后续对话会被移除，但已经执行的文件修改或外部操作不会撤销；如果当前 Composer 有草稿，同时提示草稿将被替换。不使用系统 `window.confirm`。
2. 用户确认后，Desktop 提交目标 `runId` 与当前可见 active head。Core 成功前不乐观删除 UI。
3. 成功后，目标用户消息及其后全部 turn 从 active lineage 消失；目标 run 的正文、附件、Composer token 和文件评论恢复到当前 thread 的 Composer，光标位于正文末尾。
4. 撤销首轮后 thread 本身保留、继续选中，active head 为空，并使用既有 center Composer 规则。

“回复消失”是因果后缀失效：撤销第 N 轮会同时移除第 N 轮用户消息、其回复/工具过程，以及所有后续轮次。这些 run 不再进入 transcript、Workbench 重放或下一次模型上下文。

### 2.3 编辑

1. 点击「编辑此消息」只进入 Renderer 受控编辑态；原回复在提交前仍可见。
2. 编辑面在原气泡位置展示 textarea，以及「取消」「发送」按钮。`Escape` 在非 IME composition 状态下等价于取消。
3. 取消只退出编辑态，不修改会话历史或底部 Composer 草稿。
4. 发送前显示与撤销相同的副作用和草稿替换提示，同样使用 `AwakenDialog`。确认后先提交 rewind，再用修改后的正文和原 run 的附件、Composer token、文件评论走现有 `StartRun` 校验与创建链路。取消确认只关闭弹窗，保留 inline editor 与底部 Composer 草稿。
5. canonical transcript 重放一次性移除旧后缀；新 run 创建后按普通 run 进入计时、事件订阅和回复生成。

当前 inline editor 只修改纯文本正文；原消息的 token、附件和文件评论会原样保留并随新 run 重新校验。需要增删这些结构化输入时，应先撤销到普通 Composer 中操作。

## 3. 副作用边界

历史改写绝不等同于操作回滚：

- 已写入、删除或移动的项目文件不会自动复原；
- 已发送的邮件、消息、MCP/CLI mutation 和系统操作不会反向执行；
- Memory mutation 使用独立耐久 authority，不随 thread rewind 删除；
- 失效 run 的磁盘附件/blob 暂时保留，但不再属于 active conversation；本功能不承担垃圾回收。

因此用户如果需要恢复文件，应使用 Git、编辑器历史、废纸篓或对应外部系统提供的恢复能力，不能依赖消息撤销。

## 4. 耐久历史与恢复

### 4.1 Append-only marker

物理 journal 不截断或覆盖。成功改写追加一个无可见 AG-UI 帧的 `thread_rewound`：

```json
{
  "kind": "thread_rewound",
  "thread_id": "thread_...",
  "payload": {
    "rewind_id": "rewind_...",
    "target_run_id": "run_...",
    "previous_active_head_run_id": "run_...",
    "mode": "undo"
  }
}
```

读取层按 semantic sequence 折叠 active run lineage：marker 使 active lineage 中从 `target_run_id` 到当时头部的所有 run 失效；marker 自身不进入模型消息或 Workbench narrative。后续新 run 正常追加，因此编辑表现为“rewind 后追加 replacement run”。

所有下列路径必须消费同一 active lineage：

- `messagesFromSemanticRecords()` 的模型 conversation 恢复；
- `RestoreThread()` 的内存 Agent/thread 重建；
- `GetThreadTranscript()` 与 Desktop replay；
- `ThreadSnapshot.RunID` 和侧栏 preview 投影。

rewind 成功后 Runtime 丢弃该 thread 的内存 sessions/thread；下一次运行必须从折叠后的耐久历史重建，不能携带失效后缀的 conversation 或 provider opaque state。metadata 的 latest run/preview 是投影；首轮撤销时必须显式清空，不能因空值合并规则保留旧头部。

### 4.2 并发与失败

- `RewindThread` 持有排他的 thread/project mutation 边界，和 `StartRun` 互斥。
- 请求的 `expected_head_run_id` 必须等于当前 active head，且 target 必须仍在 active lineage；否则返回 `THREAD_HISTORY_CONFLICT`。
- journal marker append + flush 成功后才更新 metadata 和丢弃内存状态。
- Core 提交失败时 Desktop 保留原回复与编辑内容。
- 当前编辑发送由 `rewind` 与现有 `StartRun` 两步组成：若 rewind 已提交而新 run 创建失败，旧后缀保持失效，修改后的结构化草稿恢复到 Composer 供用户修正或重试，不伪造 replacement run。

## 5. 接口

### 5.1 Core HTTP

```text
POST /v1/threads/{thread_id}/rewind
Content-Type: application/json
```

请求：

```json
{
  "target_run_id": "run_被撤销的用户轮次",
  "expected_head_run_id": "run_当前有效头部"
}
```

成功响应：

```json
{
  "thread": { "thread_id": "thread_...", "run_id": "run_前驱或空" },
  "target_run": { "run_id": "run_...", "input": "..." },
  "removed_run_ids": ["run_...", "run_后续..."]
}
```

`target_run` 是 Core 在改写前读取的 canonical run，用于恢复正文、附件、token 和文件评论；客户端不能从已渲染 DOM 反推耐久输入。`removed_run_ids` 是回执，不是 Renderer 本地 splice 的 authority；UI 必须重读 canonical transcript。

稳定错误：

| HTTP | code | 含义 |
|---|---|---|
| 400 | `INVALID_REWIND_TARGET` | thread/target/head 缺失 |
| 404 | `THREAD_NOT_FOUND` | 会话不存在 |
| 409 | `THREAD_BUSY` | 会话有活动 run 或正在删除 |
| 409 | `THREAD_HISTORY_CONFLICT` | target/head 已不是当前有效谱系 |
| 409 | `THREAD_REWIND_UNSUPPORTED` | v1、归档、定时或 ACP 会话 |
| 503 | `PERSISTENCE_UNAVAILABLE` | 无耐久 journal |

### 5.2 Desktop bridge

Renderer 只通过 `RuntimeClient.rewindThread()` 调用 typed Preload/Main bridge。Main 对 path segment 编码并映射 wire DTO；Renderer 不获得 journal 路径、FileStore 路径或模型凭据。新回复仍通过既有 `startRun()`，Main 继续负责完整模型配置和 secret 边界。

## 6. Owner

| 层 | Owner | 职责 |
|---|---|---|
| Design System | `AwakenUserPromptBlock.tsx`、`tokens/components.css` | UI-only 操作栏、Tooltip、编辑面和 disabled/pending 样式 |
| Renderer | `App.tsx`、`run-narrative/*`、`runtime/reducer.ts`、`runtime/thread-transcript.ts` | 稳定 `runId` 绑定、编辑暂存、确认、canonical replay、Composer 恢复与新 run 订阅 |
| Main/Preload/shared | `apps/desktop/src/main/index.ts`、`preload/index.ts`、`shared/runtime.ts` | typed IPC、wire normalize、runtime 请求 |
| Server | `src/server/router.go`、`handlers.go` | route、严格 JSON 与稳定错误映射 |
| Runtime/Store | `src/runtime/run_service.go`、`journal_store.go`、`threads_shared.go`、`file_desktop_store.go` | 排他改写、append/flush、active lineage、metadata 和恢复 |
| Semantic schema | `src/agentcore/semantic_record.go` | `thread_rewound` kind；不生成可见 narrative |

## 7. 验收

自动化至少运行：

```bash
npm --workspace @awaken/desktop run test
npm run typecheck:desktop
npm run typecheck:ui
go test ./src/runtime ./src/server ./src/protocol/agui
npm run test:docs-links
git diff --check
```

真实 Desktop 通过根 README 的 `npm run open:desktop` 验收：

| ID | 旅程与预期 |
|---|---|
| ME-01 | 终态普通会话每个耐久 prompt 下显示撤销/编辑/复制；Tooltip 与 accessible name 为指定中文文案。 |
| ME-02 | 撤销最新轮次后该 turn 消失，正文和结构化输入回到同一 thread Composer。 |
| ME-03 | 三轮会话撤销第二轮，第二、第三轮全部消失；完整重启后不复现。 |
| ME-04 | 编辑正文后取消或按 Escape，原消息和回复完全不变。 |
| ME-05 | 编辑发送后旧后缀消失，新 prompt 生成新回复；重启后只恢复 active lineage。 |
| ME-06 | 撤销/编辑含附件、token、文件评论的消息，结构化输入保持；无效输入由现有 StartRun 校验并恢复草稿。 |
| ME-07 | busy、stale head、v1、归档、定时和 ACP 会话不可改写；Core 不产生半条可见历史。 |
| ME-08 | 对写过文件的轮次执行撤销，确认提示明确说明不回滚；文件保持原状，失效回复不再进入模型上下文。 |
| ME-09 | 浅/深色、长消息、窄窗口和文件 surface 中操作栏与编辑面不建立第二滚动 owner，不错误触发气泡展开或 follow。 |

Gallery 和静态组件渲染只能辅助检查，不能代替真实 Desktop 的 ME-02～ME-09。
