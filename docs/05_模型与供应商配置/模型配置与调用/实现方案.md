# 模型配置与调用 · 实现方案

本文说明代码职责、数据与接口、异常恢复和验证方法。功能范围及用户操作见[需求文档](需求文档.md)。

## 流式响应的结束边界

Responses 收到 `response.completed`、已识别的协议终态或 `[DONE]`，Anthropic Messages 收到 `message_stop` 后，立即结束扫描并返回已累积正文、工具和用量，关闭本地响应体；不等待服务端关闭 TCP。终态前 EOF 仍按断流处理，空闲超时不能覆盖已完整收到的成功终态。`terminal_stream_test.go` 用发送终态后保持连接的本地 HTTP server 验证这两个 adapter；`TestStreamInvokeAnthropicUnexpectedEOFWithClosedToolsDisconnects` 锁定 unexpected EOF 不得把已闭合 tool_use 当成功。该故障注入不等于所有供应商实机兼容性验收。

OpenAI 最新模型及窗口来自 [OpenAI Models](https://developers.openai.com/api/docs/models)，Anthropic 当前模型和 Models API 字段来自 [Anthropic models overview](https://platform.claude.com/docs/en/about-claude/models/overview) 与 [Models list](https://platform.claude.com/docs/en/api/models/list)，Google 当前模型与可编程 token 上限来自 [Gemini models](https://ai.google.dev/gemini-api/docs/models) 与 [Models API](https://ai.google.dev/api/models)。Qwen 的三协议合同分别以 [Qwen API reference](https://help.aliyun.com/en/model-studio/qwen-api-reference/)、[Responses compatibility](https://help.aliyun.com/en/model-studio/compatibility-with-openai-responses-api) 和 [Anthropic Messages compatibility](https://help.aliyun.com/en/model-studio/anthropic-api-messages) 为准；普通 API 与 [Token Plan](https://help.aliyun.com/zh/model-studio/token-plan-personal-quick-start) 使用不同 Base URL 和凭据。目录 API 未公开稳定元数据、当前套餐未开放模型列表或凭据不能列出 endpoint 时明确保留“官方清单/手填”，不把静态候选标成 API 实时结果。

三协议由 profile 显式保存，Core 不按 URL 猜测；未知非空协议 fail closed。同一供应商、Base URL 和模型可以分别创建 Chat 与 Responses profile。三种 adapter 都投影为统一文本、思考、工具开始/参数增量/完成、usage、完成或失败事件；上层不解析供应商 SSE。Responses 固定 `store:false` 且不依赖 `previous_response_id`；stateless 历史重放给每个 user/assistant message 显式写 `type=message`，已完成的 assistant output message 与 `function_call` 写 `status=completed`，user input 与 `function_call_output` 不伪造 output status。该 lowering 同时用于主 turn、标题、压缩、Subagent、定时任务、Memory、连接测试、模型 Hook 与 exact native compaction prepared body。Messages 处理 system/content blocks、图片/PDF、`tool_use/tool_result`、thinking/signature、`cache_control`；Chat 处理兼容消息、图片/文件 block、工具、reasoning 和 usage。Chat/Responses 的 function parameters 在 adapter 边界从 canonical tool schema 生成兼容副本：根保持 object 并去掉根级组合关键字，真实执行仍使用未改写的 canonical schema 校验。

OpenAI 官方当前定义了 [`POST /responses/compact`](https://developers.openai.com/api/reference/java/resources/responses/methods/compact)：返回所有 user messages 后跟一个加密 compaction item。Awaken 已接入受限 native adapter：只有 exact `provider=openai + protocol=openai_responses + https://api.openai.com/v1 + 显式模型 capability` 才会在本地 V2 draft 完成后调用；opaque output 绑定 profile、credential revision、model、protocol 和 endpoint contract，随 `context_compacted_v2` 原子持久化，并在同 identity 的后续 Responses `input[]` 前原样重放。Awaken 仍固定 `store:false`，不把 `previous_response_id` 作为 thread authority；native 调用失败、返回无效 item 或完整 prepared body 超过同一硬 10% target 时回落 provider-neutral checkpoint，且只提交一个 compact boundary。OpenAI Chat、Messages、custom/兼容网关不得继承。当前 mock/自动化已覆盖 exact route、identity、重启与 fallback；本机没有 ready OpenAI profile，真实 OpenAI endpoint/Desktop 调用未列为已通过，也不属于本次 V2 收口检查要求。

`temperature` 是可选 wire 参数：只有请求 purpose 的明确策略、显式 request override 或 profile 中非零配置提供值时才发送，显式 override `0` 仍会保留；没有已知值时三个 adapter 都省略该字段，由目标模型使用自身默认值。Core 不再为未知/自定义模型注入通用 `0.7`。Kimi、DeepSeek、Ark 等已有 purpose/provider 策略继续通过明确 override 生效，不受该缺省变化影响。Kimi 可调推理模型（普通 API 的 `kimi-k3`、Coding Plan 的 `k3`/`k3-256k`/`kimi-for-coding`）思考模式辅助调用使用 `temperature=1`，Coding Plan 关闭思考的 Chat 请求使用 `0.6`，且当当前路由没有可确认的禁思考合同时，不再伪造 `DisableReasoning`，而是把辅助调用降到 `reasoning_effort=low` 以减少 compact/title 等有限预算请求被 reasoning 吞掉的概率；exact 火山方舟按量、且已列入[深度思考](https://docs.volcengine.com/docs/82379/1449737)的 Chat 与 Responses 模型，在官方 Base URL 上发送 `thinking.type=disabled`：豆包 Seed（Evolving、2.1 Pro/Turbo、当前 2.0 Code/Pro/Lite/Mini）、托管 DeepSeek GA/预览日期 ID，以及 `glm-5-2-260617`。title、compact、Memory recall 与 Hook prompt 的 `DisableReasoning` 走该线字段，不再把关思考写成最低档 `low`，也不伪造 `reasoning.effort=none`。已绑定上述 family 的 `ep-*` 同样发送。自建网关或不在白名单的 Seed / 托管 DeepSeek GA 身份仍降到 `low`。`glm-5-3-flash-260828`、无 family 的 `ep-*`、Coding Plan 与 Agent Plan 的 Chat/Responses 不继承该关思考字段。火山 Coding / Agent Plan 若走 Messages，仍按协议省略 thinking 块。K2.5/K2.6 的可禁用思考辅助调用使用 `0.6`，K2.7 Code 同样使用 `1` 且不得伪造禁用思考字段。`DisableReasoning` 只是逻辑意图；协议 adapter 按 `ResolveReasoningOffDecision` 写成已公布的线字段、Messages 省略 thinking 块、最低 effort，或保持不发送私有字段。

DeepSeek 当前官方推荐 ID 为 `deepseek-flash`（V4.1-Flash，原生多模态）。`deepseek-v4-flash` 与 `deepseek-v4-flash-vision-exp` 已退役，官方仍临时路由到 V4.1-Flash；选择器不再展示退役 ID，存量 profile 仍可解析。`deepseek-v4-pro` 仍出现在官方入门文档中，因此保留在清单里。Responses 的思考模式默认开启；只有 exact `provider=deepseek + official base + openai_responses + deepseek-flash/v4-flash/pro` 的辅助请求才在 `DisableReasoning` 时发送官方定义的 `reasoning.effort="none"`，避免 title/compact 的有限输出预算被 reasoning 耗尽；OpenAI 官方与 custom/兼容网关不继承该字段。

协议能力分为 provider 与 model 两级。provider 的 `supported_protocols` 决定连接弹窗可声明的 adapter；具体模型的 `model_capabilities[].supported_protocols` 只记录 API observation 或版本化官方清单已经确认的组合。目录候选会排除“明确不支持当前协议”的模型，缺少模型级事实的未来模型与手填 ID 仍可输入，不因静态清单过期而硬拦截；连接探针和正式 run 返回才是当前 endpoint 的最终事实。同模型不同协议继续形成独立 profile、usage 与 cache identity。

Qwen 普通 API 与 Token Plan 是两个独立入口：普通 API 默认使用 `qwen3.8-max`，Token Plan 也默认 `qwen3.8-max`，不能用同一 endpoint/profile 混合解释。`qwen3.8-max-preview` 已结束预览，官方仍接受该 ID 并路由到 `qwen3.8-max`；选择器不再展示 preview，存量 profile 仍可解析。官方当前也把 `qwen3.8-flash` 与 `qwen3.7-plus` 列为可用文本模型；Awaken 在 exact model capability 中保守采用思考模式最大输入 983,616。当前官方 Messages 的 effort 枚举只明确列出 Qwen3.8，所以不为 `qwen3.7-plus` 伪造推理强度档位。两类凭据都可按官方合同选择 Chat、Responses 或 Messages，但 Base URL 与 API Key 必须按计费入口成套使用。Token Plan 的目录同步只使用 Token Plan Key 请求 `https://token-plan.cn-beijing.maas.aliyuncs.com/compatible-mode/v1/models`，不得回退普通 DashScope 目录；请求失败或返回空目录时保留版本化官方清单，并继续允许手填模型 ID。

当前 macOS Desktop 已用普通 Qwen API 的真实 `qwen3.7-plus` + `anthropic_messages` profile 完成多轮 agent run；journal 的每个请求与 usage 都记录同一 model/protocol/profile identity。模型先调用 `tool_find`，宿主写入 `deferred_tools_activated`，下一 Messages 请求再以 `input_schema` 接收新增的 10 个内建工具、点号 Plugin MCP 工具和 4 个远程 MCP 工具，并全部形成真实 tool call/tool result。该基线确认的是 Awaken 在 Messages 兼容 API 上的宿主级动态工具披露与工具回路可用，不把它表述为 Qwen 提供 Anthropic 原生 `defer_loading`。

MiniMax API 与 Token Plan 的内置入口固定为中国区：Chat/Responses 使用 `https://api.minimaxi.com/v1`，Messages 使用 `https://api.minimaxi.com/anthropic`。中国区与国际区 Key 不保证互通；读取存量 profile 时只把已知旧预置 `api.minimax.io` 地址归一化为中国区地址，用户显式填写的完整推理地址不被改写。MiniMax Chat 请求发送 `reasoning_split:true`，adapter 把累计 `reasoning_details` 快照去重为统一 reasoning delta；兼容端点仍把思考嵌在 content 时，由跨 SSE chunk 的前导 `<think>...</think>` 状态机分流。Renderer 永远只消费统一 reasoning/text 事件；存量 journal 中以 `<think>` 开头的完整 assistant 快照在重放时拆成 Thought 与清理后的回答，原标签和 Host policy 不再进入普通回答。

## Profile、能力与持久化

`~/.awaken/config/models.json` 当前写入 version 3，version 1/2 继续兼容读取并在首次成功读取后无损迁移。`protocol` 是必填身份字段；旧 profile 只按所属 provider 的既有固定协议补齐，不按 URL 推测。每个 profile 的非敏感事实包括：

```text
id / providerId / displayName / modelId
baseURL / protocol / authScheme
enabled / isDefault
advanced.maxInputTokens / contextWindow / maxTokens / temperature
advanced.endpointId / inferenceEndpoint
advanced.supportsVision / supportsNativePDF / supportsVideo
advanced.supportsTools / supportsPromptCache / defaultReasoningEffort
credentialRevision / credentialReference / keyLast4
purposeRoutes.thread_title / compact_summary / subagent / scheduled_task / hook_prompt / hook_agent
```

其中 capability 与 purpose 字段保留为存量 schema、Core 快照和 Host 内部路由合同，不代表每个字段都存在对应开关。Desktop 允许用户编辑有效 `contextWindow`、`maxTokens`、模型启停与默认项；内置 provider 的媒体、工具、缓存和 reasoning 仍由 API observation、官方清单和协议合同决定。只有 `custom` 允许在连接弹窗显式写入 `advanced.supportsVision=true|false`，缺省按 `false` 读取；Core 对 `custom` 始终把 `supportsNativePDF` 收窄为 `false`，即使旧配置或手工文件把它写成 `true` 也不提升原生 PDF 能力。

凭据引用分为 `profile_secret(profileId)` 与 `provider_account(providerId, accountId)`。存量 profile 缺少该字段时解释为 `profile_secret`；Agent Plan profile 固定引用 `volcengine-agent-plan-default`，不复制账户 key。

profile 去重身份为 `providerId + normalized Base URL + model/endpoint selector + protocol`；因此同模型的 Chat 与 Responses 可以共存，同协议同 endpoint 的重复项被拒绝。disabled profile 不能是 default；删除 default 后选择剩余可用项。默认模型只是新会话的初值，不是既有 thread 的强制覆盖。

`defaultReasoningEffort` 继续作为 capability 派生值和存量 schema 兼容字段存在，但 Desktop 设置页不提供编辑入口。用户可见选择只发生在 Composer；没有 thread 覆盖时由内部 profile/capability 默认值兜底。

### 能力来源与合并

内置 provider 的能力事实合并为：

```text
版本化官方 MODEL_CAPABILITIES
  -> exact-scope 供应商 Models API observation 覆盖同字段
  -> 未提供字段保持 unknown
```

每个内置能力字段（包括模型级 `supportedProtocols`）同时携带 `source` 与可用时的 `observedAt`。供应商 API 返回值覆盖旧 observation 和官方兜底；用户只可把有效上下文/输出预算设得更低，或在最大窗口未知时手填该 profile 的运行限制，不能在前端提升内置模型的图片、PDF、视频、工具或缓存支持。`custom` 的视觉开关是用户对 exact transport contract 的显式声明，不是连接测试或供应商 observation；默认关闭，且只影响 `supportsVision`。OpenAI `/models` 只提供基础目录，因此上下文与能力由版本化官方清单补齐；Anthropic/Google/Qwen 的 token 上限和嵌套 `capabilities/features/limits` 在 API 返回时直接归一化。模型原生能力不等于当前协议能力：Google 本轮经 OpenAI-compatible Chat 调用，官方兼容文档只确认图片输入，因此原生 PDF/video 与 `cached_content` 不被冒充为当前 Chat/file 或 `prompt_cache_key` 合同；PDF 走页面渲染回退。

动态缓存为 v2 scoped cache，严格 identity 至少包含 `provider + normalized Base URL + protocol + profile + credential revision + selector kind + endpoint contract`；相同 provider/model 但不同凭据、代理、自定义 Base URL 或接入点不得复用。v1 的 provider-global 缓存只能当冷缓存忽略，不迁移为新作用域事实。`/models` 只返回 context 时，不能覆盖同作用域内经过验证的 effort。新鲜 observation 在自己的 exact scope 内合并，不投影到其他 profile。

provider catalog 可以把同一 provider 已观测到的模型 ID 合并进候选列表，并标记 API 来源与最新观测时间；Main 先按上游 type/task/category/method 和已知模型族把目录条目归一化为 `llm | image | video | audio | embedding | unknown`，官方 LLM 选择器只接收 `llm | unknown`，不会把 Qwen `happyhorse-*` 等视频模型混入对话模型。稀疏标准 `/models` 返回的 unknown ID 继续允许选择，避免错误删掉未来 LLM。目录不得把某个 profile 的 scoped capability 值传播给其他 profile。Renderer 展示能力时优先使用 profile 摘要上的 exact-scope `effectiveCapability`，缺失时才回退版本化官方 catalog。

`default_max_tokens` 是新 profile 和缺省配置的输出预算，`max_output_tokens` 是不可突破的模型上限；Desktop、Desktop 启动的 Core、ACP 和定时任务必须遵守同一优先级与 clamp 规则。

`supportsTools` 不再对动态模型强制写 `ready`。API/官方清单未提供时保持 `unknown`；`unsupported` profile 不下发 function tool schema，未知时由运行时保守处理。连接测试不改写该字段。

## Agent Plan 账户、目录分流与生成工具

当前只有固定账户 `volcengine-agent-plan-default`。非敏感 metadata 原子写入 `~/.awaken/config/agent-plan-account.json` version 2，保留旧 `modelIds` 读取兼容，并增加结构化 `catalog[]` 与 `builtinCatalogRevision`；文件权限为 `0600`。Key 使用 `.env` 中独立的 `AWAKEN_AGENT_PLAN_API_KEY_<accountId>` 命名空间；Renderer 只获得 `hasKey`、掩码、`credentialRevision`、结构化目录和更新时间。

`catalog[].kind` 只允许 `llm | image | video | unsupported | unknown`。分类由 Electron Main 完成：Main 先装载版本化的官方精确模型清单，再兼容消费上游未来可能提供的 `/models` 类型字段和已知模型族规则；Renderer 不按名称猜测。当前内置媒体清单包含 `doubao-seedream-5.0-lite` 与官方列出的 Seedance 2.0 / 2.0 Fast / 2.0 Mini / 1.5 Pro 精确 ID。两个选择器严格分流：

- Agent Plan 新建连接的主模型候选固定只展示 `ark-code-latest`；账户目录中的图片和视频条目不进入主模型选择和 Composer；
- Agent Plan“模型与工具”中的生成工具卡片只接收 `image | video`；每种 capability 最多一个配置；
- `unsupported | unknown` 默认不进入任一选择器；Agent Plan 主模型当前不提供任意自定义 ID 输入；
- Core 再读取账户 catalog 防御性校验，旧 profile 不能绕过 Main 把媒体模型作为主模型；`ark-code-latest` 始终作为已知 `llm` fallback。

保存账户或点击更新清单会对固定 endpoint 的 `/models` 做兼容探测。主模型候选始终固定为 `ark-code-latest`；完整目录继续分类、持久化并把最新的 `image | video` 条目提供给“模型与工具”页。火山 Agent Plan 当前对该路径返回 `404` 时，Main 写入版本化内置媒体清单；这表示供应商未提供目录接口，不表示 Key 无效。网络错误或其他上游失败保留内置与已有缓存。内置媒体清单只证明模型 ID 与类型受支持，具体套餐权限在首次真实工具调用时确认。旧 version 2 文件在读取时自动补齐内置条目并原子回写，保证 Core 与 Renderer 消费同一目录。`ark-code-latest` 的实际路由模型不固定，永远不展示 effort。Key 实际变化时 revision 单调递增；metadata 写入失败恢复旧 key。

媒体工具非敏感配置由 Main 独占写入 `~/.awaken/config/agent-plan-media-tools.json` version 1、`0600`：每条只保存固定账户引用、`media.image.generate | media.video.generate`、精确模型、enabled 和 configuration revision，不复制 Key。重复保存相同模型与状态是幂等操作；换模型、启停或 Key revision 变化都会形成新的后续 run provider identity。账户仍被任一 profile 或任一 enabled/disabled 媒体配置引用时拒绝删除。

配置保存、启停或删除在无 active run 时先原子写入配置，再通过 Desktop 与 Core 之间受 control token 保护的本地路由，只热刷新对应的 `image_generate` 或 `video_generate` 注册；这条路径不停止 Core、不清空会话，也不重新同步模型目录。工具注册表的替换或移除只影响后续新建 run 的工具快照，已经固定的 run 继续使用原 runtime instance。账户仍有媒体配置引用时，保存/轮换 Key 或刷新目录继续走同一 active-run 检查要求并重启 Core，避免另一个工具仍持有旧 credential/catalog。Core 启动与热刷新都只为同时满足“配置 enabled、能力与模型 kind 一致、固定账户 Key 可读”的条目注册稳定工具：

| 配置 capability        | 模型可见工具     | Provider capability |
| ---------------------- | ---------------- | ------------------- |
| `media.image.generate` | `image_generate` | `image.generate`    |
| `media.video.generate` | `video_generate` | `video.generate`    |

工具 schema 不含 provider、账户、Base URL、Key、生成模型或保存绝对路径；这些事实由配置快照固定。`image_generate` 当前支持文本生成单图或最多 15 张组图、可选 size/output format/watermark，调用 Agent Plan 图片生成接口，下载或解码结果并原子写入 `output/generated-media/`；组图逐项返回状态，单项失败时保留并发布已验证的 ready Artifact。图片创建使用独立 10 分钟上限，POST 超时按 unknown side effect 收口，禁止盲目重发。

`video_generate` 支持文本生成视频、可选 ratio/resolution/duration/audio/watermark，也支持把 ready PNG/JPEG Artifact 路径作为 `source_image_path`。Core 会为内联上传压缩过大的图片副本；`first_frame` 使用官方省略 role 的首帧结构，`reference_image` 显式发送 role。视频任务创建后立即耐久保存 task ID；同一 workspace、账户/模型和结构化请求在 Core 重启后再次执行会续查旧任务而不重复创建，也可显式传 `task_id` 续查。官方任务状态只投影 `queued/running/succeeded/failed/cancelled`，不伪造百分比；轮询窗口结束但 provider 未给终态时返回“状态待确认”，保留 task ID。提交超时且没有 task ID 时返回“创建状态未知”，当前 run 禁止再次提交视频任务，必须由用户先核对火山控制台。401/403、429、上游失败、部分成功、任务待确认与下载失败保持不同稳定错误码；未收到 HTTP 响应的网络故障只保留去敏 transport 分类，具体 Outcome 语义由[工具定义与暴露](../../04_工具权限与审批/工具发现与执行/实现方案.md)拥有。

当前已知缺口：尚未实现图片编辑、基于稳定 Artifact ID 的通用参考解析、按具体模型动态收窄全部参数矩阵、Core 启动后主动轮询、detached completion、完整媒体谱系与历史版本回选。现有恢复是在相同请求再次进入 `video_generate` 或显式携带 task ID 时续查，不在没有 run 的后台自行完成。图片/视频的 Workbench 过程卡和终态交付能力由[中间区域产品与交互契约](../../01_桌面工作台/工作台布局与运行展示/需求文档.md)拥有。搜索、Embedding 等其他 Agent Plan 独立工具不因本节自动获得支持。

## Run 注入和缓存边界

Renderer 启动请求只传 `modelProfileId + reasoningEffort`，不传 Key、Base URL 或完整 profile。Electron Main 重新验证所选 profile enabled/ready，解析 profile/账户凭据、能力和有效 effort，再构造只发往本机 Core 的 `model_profile`。Renderer hints 在 Main 中清除，不进入 Core 的严格 create-run decoder。

Core 将有效选择写入：

- `AgentConfig.ModelConfig`；
- model profile/Agent cache key；
- prompt-cache affinity 与 reasoning policy；
- thread metadata；
- run snapshot 的 `model_profile_id` 与 `reasoning_effort`。

火山方舟按量（provider `doubao`）的 `model` 参数接受三类 transport selector：豆包 Seed 按量使用版本化精确 Model ID（例如 `doubao-seed-2-1-pro-260628`），托管第三方按量同样使用[模型列表](https://docs.volcengine.com/docs/82379/1330310)的日期 Model ID（例如 `deepseek-v4-pro-ga-260813`、`glm-5-3-flash-260828`、`glm-5-2-260617`），自建推理接入点使用 `ep-*` Endpoint ID。设置弹窗在同一输入控件中提供官方 Model ID 候选并允许手填 Endpoint ID，不再把 `doubao-seed-2.1-pro` 或计价页短名 `deepseek-v4-pro` 当成可调用 ID，存量该值读取/保存时迁移为当前精确 ID；也不强制按量用户先创建 endpoint。直接 Model ID profile 的 `model_id`、`capability_model_id` 相同且 `model_selector_kind=model`；`ep-*` profile 使用 `model_selector_kind=endpoint`，在没有明确 family 绑定时能力保持未知。Context Epoch、usage、Agent/profile cache identity 包含实际 selector 与 selector kind。旧 profile 若已经同时保存 family 和 `advanced.endpointId`，仍按原绑定读取，不破坏既有 endpoint。火山官方文档将 [Model ID 与 Endpoint ID](https://www.volcengine.com/docs/82379/1298459) 都定义为合法调用身份。

当前 macOS Desktop 的 `doubao-seed-2-1-pro-260628 + openai_responses` 真实基线已覆盖：同一 thread 第二轮 assistant 历史、`tool_find` 与 `calculator` 的 function call/output 回路、`thread_title`、`memory_recall`、原生 `subagent` purpose、切到 DeepSeek Responses 后再切回豆包，以及完整 Desktop/Core 重启后的 stateless replay。所有主 run 均正常终止且保存 provider request ID；连接测试仍遵守“当前表单必须重新输入 Key”的安全合同，不能拿已保存凭据替代当前表单测试。

主调用和普通 child 使用本次已解析的实际 effort。Main 的 resolveRunBundle 在同一次存储读取与变更锁内解析主配置、有效用途路由及凭据，按 profile/account 去重；用途未覆盖时继承本次主选择，内部可选 route 失效记录 optional_route_fallback。公开配置 digest 形成 config_snapshot_revision，进入 Core cache identity 和路由来源；密钥不进入 digest 输出或 Renderer。子任务的 models 查询只返回已配置且可运行的 profile，显式 model_profile_id 和 reasoning_effort 必须匹配该配置；Skill/Plugin model hint 只允许精确 ID 或唯一名称，不能仅替换别的 profile 中的 model 字符串。标题、Memory recall、compact、Dream、两类 Hook 和定时任务继续区分 purpose/cache identity，辅助请求的协议策略与实际 effort 分别记录。深度研究主编循环使用普通主调用 purpose，不再单独走 research_synthesis；历史用量记录仍可出现该 purpose。定时任务先使用任务显式 profile，未 pin 时才使用 Host 默认；显式 pin 失效时失败，不静默更换供应商。

## 用户入口的实现

`AwakenModelProviderForm` 在模型 combobox 容器处理展开态的 Escape，阻止该次事件继续关闭外层 Dialog；输入框、候选项和展开按钮使用同一规则。恢复输入框焦点可能触发其打开目录逻辑，因此先恢复焦点、再关闭目录。`NestedMenuEscape.behavior.test.tsx` 覆盖三个事件来源及父弹窗草稿保留。真实 Desktop 通过“设置 > 模型 > API > 配置 API Key > 火山方舟”验证 endpoint 模型目录关闭后配置面板仍在；记录见[浮层验证记录](../../../apps/desktop/test-fixtures/related-popover-layout/verification.json)。该检查不修改凭据、不保存配置，也不代表供应商连接验收。

- 连接配置：Coding Plan 显示“配置 Token”，API 与自定义显示“配置 API Key”，Agent Plan 显示“配置账户”；当前类型的 provider 以固定三列、统一高度的紧凑卡片展示官方产品 Logo、名称和“配置”动作。点击卡片在屏幕中央打开配置弹窗，连接状态紧邻供应商名称右侧。内置 provider 的弹窗只展示连接必需的协议、模型、密钥与目录状态，不提供媒体、工具、缓存、上下文或推理强度等“高级能力”开关；自定义 API 是唯一例外，额外提供默认关闭的“视觉多模态”开关。用户开启后只声明该 exact profile 的当前网关、协议和模型接受图片输入，并允许 `Read` 把 PDF 页面渲染为图片发送；它不声明原生 PDF、视频、工具或缓存支持。协议选择按供应商约束：OpenAI 仅公开 Chat Completions 和 Responses，Anthropic 仅公开 Messages，自定义 API 可选三种协议；其他国内计划按其官方合同显示可选协议，不把默认官方地址当万能三协议网关。存量 MiniMax `minimax_chat` profile 只保留读取迁移兼容，新配置不再使用该协议。
- “API 密钥发送方式”只决定 HTTP 认证 Header，不是第四种模型协议：Bearer 发送 `Authorization: Bearer <API_KEY>`，其余合同分别发送 `x-api-key`、`api-key`、`x-goog-api-key`，无鉴权不发送认证 Header。内置厂商的 Header 与 Base URL 由 Main 按所选协议固定；连接弹窗以只读字段展示当前实际 Base URL，切换协议时同步显示对应官方地址。只有自定义 API 的鉴权和 Base URL 可编辑，由用户声明网关合同。不接受任意秘密 Header。OpenAI/Anthropic 可另存只用于组织用量与成本的管理密钥；它与推理密钥分开保存、轮换和掩码，Renderer 不取得明文。
- 打开已保存凭据的内置供应商配置弹窗时，Main 按 profile、凭据 revision、Base URL、协议与 endpoint contract 自动刷新模型目录。内置 API 与 Coding Plan 弹窗以右侧复选框罗列当前协议兼容的 LLM；首次打开先展示版本化官方清单并默认全选。目录 API 成功返回非空 LLM 列表后，选择器改为只展示该次官方目录，不再把已下线的内置 ID 永久合并进去。刷新后只保留用户此前已勾选且仍出现在新目录中的模型；若交集为空，则勾选默认模型或第一个候选。新出现的官方 ID 默认不勾选，避免一次保存创建大量 profile。用户可再勾选或取消，保存时 Desktop 只为仍被勾选、且该 Key 实际返回的模型建立或更新 profile，至少需要勾选一个。无目录 API 的内置套餐以版本化官方清单作为复选项。取消勾选表示本次不加入，不删除已有 profile；自定义 API 仍只保存手填模型。用户也可直接点击“刷新模型目录”。同步过程显示 loading、成功条数、失败原因、缓存来源和观测时间，不再静默用旧目录冒充最新。目录失败或返回空列表时保留当前勾选和版本化官方清单。自定义 API 不请求 `/models`、不显示候选列表或刷新入口，模型 ID 始终由用户在纯文本输入框填写。
- LLM 设置：Coding Plan、API 和自定义只展示当前类型已经配置的模型卡片，并显示对应产品 Logo；标题固定按“厂商名：模型展示名”单行展示，同模型存在多协议 profile 时同时显示协议，管理默认模型、启停、上下文、输出上限和删除。供应商要求日期后缀等精确调用 ID 时，Main 同时保存不参与请求的展示名映射；连接弹窗、LLM 卡片、Composer 与定时任务只显示稳定产品名，请求、profile identity 与能力查找仍使用精确 ID。未收录和用户手填 ID 原样显示。已知上下文显示滑杆和精确输入；供应商 API 与官方清单都未提供时显示手填输入，保存为该 profile 的有效上下文限制。展开参数导致页面超过窗口高度时，模型页使用标准设置滚动面，滚轮移动右侧页面且左侧一级设置导航保持固定；模型卡片内部不创建嵌套滚动。滚动指示沿用标准设置页窄 thumb，不再从 168px 装饰页头下方起算。图片、PDF、视频、工具、reasoning 与缓存能力不在此处编辑。
- 辅助调用不在前端提供独立“用途模型”设置。`thread_title`、`compact_summary`、`subagent`、`hook_prompt`、`hook_agent` 默认继承 thread/父 profile，定时任务使用任务显式 profile 或 Host 默认；Host 仍负责凭据、成本和失效回退，Renderer 不创建第二套模型目录。
- 模型与工具：Agent Plan 的第二页使用该名称。页面上部沿用相同的主模型卡片，下部直接展示“图片生成”和“视频生成”两张生成工具卡片；每张卡只保留模型单选、保存、启停和删除。模型单选统一使用 Design System `AwakenSelect`，与连接配置中的模型列表共享触发器、列表表面、选中态、键盘操作、前述视口自适应和无可见轨道的滚动样式，不使用操作系统原生 `<select>` 菜单。API Key 只在“配置账户”保存一次，生成工具区不重复出现凭据表单、供应商弹窗或“已配置工具”子页。图片和视频每类最多保存一个精确模型；媒体配置不创建 `ModelProfile`，不进入 Composer 模型选择器。配置并启用后，用户无需在会话中选择媒体模型，直接在输入框描述需求，由主 Agent 调用稳定工具。

供应商 Logo 作为本地静态资源随 Design System 打包，Renderer 不在运行时请求远程图片；同一套 Logo 同时用于连接卡片、LLM 设置卡片、Composer 当前模型按钮、模型选择器和推理强度二级面板标题。连接配置区固定为三列、统一卡片高度，入口只展示 Logo、供应商名称和“配置”动作；API 类型已经由左侧接入分类明确，厂商名称和配置弹窗标题不再重复附加 `API` 后缀。卡片右侧的“配置”文字与箭头统一使用主文字色，不继承供应商 Logo 的品牌强调色。连接状态只在居中配置弹窗标题区、紧邻名称右侧展示，不在入口卡片重复展示模型数量。连接卡片和 LLM 卡片统一使用纯色表面与细边框，不使用渐变炫光、悬浮阴影或上浮位移。Logo 使用带细边框的浅色内衬容器，品牌图保持克制比例；Kimi 官方 App Icon 因原图自带安全留白而使用更高的容器占比，不裁切官方资源。位图至少使用 640 × 640 原图，其余使用可缩放 SVG。Kimi 与 Kimi Coding Plan 共用从官方 Kimi App 提取的 1024 × 1024 App Icon；Qwen 与 Qwen Token Plan 共用 Qwen Logo；火山方舟、火山 Coding Plan 与火山 Agent Plan 使用火山引擎 Logo。资源与来源清单由 `Awaken Design System/src/assets/model-providers/README.md` 维护。

### 保存、连接与 effort 验证

1. Renderer 从 Main 取得非敏感 provider catalog 和 profile 摘要。
2. `测试连接` 对当前表单执行协议正确的最小请求：Chat 使用 `/chat/completions`，发送 `model + messages + stream:false`；Responses 使用 `/responses`，发送 `model + input + stream:false + store:false`；这两种探针都不再强制 1 token 输出预算。Messages 使用 `/messages`，因协议必填而发送安全的小预算 `max_tokens:64` 并关闭 thinking。完整推理地址覆盖时不再拼接路径。除显式“无鉴权”外，测试只在当前弹窗输入非空 API key 时可用；Main 不得隐式回退已保存 key 来伪造当前表单验证。上游失败只向 Renderer 返回 status、provider code 和有界脱敏 message，不返回 Key、Authorization、完整请求体或原始响应。测试只证明 endpoint/key/model 可以响应，不证明工具、PDF、缓存或 effort；动态模型不得因此被强制标记为支持工具。
3. 推理强度只在配置完成后的 Composer 展示；只有 exact-scope API observation 或版本化官方清单给出 Awaken 可映射的档位时才出现。未知模型不展示 effort，单次 HTTP 200 不能推导全部档位可用。`ark-code-latest` 不展示 effort。
4. 提交先保存凭据，再原子保存非敏感 metadata；成功前 UI 不显示已完成。
5. Agent Plan“模型与工具”中的生成工具配置只允许在没有 active run 时保存、启停或删除；成功后 Main 通过带 control token 的本地控制路由热刷新对应的 Core 工具注册，不重启 Core。已经固定的 run 工具快照不被改写，新注册从下一次输入创建的新快照开始生效。

## Composer 与 thread 选择的实现

```text
RuntimeThread.selectedModelProfileId
RuntimeThread.reasoningEffortByProfile[profileId]
```

- Composer 当前模型按钮和模型列表只显示模型 ID，不追加 `Chat`、`Responses` 或 `Messages`；协议继续保存在 profile 中并参与调用、持久化和缓存 identity，但不作为输入框模型名称的一部分。
- 既有 thread 的 effort 吸附到档位后立即通过 typed IPC/API 持久化；
- 尚未创建 thread 时先保存在 Renderer 草稿，首次 run 与 thread 创建一并写入；
- 支持 effort 的模型从模型列表进入二级面板；卡点轨道与即时保存交互由[输入、斜杠菜单与附件](../../01_桌面工作台/消息输入与编辑/实现方案.md)统一定义；
- 不支持档位的模型直接选择，不显示入口或占位；
- 标签显示 `模型名 · max` 等当前有效选择；
- run 期间禁用模型/effort 修改，变化只影响下一次 run；
- thread 已有消息时提示切换会重新建立上下文缓存；
- profile 被禁用、删除或能力变化时忽略失效 preference，回退当前可用 default，不批量改写历史 thread。
- `modelPreferencePresentation.tsx` 为明确失效的历史偏好生成 recovery key；App 使用组件生命周期内的 Set 按 thread/profile/effort 去重，返回已提示会话不再弹出。只有 runtime 与模型目录已成功加载才消费提示；模型缺失和 effort 失效使用不同文案，说明后续发送的选择。刷新页面或重新打开应用后允许再次提示，历史 metadata 保持不变。
- `App.test.ts` 覆盖跨会话去重、不同失效配置可再次提示、目录未就绪不消费提示和无显式偏好不误报。macOS 正式 Desktop 已验证两个旧 profile 会话首次进入显示回退模型、交替返回不重复弹出，见[恢复提示回读](../../../apps/desktop/test-fixtures/run-reliability/model-recovery-return.png)；验收只切换历史，没有发送任务或更改模型偏好。

Messages adapter 将流内 `error` 与正常 `message_stop` 分开处理：失败时返回空 Response 和 `RequestError`，只保留协议白名单错误类型，发布 `StreamEventFailed`，不发布 `StreamEventCompleted`。已收到的部分正文、tool_use 和 opaque state 不作为有效响应返回。已知限流／过载映射为 429／529，未知类型不自行判为可重试；原始 message 与未知 type 不进入错误文本。`src/llm/anthropic_stream_error_test.go` 覆盖部分文字、已完成工具块、空响应及错误去敏；本地模拟流不能证明所有 Messages 供应商的真实错误兼容性。[协议依据](https://platform.claude.com/docs/en/build-with-claude/streaming)。

## 连接、余额与错误的实现

连接测试请求正文、key 和 Authorization 不进入 Renderer、SemanticJournal 或 thread metadata。连接探针允许最多 30 秒等待供应商完成非流式最小响应；超时只表示本次探针未在时限内完成，不改变已经保存的 profile、协议或凭据状态。火山方舟 `ModelNotOpen` / “has not activated the model” 表示账号未开通该 Model ID，Key 与地址已经打通；连接测试不得把它映射成“推理端点或模型不存在”。设置弹窗切换协议时保留当前仍兼容的模型，其次才回退默认模型，不能改成清单第一项。profile-scoped usage ledger 只保存 request identity、脱敏 shape、nullable usage、最近一次白名单 rate-limit observation 和结果。用量窗口只展示供应商官方 API 返回的余额、套餐额度或组织用量：DeepSeek `GET /user/balance`、Kimi 普通 API 余额、Kimi Coding 套餐窗口、MiniMax Token Plan `GET /v1/token_plan/remains`，以及 OpenAI/Anthropic 组织用量与成本接口已接入。MiniMax Token Plan 复用用户保存的套餐 Key，按中国区 `www.minimaxi.com` 与国际区 `www.minimax.io` 的显式合同查询；文字模型 profile 只消费返回值中的 `general` 资源桶，并归一化为“5 小时额度”和“周额度”，不把 `video` 等媒体工具额度混进文字模型用量。计数型窗口展示计数，时间型套餐按供应商返回的 remaining percent 展示百分比；`status=3` 的窗口显示为无限，不用 `0 / 0` 或有限的 100% 伪装额度。若厂商未提供稳定公开 API，则不把未确认接口写死，也不扫描或汇总本地 journal、profile usage ledger、token、请求次数、rate-limit observation 或本地成本作为替代。

正式模型 run 的 Core transport 使用 03 域的[跨平台网络代理与恢复](../../03_运行时与本地服务/网络代理与恢复/实现方案.md)：macOS/Windows Desktop 在系统代理或继承的 loopback 代理开启/关闭后热同步 route，并在 model run 真正发起前完成一次有界校准；新连接自动选择可用代理或 direct。已写出请求体、已经产生 assistant stream 内容或可能计费的请求不因 route 变化盲目重放；错误分类（`TransportError` / `StreamDisconnectedError` / `RequestError` 与去敏 detail）由本域 `src/llm` 拥有，已接受响应但未见协议终止信号的 clean EOF 必须分类为 `StreamDisconnectedError`，不能返回半截成功。同一 turn 是否等待网络、重试几次、tool-call start 后是否禁止重放以及 live reconnect 事件由 [02 运行终止与失败编排](../../02_主智能体闭环/对话运行与恢复/实现方案.md) 拥有。模型设置中的连接测试、余额与 Agent Plan 目录探测也先请求 Main 校准 route，但仍是 Electron Main 拥有的独立请求路径，不能单独证明正式 run route 已恢复；无论哪条路径都不得把代理失败改写为 key 无效或本地 `.env` 故障。

## 在途请求与可观测性

src/llm/request_scheduler.go 在实际 transport 前取得请求位，结束、失败与取消后释放；准备、压缩和重试退避在请求位之外。Core 启动的 --model-requests 设置全局上限，--account-model-requests 设置账户上限，0 表示继承全局上限。账户分组使用宿主身份或仅存在于内存的凭据分组值，不记录密钥。请求优先级与公平性、队列背压由[子智能体协作](../../02_主智能体闭环/子智能体协作/实现方案.md)说明。model_usage 可含 prepare_ms、queue_wait_ms、transport_ms、first_token_ms；这些阶段不等于完整网络 trace。

Core 显式子模型配置先复用 `runtime.ModelProfileConfigFromResolved` 转换已解析 profile，再复用 `modelConfigFromProfile` 构建 Agent 配置；主调用和子模型不再分别枚举模型字段。精确 profile 的可用性、effort 校验和不含凭据的配置摘要仍在解析边界完成。
