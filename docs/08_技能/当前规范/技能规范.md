### Requirement: SKILL.md Schema

Awaken SHALL accept local Skills as directory packages. Each local Skill MUST live at `<skills-root>/<skill-id>/SKILL.md`; files beside `SKILL.md` such as `references/`, `scripts/`, `assets/`, `LICENSE`, and `NOTICE` are part of the Skill package. Flat files such as `<skills-root>/<skill-id>.md` are legacy-invalid and MUST NOT load.

`SKILL.md` contains YAML frontmatter delimited by `---` lines. The frontmatter SHOULD contain `name` (kebab-case, unique within source) and MUST contain `description` (one-line summary). If `name` is omitted, the package directory name is used as the Skill name/id. It MAY contain: `whenToUse` (free text describing trigger context), `allowedTools` (array of tool name patterns; supports `mcp__server__*` glob), `arguments` (array of `{ name, type, required, default }`), `model` (declared but not yet applied), `effort` (declared but not yet applied), `context` (`inline` | `fork`, default `inline`), `agent` (declared but not yet applied), `hooks` (declared but not yet applied), `requiredConnectors` (array of connector ids).

The Markdown body after the frontmatter is the Skill prompt; it MAY contain `${arg_name}` placeholders that are substituted at execution time. It MAY also contain `${AWAKEN_SKILL_DIR}`, which resolves to the installed Skill package root.

A Skill package whose `SKILL.md` fails frontmatter validation MUST be skipped with a single warning log; other Skill packages in the same directory MUST continue to load.

#### Scenario: Minimal valid SKILL.md loads

- **WHEN** a package contains `foo/SKILL.md` with `name: foo` and `description: bar` in frontmatter plus a body
- **THEN** the skill is loaded with `context: inline` defaulting and registered into the registry

#### Scenario: Skill with missing required arg returns structured error

- **WHEN** a skill declares `arguments: [{ name: client, required: true }]` and the agent calls the corresponding tool without `client`
- **THEN** the tool call returns a structured `missing_argument` error (no LLM call is made) and the run continues

#### Scenario: One invalid package does not block the directory

- **WHEN** a user skills directory contains three package directories, one with malformed YAML frontmatter
- **THEN** the runtime loads the two valid skills, logs a single warning for the malformed file, and `GET /v1/skills` lists both valid skills

### Requirement: Skill Source Hierarchy

The runtime SHALL load local Skills from two sources in descending priority: `project` (`<workspace>/.awaken/skills/<skill-id>/SKILL.md`) and `user` (`~/.awaken/skills/<skill-id>/SKILL.md`). Public UI language calls `user` source Skills "全局 Skills".

`user` Skills are global to the local Awaken user. They MUST load and remain usable regardless of the currently selected project folder, including states where no project folder is selected or no valid project folder is available.

`project` Skills are scoped to one workspace folder. They MUST be loaded into the runtime tool pool only for runs whose `workspace_root` is that project folder. Listing or previewing another project's Skills in Desktop MUST NOT switch the live runtime tool pool away from the active run workspace.

When two sources declare a Skill with the same `name`, the higher-priority entry wins. The lower-priority entry MUST remain in the registry as `state: shadowed` with a `shadowedBy` field indicating the winning source, so the UI can surface the conflict.

#### Scenario: Project skill overrides user skill of same name

- **WHEN** both project and user directories contain `daily-followup/SKILL.md`
- **THEN** the project version is active and the user version's registry entry has `state: shadowed`, `shadowedBy: "project"`

#### Scenario: User skill is active when project does not override it

- **WHEN** a user creates `~/.awaken/skills/research-summary/SKILL.md` and no project skill has the same id
- **THEN** the user version is active

#### Scenario: User skill loads without project folder

- **WHEN** no project root is selected or available
- **THEN** `GET /v1/skills` still returns user Skills from `~/.awaken/skills/`
- **AND** no project Skill directory is required

#### Scenario: Project skill is scoped to its project run

- **WHEN** project A and project B each define different project Skills
- **THEN** a run started with project A's `workspace_root` exposes project A Skills plus user Skills
- **AND** a run started with project B's `workspace_root` exposes project B Skills plus user Skills
- **AND** viewing project B in the Skills UI does not mutate the runtime tool pool for project A

### Requirement: Desktop Skill Source Layout

Awaken Desktop 的技能窗口 SHALL 在搜索框同一行提供 `项目 Skills` 与 `全局 Skills` 两个视图切换，按用户心智分别管理本地 Skill。

`项目 Skills` 视图 SHALL 展示已知项目列表。项目来源包括 Desktop workspace registry、最近 workspace、默认 workspace，以及刚安装 Skill 时选择的项目目录。每个项目默认收起；用户点击项目行后展开，才显示该项目通过 `/v1/skills?projectRoot=<project>` 返回的 `sourceOrigin: project` Skills。没有项目 Skills 的项目仍可显示，展开后显示空状态。

`全局 Skills` 视图 SHALL 展示 `sourceOrigin: user` 的 Skills，即 `~/.awaken/skills/` 提供的跨项目通用能力。MCP 来源 Skill 属于运行时动态桥接来源，不能作为本地文件加载层处理。

#### Scenario: Skills are grouped by source in Desktop

- **WHEN** Desktop 技能窗口加载 `/v1/skills`
- **THEN** 顶部工具栏显示 `项目 Skills` 与 `全局 Skills` 视图切换，并与搜索框横向对齐
- **AND** `sourceOrigin: project` 的 Skill 显示在对应项目的折叠组内
- **AND** `sourceOrigin: user` 的 Skill 显示在 `全局 Skills` 视图

#### Scenario: Project skill groups start collapsed

- **WHEN** Desktop 技能窗口进入 `项目 Skills` 视图
- **THEN** 每个已知项目先显示为收起行
- **AND** 点击某个项目行后，只展开该项目的 Skill 列表

### Requirement: Skill Installation Scope

Awaken Desktop 的安装 Skill 弹窗 SHALL 提供 `项目 Skills` 与 `全局 Skills` 安装范围选择。

选择 `项目 Skills` 时，用户 MUST be able to choose a local project folder. The runtime SHALL install the uploaded Skill into `<selected-project>/.awaken/skills/<skill-id>/SKILL.md` and return `sourceOrigin: project`, `scope: project`, `rootDir`, `skillFilePath`, and `projectPath`.

选择 `全局 Skills` 时，runtime SHALL install the uploaded Skill into `~/.awaken/skills/<skill-id>/SKILL.md` and return `sourceOrigin: user`, `scope: global`, `rootDir`, and `skillFilePath`.

安装接口 SHALL accept either a single `SKILL.md`/`.md` file or a zip containing exactly one `SKILL.md`. For zip uploads, the directory containing that `SKILL.md` is the Skill package root and MUST be copied in full. Zip packages with no `SKILL.md`, multiple `SKILL.md`, path traversal, absolute paths, symlinks, excessive file count, or excessive extracted size MUST be rejected.

安装弹窗 SHALL 明确提示：新安装的 Skill 会在创建新会话或发起新任务时加载；正在运行的会话不会中途加载新 Skill。

#### Scenario: Project install writes selected project folder

- **WHEN** a user installs `SKILL.md` with scope `project` and project root `/path/to/project`
- **THEN** the runtime writes `/path/to/project/.awaken/skills/<skill-id>/SKILL.md`
- **AND** `/v1/skills?projectRoot=/path/to/project` includes that Skill with `sourceOrigin: project`

#### Scenario: Global install writes home skills folder

- **WHEN** a user installs `SKILL.md` with scope `global`
- **THEN** the runtime writes `~/.awaken/skills/<skill-id>/SKILL.md`
- **AND** `/v1/skills` includes that Skill with `sourceOrigin: user`

### Requirement: Skill Refresh Reflects Disk State

`GET /v1/skills` SHALL reload project and user Skill files from disk before returning the list. Removed or moved local Skill files MUST disappear from the response on the next refresh. MCP-sourced Skills remain managed by the MCP bridge and MUST NOT be removed by local disk reloads.

#### Scenario: Removed project skill disappears on refresh

- **WHEN** a project Skill was previously loaded from `<workspace>/.awaken/skills/dws/SKILL.md`
- **AND** the `.awaken` folder is removed from that workspace
- **THEN** the next `GET /v1/skills` response no longer contains `dws`

### Requirement: Skill Availability Driven by Dependencies

A Skill's `state` MUST be one of `available`, `unavailable`, or `shadowed`. A Skill MUST transition to `unavailable` when any entry in its `requiredConnectors` is not in `connected` state (per the `connectors` capability) or when any entry in `requiredMcpServers` is not connected. `allowedTools` is currently passed into the Skill execution context but is not yet used as an availability gate.

When `unavailable`, the Skill MUST NOT be registered into the tool pool exposed to the LLM, but MUST still appear in `GET /v1/skills` with an `unavailableReason` explaining the missing dependency.

When the dependency becomes satisfied (connector connects, tool registered), the Skill MUST automatically transition to `available` and re-register into the tool pool.

#### Scenario: Skill becomes unavailable when connector disconnects

- **WHEN** a skill declares `requiredConnectors: [notion]` and the notion connector transitions away from `connected`
- **THEN** the skill state becomes `unavailable` with `unavailableReason` mentioning the notion connector, and the tool `skill__<id>` is removed from the LLM's tool list

#### Scenario: Skill recovers when connector reconnects

- **WHEN** the notion connector re-enters `connected` state
- **THEN** the dependent skill state returns to `available` and the tool re-registers in the tool pool

### Requirement: Skills Exposed as Tools

Each `available` Skill SHALL be registered in `src/tool/registry.go` as a tool named `skill__{skill_name}`. The tool's `description` MUST be derived from the Skill's `whenToUse` (falling back to `description` if absent). The tool's input schema MUST be derived from the Skill's `arguments` declaration.

The agent SHALL invoke a Skill by calling its tool; the runtime then executes the Skill per its `context` mode (see Skill Execution Modes). The agent need not understand the Skill concept — it sees only a tool list.

When a local Skill is executed, the runtime MUST prepend the prompt with `Base directory for this skill: <RootDir>` and expose a read-only `skill_resource_read` tool. `skill_resource_read` MUST accept `skill_id` and a relative `path`, and MUST reject absolute paths or traversal outside the Skill package root.

The runtime MUST emit a `skill_id` field on tool-call events so the audit trail records which Skill was executed (consumed by the `tool-platform` capability for observability).

#### Scenario: Available skill appears as tool

- **WHEN** the skill `daily-followup` is `available`
- **THEN** the LLM-facing tool list includes a tool `skill__daily_followup` with description from its `whenToUse`

### Requirement: Skill Tool Execution Follows No-Review Runtime

Skill execution MUST use the same no-review tool runtime as the main agent. A Skill MAY narrow `allowedTools`, `requiredConnectors`, and `requiredMcpServers`, but MUST NOT reintroduce generic tool approval, hidden `ask` decisions, user override `always_ask`, or custom approval prompts.

When a Skill needs Office/PDF/media work, it MUST call typed artifact tools (`spreadsheet_*`, `document_*`, `presentation_*`, `pdf_*`, `image_*`, `media_*`) after `runtime_preflight`. It MUST NOT depend on the developer machine's Python/Node, Codex cache, or vendored third-party runtime source copied into the project.

Skill-authored workflows MUST treat missing authorization as `needs_auth`, missing runtime as `needs_runtime`, unsupported work as `unsupported`, and group/bulk outbound messaging as `needs_mass_message_review`. OCR, scanned PDF recognition, and searchable PDF generation are not supported by the current Work runtime.

#### Scenario: Skill cannot create generic approval

- **WHEN** a Skill calls a write-capable tool
- **THEN** the runtime either auto-executes within `TaskScope`, transforms to a safer typed/file chain, or returns a structured refusal/recovery state; it never creates a generic approval prompt

#### Scenario: Skill uses packaged artifact runtime

- **WHEN** a Skill creates or edits a `.docx`, `.xlsx`, `.pptx`, `.pdf`, image, or media artifact
- **THEN** it uses the registered typed artifact tools and fails with `needs_runtime` when the packaged runtime is unavailable

### Requirement: Skill Execution Modes

The runtime SHALL support two execution modes selected by the Skill's `context` field:

- `inline` (default): the Skill prompt (after argument substitution) is returned to the current run as the tool result, with `allowedTools` passed to the executor for future tool-pool narrowing.
- `fork`: the runtime attempts to use a child-run `StartChild` interface when available. In the current implementation that interface is not wired, so `fork` degrades to `inline` with a warning log.

If the `StartChild` interface is unavailable at runtime (delivered by a separate change), `fork` MUST degrade to `inline` with a warning log; the Skill MUST still execute, not fail.

#### Scenario: Inline skill appends to current run

- **WHEN** the agent calls `skill__doc_to_actions` with valid args and the Skill is `context: inline`
- **THEN** the Skill's substituted prompt is appended to the current run as a user message and the agent proceeds within the same run

#### Scenario: Fork skill degrades before child runner is wired

- **WHEN** the agent calls `skill__customer_followup_daily` and the Skill is `context: fork`
- **THEN** the runtime logs a warning and executes the Skill prompt inline

#### Scenario: Fork degrades when child runs are not supported

- **WHEN** a Skill requests `fork` execution but the runtime does not provide `StartChild`
- **THEN** the runtime logs a warning, executes the Skill in `inline` mode instead, and the tool call still returns a result

### Requirement: Skills HTTP API

The runtime SHALL expose two HTTP endpoints under `/v1/skills/`:

- `GET /v1/skills` — returns an array of `{ id, displayName, description, whenToUse, state, sourceOrigin, scope, rootDir?, skillFilePath?, projectPath?, shadowedBy?, unavailableReason?, requiredConnectors, allowedTools }`. The list MUST include `shadowed` and `unavailable` entries (not only `available` ones).
- `POST /v1/skills/{id}/execute` — direct execution endpoint for testing and future UI invocation; accepts JSON body matching the Skill's `arguments` schema; returns the run id and initial event stream URL. MUST refuse with HTTP 409 when the Skill is not `available`.

These endpoints MUST be registered in `src/server/router.go`.

#### Scenario: GET /v1/skills includes shadowed and unavailable entries

- **WHEN** a project skill shadows a user skill, and another user skill is unavailable due to a missing connector
- **THEN** the response contains all entries, the shadowed user skill has `state: "shadowed"` and `shadowedBy: "project"`, and the unavailable skill has `state: "unavailable"` with `unavailableReason`

#### Scenario: Execute refuses unavailable skill

- **WHEN** a POST to `/v1/skills/blocked-followup/execute` arrives while that skill is `unavailable`
- **THEN** the runtime responds HTTP 409 with a body containing the `unavailableReason` and does not start a run

### Requirement: MCP-Source Skill Metadata

`SkillDefinition` SHALL include two additional optional fields to represent MCP-sourced skills and MCP-dependent local skills:

- `mcpBinding`: present only when the Skill is bridged from an MCP server; contains at minimum `{ serverName: string, promptName: string, kind: "prompt" | "resource" }`. Absent for purely local Skills.
- `requiredMcpServers`: a string array of MCP server names whose `connected` state is required for this Skill to be `available`. May be present on bridged Skills (auto-derived) or on hand-authored local SKILL.md files (manually declared).

Skill availability MUST treat `requiredMcpServers` as an independent gate from `requiredConnectors`: a Skill is `available` only when both `requiredConnectors` AND `requiredMcpServers` are satisfied (every connector in `connected`, every server in `connected`).

The SKILL.md loader for `user` and `project` sources MUST reject any frontmatter declaring a `name` starting with `mcp__`. The `mcp__` namespace is reserved for the bridge.

#### Scenario: Local SKILL.md may declare requiredMcpServers

- **WHEN** a project SKILL.md frontmatter includes `requiredMcpServers: [internal-search]`
- **THEN** the loaded Skill carries `requiredMcpServers: ["internal-search"]` and becomes `unavailable` whenever the `internal-search` MCP server is not `connected`

#### Scenario: Local SKILL.md with reserved prefix is rejected

- **WHEN** a user creates `~/.awaken/skills/mcp__foo__bar/SKILL.md` or sets `name: mcp__foo__bar` in frontmatter
- **THEN** the loader skips the file with a warning explaining that the `mcp__` namespace is reserved

#### Scenario: Bridged Skill is unavailable when its source server disconnects

- **WHEN** the bridged Skill `mcp__crm__client-followup` has `requiredMcpServers: ["crm"]` and server `crm` transitions to `failed`
- **THEN** the Skill's state becomes `unavailable` with `unavailableReason` naming the `crm` server, and the corresponding LLM-facing tool is removed
