## Awaken 当前接入

- 普通 API：provider ID `kimi-cn`，Chat / Responses Base `https://api.moonshot.cn/v1`，Messages Base `https://api.moonshot.cn/anthropic`。
- Kimi Coding Plan：provider ID `kimi-coding-plan`；Chat / Responses Base `https://api.kimi.com/coding/v1`，Messages Base `https://api.kimi.com/coding`。
- 两种入口使用不同 Key、模型清单、网关和计费合同，不能互换。
- 普通 API 与 Coding Plan 的默认模型及候选分别从 Awaken provider catalog 读取；下文的精确模型 ID 用于说明已核对的协议与推理合同，不作为永久模型清单。

## 三协议兼容矩阵

| 协议 | 官方合同 | Awaken 当前 | 结论 |
| --- | --- | --- | --- |
| Chat Completions | 普通 API 与 Coding Plan 均有 | 两个 provider 均已接入 | 支持；Base/Key 分开 |
| Responses | API 与 Code 均有官方合同 | 两入口已接入；API 仅 K3 | 自动化与真实服务验证分开 |
| Messages | API 与 Code 均有官方合同 | 两入口已接入；API 仅 K3 | 普通 API 使用 `/anthropic` Base |

## 鉴权、端点与模型

- 普通 API：Bearer `MOONSHOT_API_KEY`，Chat `POST /v1/chat/completions`，模型目录 `GET /v1/models`。
- Coding Plan：Bearer `KIMI_CODE_API_KEY`；三协议使用上面的专用 Base URL。
- 不把 Kimi 网页会员、开放平台 API 余额和 Kimi Code 套餐当成同一账户额度。
- 精确模型 ID、上下文和 availability 以对应产品文档为准；普通 API 目录结果不传播给 Coding Plan。

## 上下文、多模态与工具

- 图片、工具、上下文窗口和最大输出按 exact Kimi model + protocol 判断。
- Kimi 普通 API 的视觉合同不自动覆盖 Coding Plan 的 Messages；反之亦然。
- Kimi reasoning state 可能带 provider-opaque 数据；Awaken 历史重放必须保持完整，不能只保存显示文本。
- Kimi Code 套餐面向编程工具；Subagent/定时任务等自动调用需遵守当前套餐使用条款和频率限制。

## 提示词缓存

- 普通 API Chat 官方建议发送稳定 `prompt_cache_key`；Awaken 为 `kimi-cn` 生成 purpose/profile scoped key。
- Coding Plan Chat 官方要求稳定 `prompt_cache_key`；Awaken 将其标为 required，并独立于普通 API。
- 解析 `prompt_tokens_details.cached_tokens`；缺失表示未知，不等于 0。
- 模型、reasoning、purpose、凭据 revision 或历史前缀变化会改变缓存 identity。

## 推理开启关闭

- Kimi 的 thinking 开关和模型族有关，官方文档可能使用 `thinking.type`；不能把 K2.x 的合同直接套到 K3。
- 当前 Awaken 私有开关白名单只覆盖确切 provider/base/protocol/model；资料更新后必须同步代码和测试，不能仅在 UI 声明。
- 辅助请求关闭 reasoning 前，先确认对应 Kimi 模型允许关闭。

## 推理强度

- Chat 使用顶层 `reasoning_effort`，Responses 使用 `reasoning.effort`，Messages 使用 `output_config.effort`，不能用 Anthropic token budget 代替。
- `kimi-for-coding` 自 2026-09-11 升级为 K2.8 Preview，三档默认 max，1M 上下文；高速版仍是 K2.7，不提供三档。
- 普通 API K3 始终推理；Coding Plan K3/K2.8 的 Chat / Messages 可按 Code 关闭规则路由到 K2.8 无思考版；K2.8 Chat 实测关闭时温度必须为 0.6。2026-09-14 实测 Responses 拒绝 none，与总说明存在差异，当前辅助请求使用 low。
- Awaken 当前把普通 `kimi-k3` 与 Coding `k3/k3-256k/kimi-for-coding` 映射到统一 `low | high | max`，默认值可因入口不同。
- thinking 开关与 reasoning effort 独立；改变任一项都要重新评估缓存和 reasoning state 重放。

## 用量、余额、限流与套餐

### 用量查询合同

- `kimi-cn` B 类：`GET https://api.moonshot.cn/v1/users/me/balance` 使用普通 Moonshot API Key 和 Bearer 鉴权，返回可用、赠送与现金余额；中国区与国际区 Key/账户独立。
- `kimi-coding-plan` B 类：`GET https://api.kimi.com/coding/v1/usages` 使用 Kimi Coding 套餐 Key 和 Bearer 鉴权。官方论坛给出 5 小时窗口字段，Moonshot 官方客户端源码解析 weekly、window 与 `boosterWallet`；`limit/used/remaining` 表达 token 限额百分比，不是实际 token 或请求数。
- 凭据：普通 API Key 与 Kimi Coding 套餐 Key 不可互换。`/usages` 有官方一方来源，但官方说明为 legacy/experimental，稳定性低于开放平台正式 API reference。
- Awaken 当前：已接入普通 API balance；Kimi Coding 已展示周窗口与 300 分钟窗口，但名称仍写“请求”、没有明确百分比单位，且尚未展示 `boosterWallet`，这些都应作为已知缺口保留。

- Kimi Code 是套餐服务，额度、并发、支持模型和有效期以 Code 控制台/条款为准；不按普通 API token 单价计算成本。
- 余额 API 成功不证明某个模型或协议可用；模型调用仍要处理 401/403/429/model-not-found。
- 套餐 Key 不能回退普通 API endpoint，否则可能无法扣套餐或产生不同计费。

## Awaken 落地规则

- 始终把 `kimi-cn` 与 `kimi-coding-plan` 当作两个接入身份。
- 只有普通 API Chat 和 Coding Plan Chat 进入当前 Kimi cache capability；Coding Messages 的 cache 必须另有官方和 adapter 合同。
- 新模型更新时同时核对 thinking、effort、opaque reasoning state、tools 和 cache key。
- 标题、压缩、Memory 等辅助请求的 purpose 必须独立，防止污染主会话缓存。
