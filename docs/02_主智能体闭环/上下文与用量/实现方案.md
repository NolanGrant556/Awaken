# 上下文与用量 · 实现方案

本文说明代码职责、数据与接口、异常恢复和验证方法。功能范围及用户操作见[需求文档](需求文档.md)。

## Request envelope

模型上下文由稳定 system prompt、结构化历史、attachments、inline SkillContextBlocks、runtime snapshot 和 tool schemas 组成。runtime snapshot 记录 workspace/cwd、模型、tool snapshot ID、environment ID 和 Skill summary；tool schemas 来自本 run 固定可用性快照。工具渐进披露启用时，未激活的延迟定义（内建辅助组或 MCP）不进入该投影，由 [04 工具定义与暴露](../../04_工具权限与审批/工具发现与执行/实现方案.md#模型暴露) 唯一拥有；被激活的工具按 Context Epoch 的 dynamic tools append-only 语义进入后续请求，激活集合经 `deferred_tools_activated` 语义记录耐久（恢复兼容旧 `mcp_tools_activated`），压缩与重启不丢失。

runtime snapshot 有宿主侧与模型侧两个投影，只有后者进入 provider 请求。宿主侧 `runtime_snapshot` context item 记录全部 scope 字段（project ID、scope_id、三组 roots、protected roots、temporary work root 等），用于 journal 与用量核算；模型侧由 `prompt.FormatRuntimeInfo` 渲染结构化 `<environment_context>`，当前分开包含项目 ID/名称、工作目录、逐项保留的精确 `workspace_roots`、unrestricted permission profile、日期、模型、入口、工具与 Skill 摘要和已授权附件。多个 roots 不折叠为共同父目录。零文件夹项目与独立对话分别标明其 project/conversation scope 和 Awaken 管理的 session 目录，不伪造成用户选择的项目文件夹。项目重命名不改写已经运行中的请求快照；Desktop 从项目 authority 刷新后，下一次 run/follow-up 携带新名称，`sameTaskScope` 与 runtime snapshot identity 都把名称变化视为需要重建模型上下文。Windows drive/UNC 根在 Renderer 项目归属阶段按本机大小写不敏感和分隔符等价语义比较，不能因盘符大小写或 `\\`/`/` 表现差异丢掉 `project_name`。往宿主侧加字段不等于模型能看到，两侧要分别确认。

RequestBuilder 在 system prompt 的最后追加稳定、host-owned `conversation_continuity` 块：最终请求中当前 user 输入之前的 user/assistant/tool 消息都是当前同一个 Awaken 任务的历史轮次；跨日期、Desktop/Core 关闭、重启或重新打开不会把这些已恢复历史变成另一个独立会话。只要当前输入之前存在消息，用户使用“上一个对话”“上一轮”“刚才”或“之前”等指代，模型必须默认解析到当前任务中最近的相关历史并直接回答，不得声称系统未提供；只有用户明确说另一个任务/独立会话时才按跨任务不可见处理。该块不复制历史正文，不把数量、thread/run/session ID、时间戳、message origin 或内部 message/turn identity 下发为供应商私有字段，也不允许模型声称看到了请求之外的其他任务或编造未提供的时间。它的 Context Epoch 与缓存身份由[提示词缓存、上下文用量与成本治理](实现方案.md)统一定义。

Skill 不在估算前与 tools 求交。目录只暴露统一 `skill` 工具及有预算的 Skill catalog；调用后的 inline 正文才进入上下文。

## 预算

Awaken 模型 profile 的 `ContextWindow` 就是用户配置的可用输入容量，也是 Desktop 上下文用量的分母；它不是还要再扣输出的总窗口。`MaxTokens` 是独立的单次输出上限，不得从 `ContextWindow` 中扣减。若存在更小的明确 `MaxInputTokens`，它作为硬输入上限约束配置容量。Core 的 `ModelWindowTokens` 与 `EffectiveInputWindowTokens` 都保持这一配置后的输入容量，`OutputReserveTokens` 只独立记录输出上限；warning/auto-compact threshold 和 compact target 均以输入容量为基数。当前 `awaken_leaf_v4` 从 provider-visible projection 生成 `ContextUsageSnapshot`，按 typed prompt/message/tool provenance 统计分类并保证分类和等于总估算。它仍是版本化本地估算，不是 provider tokenizer 的精确输入量。

`ContextActualTokens`、最近响应的 input/output/total 和 cached usage 都不能改写 Core 的本地 snapshot。每次主请求会把最终 `sent_request` 的 `estimated_input_tokens` 一并写入 `ModelUsageRecord`。Desktop 的当前总输入直接显示最近一次兼容、成功且完整的主请求 inclusive input，不加入 output，也不叠加当前本地变化量；缺少兼容 input 时回退 v4 snapshot，并把与七项 typed 分类（系统、内置工具、MCP、技能、记忆、任务检查点、对话）之间的正残差列为“其他/协议开销”。Core 的 warning/auto-compact/block 仍独立用 provider total/input 与本地变化得到锚定投影，并取该投影与本地估算中的更保守值；同一 context epoch 内 provider 锚点不得因“压缩判断前投影”与“Context Epoch lowering 后 sent request”处于不同阶段而向下回退，只有成功 compact 或 model identity 不兼容边界可清除它。新的 run 或旧 thread 恢复时会从最后兼容硬边界之后成对恢复最近成功完整主请求的 provider total/input 与发送时估算，使首个请求也使用同一保守锚点。打开旧 thread 时，Desktop 仍以当前可运行 profile 从耐久历史与当前工具/Skill/Memory/checkpoint 重建 v4 snapshot；provider/model/protocol/effort、compact 等不兼容边界不复用旧实报，source/tool 重建边界只允许继续展示最近请求 input。无法重建且旧记录没有 breakdown 时才显示已有汇总和“暂无分类明细”。完整口径见 [提示词缓存、上下文用量与成本治理](实现方案.md)。

Skill catalog 预算约窗口 1%。compact 前已激活 inline Skill 仍使用完整正文；compact 成功后不再使用互相独立的单 Skill 5K/合计 25K 配额，而是把每个 active Skill 降为包含 Skill ID、正文 digest 和精确 `SKILL.md` 路径的有界引用。后续再次应用该 Skill 前必须用 `Read` 重载原始路径；active Skill 不因数量排序被静默删除。Skill 引用与其他输入统一进入完整请求 10% 分配器。

## 压缩与耐久边界

一批 tool call 仍按现有顺序执行（失败监督、Hook、journal 顺序不变），但每条结果 persist/offload 之后，用与 `PrepareRequest` 同一套保守投影计算 `remaining = blockingThreshold - ConservativeProjectedTokens - 本批已执行结果`。下一条媒体类 `Read`（图片或 PDF）按参数预估：图片 2000 token，PDF 为页数 × 2000，省略 `pages` 的 PDF 按 10 页。`estimated > remaining` 时该调用不执行，写入合成失败 `error_code=context_admission_exhausted`，说明剩余 token 并建议减少页数/条数或等下一轮压缩；同批后续调用同样不再执行。入场拒绝不切 Context Epoch，也不是 compact 成功。文本 `Read` 预估为 0，不受该门限拦截。

每次 `Build` / replay 按**当前** `ContextWindow` 重算 provider 可见投影，不把某次大窗口留下的整组原图写成永久 tail：

- 近尾 1 个安全组内的媒体可以 hydrate，但受剩余窗口夹紧；
- 更早 Read/图/PDF 页去掉 `DataBase64`，正文加 stub（路径/页码，可再 Read）；durable `storage_key` / `ByteSize` 仍计入本地账，避免轻量投影后假瘦；
- 已 offload 的大文本不再全量灌回模型，请求只保留 stub；
- 摘要请求全部去掉 image/file payload；`structurallyCompactMessage` 同时清空 `ModelContent`；
- 最后一组自身超过 `CompactTarget`（或 `block - summary预算`）时，先组内轻量投影；仍超限则整组进入 prefix 摘要，tail 只留最新 user 与未闭合 pairing。单条不可投影 remainder 拒绝压缩，不写假成功。

`CompactTarget` 的语义是压缩后**完整 provider-visible input** 的硬目标：`floor(EffectiveInput × 10%)`。通常 `EffectiveInput = ContextWindow`；仅当明确的 `MaxInputTokens` 更小时才取该上限。`MaxTokens` 不参与扣减。该目标不是“触发后剩余窗口”或只保留消息尾部的预算。只有 profile 提供明确 `ContextWindow` 或 `MaxInputTokens` 时才宣称硬检查要求成立；未知上限不会拿 128K 默认值伪造达标 receipt。governor 把目标换算成交给 `splitCompactGroups` 的对话尾部预算：供应商实报大于发送时本地估算时先按该比值通缩，再扣除稳定前缀、动态摘要预算和压后 checkpoint provider projection reserve。摘要预算也先使用同一校准目标，再按剩余预算 35% 计算并夹在 1024–4096 tokens；不能一边按 provider ratio 缩小 tail、一边仍保留未校准的 4096 summary 配额。摘要请求必须把这个硬输出预算显式交给模型，禁止先输出 analysis/reasoning/preamble，并要求先完成全部 13 个 section 与 `</summary>` 再增加第二条 bullet，避免 1024 紧预算在结构未闭合前被供应商截断。Host 还会把被压缩 prefix 中最后一条非空 assistant 进度压成有界、确定性的 `Latest compacted assistant progress` header；它不依赖模型摘要是否主动注意到“21/24、继续最后三份”之类断点，并与受保护尾部共同恢复精确续跑位置。若供应商忽略摘要请求的 `MaxTokens`，Host 会在 section 归一化后再次按同一预算裁剪：优先保留 Active Task、Pending Asks、约束、进行中/阻塞/剩余工作与 Critical Context，supporting bullets 延迟到 TaskCheckpoint/Journal；Host 自身 summary header 预留独立计入。checkpoint reserve 取 `CompactTarget / 8` 并同样夹在 1024–4096 tokens。两者都是 global allocator 的入场保留额，最终仍以 exact prepared body receipt 为准；尾部预算只缩小、不放大，最低夹到 1 token。compactor 对“最后一个安全组是否过大”的判定使用 `min(分配后 tail budget, CompactTarget)`，不得再用较大的整体 10% 目标把 allocator 已决定延迟的工具结果强行留在 tail；完整 pairing 先进 summary/checkpoint/Journal，未闭合 pairing 仍 fail closed。

压缩提交前会用 proposed messages、TaskCheckpoint、Memory/Skill refs、Instruction、RunPlan、Hook、Tool/MCP schemas 和 attachments 重新构造完整请求，再调用与正式发送相同的 `llm.PrepareRequest` 完成 Chat、Responses 或 Messages lowering；预算以最终 prepared JSON body 为兜底并写 `CompactBudgetReceipt`。draft 会模拟提交后的 Memory 状态：已 compact 的正文不再由 `MemoryContextProvider` 重复注入，只保留 bundle/checkpoint 中的 identity refs。压缩边界后的上下文敏感工具描述和 Skill catalog 按 `CompactTarget` 重新编译，不沿用按完整模型窗口生成的目录预算；这只缩短可检索目录/描述，不改变 pinned tool implementation、暴露策略或已激活 Skill identity。若 mandatory floor 可达但完整 projection 只因 compacted active-Skill reference block 超额，allocator 可以延迟该 system block；bundle/checkpoint 仍保留 Skill ID、路径和 digest，模型可通过 Skill catalog/Read 按需重载，live 与 restart 使用同一空 projection。成功条件是 `ConservativeProjected <= CompactTarget`；provider-actual/local-estimate 比值只会把结果向更保守方向校准。压缩后的 provider opaque reasoning/thinking 不进入 provider-neutral conversation 或 RecentTurns，避免跨模型误重放与未计量输入。若连 system/instructions/tools/checkpoint/summary mandatory floor 都超过 10%，返回带 `category_breakdown` 的 `COMPACT_TARGET_UNACHIEVABLE` 与 lower-snake-case reason，不通过删除 critical facts 伪造成功。

压缩保留最新用户意图、未完成工具配对、active gate、canonical tool outcome、artifact/change identity 和必要恢复事实。`PostCompactContextBundleV2` 同时保存宿主生成的 `TaskCheckpointV2`、最近最多三个已闭合的完整 user-task turns、Instruction/Memory/RunPlan/Skill/Tool/Hook/Subagent/Artifact refs、当前 thread Journal locator、coverage 与预算 receipt。完整 checkpoint 的 fact digest、record ID、sequence 和 coverage 只属于宿主耐久校验，不原样重复发给模型；provider-visible 投影只携带去重后的语义值、各类耐久 fact 数量和 Journal locator。单个长语义值在 provider projection 中保留有界头尾，避免多轮重复 follow-up 把耐久事实复制成新的 mandatory floor；完整值仍留在 typed checkpoint。critical/当前状态保留语义投影；relevant file、command 和 tool finding 属于 `supporting` 可检索事实，不进入 critical/important coverage 分母。每个 checkpoint 事实类别保留最近 64 条；只有被该滚动上限明确淘汰的旧 fact ID 才退出 coverage 分母，并继续由同一 `TranscriptLocator + thread_history_read` 精确回读，其他任何非预期缺失仍硬失败。completed actions 和 relevant files 只投影最新少量值，commands/tool findings 的精确值默认只通过耐久 fact 数量与 Journal locator 延迟读取，被延迟的事实仍在同一 bundle/Journal 中由 `thread_history_read` 找回。Glob 工具返回的批量清单保留为有界 tool finding 与 Journal 原文，不把其中上百条尚未使用的路径全部升级为 active `relevant_file`；用户点名、Read 参数/结果或其他工具实际使用的路径仍正常进入 checkpoint。tool result 的 error/blocker 抽取以 canonical `IsError` 为准；成功 outcome 即使正文或 JSON key 含 `error/failed` 也不升级为 critical 失败，真实失败仍同时保留 error 与 blocker。当前尚未闭合的任务由最新 user anchor、semantic summary 与 typed checkpoint 承载，不把已在当前轮中的工具历史整轮重复注入 RecentTurns。已闭合 RecentTurns 在全局 10% 预算中仍属可延迟检索层：超预算时按从旧到新移出 provider-visible projection，精确内容仍由 `TranscriptLocator + thread_history_read` 找回，不删除 checkpoint 滚动窗口内的 critical facts。Checkpoint 通过 range-bounded Journal reader 直接从 `user_message/tool_call/tool_result` 与 RunPlan/Subagent authority 抽取稳定 fact ID、record ID 和 sequence；只读取与当前 root/child `agent_id` 精确相同的记录，不能让共享 Journal 中的 sibling/child 私有事实串入 root。fact identity 同时绑定 kind、规范值和 source record identity，所以不同 sequence 重复执行同一命令不会因 FactID 相同而制造 coverage digest 冲突。shell tool 的结构化 `command/cmd/script/argv/args` 是 supporting 命令事实，不依赖 `go test` 等固定前缀；tool arguments 中的命令与绝对路径保留原始 `/`。coverage receipt 绑定经滚动保留的独立 source fact-ID 集，而不是把已写入 checkpoint 的条目自行计成 100%。预算允许时 RecentTurns 作为带 pairing 的 conversation data 随 checkpoint 显式进入 provider 请求。Checkpoint projection。

压缩成功必须同时满足：pairing 合法、summary 非空（fallback 不算成功）、可压量足够时对话至少缩 20%、typed checkpoint/section/digest/coverage 全部合法、完整请求硬 10% receipt 合法，并低于 auto/block。任一检查要求失败都不 append、不换内存、不切 epoch、不清 usage 锚点。主动压缩在可压量小于约 5000 token 时直接 `not enough compactable history`。`CONTEXT_BLOCKED` 不能再触发 reactive；mandatory floor 已超过 target 的 `compact_target_unachievable` 会立即打开熔断；仅完整投影超 target、但 mandatory floor 仍可达时允许一次更轻 tail 重试。其余情况连续三次落在同一失败族（例如 `insufficient_reduction` / `still_above_*` 这类预算未解）也会熔断，不要求三次完全相同的具体 reason。

压缩成功产生唯一 `compact_boundary_id` 和一个原子 `PostCompactContextBundleV2`。Runner 的提交顺序固定为：

```text
计算 summary/tail + TaskCheckpoint + refs + coverage/budget
  -> validate/seal bundle digest
  -> append context_compacted_v2
  -> flush journal
  -> 一次安装 conversation / checkpoint / Memory refs / Skill refs
  -> 发出 compact finished
```

V2 使用 journal 的 transactional `AppendFlushed`：先把现有合法 records 与新 boundary 编码为完整 JSONL，再通过同目录 temp、temp fsync、atomic rename、parent fsync 一次替换 authority，不在原文件尾部写入后再 truncate 回滚。rename 前失败时旧文件保持完整；若底层在 rename 已完成后才返回错误，Journal 会比较 target 与本次精确 transaction bytes，把已经完整提交的 boundary 认作成功，不能让调用方保留旧内存而重启又读到新 boundary。live record 只在该事务确认提交后发布。因此失败 boundary 不会在后续 flush/restart 复活。Memory 不清空 identity：V2 bundle 保留旧 identity/revision/content-digest refs，但提交后会从当前 Runner snapshot 和 RecallManager 的后续注入集合移除这些旧正文，child 也不能重新继承；压缩后 selector 新召回的未压缩正文仍可合并。Skill 不改写，Subagent terminal handoff 不消费。服务重建按最后一个合法 v1/v2 boundary 选择 authority；V2 后出现合法 v1 会清除旧 V2 checkpoint/Memory/Skill refs，v1 后出现 V2 则恢复最新 V2，不能拼成混合状态。旧 v1 transcript thread 仍写并读取 `context_compacted.messages`，直到 journal 迁移。Skill 使用 bundle 内压后投影。`AWAKEN_CONTEXT_COMPACTION_V2=false` 可显式回退写 v1 record；semantic journal thread 默认启用 V2。

完整 thread Journal 始终保留。root Agent 可按 bundle 的 sequence/boundary locator 调用延迟披露的 `thread_history_read`，只读当前 thread 的有界 query/sequence 页面；该工具不接受其他 thread ID，不返回物理 store 路径、provider opaque state 或原始 tool arguments，并遮蔽 bearer/basic、常见 API/token 前缀、`client_secret`、AWS secret access key、passphrase/private key/credential 等命名敏感值，包括带空格的引号值。默认每项最多 2,000 字符、单次正文合计最多 12,000 字符；可调硬上限分别为 4,000/24,000，耐久 tool result 只保存无正文 receipt。

`src/runtime/thread_history.go` 的 `boundThreadHistoryItems` 按 Unicode 字符计正文预算。向后读取优先保留页尾的新记录，向前读取优先保留页首记录，结果始终按记录顺序返回。两种方向共用一次遍历；从页尾收集时只在结束后反转结果，避免逐条在切片头部插入。预算不足时只截短边界项并标记 `ContentTruncated`，不修改输入记录。`src/runtime/thread_history_test.go` 覆盖前后翻页、中文和 emoji、预算恰好耗尽与原始记录保持不变；历史记录的合并排序与归档入口共享，职责见[会话管理实现](../../01_桌面工作台/会话管理/实现方案.md#core-与-filestore)。

fork body 属于 child 上下文，不纳入父压缩；父只保留 child result/identity。child 自己的 compaction record 带 agent identity。attachments 与 tool result media 通过 runtime storage key 恢复，不重复持久化 image/PDF base64。

自动化必须覆盖主动/被动压缩、circuit breaker、Skill 预算、auxiliary purpose/budget、append/flush 失败不替换内存或 epoch、compaction payload 校验、大结果 projection 不二次截断，以及新 `RunService` 从磁盘恢复 post-compact summary+tail。真实 Desktop 验收按 [02 域验收](../对话运行与恢复/实现方案.md) 执行成功/失败 compact、完整重启和继续追问。

## 当前上下文估算合同

Core 在最终请求投影完成后生成 `ContextUsageSnapshot`：

```text
schema_version / snapshot_id / estimator_id
basis: current_projection | sent_request
request_id? / request_sequence?
model_id / protocol_family / context_epoch_id? / context_epoch_boundary_reason? / request_shape_digest
model_window_tokens / output_reserve_tokens / effective_input_window_tokens
estimated_input_tokens
warning_threshold_tokens / auto_compact_threshold_tokens / compact_target_tokens
contributions[]: kind / estimated_tokens / source_count
generated_at
```

当前估算器 ID 为 `awaken_leaf_v4`，snapshot schema 为 v4。它统计 provider-visible leaf；发送请求时工具分类优先使用协议 lowering 后的最终工具 JSON，媒体使用本地模型估算，JSON/协议结构开销并入对话。以下不变量不可绕过：

1. `sum(contributions.estimated_tokens) == estimated_input_tokens`；
2. debug-only projection 不计入；
3. Memory context 单独计数；Skill 只统计统一 `skill` 工具中模型可见的 catalog name/description/when-to-use，`skill` 工具自身的触发规则与参数 schema 仍属内置工具；渐进披露启用时同理：`tool_find` 描述中内嵌的 deferred MCP 目录计入 `mcp` 分类，`tool_find` 包装与内嵌的 deferred 内建工具目录仍属内置工具，未激活因此未下发的 deferred 定义（内建或 MCP）不计入任何分类；已激活 Skill 正文、host selection binding、附件和 tool result 均进入对话且同一内容只能计入一次；
4. 分类来自 prompt section、message origin/identity 和 tool provenance，不由 Renderer 按字符串猜测；
5. `ContextActualTokens`、最近 provider input/total/output 都不改写 Core 本地 snapshot；最近兼容主请求的 inclusive input 只按 [产品行为](需求文档.md#产品行为) 投影 Desktop 当前总输入，provider total/input 与 `sent_estimated_input_tokens` 只按[上下文窗口与压缩](实现方案.md)参与保守 warning/auto-compact/block 判断；
6. 历史附件和 tool-result media 先按当前 pinned profile 的 vision/native-PDF 能力与**当前窗口**生成请求副本。不支持的二进制媒体仍留在 thread storage，请求克隆会清掉 payload/`storage_key`/`ByteSize`，因此不计媒体 payload token。当前模型支持但落在近尾以外的媒体：请求克隆去掉 `DataBase64` 并加 stub，但保留 `storage_key`/`ByteSize`，本地账仍按 `MediaPartTokenEstimate`（2000/张或每份原生 PDF）计价，避免轻量投影后假瘦。近尾 1 个安全组可以 hydrate，但受剩余窗口夹紧。稳定文本说明与 metadata 仍归对话。禁止 `len(base64)/4`、`JSON.stringify(图)/4`、把其他供应商图价当 MiniMax 主价，或把字节上限当成窗口门。`ConservativeProjectedTokens = max(本地 v4, provider 锚定)`，不覆盖 snapshot；
7. 打开 thread 时，Desktop 先用当前可运行的默认模型 profile 请求 Core 重建当前下一请求的 v4 projection；Core 从耐久 conversation、当前工具/MCP、Skill catalog/已激活正文和 Memory 生成并 flush `context_snapshot`，再读取 transcript。Computer 已开启且模型视觉能力、全局 Host 健康与两项系统权限均 ready 时，重建路径必须在不创建 run-bound Runtime 的前提下保留三个 `computer_*` 工具；只有这些真实条件变化时才能改变工具集。旧记录没有 breakdown、只有 v1 `skills_memory` 合并值或来自 `awaken_leaf_v2` 时不得拆分旧数值；无法取得可运行 profile 时才保留已有汇总和“暂无分类明细”。已耐久的 `awaken_leaf_v3` 不原地改写，成功生成的 v4 新 record 作为后续 authority；
8. 算法版本变化必须通过 `estimator_id` 显式呈现。

`builtin_tools` 统计的是本次请求真正下发模型的全部内置 schema，不是用户手工安装数量。Computer Use 已开启且 Host/权限 ready 时，`computer_observe`、`computer_act`、`computer_verify` 三项会进入当前 run 和同状态的 thread 重建投影，因此内置工具 token 和 `source_count` 会比 Computer 不可用的 run 增加；关闭或 readiness 丢失时又会移除并形成新的 Context Epoch。仅切换 thread 不是 readiness 变化，不得因投影 Agent 没有 run-bound Runtime 而伪造 `tool_removed`；相同 model/profile 仍不是工具集相同的充分条件，必须同时比较全局 Computer/Host/权限状态。

当前 wire kind：

| Kind | 中文标签 | 内容 owner |
| --- | --- | --- |
| `system_prompt` | 系统提示词 | base instructions、host/project rules 与当前兼容性 authority definitions |
| `builtin_tools` | 内置工具 | 源码注册的稳定 builtin tool schema，内置 `skill`/Skill resource 工具自身的触发规则与参数 schema，以及渐进披露启用时 `tool_find` 包装和其内嵌的 deferred 内建工具目录；不含 Skill catalog metadata、deferred MCP 目录和任何 MCP adapter tool |
| `mcp` | MCP | 用户在连接器/MCP 配置中接入、由 MCP server 当前返回且实际下发模型的工具 name/description/input schema，以及渐进披露启用时 `tool_find` 内嵌的 deferred MCP 目录文本；connector-backed adapter 的 model-facing origin 仍为 `SourceMCP`，connector ownership 只保留在 provider manifest；MCP 调用结果进入对话 |

## 请求准备与 provenance

prompt section 保留稳定 ID 和 typed kind；`context.Message` 保留 host-owned origin、message/turn identity；model-visible tool schema 通过不下发 provider 的 wrapper 保留 builtin/MCP/dynamic、provider 和 Skill catalog 等稳定 provenance。`RegistrationID` 只是调用当下 runtime 的执行 pin，不参与工具排序、model-visible digest 或 Context Epoch 等价性判定；相同 schema 重新绑定不能单独导致 `tool_schema_changed`。provider 仍只看到普通协议工具定义，不看到这些 host 字段。

`conversation_continuity` 是位于 system prompt 尾部的稳定 `system_prompt` section 与 Context Epoch source。它只声明同一任务历史的解释规则，不复制历史正文、不携带历史数量或任何 thread/run/session/message/turn identity；内容不随消息轮数变化，因此同一版本不会产生逐轮 `append_only_host_delta`，也不会因会话增长破坏已建立的稳定前缀。会话指代行为由[上下文窗口与压缩](实现方案.md)拥有。

LLM transport 使用 prepare-once 合同：adapter 只做一次协议 lowering，产出不可变 `PreparedRequest`，其中包含最终 endpoint、精确 HTTP body、request-shape digest、stream 属性和 prompt-cache metadata。`InvokePrepared` / `StreamPreparedWithObserver` 只能发送该 body，不能在 journal fsync 后再次重建或改变请求。

真实模型请求前必须先耐久并 flush 脱敏 `model_request`；响应、错误或取消使用同一 request ID 写 `model_usage`。对话状态变化后写当前下一请求的 `context_snapshot`。打开旧 thread 时，`POST /v1/threads/{thread_id}/context-snapshot` 优先使用该 thread 已保存且仍可运行的 profile/effort；只有它已删除、停用或凭据不可用时才回退当前 default。该路径只重建并耐久化 current projection，不调用 provider、不生成 model usage；相同 projection 不重复追加。重建必须装配与 `StartRun` 相同的 provider-visible 请求来源（含 AGENTS 指令快照），任何来源缺失只能表现为“未评估”，不得被 Epoch 比较当成真实变化而伪造冷边界。终态 session 仍在内存时，transcript 合并器必须补入该耐久 snapshot，不能因它未经过旧 run 的 live EventBus 而过滤。以上 records 不包含 prompt、规则正文、tool 参数、Memory、路径、cache key、API key 或 reasoning 正文。

## Provider 缓存 capability

唯一 `PromptCacheCapability` 由规范化 provider ID、精确 Base URL、protocol family 和 endpoint contract 联合匹配。仅完整匹配已核验厂商 endpoint 时可发送厂商私有字段；custom/兼容 endpoint 只发送协议通用字段并探测响应。

| Provider / endpoint | 当前模式 | 请求行为 | usage 语义 |
| --- | --- | --- | --- |
| OpenAI Chat `https://api.openai.com/v1` | `affinity` | 发送 host `prompt_cache_key`，stream 请求 usage | 解析 prompt cached 与 reasoning breakdown |
| OpenAI Responses `https://api.openai.com/v1` | `affinity` | `store:false`，发送 host `prompt_cache_key` | 解析 input cached、output reasoning 与 total |
| Anthropic Messages `https://api.anthropic.com` | `explicit_breakpoint` | 稳定 system block 写 `cache_control: ephemeral` | inclusive input = non-cached + cache read + cache creation |
| DeepSeek `https://api.deepseek.com` | `automatic_prefix` | 不发送 cache key 或私有缓存字段 | 解析 hit/miss；input 为二者可验证组合 |
| Kimi CN `https://api.moonshot.cn/v1` | `affinity` | host 自动发送 `prompt_cache_key`，stream 请求 `include_usage` | 解析 `cached_tokens`；缺失保持 unknown |
| Kimi Coding Plan `https://api.kimi.com/coding/v1` | `affinity` | 必须发送 host key，stream 请求 `include_usage` | 解析 `cached_tokens`；缺失保持 unknown |
| Doubao Ark `https://ark.cn-beijing.volces.com/api/v3` | 当前未接入 | 普通 Chat/Responses 请求不冒充 Context API；Chat stream 独立请求 `stream_options.include_usage` | 解析供应商实际返回的通用 input/output/cached 字段；不把 Context Epoch 原因显示成供应商缓存状态 |
| 火山 Coding Plan `https://ark.cn-beijing.volces.com/api/coding/v3` | `undocumented` | 不发送缓存私有字段，只做响应探测 | 未确认字段保持 unknown |
| Google OpenAI-compatible Chat | 当前禁用主动缓存 | 不冒充 `prompt_cache_key`；原生 `cached_content` 尚未接入 | 保留 provider 实际返回的通用 cached usage |
| custom Base URL | 默认无缓存 capability；可由 exact profile 合同开启 | 只按所选协议发送通用 Chat/Responses 字段或 Messages `cache_control` | 只保留 provider 实际返回的通用字段 |

DeepSeek 合同依据为[自动前缀缓存文档](https://api-docs.deepseek.com/guides/kv_cache/)，Kimi 请求合同依据为[Chat API](https://platform.kimi.com/docs/api/chat)。Doubao Ark 的[上下文缓存创建 API](https://api.volcengine.com/api-docs/view?action=ContextCreate&serviceCode=ark&version=2024-01-01)要求显式创建缓存并使用推理接入点 ID；当前普通 Model ID / Endpoint ID profile 都没有这条 Context API 生命周期，因此不能仅凭模型价格包含缓存命中价就宣称当前请求已启用缓存。厂商合同变化时先更新 manifest、最终-body fixture 和 usage normalizer，再修改 transport。

`llm.Usage` 采用与 OpenCode 相同的双层语义：厂商回报是用量事实，协议 mapper 只做归一化；本地 `awaken_leaf_v4` 不参与计费。`input` 与 `output` 是 inclusive total，分别包含 cache read/write 与 reasoning；`uncached input`、`cached input`、`cache write` 和 `reasoning` 是互不重叠的 breakdown，raw typed usage 保留厂商原字段供审计。字段均为 nullable，缺字段不能折 0。

OpenAI Chat/兼容协议从 prompt/completion details 归一化 cached、cache write 与 reasoning；Responses 从 `input_tokens_details.cached_tokens` 与 `output_tokens_details.reasoning_tokens` 归一化；`uncached = input - cached - cache_write` 仅在关系合法时生成。Chat 的 `stream_options.include_usage` 是用量回传合同，与 prompt-cache 请求合同独立；只对 provider、精确 Base URL 与 Chat 协议均已核验的 endpoint 发送，自定义代理不会因 URL 相似被推断支持。Anthropic 的 `input_tokens` 是 non-cached，归一化时使用 `inclusive input = input_tokens + cache_read_input_tokens + cache_creation_input_tokens`，并合并 stream `message_start` 与最终 `message_delta` usage。Gemini 经 Chat 兼容 mapper 保留实际返回字段；缺失不补 0。当前没有 Google 原生 `generateContent` 或 Bedrock protocol mapper。

## Affinity、凭据 revision 与 Context Epoch

### Affinity key

需要 affinity 的 endpoint 使用：

```text
aw1_ + base64url(SHA-256(
  provider_id + profile_id + credential_revision
  + endpoint_contract_id + affinity_scope_id
  + model_id + reasoning_policy + prompt_schema_version + purpose
))
```

同一 root thread、profile、credential、model、protocol、endpoint、reasoning policy 和 purpose 的 resume/restart 保持稳定；任一 identity 变化形成冷边界。`reasoning_policy` 使用 Main/Core 已归一化的 Awaken effort，因此同一模型从 `high` 切到 `max` 必须形成新的 profile/Agent cache 与 affinity identity。标题、Memory recall、compact、Subagent、定时任务和 Dream 使用独立 purpose/scope，不污染 `agent_turn`；用途模型先走 host-owned route，再继承调用方 profile，不继承 Composer effort 或发送不适用的 provider reasoning 参数。

`models.json` 的 `credentialRevision` 单调递增：新 profile 为 1，API key 实际变化才递增；旧 profile 缺字段时稳定解释为 1。兼容字段 `promptCacheKey` 仅可读取，不再作为 transport override。journal、telemetry 和 UI 只保留 key 是否 applied 与摘要，不保存 key 正文。

### Context Epoch

system、rules 和初始 canonical tools 构成 byte-stable baseline；日期为日粒度。Memory、Skill、MCP、runtime 和跨日变化只在安全 provider-turn boundary 追加 typed host delta。

exact baseline、synthetic prefix messages、instruction digest、source snapshots、canonical tools 和动态 trailing partition 耐久写入 `sessions/<thread>/context/epochs/` 的 `0600` 原子 sidecar。当前 sidecar schema 为 v4，将指令快照、归一化 `reasoning_policy` 以及 endpoint-model provider 的 transport selector / capability family 双身份纳入 identity；旧 schema 只做安全冷迁移，不沿用缺少当前身份的热 epoch。SemanticJournal 只保存 epoch ID、digest、状态和边界原因，不把 prompt、规则正文或路径投影到 wire。

source 在 epoch baseline 建立后首次加入时，其 `baseline_value` 明确为空，`baseline_digest` 必须写入空文本的标准 digest；当前值和值 digest 只由对应 append delta 承载。读取时仅允许对一种已证明的旧 v4 writer 缺口做原子归一化：baseline value/digest 均为空、current value digest 有效，且 source key、kind、state、sequence、digest、delta content 全部精确互证。其他 baseline、source、delta、tool 或 pointer 损坏仍 fail-stop、保留原数据并阻止模型请求。

builtin tools 按类别/名称固定排序；dynamic tools 按首次发现顺序耐久追加。更新、删除或 authority 不兼容等无法 append-only 表达的变化建立新 epoch，绝不降成普通 user message。compact 只有在摘要校验、journal append 和 flush 成功后才以 `compact_succeeded` 切换 epoch；失败或中断继续使用旧 epoch。

`ContextEpochReceipt.BoundaryReason` 携带本次 projection 的 prefix 变化诊断并写入 `ModelUsageRecord.InvalidationReason`；该字段只供 Journal、运行时诊断和缓存兼容性判定使用，不进入 Desktop 上下文面板。`CreationBoundaryReason` 在新 epoch 创建时固化并跨重启保留，随 `ContextUsageSnapshot.context_epoch_boundary_reason` 进入 Desktop，用于区分可继续做锚定差量投影的 source/tool 更新与 provider/model/compact 等不兼容边界：

- 硬边界返回 `initial_baseline`、`prompt_schema_incompatible`、`workspace_moved`、`provider_credential_changed`、`model_changed`、`reasoning_policy_changed`、`provider_authority_incompatible`、`compact_succeeded`。
- source/tool 触发重建返回 `system_prompt_changed`、`agents_instructions_changed`、`tool_removed`、`tool_schema_changed`、`canonical_tool_added`。`agents_instructions_changed` 只能由真实加载得到的非空指令 digest 变化触发；投影缺失指令快照产生的空 digest 是“未评估”，不得触发轮换（见 [AGENTS 指令与运行快照](../规则指令/实现方案.md)）。
- append-only host delta 返回 `append_only_host_delta:<segment1>,<segment2>`，segment label 为变化的 source key（如 `runtime_context`、`skills`、`memory`）或 `tool:<name>`（新接入的动态工具）。空 detail 退化为 `append_only_host_delta`。这让“MCP/技能/日期变化导致缓存打冷”可以从 reason 直接定位到具体 segment，而不是一个笼统的 host delta。

provider 私有 reasoning/续接状态作为 assistant record 的 `provider_opaque_state` 保存。只有 provider/profile、credential revision、model、protocol 和 endpoint 全匹配时才重放给 provider；普通 projector、Memory、日志和 telemetry 忽略其正文。面向用户的过程历史是另一条 provider-neutral 路径：transport 归一化的可展示 reasoning 在 SemanticJournal 写为 `reasoning_summary`，只用于 AG-UI/Desktop 重放，不参与 provider cache/history 续接，也绝不从 opaque state 降级生成。

## 逐请求账本与成本

`ContextUsageSnapshot` 是当前 provider-visible 内容的本地分类估算；`ModelUsageRecord` 是一个已结束 provider 请求的用量事实，并保存该请求对应的 `sent_estimated_input_tokens`。二者必须继续独立耐久化；Desktop 只按 [产品行为](需求文档.md#产品行为) 做临时显示投影，不把两类 authority 合并成一条 record。

`ModelUsageRecord` 保存 request/purpose/provider/profile/credential/transport model/capability model/selector kind/protocol/endpoint/reasoning policy、cache mode/applied、epoch/prefix digest、retry/fallback、`sent_estimated_input_tokens`、nullable normalized usage、raw typed usage、完整性、pricing snapshot/cost、provider request ID、latency、status/error 与完成时间。Desktop 只在 provider/profile/credential/transport selector/capability family/protocol/endpoint 和 effort 都与当前选择兼容时复用该实报。

开始新的 run 或从磁盘恢复旧 thread 时，Core 还会从最后一个兼容硬边界之后选择最近一条成功、完整的 `agent_turn` usage，按同一 provider/profile/credential/transport selector/capability family/protocol/endpoint/effort identity 恢复 governor 的预算锚点。锚点优先使用 provider `total_tokens`，缺失时回退 `input_tokens`，并成对恢复 `sent_estimated_input_tokens`；任一关键字段缺失、identity 不兼容或最后边界为成功 compact 时都不复用。该锚点只参与下一请求 warning/auto-compact/block，不覆盖本地 snapshot，也不改变 Desktop 的 usage 兼容性判定。

作用域互斥：

- thread-bound `agent_turn`、`thread_title`、`memory_recall`、`compact_summary`、OpenAI exact `native_compaction` 和 retry 写当前 thread SemanticJournal；
- Dream 的 `memory_maintenance` request/usage 嵌入独立 DreamTask authority，不双写 thread journal；
- `connection_test` 写 profile-scoped `~/.awaken/usage/model-profiles/*.jsonl`，不写 thread 或 Dream authority。

启动恢复发现 `model_request` 没有终态 usage 时，补 `status=interrupted`、`error_code=usage_unknown`，不伪造 token。provider request ID 只有响应确实提供时才保存。

辅助调用不再按供应商硬编码切换小模型，也不在 Renderer 暴露独立用途选择器。`thread_title`、`compact_summary`、`subagent` 默认继承 thread/父 profile；Host 内部 route 存在且有效时可优先使用。定时任务显式 pin 失效时 fail closed，不走用途或默认 profile。模型工具不能在 Subagent spawn 参数中注入 `model_profile_id`。

预算为：标题 48、Memory recall 256、compact 8192、Dream 4096、连接测试 1；实际最大输出还受用途 profile 能力上限约束。标题先使用本地规则：attachment/Skill label，或无问号换行且不超过 12 个中文字符/8 个英文词的短输入；其余才调用所选 profile。

DeepSeek `deepseek-v4-flash` 与 `deepseek-v4-pro` 使用随 record 固化的官方美元 pricing snapshot；实现中的当前 snapshot 生效日为 2026-07-19，来源为[官方价格页](https://api-docs.deepseek.com/quick_start/pricing/)。Kimi Coding Plan、火山套餐和 custom endpoint 不做 token-to-plan 换算，`calculated_cost` 保持 unknown。

## 大 tool result admission

超过 32 KiB 的文本 tool result 在第一次进入 journal/model context 前完成一次性 offload：完整内容写入 `sessions/<thread>/tool-results/<tool-call>/content.txt`，目录 `0700`、文件 `0600`；journal/context 只使用含 digest、字节数、稳定 preview 和 storage key 的 admission projection。恢复消费已经投影的 record，不重新截断，也不在请求后事后替换。

媒体 tool result 继续使用同一 thread-owned tool-results authority。Journal 只恢复 `storage_key` 与元数据；hydrate 只发生在近尾媒体预算内。Base64 不进入 journal、AG-UI 或日志。已 offload 的大文本在模型请求中保持 stub，不再全量灌回。

## 主动与被动压缩的实现

- 接近 auto-compact threshold 时执行 proactive compact；
- 除此之外，`ContextWindowState.ShouldAutoCompactByActualUsage` 作为并行主动触发：`LastAPIUsageTokens > 0` 时以 provider 实报为同 epoch 的非递减下界，再叠加 `max(EstimatedDeltaTokens, EstimatedTokens - LastSentEstimatedInputTokens, 0)`；这既保留同基准下真实增长，也阻止压缩判断前投影与 Context Epoch lowering 后 sent request 的阶段差异被误当成负增长。它与 v4 `EstimatedTokens` 触发是 OR 关系，不修改 `awaken_leaf_v4` snapshot。`LastAPIUsageTokens` 在同一 run 的连续请求以及新 run/旧 thread 的兼容恢复中优先取 provider `total_tokens`，provider 未返回 total 时回退 `input_tokens`；warning 和 block 同样取该锚定投影与本地估算的较大值，避免显示已接近窗口但安全门仍过晚。恢复只接受成功、完整、同 identity 的主请求，并要求成对存在发送时估算；成功 compact 与 provider/model/credential/protocol/reasoning 等硬边界清除或拒绝旧锚点。算术溢出按越过阈值处理。成功压缩后 governor 同时清零 provider 实报与发送时估算锚点，因为 compact 后的新 prefix 已不再对应上一请求；
- provider 返回上下文过长且仍可安全重试时执行 reactive compact；
- 同一 governor 的失败计数和 circuit breaker 防止无限压缩循环；同一次 compact 的 postcondition 最多允许 1 次更轻 tail 重试（即摘要模型总调用最多 2 次）。fallback summary、`insufficient_reduction`、以及 mandatory floor 已超过 hard target 的 `compact_target_unachievable` 属当轮终态，不再继续请求同一摘要模型；其余失败 reason 为 `still_above_auto_threshold` / `still_above_block_threshold` / `oversized_protected_tail`；
- summary 请求使用 `compact_summary` purpose、独立 affinity 和动态 1024–4096 token 上限；默认继承 thread profile，Host 内部存在有效 route 时可先解析该 route，并按所选模型能力进一步限制输出；Renderer 不提供独立用途模型选择器；
- summary model 失败可使用明确标记的本地 fallback，失败或中断不切 epoch；
- 无法安全裁剪 tool pair 或最新用户意图时 block，而不是静默丢失。

## 产品行为的实现

### Composer 与中文面板

- dock Composer 的“上下文窗口”入口常驻为圆环占比指示；可访问名称为“上下文窗口”并附带「当前总输入 / 可用输入窗口」；hover 展示「N% 当前使用」与上述两个数值，不追加“可用输入”文字；可用输入窗口直接取 Awaken 当前模型 profile 配置的 `ContextWindow`，存在更小的明确 `MaxInputTokens` 时才受其约束，不能再扣 `MaxTokens`。最近一次成功且 usage 完整的主调用与当前 identity/Context Epoch 兼容时，当前总输入直接取 provider `input_tokens`；该字段缺失但 cached/uncached 分项完整时，取 `cached_input_tokens + uncached_input_tokens + cache_write_tokens`。Desktop 不加入 output，也不叠加发送后的本地估算差量；没有兼容的 provider input 时才回退当前 `ContextUsageSnapshot` 本地估算。
- center 空态没有上下文快照时不显示假 0。
- 入口是 button，支持鼠标、Enter、Space，并暴露 `aria-haspopup="dialog"`、`aria-expanded` 和锚定关系；点击仍打开既有中文「上下文用量」完整分类面板。
- 面板首行标题“上下文用量”与关闭按钮同行，避免关闭钮独占一行留下大块空白；汇总行左侧为「N% 当前使用」、右侧为「当前总输入 / 可用输入窗口 Token」，其下为分类进度条。不显示 `~`、“预计”、“本地估算”徽标、模型总窗口、输出预留或自动压缩阈值文案。Core typed 分类为系统提示词、内置工具、MCP、技能、记忆、任务检查点、对话七项；当前总输入高于七项本地和时，Desktop 追加“其他/协议开销”承载未分类残差。进度条与图例都按分类语义绑定固定颜色，某个中间分类为 0 而不绘制 segment 时，后续分类不得顺位改色；不展示多次调用账本或主/辅助调用分类。
- 面板在分类明细后直接展示最近一条 `ModelUsageRecord` 的缓存与成本摘要，不添加“上次请求”标题或分隔线，不累加多条调用，不展示 `raw_typed_usage`。该明细与上方“当前总输入”共用同一次 identity/Context Epoch 兼容性判定：判定不兼容、总输入回退本地估算时，缓存与成本明细整段隐藏，不得出现“总用量小于输入与缓存”的混合面板：
  - 缓存徽标由 `cache_mode` 与 `cached_input_tokens` 联合判定。`undocumented`（火山 Coding Plan）固定显示“未确认”，不声称命中或未命中；`automatic_prefix`/`affinity` 在 `cached_input_tokens` 缺失时显示“未知”，`> 0` 显示“已命中”，`= 0` 显示“未命中”；无 `cache_mode` 不显示徽标。
  - 缓存率使用同一兼容请求的 `cached_input_tokens / input_tokens × 100`，保留一位小数；分母使用 Renderer 规范化的 inclusive input（支持完整分项重建），不使用窗口容量、输出或多请求累加。缺失、非有限值、总输入不大于零或命中数超出输入范围时显示“未知”；`undocumented` 显示“未确认”。
  - 输入、命中、未命中和输出 Token 使用原生 `details/summary` 放入“Token 明细”，不设置 `open`，每次挂载面板默认收起，支持鼠标与键盘切换；缓存状态、缓存率和成本始终位于折叠区外。输入 Token、命中/未命中 Token、输出 Token 行仅在对应字段非 null 时显示；缺失不折 0、不显示。输入是最近请求的 inclusive input；缓存命中、未命中和缓存写入是其互不重叠的 breakdown。存在兼容的完整 `input_tokens` 时，上方当前总输入与这里的“输入 Token”严格相等。
  - 成本行：`calculated_cost_usd` 非 null 显示 `$<amount>`（4 位小数）；为 null 显示“未知”，覆盖 Kimi Coding Plan、火山套餐与 custom endpoint 等无 token-to-plan 换算合同的情形。
  - `invalidation_reason` 继续留在 `ModelUsageRecord`、Journal 和运行时诊断中，不进入用户上下文面板；Host 的 prefix 冷边界和 append-only delta 不作为用户用量字段展示。
  - 这些明细仅在该 record 携带 cache 或 cost 信号时渲染；只有 status/purpose/inputTokens/host boundary 的 record 不渲染，避免噪声。
- provider usage 仍以 nullable typed records 进入调用账本；它不改写 `ContextUsageSnapshot`。兼容的 inclusive input 是 Desktop 当前总输入的优先事实；provider total 与 `sent_estimated_input_tokens` 只用于 Core 保守窗口判断。缺失 cached/cost 不折 0。

### Composer 与中文面板

1. provider 实报只使用 `purpose=agent_turn`、`status=succeeded`、`usage_complete=true` 的最近记录；model、protocol、effort 或 provider profile identity 不兼容时不得复用旧值；同 epoch 或 `system_prompt_changed`、`agents_instructions_changed`、`tool_removed`、`tool_schema_changed`、`canonical_tool_added` 这类不会改变 provider/model identity 的重建边界允许继续显示最近请求 input，`compact_succeeded`、provider/model/credential/reasoning 等硬边界必须回退本地估算；
2. Desktop 优先取规范化 `input_tokens`；缺失时只允许用完整且互不重叠的 cached/uncached/cache-write 输入分项重建，不读取 `total_tokens` 或 `output_tokens`，也不使用 `sent_estimated_input_tokens` 推演下一次请求；
3. 七项 typed 分类仍由 Core 本地 estimator 生成，provider 不提供分类。当前总输入高于七项本地和时，正残差单独显示为“其他/协议开销”；当前总输入低于本地和时，七项按原占比非负缩放；
4. 显示分类和严格等于当前总输入；该 reconciliation 不回写 journal、不参与成本计算，也不覆盖七项 snapshot。Core 的 warning/auto-compact/block 仍按[上下文窗口与压缩](实现方案.md)取本地估算与 provider total/input 加本地差量所得锚定投影中的更保守值。
