# 会话标题生成与重命名方案

## 需求

左侧栏会话标题需要对齐 Codex Desktop 的会话体验：标题是会话级元数据，不是当前输入框内容或当前 run prompt 的临时投影。

1. 新会话发起第一条消息后，左侧栏立即出现一条会话记录。
2. 在 LLM 标题尚未生成前，会话标题默认使用用户第一条消息的可读截断文本。
3. 默认标题只能来自第一条消息，后续每一轮用户消息都不能再覆盖该会话标题。
4. 系统需要在后台基于用户第一条消息生成更短、更语义化的标题，并在生成成功后覆盖默认标题。
5. 标题生成必须使用用户当前选择的 LLM 配置，与主 run 并发执行。
6. 标题生成不能阻塞主 run 创建、SSE 订阅、中间区域执行流或 Workbench narrative 渲染。
7. 用户手动重命名后，标题进入 manual 状态，任何自动标题生成或后续消息都不能覆盖用户手动标题。
8. 重命名交互应在 Awaken Desktop 内完成，不依赖系统级 `window.prompt`。
9. 左侧栏加载圈只表示中间区域 run 正在执行，不能绑定标题生成状态。
10. 标题生成失败时不向 UI 返回错误状态，左侧栏继续展示第一条用户消息兜底标题。

## 现有问题

### 标题没有独立生命周期

当前 thread 只暴露 `label`，没有记录标题来源、标题状态或标题生成任务信息。因此系统无法区分下面三种完全不同的状态：

- 第一条消息兜底标题。
- LLM 自动生成标题。
- 用户手动重命名标题。

缺少状态后，前端和后端只能用“最近一次输入”或“最近一次 listThreads 结果”粗略覆盖 `label`，导致标题被普通 run 流程污染。

### 后端没有自动标题生成

当前 runtime 创建 thread 时使用 `threadLabelForInputAndTokens()` 从输入、附件或 skill token 中直接推导 label。这个逻辑只是本地截断/兜底，不会调用 LLM，也不会创建后台标题任务。

相关链路：

- `src/runtime/run_service.go`：创建 thread 时计算 `threadLabel`。
- `src/runtime/transcript_store.go`：`trimThreadLabel()` 只做 50 字符截断。
- `src/runtime/thread_store.go`：`threads.title` 当前只保存最终 label。

### 后续消息会覆盖左侧栏标题

Desktop 每次提交 composer 都会重新计算 `nextThreadLabel`，然后 dispatch `run/threadAdded`。即使当前是在已有 thread 里继续发送消息，这个 action 仍会把本轮输入当作 thread label 合并进左侧栏状态。

相关链路：

- `apps/desktop/src/renderer/App.tsx`：`handleSubmit()` 每次 start run 后 dispatch `run/threadAdded`。
- `apps/desktop/src/renderer/runtime/reducer.ts`：`run/threadAdded` 使用 `action.label` upsert thread。
- `apps/desktop/src/renderer/runtime/reducer.ts`：`RUN_STARTED` 分支也会用 `state.prompt || "Untitled thread"` upsert thread。
- `syncActiveThreadSummary()` 会在多个 run 状态更新路径中同步 thread summary，如果没有稳定标题元数据，也可能把当前 prompt 间接写回 thread item。

### 重命名缺少产品化交互和保护语义

后端已经有 `PATCH /v1/threads/{thread_id}`，Desktop main 也有 `awaken:rename-thread` IPC，但 renderer 当前使用 `window.prompt("重命名会话", thread.label)` 完成输入。这会带来三个问题：

- 体验不像 Awaken Desktop 内部交互，截图中用户感知为“重命名不能用”。
- 重命名成功后只刷新列表，没有显式更新当前 active thread view 的标题状态。
- 没有 manual 标题状态，后续 run/event 仍可能把用户手动标题覆盖掉。

## 解决方案

### 一、建立 thread 标题状态机

在 runtime thread metadata 中把 `label` 从“普通字符串”升级为“展示标题 + 标题状态”。

建议新增字段：

```go
type ThreadTitleSource string

const (
    ThreadTitleSourceFirstUser ThreadTitleSource = "first_user"
    ThreadTitleSourceLLM       ThreadTitleSource = "llm"
    ThreadTitleSourceManual    ThreadTitleSource = "manual"
)

type ThreadTitleStatus string

const (
    ThreadTitleStatusPending ThreadTitleStatus = "pending"
    ThreadTitleStatusReady   ThreadTitleStatus = "ready"
    ThreadTitleStatusFailed  ThreadTitleStatus = "failed"
)
```

`ThreadSnapshot` 和 Desktop `RuntimeThread` 继续保留 `label` 作为展示字段，同时增加：

- `title_source`
- `title_status`
- `title_updated_at`
- `title_seed_run_id`

兼容策略：

- 旧 thread 没有 title metadata 时，按 `title_source=manual` 或 `title_source=first_user,title_status=ready` 迁移均可。
- 为避免历史标题被自动覆盖，建议旧数据默认视为 `manual`，只对新建 thread 启用自动标题生成。

### 二、新 thread 只用第一条消息设置兜底标题

`StartRun()` 需要区分新 thread 和已有 thread：

- `req.ThreadID == ""`：创建新 thread，使用第一条消息生成 fallback label。
- 当本次 run 已携带模型 profile 时，内部标记 `first_user + pending` 并启动标题生成。
- 当没有可用模型 profile 时，内部标记 `first_user + ready`，表示第一条消息兜底标题就是当前稳定标题。
- `req.ThreadID != ""`：复用已有 thread，只更新 run 状态、latest run id、active run id，不再改 label。

前端也同步收窄：

- `handleSubmit()` 只有新 thread 才允许提供 fallback label。
- 已有 thread 继续对话时，`run/threadAdded` 不再接受本轮 prompt 作为 label。
- reducer 中 `RUN_STARTED` 只更新 run 状态，不写 `label: state.prompt`。
- `syncActiveThreadSummary()` 只补齐不存在的 thread title，不覆盖已有 label。

### 三、后台并发生成 LLM 标题

runtime 在新 thread 创建成功后立即启动独立后台任务生成标题：

1. 输入：用户第一条消息、首轮附件摘要、首轮 composer token 摘要、当前 `ModelProfileConfig`。
2. 模型：使用 Desktop main 在 `awaken:start-run` 中传入的用户当前默认模型 profile。
3. 请求：独立 `context.WithTimeout`，建议 6-10 秒；`MaxTokens` 32-64；`DisableReasoning=true`；不带工具；不写入 agent conversation。
4. Provider 策略：标题生成必须复用主 LLM 层已有的 provider request policy，不能硬编码 temperature 或 reasoning 字段；例如 `kimi-for-coding` 的标题请求也要走 Kimi 合法温度与 thinking 控制，否则会出现主 run 可用但标题后台请求失败。
5. Prompt：要求输出 4-12 个中文字符或 3-8 个英文词，禁止引号、句号、换行、解释，且不能复读用户原句。
6. 质量门禁：拒绝空标题、过长标题、问句、明显复读第一条消息的标题。
7. 重试：标题生成失败或质量门禁不通过时，在后台短退避重试；重试仍失败则静默结束。
8. 成功：清洗标题，若 thread 仍处于 `first_user + pending`，则写回 `label` 并标记 `llm + ready`。
9. 失败：保留第一条消息兜底标题，标记 `first_user + failed`，不向中间区域或左侧栏报错。
10. 用户已手动重命名：如果 source 已是 `manual`，自动标题结果直接丢弃。

建议封装为：

- `src/runtime/thread_title.go`
- `RunService.scheduleThreadTitleGeneration(...)`
- `RunService.ApplyGeneratedThreadTitle(threadID, seedRunID, title)`

标题生成不能复用主 agent 的 conversation，也不能向 SSE event bus 写 execution event。它是 thread metadata 的后台维护任务，不属于中间区域执行流。

### 四、左侧栏只刷新标题，不展示标题任务状态

为了让左侧栏尽快显示 LLM 标题，有两种实现路径：

短期方案：

- 新 thread 创建后，renderer 静默轮询 `listThreads()`，轮询窗口要覆盖 runtime 标题生成 timeout 与重试退避。
- 成功拿到 `title_source=llm,title_status=ready` 后刷新左侧栏 thread item。
- 如果拿到 `title_status=failed`，停止轮询但不向 UI 展示失败状态。
- 不影响主 run 订阅和中间区域渲染。
- 左侧栏加载圈继续只由 run `activeRunId/runStatus` 决定，与标题生成无关。

长期方案：

- 增加 thread-level event，例如 `THREAD_UPDATED` 或独立 `/v1/threads/events`。
- Desktop 订阅 thread metadata 更新，只更新左侧栏 thread item。
- 不把标题更新映射为 Workbench narrative。

建议先采用短期方案，降低改动面；当左侧栏 thread metadata 事件增多后，再升级长期方案。

### 五、重命名改为 Desktop 内交互

把 `window.prompt` 改成 Awaken Desktop 内部 dialog 或行内输入。

推荐交互：

- 点击 `... -> 重命名` 后，在当前左侧栏上方或居中弹出轻量 dialog。
- 输入框默认填入当前标题。
- Enter 提交，Esc 取消。
- 空标题禁用提交。
- 提交时调用 `runtimeClient.renameThread(threadId, nextLabel)`。
- 成功后立即 dispatch `run/threadRenamed` 或直接用返回的 thread 更新 reducer。
- 后端将标题标记为 `manual + ready`。

manual 保护规则：

- 手动重命名成功后，任何 pending LLM title job 的结果不能覆盖。
- 后续用户继续发送消息不能覆盖。
- listThreads 刷新也以后端 `manual` 标题为准。

### 六、测试与验收

后端测试：

- 新 thread 使用第一条消息作为 fallback title。
- 同一 thread 第二次 StartRun 不覆盖 title。
- LLM 自动标题只覆盖 `first_user + pending`。
- manual title 不被 LLM 结果覆盖。
- rename 持久化并带 `manual` metadata。
- 重启后 title source/status/label 可恢复。

前端 reducer 测试：

- `run/threadAdded` 对已有 thread 不覆盖 label。
- `RUN_STARTED` 不用当前 prompt 覆盖 label。
- `run/threadsLoaded` 能刷新 LLM title。
- `run/threadRenamed` 立即更新 active thread 和列表。

Desktop 验收：

1. 打开 Awaken Desktop。
2. 新建会话发送“这些呢？”。
3. 左侧栏立即显示“这些呢？”。
4. 在同一会话继续发送“你好”。
5. 左侧标题仍是“这些呢？”，不会变成“你好”。
6. 后台标题生成完成后，左侧标题变为 LLM 生成的短标题。
7. 手动重命名为“ERP附件检查”。
8. 继续发送新消息，标题仍保持“ERP附件检查”。
9. 重启 Desktop 后，标题仍保持手动标题。

最终验收必须使用根 `README.md` 的 Desktop 入口执行真实 UI smoke；不能只用底层 provider/API smoke 代替。
