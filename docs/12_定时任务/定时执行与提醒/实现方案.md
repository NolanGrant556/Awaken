# 定时执行与提醒 · 实现方案

本文说明代码职责、数据与接口、异常恢复和验证方法。功能范围及用户操作见[需求文档](需求文档.md)。

## Qwenpaw 参考结论与 Awaken 适配

设计参考 Qwenpaw 的任务调度。以下路径属于参考项目，用于说明采用了哪些行为：

- `src/qwenpaw/app/crons/models.py`：任务、调度、投递、运行参数、状态和执行记录；
- `manager.py`：调度器生命周期、启停、立即执行、misfire、并发和历史；
- `executor.py`：固定文本和 Agent 两类执行；
- `repo/json_repo.py`：`jobs.json` 与每任务历史；
- `api.py`：CRUD、pause/resume/run/state/history；
- `console/src/pages/Control/CronJobs/`：列表、日历、编辑抽屉、模板选择与 10 个内置模板。

复用的是产品行为和边界，不复制 Python/React 实现。两边概念映射如下：

| Qwenpaw | Awaken 目标 |
|---|---|
| APScheduler | Core 内 `src/scheduledtask` 调度服务；Cron 解析采用 Go 依赖 |
| agent/channel/user/session | project + 每任务稳定专属 thread |
| console/inbox | 专属 thread + 独立执行历史；提醒额外发 Desktop 原生通知 |
| `jobs.json` | 当前 FileStore generation 下的 journal-first authority |
| 前端模板返回 API payload | Renderer 拥有内置产品模板，转换为受控编辑表单；Core 重新校验全部字段 |
| request 中携带运行参数 | 任务只保存 profile ID、project ID 和用户配置；凭据及真实 workspace 在每次触发时由 Core 解析 |
| `tool_safety` 可关闭审批 | Awaken 沿用当前零审批工具合同；需要用户交互的无人值守调用 fail fast |
| `share_session` | 初版固定为每任务一个稳定专属线程，同一任务历次执行共享、不同任务隔离 |

不能直接搬用的行为：

- Awaken 没有 Qwenpaw 的 channel/inbox authority，不能把 `channel/user_id/session_id` 硬塞进 Renderer 或 Connector。
- Awaken 的模型凭据由 `~/.awaken/config/models.json` 与 `~/.awaken/.env` 管理，定时任务定义不得保存 API key、Base URL 快照或完整模型配置。
- Awaken 的 workspace/项目边界由 Core FileStore 解析，定时任务不得保存可绕过项目变更的旧路径权限快照。
- Awaken 的 Desktop 关闭时 Core 也停止；首版不承诺应用退出后由操作系统唤醒执行。

## 数据模型

### 定义

目标 Go/JSON 结构：

```json
{
  "task_id": "sched_...",
  "version": 3,
  "name": "工作日科技新闻早报",
  "enabled": true,
  "project_id": "project_...",
  "thread_id": "thread_...",
  "schedule": {
    "kind": "cron",
    "cron": "30 9 * * 1-5",
    "timezone": "Asia/Shanghai"
  },
  "action": {
    "kind": "agent",
    "content": "整理今天最值得关注的科技新闻……",
    "composer_tokens": [
      {
        "id": "skill:daily-news:project",
        "type": "skill",
        "label": "daily-news",
        "payload": {
          "skillId": "daily-news",
          "sourceOrigin": "project",
          "skillFilePath": "/当前项目/.awaken/skills/daily-news/SKILL.md",
          "rootDir": "/当前项目/.awaken/skills/daily-news"
        }
      }
    ]
  },
  "execution": {
    "profile_id": "",
    "timeout_seconds": 600,
    "misfire_grace_seconds": 600
  },
  "template_origin": {
    "template_id": "daily_tech_news_brief",
    "source": "builtin"
  },
  "created_at": "2026-07-26T10:00:00Z",
  "updated_at": "2026-07-26T10:00:00Z"
}
```

日程 `schedule`：

```json
{
  "kind": "calendar",
  "run_at": "2026-07-27T08:00:00+08:00",
  "timezone": "Asia/Shanghai",
  "repeat_every_days": 1,
  "repeat_end": {
    "kind": "count",
    "count": 14
  }
}
```

`repeat_end.kind` 为 `never | until | count`；不重复时不出现 `repeat_every_days/repeat_end`。`until` 必须晚于 `run_at`。`count` 范围为 1–10,000。

### 状态与执行记录

任务 materialized state：

```text
enabled | paused | running | completed | invalid
```

执行状态：

```text
queued | running | success | error | skipped | cancelled | interrupted
```

执行记录至少包含：

```json
{
  "execution_id": "exec_...",
  "task_id": "sched_...",
  "task_version": 3,
  "trigger": "scheduled",
  "scheduled_for": "2026-07-27T00:00:00Z",
  "started_at": "2026-07-27T00:00:01Z",
  "finished_at": "2026-07-27T00:01:20Z",
  "status": "success",
  "run_id": "run_...",
  "thread_id": "thread_...",
  "error_code": "",
  "error_message": ""
}
```

`trigger` 为 `scheduled | manual | misfire`。运行次数限制只消费 scheduled/misfire 的 occurrence，手动执行不消费。失败或 skipped 的已到期 occurrence 也计入限定次数，避免失败后无限延长日程。

### 校验

Core 是唯一校验 owner：

- 名称 1–120 个 Unicode 字符；
- reminder content 非空且不允许 Composer token；Agent 必须至少有 content 或一个 Composer token；
- Agent `composer_tokens` 当前最多 24 个且只接受结构化 Skill、Plugin 或 capability token，token ID 唯一；Plugin 必须携带 `pluginName + pluginDigest`，capability 只允许固定 `capabilityId=computer-use`，未知 capability 必须拒绝。这个 token 数量安全预算不限制 `/`、`@` 目录结果数量；可见 prompt 由各 token 的 `leadingText` 与末尾 content 组成，总计最大 32 KiB，token metadata 总计最大 16 KiB；
- Cron 必须是五段“分 时 日 月 周”，不接受秒；数字周日 `0/7` 规范化为 `sun`，并支持英文 `sun..sat`；
- IANA 时区必须由 Go `time.LoadLocation` 成功加载；
- 自定义 Cron 必须能计算出未来 occurrence；
- project 必须存在且为 active；
- profile ID 只保存 opaque ID；创建时若显式 profile 不 ready 则拒绝；
- 超时 30–3,600 秒，misfire grace 0–86,400 秒；
- client 提供的 task/thread/execution ID、状态、next run 和时间戳均不可信，由 Core 生成。

## 持久化与 authority

`FileRepository` 的读取、版本比较、执行去重、状态转换与提交在同一个 generation 文件锁内进行；取得锁后先从 mutation journal 刷新定义，再从对应 execution journal 刷新执行索引。启动始终以 journal 重建快照，不信任仅格式有效的 `state.json`。旧实例不能绕过版本、tombstone 或 terminal 检查；删除回执随 journal 同步。`repository_consistency_test.go` 使用两个长期存活实例和独立重新打开的实例验证旧版本冲突、执行幂等、终态保护和删除读回。

定时任务属于全局业务数据，进入当前 FileStore generation：

```text
~/.awaken/
└── store-generations/<CURRENT>/
    └── scheduled-tasks/
        ├── mutations.jsonl
        ├── state.json
        └── executions/
            └── <task-id>.jsonl
```

- `mutations.jsonl` 是定义、版本、启停、thread 绑定、完成/tombstone 的 authority。
- `state.json` 是可重建快照，损坏时从 journal 重建。
- execution 文件是每任务追加历史，最多向 API 投影最近 50 条；中段损坏 fail closed，尾部半条按 FileStore committed offset 截断。
- 所有目录 `0700`、文件 `0600`，写入使用 `src/filestore` 的 atomic/journal 原语。
- mutation 与项目 lifecycle 共享 `locks/store.lock` 或同等级的 generation 级锁；持锁 writer 在每次 append 前必须刷新磁盘 journal 尾部序号，不能让两个先后取得锁的 Core 复用各自打开文件时缓存的 `lastSeq`。execution journal 遵守同一规则。
- task prompt/content 是用户业务数据，不进入日志、错误 message、Desktop 偏好或 Renderer localStorage。
- API key、Authorization、完整 resolved profile 和工具快照不进入任务定义。
- 删除写 tombstone 并停止调度；用户可见定义和执行历史立即消失。物理 journal 压缩遵守未来 FileStore generation compaction，不用危险的原地改写伪装硬删除。

## 调度语义

### Core 生命周期

调度器由 `cmd/awaken-core` 随 RunService 启动并在 HTTP ready 前完成：

1. 打开 repository 并恢复任务；
2. 把遗留 `running/queued` execution 封口为 `interrupted`；
3. 校验每条 enabled 定义；
4. 单条无效任务标记 `invalid` 并从调度器移除，不阻止其他任务/Core 启动；
5. 计算 next occurrence 和启动期 misfire；
6. 启动调度 loop；
7. HTTP 才开始对外 ready。

shutdown 顺序：

1. 停止接收新 occurrence；
2. 标记队列中未开始项 cancelled；
3. 请求取消活动 scheduled run；
4. 等待现有 Core graceful shutdown 上限；
5. 未闭合 execution 由重启恢复为 interrupted。

### Desktop 关闭边界

首版调度器只在受管 Core 存活时运行。Desktop 完全退出期间：

- 不运行任务；
- 不使用 OS crontab、launchd 或 Windows Task Scheduler；
- 再次启动时只按 misfire 规则最多合并补一次；
- UI 必须始终展示这一限制，不能用“后台运行”误导用户。

如果未来要求关掉窗口仍执行，应先单独设计 Desktop close-to-tray 或受 lease 管理的 headless Core；不能在本功能里偷偷留下孤儿 Core。

### misfire、时区和 DST

- 每条任务记录最近已处理 occurrence，重启后从该点和当前时间计算。
- 若最新到期点距离当前时间不超过 `misfire_grace_seconds`，合并为一次 `trigger=misfire`；多个漏点不逐个补跑。
- 超过宽限时写 `skipped/MISFIRE_GRACE_EXCEEDED`，再计算下一次。
- 一次性日程超过宽限后写 skipped 并进入 completed。
- DST 不存在的本地时间跳到调度库计算的下一个合法 occurrence；重复的本地时间每个表达式 occurrence 只执行一次。测试必须固定 location 和 clock，不能依赖 CI 机器时区。
- scheduler 使用可注入 Clock 和 Timer，单元测试不得真实等待分钟。

Cron 星期字段把 `7` 兼容为周日 `0` 前，先按范围起点和 step 计算实际星期。例如 `2-7/2` 得到二、四、六，`1-7/2` 才包含周日；不能因范围上界为 7 就无条件补周日。`clock_test.go` 覆盖数值/命名起点、步长、单点范围、组合字段和非法参数。Renderer 的 `describeCronExpression` 只为能完整解释的规则生成中文；不认识的星期步长、月份或组合日期限制保留原 Cron，不得丢掉限制后显示“每天”。对应回归在 `scheduled-tasks/adapter.test.ts`。

### 并发与幂等

- 每任务 semaphore=1，全局 Agent semaphore=2；reminder 不占 Agent semaphore。
- `(task_id, scheduled_for)` 形成 occurrence 幂等键；同一到期点在重启、定时器迟到或 API 重试中只能创建一个 execution，`scheduled` 与 `misfire` 共享该键。
- “立即执行”必须携带 idempotency key；Main/Renderer 网络重试不能创建两次。`consumeIfNeeded` 统一检查 execution trigger，manual 在正常完成和排队 skipped 等所有路径都不推进 occurrence 游标或次数。
- definition version 在 execution 开始时冻结；执行过程中编辑不会改变其 prompt/profile/project。

## 执行、线程与无人值守边界

RunServiceExecutor 等待 [Runtime 的 run 完成信号](../../03_运行时与本地服务/数据存储与重放/实现方案.md#权威与稳定-kind)，与订阅的事件通道分开。run 在订阅前已结束时立即读取记录结果；订阅缓冲溢出时重订阅保留历史，不能提前释放执行名额。处理终态前再次检查完整历史，避免终态和交互门同时到达时漏掉门；取消等待同一个完成信号，不遍历可能为 nil 的通道。`execution_boundaries_test.go` 覆盖订阅前成功、失败和交互门终态，以及 manual 排队跳过不消费次数；`executor_test.go` 继续覆盖运行中取消和超时。当前 macOS 的[真实列表证据](../../../apps/desktop/test-fixtures/runtime-consistency/desktop-schedule-success.png)与[机器记录](../../../apps/desktop/test-fixtures/runtime-consistency/manifest.json)覆盖暂停 Agent 任务保存 `0 9 * * 2-7/2`、立即执行一次、专属线程返回指定文本、列表成功以及完整重启后仍暂停。订阅前终态、并发满后的手动跳过、星期步长的具体触发日期由自动化覆盖；此证据不替代后文完整定时任务矩阵中尚未执行的项目。

### 项目与 TaskScope

触发时用 `project_id` 重新读取当前 active project：

- cwd 为当前 primary folder；
- readable/writable/output roots 为当前全部 folders；
- 零文件夹项目使用现有 session workspace；
- 项目 removed、删除操作中或路径失效时不猜旧路径，execution 记为 `PROJECT_UNAVAILABLE` 或现有 project conflict code；
- 定义中不保存创建时的绝对 roots 快照。

### 模型 profile

- `profile_id=""`：每次触发通过 `src/modelprofile.UserStore.Resolve("")` 解析当时默认 ready profile；
- 显式 ID：每次触发重新 resolve；已禁用、缺 key 或删除时 execution 失败为 `MODEL_PROFILE_UNAVAILABLE`；
- resolved API key 只在内存中转换为 `runtime.ModelProfileConfig`，沿用 ACP control route 已有转换模式；
- 不静默切换显式选择的付费 provider。

### Agent 任务

新增 host-only `RunService.StartScheduledRun`，不向普通 renderer HTTP client开放伪造 source 的旁路。它负责：

1. 解析/建立该任务稳定 thread；
2. 构造 `ClientInfo{EntryPoint:"scheduled_task", Source:"scheduled_task", RequestID:execution_id}`；
3. 使用现有 `StartRun` 的 journal、上下文、工具快照、Composer token 预激活和恢复路径；计划触发时按当前 Skill Registry 重新核对 Skill ID、来源、包根和 `SKILL.md`，并按 Plugin Store 重新核对 Plugin 名称、启用状态、digest 和可用组件，Renderer 保存的路径、digest 或组件数量都不是授权来源；
4. 禁止普通 LLM 标题生成，任务名是 thread 初始标题；
5. 订阅 run 直至 terminal 或超时；
6. 超时调用 `CancelRun`，等待终态后记录 execution。

定时 Agent 不因 token 获得额外工具、不绕过 TaskScope、不自动安装额外 Connector、不改变零审批合同。Computer Use 是否进入该次固定工具快照，仍由触发时的模型视觉能力、全局开关、Host/TCC/Driver readiness 决定。

定时任务保存的是用户当时的结构化 Skill/Plugin/Computer Use 选择，不缓存 Skill 正文、Plugin 组件或宿主隐藏引导。每次触发都重新校验 token；Skill token 作为该次 run 的 `invocation=user_composer` 选择预激活，Plugin 与 Computer Use token 只加入各自 host-owned model instruction 并消费当次固定工具/技能快照。Skill 被删除、禁用或换源，或 Plugin 被禁用、删除、升级/换 digest、失去全部可用组件时，该次 execution 在模型启动前失败，不静默改选同名 identity；未知 capability 同样在模型启动前失败。

无人值守 run 不能无限等待：

- `ask_user`、外部授权、ACP permission 等交互一旦出现，立即以 `SCHEDULED_INTERACTION_REQUIRED` 取消并失败；
- Computer review/handoff 保持 Computer Runtime 的专用 run-bound gate：绝不自动批准、自动接管或自动授予系统权限；用户可在任务 timeout 前进入专属 thread 处理，超时后 Scheduler 取消 run 并记录终态；
- 错误记录只保存 gate 类型和安全错误，不保存 token、二维码、原始 stdout/stderr；
- 用户可从执行记录打开 thread，在普通交互 run 中处理依赖后再手动重试。

### 固定提醒

`reminder` 不调用模型。新增 `RunService.PublishScheduledNotice`：

- 建立/复用同一专属 thread；
- 写 `run_started -> scheduled_notice -> run_terminal(success)` 的 host-owned SemanticJournal 记录；
- 新语义 kind 为 `scheduled_notice`，payload 只含 task/execution identity、任务名和固定正文；
- 09 域映射为 `AWAKEN_SCHEDULED_NOTICE`；
- Workbench 投影专用“定时提醒”卡，不伪装为 user 或 assistant 文本；
- Main 收到 live 事件时使用 Electron `Notification`，点击后聚焦主窗口并打开对应 thread；
- replay 只还原卡片，不重复发系统通知。

### 结果与交付物

Agent 的文本、工具、文件变化和 artifact 沿用普通 run。执行记录只引用 run/thread，不复制 assistant 正文或 artifact 路径。任务历史页跳转 thread 查看完整过程，避免形成第二份 transcript。

`Scheduler.transitionTerminal` 返回持久化是否成功，所有终态的 `execution_finished` 及固定提醒的成功通知以该结果为前提。保存失败保留 journal 中 queued/running 的身份，发出 `notice(status=error)` 和不含输入、凭据或磁盘路径的恢复说明。这里重用 notice 的通知能力，不把错误伪装成完成事件；Core 重启用 `SealInterrupted` 收口，不能为补写结果重放 executor。`terminal_persistence_test.go` 覆盖四种终态的写入失败、独立磁盘读回和中断恢复。

## HTTP、IPC 与事件

目标 HTTP：

```text
GET    /v1/scheduled-tasks
POST   /v1/scheduled-tasks
GET    /v1/scheduled-tasks/{task_id}
PATCH  /v1/scheduled-tasks/{task_id}
DELETE /v1/scheduled-tasks/{task_id}
POST   /v1/scheduled-tasks/{task_id}/pause
POST   /v1/scheduled-tasks/{task_id}/resume
POST   /v1/scheduled-tasks/{task_id}/run
POST   /v1/scheduled-tasks/{task_id}/cancel
GET    /v1/scheduled-tasks/{task_id}/executions
```

- write 请求统一携带 `expected_version`；run/delete 携带 idempotency key。
- create 返回 201，异步 run 返回 202；字段错误 422；版本冲突 409；不存在 404。
- Renderer 不直接持有 loopback URL，通过 preload/Main typed bridge。
- `apps/desktop/src/shared/runtime.ts` 定义 wire/camelCase 转换；不得在 `ScheduledTasksView` 手写 snake_case payload。
- Main 订阅 scheduled task 状态/notice 并转为受控 IPC event，用于实时刷新、原生通知和点击定位；Renderer 页面未挂载也不能丢失 Core durable 状态。
- `execution_started` wire/camelCase 事件携带 `project_id/projectId`、`run_id/runId` 和 `thread_id/threadId`。顶层 `App` 常驻订阅 started/finished：有 thread identity 时立即从 thread authority 对账侧栏，但不切页面、不激活 thread、不抢焦点；`ScheduledTasksView` 只刷新任务列表，不拥有全局 thread 可见性。

新增公开 AG-UI-compatible 事件仅限 thread 内可重放事实：

```text
AWAKEN_SCHEDULED_NOTICE
```

任务 CRUD、next run 和全局队列状态不是 thread 叙事，不塞进 AG-UI；由 scheduled-task HTTP/IPC surface 读取。

定时任务 IPC 使用[本地服务管理](../../03_运行时与本地服务/本地服务管理/实现方案.md)定义的结构化结果。`scheduled-tasks/adapter.ts` 按 `VERSION_CONFLICT`、`TASK_ALREADY_RUNNING` 和 `details.field/reason` 决定表单反馈，错误文案变化不改变分支；旧文本只经共享兼容解析。

| 定义/触发/状态 | `src/scheduledtask` | schema、Cron/日程计算、repository、scheduler、execution、misfire、幂等 | UI、模型实现、工具执行 |
| Agent/提醒线程 | `src/runtime` | 专属 thread、普通 run 复用、scheduled notice、取消/终态 | 定时表达式解析 |
| 模型配置 | `src/modelprofile` | 触发时按 opaque ID 解析 ready profile | 保存到任务定义的 credential |
| HTTP | `src/server/handlers_scheduled_tasks.go`、`router.go` | typed route、状态码、错误映射 | 调度状态 authority |
| Core 装配 | `cmd/awaken-core/main.go` | repository/service 注入、start/stop 顺序 | 第二套 scheduler |
| Main/preload/shared | `apps/desktop/src/main`、`preload`、`shared/runtime.ts` | typed bridge、通知、窗口聚焦、wire normalize | 任务 authority、Cron 校验 |
| Renderer | `ScheduledTasksView.tsx`、`scheduled-tasks/*` | 页面数据适配、模板目录、表单和乐观状态 | 定时器、凭据、FileStore |
| Design System | `AwakenScheduledTasks*` | UI-only 列表、模板窗口、编辑器、历史窗口和状态 | API、Electron、模板业务 payload |
| 协议/Workbench | `src/protocol/agui`、renderer projector | notice live/replay 映射与卡片 | 全局任务管理 |

实现不得把 `setInterval` 当成任务调度器放进 Renderer，也不得复用 Desktop Main 的 Memory Dream scheduler store 作为定时任务 authority。Dream 是单一内部维护策略；用户定时任务需要 Core 级定义、历史和 run ownership。

### 编辑器选择器的定位与滚动

Design System 的 `AwakenScheduledTaskProjectPicker`、`AwakenScheduledTaskDateTimeField` 和 `AwakenScheduledTaskTimezonePicker` 启用 `AwakenPopover.viewportBounded`。这个模式仅用于 portal 到页面根部的选择器：使用 fixed 坐标，由 Floating UI 的 flip/shift/size 计算窗口内 8px 留白后的可用宽高，并通过 `--aw-popover-available-width/height` 传给内容；其他 Popover 的默认策略保持原有行为。

三个选择器的根容器按 border-box 消费可用宽高。项目与时区弹层使用纵向 flex，搜索区不收缩，列表以 `min-height: 0` 承担剩余空间滚动；日期时间弹层高度不足时整体内部滚动，底部操作仍可到达。定位完成前隐藏弹层并暂停焦点管理，项目与时区通过 `initialFocusRef` 将焦点移到搜索框，不再用独立定时器提前聚焦。内容层消费 Escape 并关闭本选择器，阻止外层 Dialog 同时关闭。

`ScheduledTasksView.behavior.test.tsx` 覆盖三个选择器的固定定位与尺寸约束、定位后的搜索焦点、Escape、选择结果以及未提交草稿保留；jsdom 不承担像素布局证明。真实 macOS Desktop 的 `1440×903`、`1152×760` 窗口已验证边缘展开、内部滚动与选择，打开前后 document 宽高均等于视口、横向滚动保持 0。尺寸数据与截图见 [布局验证记录](../../../apps/desktop/test-fixtures/scheduled-picker-layout/verification.json)。Windows/Linux 和其他窗口尺寸未在这次记录中实测。相关命令为 `npm test --workspace @awaken/desktop`、Design System/ Desktop build 与 Desktop typecheck。

## 执行约束

调度实现必须保持以下行为：

- occurrence 幂等，同一任务不并发启动多个 Agent run。
- 修改使用 version CAS，删除幂等；手动执行暂停任务后仍保持暂停。
- Agent 和固定提醒使用专属线程；提醒卡的 live 与 replay 展示一致，只有 live reminder 触发系统通知。
- 通知点击应聚焦窗口并定位线程，日志不能泄露 prompt 或凭据。
- Desktop 完全退出后不运行；重启按 misfire 规则处理，不逐次补跑全部漏掉的周期。

固定提醒的现有验收不能替代完整 Agent、取消、强杀恢复、通知点击和跨平台验证。

## 风险与明确决策

1. **退出后不运行：** 这是 Desktop 生命周期的真实限制，不靠文案掩盖。OS 唤醒是独立后续项目。
2. **固定提醒语义：** 用 host-owned notice，不花模型 token，也不冒充模型回复。
3. **专属线程：** 避免后台任务污染用户任意活动 thread，也自然复用当前 journal/artifact。
4. **profile 只存 ID：** 避免凭据过期与 secret 复制；每次触发重新验证。
5. **项目只存 ID：** 避免项目文件夹编辑后继续使用陈旧权限根。
6. **单任务并发 1：** 当前 RunService 的 thread busy 语义决定同一专属 thread 不能安全并行。
7. **Qwenpaw 日期动态化：** 保留模板意图，不复制已经过期的演示日期。

## 自动化

### Schema、Cron 与日程

必须覆盖：

- 五段 Cron 接受/拒绝、3/4/6 段拒绝、空表达式拒绝；
- `0/7` 周日与 `sun` 规范化，列表、范围、step；
- 每小时、每天、每周、自定义表达式；
- IANA timezone 有效/无效；
- DST 跳时与重复时间；
- 不重复、每 N 天、never/until/count；
- until 晚于 run_at、count/range 上限；
- 所有 next occurrence 都严格晚于基准或符合明确 misfire 计算；
- fake clock/timer，无真实分钟等待。

### Repository 与恢复

必须覆盖：

- create/update/pause/resume/delete 的 version CAS；
- 同 idempotency key 重试只产生一个 task/execution；
- `state.json` 缺失/损坏从 journal 重建；
- journal 尾部半条截断、中段损坏 fail closed；
- 文件/目录权限、atomic replace、跨进程锁；
- prompt、API key 和 Authorization 不进入日志/错误/snapshot；
- orphan execution 从 queued/running 恢复为 interrupted；
- tombstone 后列表、get 和 scheduler 均不可见；
- 最近 50 条执行历史顺序和边界。

### Scheduler

必须覆盖：

- start/stop 幂等；
- 单条坏定义不阻止 Core 和其他任务启动，坏任务变 invalid；
- pause 后没有 scheduled execution，resume 重新计算 next run；
- 手动执行暂停任务成功且不消费 count；
- 同一 occurrence 去重；
- 单任务防重入与全局 Agent 并发上限；
- 多个漏点合并一次；
- 宽限内 misfire 执行，宽限外 skipped；
- 一次性任务 success/skipped 后 completed；
- repeat count 对 scheduled/misfire 成败/跳过计数，manual 不计数；
- shutdown 不接收新 occurrence，活动 execution 可恢复封口。

### Agent、提醒与边界

必须覆盖：

- 触发时按 project ID 重新解析 primary/all folders；
- 零文件夹项目使用 session workspace；
- removed/project operation/path missing 均 fail closed；
- 空 profile 每次按 `scheduled_task` 用途 profile → 当前默认 profile 重新解析；显式 profile 缺失、停用或凭据不可用时不 fallback、不切协议/供应商；
- task definition、journal、wire 不出现 API key；
- Agent execution 进入稳定 dedicated thread，下一次继续同一 thread；
- 不同 task 使用不同 thread；
- 用户删除 dedicated thread 后，Agent/提醒的下一次执行各自重建 thread 并以 CAS 更新任务绑定；
- thread busy 不写入其他 thread；
- reminder 不调用模型，写 scheduled notice 和 terminal；
- ask_user、外部授权、ACP permission 立即失败为 interaction required；
- timeout 触发 CancelRun 并形成唯一 terminal；
- Agent artifact 只存在正常 transcript，execution record 只引用 run/thread；
- 删除 task 不删除 thread/artifact。

### HTTP、IPC 与 UI

必须覆盖：

- 所有 route 的 201/202/404/409/422/500 映射；
- snake_case/camelCase typed normalization；
- preload 只暴露窄方法，不暴露 Core URL 或任意 fetch；
- 主窗口来源校验；
- Renderer 乐观启停失败回滚；
- 页面卸载/切换不取消后台 execution；
- live reminder 只发一次系统通知，replay 不发通知；
- 通知点击聚焦并打开正确 thread；
- 模板目录恰好 10 项、ID 唯一、分类 4/6；
- 每个模板字段完整、时区正确、动态时间严格在未来；
- 模板选择不创建任务，只有编辑器保存才调用 create；
- 模板字段可编辑，保存 template origin；
- Agent 编辑器 `/` Skill 与 `@` Computer Use/Plugin 菜单复用首页完整目录、plugin Skill 排除规则、collapsed caret、行首/whitespace trigger 边界、句中替换、滚动、筛选和 catalog revision 规则；即使 Plugin 目录为空，`@` 仍显示 Computer Use，只含 Skill 的有效 Plugin 仍可被 `@` 选择；先输入中英文/数字再移回句中补空格并输入 marker 必须出现菜单，紧邻普通文字直接输入 marker 不得出现，选择后仅替换该 query 并保存结构化 `composer_tokens`；创建/编辑/HTTP round-trip 不丢失后续正文、token 顺序、来源、Skill 锚定路径、`capabilityId`、Plugin digest 和 `leadingText`；提醒任务拒绝 token；

## 真实 Desktop 验收

必须按根 README 正式入口打开真实 `Awaken Dev`，使用专用测试项目和可识别名称，留下截图/录屏或 manifest。

### DT-SCHED-01 导航与空状态

1. 确认左侧一级导航顺序为“连接器 → 技能 → 定时任务”。
2. 进入页面，确认空状态同时提供“创建任务”和“从模板创建”。
3. 切换连接器/技能/项目/thread，确认当前 run 和项目选择不被意外清空。

### DT-SCHED-02 从模板创建 Agent 任务

1. 打开模板窗口，切换循环/日程分类。
2. 选择“工作日科技新闻早报”或其他 Agent 模板。
3. 确认只打开预填编辑器、尚未出现在列表。
4. 打开项目下拉选择器，在项目较多时确认弹层可滚动、搜索可筛选，选择测试项目后把计划改为 1–2 分钟内的未来时间并保存。
5. 在 Agent prompt 输入 `/`，确认目录、筛选、方向键/Enter/Tab/Escape 与首页一致；选择一个项目或全局 Skill，保存后重新编辑仍显示同一个结构化 token。再输入 `@computer`，确认出现 Computer Use，选择后保存/重开仍保留 `capabilityId=computer-use` 的原子 token；Computer readiness 不满足时不得伪装成可执行，满足时由固定工具快照提供三个 `computer_*` 工具。
6. 确认列表、next run、template origin 和时区。
7. 切回 Workbench、连接器或技能页面，等待执行；确认专属 thread 在任务仍运行时就出现在正确项目下，当前页面和焦点不被抢走，并正常展示用户 prompt、所选 Skill 的 `skill_activated`、模型过程、工具和 terminal。
8. 打开执行记录并跳转同一 thread。

### DT-SCHED-03 从模板创建固定提醒

1. 选择“休息提醒”或“生日提醒”。
2. 修改为短期未来时间后保存。
3. 到期只出现 host-owned 定时提醒卡，不出现模型调用或 assistant 冒充文本。
4. Desktop live 时系统通知只出现一次；点击聚焦正确 thread。
5. 重开 thread 后卡片仍在，但不重复系统通知。

### DT-SCHED-04 生命周期

1. 创建、编辑、暂停、恢复。
2. 暂停期间等待一次到期点，确认不执行。
3. 对暂停任务立即执行，确认成功且任务仍暂停。
4. 运行中重复点击立即执行，确认稳定冲突提示。
5. 取消运行，确认 run 和 execution 均为 cancelled。
6. 删除任务，确认列表移除但 thread 与 artifact 保留。
7. 保留任务并删除其专属 thread，再立即执行，确认新 thread 创建、任务重新绑定且后续执行继续复用新 thread。

### DT-SCHED-05 重启与 misfire

1. 创建一个 1 分钟循环任务，宽限设为 5 分钟。
2. 在下次到期前完整关闭 Desktop，跨过至少一个到期点后重开。
3. 确认只合并补一次 `misfire`，不按漏掉次数轰炸执行。
4. 改用 0 秒或很短宽限重复，确认只记 skipped。
5. 在 Agent 正在运行时强制结束开发 Desktop/Core，重开后确认 execution 为 interrupted，普通 transcript 恢复且不自动重放副作用。

### DT-SCHED-06 项目、模型与交互失败

1. 创建任务后修改项目主文件夹/文件夹集合，触发后确认使用新 TaskScope。
2. 移除项目，确认任务不在旧路径执行。
3. 分别验证显式 profile、`scheduled_task` 用途 profile 和当前默认 profile 的优先级；禁用显式 profile 或移除 key，确认 `MODEL_PROFILE_UNAVAILABLE` 且不切协议/provider。
4. 使用必然触发 ask_user 或外部授权的 prompt，确认无人值守 run fail fast，页面给出可恢复提示。
5. 使用 Computer Use 任务触发一次需要 review/handoff 的动作，确认不会自动批准；在任务 timeout 前从专属 thread 处理可继续，未处理则超时取消并形成唯一终态。

### DT-SCHED-07 退出限制

1. 完全退出 Awaken，不留下 Core。
2. 到达计划时间，确认没有暗中运行或孤儿进程。
3. 重开后按 misfire 配置表现。
4. 页面说明与实际行为一致，没有“关闭后仍在后台执行”的声明。

## 内置模板目录的实现

模板定义 owner 为 `apps/desktop/src/renderer/scheduled-tasks/templates.ts`。Design System 只接收卡片数据和回调，不读取该目录或构造 Core payload。

### 相关验证证据与适用范围

真实开发版用暂停的 Agent 任务手动执行一次，k3 返回预期标记，成功记录可从执行历史打开对应线程；重启后任务仍暂停，历史和输出仍存在。见 [执行记录](../../../apps/desktop/test-fixtures/deep-audit-fixes/schedule-history.png)、[模型输出](../../../apps/desktop/test-fixtures/deep-audit-fixes/schedule-output.png) 和 [验证记录](../../../apps/desktop/test-fixtures/deep-audit-fixes/verification.json)。真实用户存储没有注入磁盘故障；终态落盘失败及 interrupted 恢复由隔离仓库测试覆盖。
