# 连接器来源、生命周期与重启边界

## 1. 权威范围

本文档唯一定义 connector source 合并、active ownership、builtin/local 持久化差异、connect/disconnect 和重启限制。

## 2. 定义来源

| 来源 | 当前实现 | 优先级 | 备注 |
| --- | --- | --- | --- |
| builtin | `source_builtin.go` 编译时 Go definitions | 0（最高） | 七个 |
| team | `source_team.go` 的 noop `TeamConnectorSource` | 2 | 当前返回空列表，无远程拉取 |
| local | `~/.awaken/connectors.json` | 3 | 每项内联一个 MCP config |

Registry 按 Connector ID 合并。优先级高的 definition 胜出；当前实现会跳过输家，不会把输家保留为另一条 `shadowed` connector snapshot。`ConnectorStatus.ShadowedBy` 只能从某些 dynamic server 所有权冲突中推导，不是完整的 source-conflict 记录。

local 配置的当前最小字段为 `id`、`displayName`、`category`和一个有效 `mcp` config。当 `authType` 空缺时，实现默认为 `oauth2`，不是 `none`。

## 3. 进程内 active ownership

`connectors.Registry.active` 以 `connectorID -> {connected, serverKeys}` 记录当前进程内所有权。Connector 只在 active entry 存在时才从这些 server snapshot 推导状态。

推导优先级：

```text
any connected -> connected
else any needs-auth -> needs-auth
else any failed -> failed
else any pending -> pending
else -> disconnected
```

这个 active map 不是 durable store，也不会在启动时从已持久化 MCP server 反向重建。

## 4. builtin 的当前 connect/disconnect

### Connect

```text
ConnectorDefinition.McpConfigFactory
  -> 生成 server config
  -> LoadUserConfig
  -> 写入/ 覆盖同名 user MCP server
  -> SaveUserConfig
  -> Manager.Start
  -> active[connectorID] = serverKeys
```

builtin 不使用 `InjectDynamic`；它们是“快捷添加 user MCP server”。Registry 在发起 `Manager.Start` 后即写 active entry，HTTP handler 也可返回成功 message；此时底层 server 可能仍是 `pending` 或随后进入 `failed`。

如同名 user MCP server 已存在，builtin connect 会以 factory 结果覆盖它，不保留可恢复的被覆盖副本。因此 connect 是会改写 userData 的操作，验收时不可当作只读按钮。

### Disconnect

```text
active serverKeys
  -> 从 user MCP config 删除
  -> Manager.Remove
  -> SaveUserConfig
  -> 清空 active entry
```

这也是持久性删除，不是仅断开当前 session。

## 5. local 的当前 connect/disconnect

local connector 把 inline MCP config 交给 `Manager.InjectDynamic(connectorID, config)`，server scope 为 `dynamic`。Disconnect 使用 `RemoveDynamic`，且 Manager 只接受 owner connector ID 移除。

local connector 定义文件会跨重启，但 dynamic server 和 active ownership 不跨重启。重启后需要用户重新发起 connect。

## 6. 重启后的已知所有权缺口

生产启动顺序是：

```text
buildMCPManager -> 加载 user/project MCP server
buildConnectorRegistry -> 加载 definitions，active 为空
```

这导致：

- 上次通过 builtin connector 写入的 user MCP server 会被 Manager 重新加载，甚至可以是 connected。
- 同一 builtin connector 卡片仍显示 disconnected，因为 `active` 没有该 server 的 owner 记录。
- 该 server 同时作为“用户安装 MCP”卡片出现，产品层可见两种不一致视图。
- 再点 builtin “连接”会再次写入 factory 默认配置，可覆盖用户对同名 server 的编辑。

在代码实现 owner 持久化或可证明的启动推导前，不得将该流程记载为“connector 跨重启保持连接状态”。

## 7. API 动作语义

具体 method/path 与注册条件只查 [09 route 清单](../09_AGUI与A2UI协议/HTTP与SSE接口契约.md)。

| 动作 | 当前语义 |
| --- | --- |
| list | 列出 resolved definitions 与按 active map 推导的状态 |
| connect | 按 source 写 user MCP config 或注入 dynamic server；不完成 OAuth |
| disconnect | 仅允许当前 active connector；按 source 删 user config 或 remove dynamic |

断开一个重启后显示 disconnected 但实际 MCP server 已存在的 builtin connector，会得到 `NOT_CONNECTED`；必须转到 MCP server 管理面处理实际配置，不能假设 connector owner 还在。

## 8. 不变量

- Connector 定义合并和 MCP server 配置 scope 是两个不同的优先级系统。
- builtin connect/disconnect 会改写 user MCP config；local connect/disconnect 不应假装已持久化 dynamic state。
- 没有 active owner 证据时，Connector 不得声称自己拥有某个同名 MCP server。
- 任何会覆盖/删除 user MCP config 的 UI 验收都必须使用隔离 profile，不得在真实用户数据上“点一下看状态”。
