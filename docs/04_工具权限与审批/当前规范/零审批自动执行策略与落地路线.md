# 零审批自动执行策略与落地路线

## 文档定位

本文档定义 Awaken 在工具权限、执行安全、沙箱和多代理继承上的目标产品策略。目标不是让用户在运行中频繁审批，而是让 Agent 在默认自动执行的前提下，仍然被内置的运行时边界、安全门和可恢复机制约束。

本文档面向：

- `src/tool` / `src/tools` 的工具接口与内置工具实现
- `src/agentcore` 的工具决策、执行编排与多代理控制
- `src/runtime` / `src/server` 的 run 生命周期与事件输出
- `apps/desktop` 的用户可见状态、停止能力和结果可视化

## 目标

- 用户体验默认不依赖中途审批。
- Agent 默认具备强工具调用能力。
- 安全措施内置在 runtime，而不是交给用户点按钮。
- 文件操作默认自动执行，但必须被严格约束在受控范围内。
- shell 保持强能力，但不与普通文件编辑混成同一能力面。
- 普通 subagent 默认继承父代理边界；只读 guardian/review agent 明确收紧。
- Mac 与 Windows 共享一套权限模型，但允许不同平台使用不同执行后端。

## 非目标

- 不把“审批中心”继续作为主产品路径。
- 不依赖 prompt 文本承担主要安全责任。
- 不要求 Mac 与 Windows 第一阶段拥有完全相同的 shell 沙箱实现。
- 不为单个工具单独发明一套权限系统。

## 当前问题

当前实现存在以下结构性问题：

- `ask` 仍然是系统里的显式能力面，容易把产品做成“Agent 每走一步都等用户批准”。
- `apply_patch` 的删除语义仍是永久删除，不符合本地桌面产品的默认预期。
- `shell` 仍然是高风险宿主机执行能力，但当前安全边界主要依赖策略拒绝，而不是执行隔离。
- 普通文件编辑和系统级命令还没有被明确拆成两条产品能力链。
- 多代理继承与收紧规则还没有形成正式契约。

## 核心原则

### 原则 1：零审批是产品目标，不是去掉安全

主路径不再把 `ask -> 用户批准 -> 继续执行` 作为默认交互。运行时只保留三类决策：

- `allow`：直接执行
- `deny`：拒绝执行，并返回结构化 `tool_result`
- `transform`：自动重写为更安全的执行方式后再执行

用户看到的是“系统做了什么、拒绝了什么、为什么拒绝”，而不是持续承担审批责任。

### 原则 2：安全必须内置在 runtime

真正的安全边界必须位于工具执行器、路径校验、沙箱适配器和多代理控制层，而不是依赖：

- prompt 提醒
- UI 弹窗
- 用户临时判断
- 模型自觉

### 原则 3：文件链优先于 shell

日常创建、修改、删除、移动文件应优先走受约束的 typed tool，而不是 shell。Awaken 要把以下能力视为同一条“文件链”：

- 新建文件
- 修改文件
- 移动文件
- 删除文件

这条链默认自动执行，但必须严格受限于 `workspace_root` 与 `writable_roots`。

### 原则 4：shell 是更强能力层

shell 不是普通编辑工具，而是系统操作能力。它应单独分级、单独收口、单独验收。任何可以稳定落到文件链的需求，都不应优先走 shell。

### 原则 5：默认可恢复

任何 destructive 操作都应优先设计为“可恢复”而不是“可逆转困难”。首要规则：

- 删除文件默认进入回收站，不做永久删除
- 文件链只允许写入受控目录
- 敏感路径默认只读或拒绝

### 原则 6：普通 subagent 继承，guardian 显式收紧

多代理体系中，普通 subagent 默认继承父代理的权限边界，这是高效协作所需；但必须同时提供一条显式只读的 guardian/review 路径，用于后台审查、复核和风险判断。

### 原则 7：共享权限模型，分平台执行

Mac 与 Windows 必须共享同一套上层权限契约；但底层执行后端可以不同。Awaken 不应把某个平台的特定沙箱实现写死为系统抽象本身。

## 目标架构

### 1. 统一执行意图层

每次工具调用在真正执行前，都先被转换成统一的 `ExecutionIntent`：

- `tool_name`
- `tool_kind`
- `requested_action`
- `paths`
- `network_scope`
- `workspace_root`
- `writable_roots`
- `subagent_origin`

`tool_kind` 至少分为：

- `file_chain`
- `shell_command`
- `mcp_app`
- `review_agent`

### 2. 统一安全决策层

运行时根据 `ExecutionIntent` 计算 `ExecutionDecision`：

- `allow`
- `deny`
- `transform`

`transform` 用于把高风险请求改写成更安全形式，例如：

- 把 shell 文件改写请求重定向到 `apply_patch`
- 把永久删除改写成“移到回收站”
- 把越界路径写入改写成拒绝

### 3. 统一执行 profile 层

所有工具执行都落到共享的 `ExecutionProfile`：

- `approval_policy`
- `permission_profile`
- `sandbox_policy`
- `sandbox_permissions`
- `network_policy`
- `env_policy`
- `visibility_policy`

推荐的内建 profile：

- `guardian_read_only`
- `workspace_read_only`
- `workspace_write`
- `open_world_restricted`
- `danger_full_access`

### 4. 统一执行器层

运行时不直接让工具随意碰宿主机，而是统一经过执行器：

- `FileChainExecutor`
- `ShellExecutor`
- `McpExecutor`
- `GuardianExecutor`

### 5. 统一观测层

零审批不等于零可见性。系统必须始终可观测：

- 执行了哪个工具
- 命中了哪个 profile
- 哪个请求被 transform
- 哪个请求被 deny
- 删除是否进入回收站
- subagent 继承了哪些边界

## 工具分层策略

### 文件链

文件链是主产品能力，默认自动执行。

约束：

- 只能在 `workspace_root` / `writable_roots` 内执行
- 强制经过 symlink 逃逸检查
- 敏感路径默认拒绝
- 删除默认进入回收站
- 不依赖 shell

敏感路径至少包括：

- `.git/`
- `.env`
- 密钥、证书、凭据文件
- Agent 自身元数据目录
- Desktop/runtime 的本地配置目录

### shell

shell 是更高风险的本机能力，应至少分为三层：

- `inspect_read_only`
- `workspace_mutation`
- `open_world_system`

规则：

- `inspect_read_only` 可在受控条件下自动执行
- 能落到文件链的写入请求，应优先 transform 到文件链
- `workspace_mutation` 不是日常主路径
- `open_world_system` 默认必须受更强 profile 约束

### MCP / app

MCP / app 工具必须有显式风险注解，至少包含：

- `read_only`
- `destructive`
- `open_world`
- `requires_auth`

缺失风险注解时，默认按高风险处理，而不是默认放行。

### guardian / review agent

guardian/review 只做只读复核，不做状态变更，不做继续放权，不触发新的开放式执行链。其 profile 固定为：

- `approval_policy = never`
- `permission_profile = read_only`
- `network_policy = restricted`

## 多代理继承规则

### 普通 subagent

普通 subagent 默认继承父代理：

- `workspace_root`
- `writable_roots`
- `permission_profile`
- `sandbox_policy`
- `network_policy`

普通 subagent 不得自动扩权。

### guardian / review agent

guardian 不继承父代理的高权限 profile，而是强制收紧到只读 profile。

### 规则总则

- 普通 subagent：可继承，不可扩权
- guardian/review：显式收紧
- 任一子代理都不得绕过敏感路径保护和回收站删除语义

## Mac 与 Windows 的平台策略

### 共享层

以下能力必须完全跨平台共享：

- `ExecutionIntent`
- `ExecutionDecision`
- `ExecutionProfile`
- 文件链路径校验
- 敏感路径规则
- subagent 继承规则
- guardian 收紧规则
- 回收站删除抽象接口

### 平台执行适配

应抽象出：

- `SandboxAdapterMac`
- `SandboxAdapterWindows`
- `TrashAdapterMac`
- `TrashAdapterWindows`

要求是“同 contract，不同 backend”，而不是“同 backend”。

### 分支策略

Mac 与 Windows 不应各自维护长期平台分支。Awaken 在工具权限、沙箱和多代理边界上的产品真相必须收敛到同一个 `main`。

禁止的做法：

- 长期维护 `mac` / `windows` 两条平台主线
- 在不同平台分支上分别演化权限模型
- 让敏感路径规则、删除语义、subagent 继承规则在不同平台分支漂移

允许的做法：

- 在 `main` 上维护共享的权限模型与产品契约
- 按能力切片创建短期实现分支
- 在同一阶段内并行开发不同平台 adapter，但最终都合回 `main`

推荐的短期分支粒度是按能力切片，而不是按平台长期分叉。例如：

- `codex/execution-profile-contract`
- `codex/trash-adapter-mac`
- `codex/trash-adapter-windows`
- `codex/shell-sandbox-mac`
- `codex/shell-policy-windows`

分支策略总则：

- `main` 是唯一长期产品主线
- 平台差异只进入 adapter / executor 实现层
- 共享 contract 先进入 `main`
- 某个平台未准备好的能力，在 `main` 中 fail-closed 或降级，不通过长期平台分支规避

### 平台现实约束

第一阶段不要求 Mac 与 Windows 同时拥有等价的 shell 沙箱强度。若某平台缺乏成熟 native sandbox，则采取以下降级原则：

- 文件链保持完整强约束
- shell 收紧为更保守策略
- 无法可信隔离的 shell 能力直接 deny

## 删除语义

删除行为统一定义为：

- 对文件链中的删除与覆盖前删除，一律使用“移到回收站”
- 用户明确要求永久删除时，也不进入主产品默认路径

运行时需要统一接口：

- `TrashPath(path string) error`

不允许任意工具各自直接 `os.Remove`。

## 事件与用户可见性

用户不再处理中途审批，但必须看得见结果。Desktop 至少展示：

- 自动执行的工具调用
- 被系统拒绝的工具调用
- transform 后的实际执行方式
- 文件改动列表
- 删除已进入回收站的提示
- 当前运行使用的 profile 摘要

UI 应强调“系统已内置保护”，而不是“请你决定要不要继续”。

## 分阶段落地路线

### Phase 1：文件链成为主路径

目标：

- `apply_patch` 默认自动执行
- 写入严格受 `workspace_root` / `writable_roots` 约束
- 删除统一进入回收站
- 补齐敏感路径拒绝

完成定义：

- 文件增删改移动不再依赖审批 UI
- 删除不会永久删除
- 越界与敏感路径写入返回结构化拒绝结果

### Phase 2：shell 独立分级

目标：

- shell 不再承担普通文件编辑主路径
- 引入 `inspect_read_only / workspace_mutation / open_world_system`
- 增加 shell 到文件链的 transform 逻辑

完成定义：

- 常见文件编辑需求不会优先落到 shell
- shell 被清晰分层并能被观测

### Phase 3：统一执行 profile

目标：

- 实现 `ExecutionIntent` / `ExecutionDecision` / `ExecutionProfile`
- 所有执行型工具走统一执行器

完成定义：

- 工具决策不再分散在多个局部规则中
- Agent runtime 能输出稳定的决策来源

### Phase 4：多代理继承与 guardian 收紧

目标：

- 普通 subagent 继承父边界
- guardian/review agent 固定只读

完成定义：

- 子代理不能扩权
- 复核代理不会触发新的高风险执行

### Phase 5：双平台 shell 收口

目标：

- 接入 Mac shell sandbox adapter
- 接入 Windows shell adapter
- 在缺失可信隔离的平台采用更保守策略

完成定义：

- Mac 与 Windows 共享同一套上层权限模型
- 平台差异体现在 adapter，而不是产品契约分裂

## 验收标准

### 用户体验验收

- 用户完成常见文件任务时不需要任何审批点击
- 用户能清楚看到做了什么、改了什么、拒绝了什么
- 用户可以随时停止 run

### 安全验收

- 文件链无法写出 `workspace_root` / `writable_roots`
- symlink 逃逸被拦截
- 敏感路径默认拒绝
- 删除默认进入回收站
- 普通 subagent 不能扩权
- guardian 始终只读

### 平台验收

- Mac 与 Windows 对文件链行为一致
- Mac 与 Windows 都有统一 profile 概念
- 某平台缺失 shell 沙箱时，系统能明确降级而不静默裸奔

## 最终产品表述

Awaken 的目标产品能力不是“审批中心”，而是：

> 一个零审批、默认自动执行、强工具能力、但受运行时内置边界严格约束的本地 Agent。

面向用户的承诺应是：

- 默认自动执行
- 默认不打断
- 默认可恢复
- 默认有边界
