# 本地服务管理 · 实现方案

本文说明代码职责、数据与接口、异常恢复和验证方法。功能范围及用户操作见[需求文档](需求文档.md)。

## 状态机与 owner

[`apps/desktop/src/main/runtime-supervisor.ts`](../../../apps/desktop/src/main/runtime-supervisor.ts) 拥有状态：

```text
stopped -> starting -> running -> stopping -> stopped
                    \-> crashed
```

- `starting`：选择新端口、构造受控环境、启动 child、轮询健康检查。
- `running`：健康检查已成功，renderer 才能获得可用 runtime。
- `crashed`：未处于显式 stop 流程的 child 退出。
- `stopping`：先请求应用级 shutdown，再升级为进程信号/强制结束。

启动默认最多 3 次，健康检查总时限 10 秒、轮询间隔 200 ms。generation token 隔离旧 start/restart 回调，避免一次迟到的健康检查把新进程状态覆盖。

## Main 与桌面调用边界

`apps/desktop/src/main/index.ts` 负责应用生命周期、窗口、事件流和服务装配。服务创建完成后、窗口创建前，分别注册 `runs-ipc.ts`、`projects-ipc.ts`、`models-ipc.ts`、`extensions-ipc.ts`、`plugins-ipc.ts`、`files-ipc.ts` 和 `computer-ipc.ts`。各注册函数显式接收已初始化的服务；窗口引用通过 getter 取得当前窗口，保留来源和窗口存活校验。

`main/runtime-http.ts` 统一处理有正文和无正文请求的 HTTP 错误。需要领域错误的 run/thread（含订阅建立）、ACP、插件与定时任务调用由 `main/runtime-request.ts` 包装成 `{ok:true,value}` 或 `{ok:false,issue}`；`issue` 保留错误码、HTTP 状态和安全字段提示。preload 传递可序列化结果，`renderer/runtime/client.ts` 解包为 `RuntimeRequestError`。业务结果本身的 `ok` 不被外层包装解释。订阅建立失败时 preload 清理本地 handler，Renderer 按 `RUN_NOT_FOUND` 停止重连；不依赖该错误的显示语言。旧错误文案的兼容解析只放在 `shared/runtime-request.ts`，页面不再自行解析 Electron 前缀。

同一次 Desktop 构建中的固定 bridge 方法为必需接口；缺少实现由 TypeScript 检出，不以可选方法和空列表掩盖。桌面两份 tsconfig 启用 `noUnusedLocals` 与 `noUnusedParameters`。`main/runtime-request.test.ts` 验证错误码跨序列化、去敏、void 和业务结果包装。

## 环境与数据根

Desktop 向 core 注入：

- `AWAKEN_CORE_ADDR`：本次随机 loopback 地址；
- `AWAKEN_RUNTIME_MANIFEST`：打包的主运行时 manifest；
- `AWAKEN_USER_DATA_DIR`：当前 launch mode 的 Electron userData，供桌面偏好、宠物、旧状态兼容和测试隔离使用；
- `AWAKEN_HOME`：由 Main 从用户主目录确定的业务数据根 `~/.awaken`，承载 FileStore、模型配置、user MCP server 配置和 connector 认证 metadata；其中 user MCP 配置唯一位于 `config/mcp-servers.json`；
- `AWAKEN_DEFAULT_WORKSPACE`：始终注入。值为用户明确选择过的 workspace；没有任何用户选择时注入空值，core 视为"无默认 workspace"启动，不回退 cwd 或用户主目录。用户主目录不再被隐式注册为默认项目；startRun 仍要求每次 run 携带有效 workspace。
- `AWAKEN_PROXY_POLICY` 与 `AWAKEN_SYSTEM_PROXY_SNAPSHOT`：Main 观察到的跨平台网络策略和无凭据系统 route；Core 启动后继续通过 authenticated control route 接收 generation 更新。完整优先级、恢复与平台边界见[跨平台网络代理与恢复](../网络代理与恢复/实现方案.md)。

启动前移除 `AWAKEN_CONFIG_DIR` 和历史 LLM provider/API key 环境变量，避免 shell 环境意外改变 Desktop 身份或泄露旧凭据。模型 key 由 05 域的 `~/.awaken/.env` 文件契约管理。MCP user config 不从 `AWAKEN_USER_DATA_DIR` 或任何旧位置迁移、导入或 fallback；没有 default workspace 时 project scope 缺席，但 user scope 的管理与连接不受影响。

## 停止与崩溃恢复

正常 stop 先调用 09 协议域定义的 shutdown 动作，最多等待 2 秒，再发送平台对应的 graceful signal；约 3 秒后仍未退出则强制结束，约 3.5 秒完成 stop 收口。Unix 使用 `SIGTERM`/`SIGKILL`，Windows 使用受支持的中断与 `taskkill` 路径。

core 另提供只读 route `GET /v1/runtime/activity`，返回当前 in-flight run 计数（`active_run_count`、`cancelling_run_count`、`observed_at`），供 Main 在更新重启等维护操作前判定运行时是否仍有活动 run；route 注册条件与字段契约由 09 协议域的 HTTP/SSE 接口契约唯一拥有。

supervisor 只保留最多 1,000 条当前进程日志；重启会清空内存日志缓冲，这不是审计或会话存储。

core 异常退出后状态为 `crashed`。重新启动会恢复线程历史，但不会恢复旧 child 中的 goroutine、SSE stream 或 Office 子进程。开放语义事实如何封口由 [SemanticJournal 与重放](../数据存储与重放/实现方案.md) 定义。

Windows 的 manifest PID 存活判定不能只以 `OpenProcess` 成功为依据：已经退出的进程对象在仍有句柄引用时仍可能被打开。Core 与 launcher 必须进一步读取进程退出状态，仅将 `STILL_ACTIVE` 判为存活；否则旧 `runtime/core.json` 会被误判为另一个运行实例，三次启动均以 `runtime manifest owned by another running instance` 失败，并使 Renderer 进入 `Awaken needs restart`。退出状态判定通过后，旧 manifest 可由新 Core 的原子 compare-and-swap 正常替换，不需要用户手工删除 userData。

## 必须保持的规则与当前不支持

- 正式 Desktop 必须使用随机 loopback 地址，不得把固定端口写入 renderer 或文档。
- renderer 不得自行 spawn core 或持有独立的 runtime lifecycle。
- userData、`AWAKEN_HOME`、manifest 和 workspace 必须显式传入；不得依赖调用者终端当前目录推断身份。
- `AWAKEN_HOME/config/mcp-servers.json` 是 user MCP server 配置的唯一 authority；无 default workspace 不能使 user scope 管理面不可用。
- stop 必须有 graceful -> force 的有界升级，不能留下孤儿 core。
- 当前没有把外部远程 runtime URL 作为正式 Desktop 产品入口。
- 当前不保证 crash 后自动续跑 active run，只保证可确认历史恢复。
- 当前不把已开始输出、可能产生费用或外部副作用的请求因代理切换而盲目重放；只保证安全的新连接读取最新 route。

## `awaken-acp` 入口

除 Desktop 外，Awaken 还提供一个小型 stdio ACP Agent 入口 `cmd/awaken-acp`。它由 `src/acp/agentbridge` 实现，行为如下：

- 通过 `--startup=desktop|core|fail` 指定没有 ready Core 时的策略；默认 `desktop`。
- 复用同一 userData identity 的现有 Core；没有时按策略拉起 Desktop 或启动一个受 lease 管理的 headless Core，禁止无约束多 Core 写同一 userData。
- Desktop 在启动前会先读取同一 userData 的 manifest：若存在存活且 identity 校验通过的 headless Core，则进入 `external-attached` 状态并创建 desktop lease，不再 spawn 第二个 Core。
- Core 在 `<AWAKEN_USER_DATA_DIR>/runtime/core.json` 发布 manifest（含随机 loopback base URL、control token、runtime identity 和 PID），launcher 校验 identity、PID 存活和 authenticated `/v1/control/runtime/identity` 后 attach。
- attach 后通过 authenticated control routes 创建 bridge lease，并每 10 秒 heartbeat；stdio EOF 或 signal 触发 5 秒有界清理，cancel active run、close session、释放 lease。
- 不执行模型与工具，只转发 ACP session lifecycle 和 prompt 到 Core HTTP routes。

模型配置由 Core 从 canonical `~/.awaken/config/models.json` 与 `~/.awaken/.env` 只读解析。`session/new` 只向 client 返回 enabled + ready profile 的非敏感 selector；client 可提交 opaque profile ID，不能提交 provider、Base URL、运行参数或 API key。未选择时使用默认 ready profile，否则回退首个 ready profile。profile/API key 不得写入 manifest、日志、journal、Renderer 或 ACP wire。

`--startup=core` 会移除继承环境中的 `AWAKEN_HOME` 覆盖并固定注入当前用户的 `~/.awaken`，因此只启动受管 Core，不需要 Desktop 或 Electron credential helper。配置损坏、无可用 profile、显式选择已禁用/缺 key profile时返回 `ACP_MODEL_PROFILE_UNAVAILABLE`，不静默切换付费 provider。

`awaken-acp` 是机器调用入口；仍禁止用户直接运行和长期维护裸 `awaken-core`。

必须按根 README 的 `open:desktop` 打开真实 `Awaken Dev`，验证服务重启、新 run 的可展示 reasoning 在旧线程中重放且不重复、inline/fork Skill、provider readiness，以及消息工具不会恢复为待审核状态。安装版存在时不得被开发入口关闭。修复前未写 `reasoning_summary` 的旧 run 不要求从 provider opaque state 补造过程历史。还必须验证：缺少 Python/LibreOffice/Poppler/FFmpeg 不阻止 Desktop；已有工具被直接复用；一个真实缺失依赖由 Agent按 Skill/Shell 安装后重试成功，后续 run 不重复安装；按[跨平台网络代理与恢复](../网络代理与恢复/实现方案.md)在 macOS/Windows 分别切换系统代理和 loopback 代理监听器，验证模型、MCP 和 CLI 新连接恢复。Gallery、mock、直接 Core API 和旧截图只能辅助。

本轮未实际执行的 Desktop 或 Windows/Linux 实机步骤必须逐项报告。自动化通过不等于 host 依赖发现、Agent 安装或文件生成与发布链路在所有平台通过。

## 使用行为与实现细则

### 当前产品行为

Desktop 主进程启动本地 Core，或经 manifest、PID、identity 和 control token 校验接管已有的受管 Core，并通过随机 `127.0.0.1` 端口与其通信。端口由操作系统使用 `listen(0)` 分配，每次重试都重新分配；`8787` 不是 Desktop 产品合同，只能出现在独立开发/测试示例中。

Windows Desktop 还启动一个无网络、无持久化的 `awaken-network-watch.exe` 辅助进程，只订阅 registry 代理变化并向 Main 输出信号；macOS 复用系统 `scutil`。它们不是第二个 Core，不持有 token、provider key 或 route 值，且由 Main 在退出时终止。完整行为由[跨平台网络代理与恢复](../网络代理与恢复/实现方案.md)拥有。

renderer 不直接管理 core URL 或子进程，必须经 preload/main bridge 使用当前 supervisor 提供的地址。
