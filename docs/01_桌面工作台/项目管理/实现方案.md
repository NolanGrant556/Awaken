# 项目管理 · 实现方案

本文说明代码职责、数据与接口、异常恢复和验证方法。功能范围及用户操作见[需求文档](需求文档.md)。

## 当前用户行为

- “项目工作区”区展示当前 active项目；removed项目不进入列表。侧栏项目行展示项目名称，不通过原生悬浮提示暴露主文件夹绝对路径；项目文件夹以末段名称展示在悬停卡片和「编辑项目」弹窗中，侧栏树的子节点只有线程。
- Workbench 首页 `center` 输入面下方提供项目作用域低栏。未绑定项目时恢复显示无图标的“选择项目”，表示当前对话在电脑全局范围中运行；它不是项目、文件夹或侧栏“对话”分区的重复入口。其后按侧栏同一顺序列出带文件夹图标的 active 项目。选中项目后，鼠标悬停整段作用域控件会让前置文件夹图标原位变成圆形 `X`；点击 `X` 只取消项目并回到无图标“选择项目”，不展开菜单。键盘聚焦清除按钮时也显示同一 `X`。点击项目名或下拉箭头仍打开菜单。从低栏选择或取消作用域与点击侧栏项目/对话调用同一套 Desktop 选择动作，因此 workspace、旧 thread 清理和两处选中状态同步。低栏里的「创建项目」打开侧栏项目「+」使用的同一个创建弹窗；它不维护第二份项目集合或创建流程。进入 `dock` 后不显示这条首页低栏。
- 侧栏「+」打开的创建弹窗以项目名称为主：填名字即可创建，选文件夹是可选步骤，可以当场加一个或多个、也可以留空。留空的项目照常出现在列表并能发起会话；它的运行位置与产出目录由 [TaskScope 与路径安全](../../04_工具权限与审批/文件操作与路径安全/实现方案.md) 拥有。已经属于其他项目的目录同样可选，同一个文件夹可以出现在多个项目里，共享带来的连带效应由 [项目生命周期与删除](实现方案.md) 拥有。
- 指针停在项目行上会在行右侧展开悬停卡片，列出项目名、对话串数量和这个项目的全部文件夹。项目行和卡片文件夹按钮都不叠加浏览器原生 `title`，避免绝对路径提示遮挡卡片；文件夹按钮的辅助技术名称使用可见文件夹名。项目行内的新建会话动作也只显示一层自定义 Tooltip，不再同时出现同文案的浏览器原生提示。点击卡片里的某个文件夹在系统文件管理器中定位它，卡片底部的「编辑项目」直接打开编辑弹窗。悬停卡片是只读入口，不提供设为主文件夹、解绑或废纸篓等写操作；零文件夹项目在卡片里显示占位文案，说明对话会在这个项目自己的工作目录里进行。拖拽排序进行中不弹出卡片；点开项目行 ⋯ 菜单时卡片立即收起，左右不同时出现两个浮层，菜单关闭后需要重新悬停才会再出现。
- 项目行 ⋯ 菜单提供「添加文件夹」「编辑项目」「从 Awaken 移除」「删除 Awaken 历史」。「编辑项目」可修改项目名称并管理文件夹；保存新名称只改变稳定 `projectId` 对应的展示名，不改变文件夹、线程归属或历史。文件夹粒度的操作在创建项目与编辑项目弹窗的文件夹行上完成：切主与移出摊在行内，「移到废纸篓」只在编辑弹窗的行内 `⋯` 里；组成语义与作用范围由 [项目生命周期与删除](实现方案.md) 拥有。
- 启动时不存在隐式默认项目：用户主目录不再被自动注册为 workspace 或项目。没有任何用户明确选择的项目时，“项目工作区”显示“暂无项目”并保留创建项目入口；`新建任务`、首页作用域低栏和“对话”分区的「+」都可以直接建立独立对话，不要求先创建项目或选择文件夹。
- 项目列表只从当前 `~/.awaken` FileStore 的 active project 读取。Electron userData registry 和 Renderer localStorage 不再承载项目集合，也不存在读取、迁移或据此 upsert project 的入口；不在 FileStore 中的目录需要用户重新通过 “Add folder” 添加。
- 每个项目节点可展开/收起，子节点是按 thread workspace归属计算的线程。
- “项目工作区”标题右侧的批量按钮只负责全部项目节点的展开/收起，不提供筛选；创建项目使用相邻的「+」。
- “对话”分区位于项目区下方，以扁平列表展示 `projectId` 为空的 thread，并提供独立的展开/收起、批量管理和新增对话「+」。普通侧栏两个分区只消费 `GET /v1/threads?view=active`（query 缺失等价 active）：已归档 thread 不出现在项目子节点和“对话”分区，归档入口、Settings 归档页与取消归档由 [会话归档设计契约](../会话管理/实现方案.md) 拥有。进入批量管理后分区自动展开，消息图标原位切换为受控 checkbox，点击整行只切换选择、不打开 thread，行内更多菜单暂时隐藏；标题显示已选数量，标题操作区依次提供全选、删除与退出，未选任何对话时删除禁用，不在列表底部增加删除按钮。全选只覆盖当前独立对话中非 `running|cancelling` 的 thread，运行中项保持可见但禁选，并说明须先停止。取消批量管理、新建任务、选择项目或进入一级导航都会清空这份 Renderer 临时选择。项目批量展开状态、对话分区展开状态与批量选择状态互不写入 FileStore 或 localStorage。
- 项目区与对话区共用中部唯一纵向滚动容器；`新建任务`、一级导航和底部账户区固定，不随项目/对话列表滚动。`新建任务` 与一级导航文字使用中等字重，保持入口清晰但不形成过重的视觉块。滚动条使用窄轨道，只有中部内容超过可用高度时出现。
- 底部账户按钮受控打开个人菜单：第一次点击展开，第二次点击收起，按钮尾部箭头同步指示展开状态。菜单与账户按钮共用左右边界，因此相对侧栏保留等宽内边距，并在侧栏拖拽调宽时同步变化。侧栏当前可拖拽最小宽度为 228px；菜单不得用固定宽度突破这个布局边界。
- 顶层项目支持鼠标按住后上下拖拽排序；拖拽激活后原行淡化，项目名称与文件夹图标以悬浮卡片跟随指针，目标位置显示插入线，释放后立即按目标顺序展示。键盘聚焦项目行时也可用 `Alt + ↑/↓` 移动。子级thread不参与项目排序。
- 排序提交完整active project id序列，经 Desktop typed bridge 写入 FileStore lifecycle journal；刷新与重启后继续使用该顺序。提交失败时Renderer恢复Core返回的顺序并显示稳定notice，不在localStorage另存副本。
- 点击项目会选择该项目的主文件夹作为 workspace；若当前活动thread属于其他workspace，Workbench清空旧活动thread上下文。选中零文件夹项目时不解析出任何路径，也不沿用上一个项目的目录：run 只带 `project_id`，由 Core 解析该项目的 session 工作目录。run 的 readable/writable/output roots 填该项目的全部文件夹。展开按「cwd 所属的项目」判定而不是「cwd 是否等于主文件夹」：锚在次文件夹上的 run（继续旧线程、或切换过主文件夹之后）同样拿到项目的全部文件夹，本次 cwd 排在数组首位，其余文件夹按项目顺序跟随。cwd 不属于任何项目时保持单根。
- 点击项目线程会同步选中/展开其所属项目并从 durable transcript 重放；点击独立对话线程会清空项目选择、切换到“对话”作用域并重放同一份 durable transcript。
- 新 thread 的可见时点统一以 durable thread identity 为准，不等待 run terminal。普通 Composer run 在 thread identity 建立后立即进入 Renderer thread state；定时任务即使页面未挂载，顶层 `App` 也常驻接收携带 `thread_id` 的 `execution_started` 并从 Core `listThreads` 对账，因此运行中的专属会话会直接落到 thread metadata 指定的项目。该同步只更新侧栏，不切换当前页面、不激活 thread、不抢输入焦点；started 事件丢失时，Renderer ready 对账和 finished 事件会恢复 authority 状态。
- 选择、展开和 workspace 目标只使用当前 Renderer 内存状态；项目集合、removed 状态和 workspace 目标均不得写入 localStorage 形成第二 authority。
- 批量删除确认使用 Desktop 统一 Dialog，并说明会删除对话记录、context/tool result 与 Awaken 管理的附件，但不会删除对话产生的文件。Core 返回逐 thread 的成功/失败结果；成功项立即从 authority 列表消失，仍可选择的失败项保留选择，竞态中变为运行态的失败项保留可见但转为禁选，并给出稳定汇总；不得把 project-less FileStore 删除伪装为可回滚的原子事务。

## 代码责任

- 跨域选择/提示和 scheduled started/finished 对账接线：`App.tsx`；项目 authority 与作用域：`useProjectRegistry.ts`、`projectRunScope.ts`；项目操作与恢复：`useProjectOperations.tsx`；线程目录/导航：`useThreadDirectory.ts`、`useThreadNavigation.ts`；侧栏展示：`DesktopSidebar.tsx`。上述文件均位于 `apps/desktop/src/renderer/`。
- workspace/project identity helper：`apps/desktop/src/renderer/projectWorkspace.ts`。
- 侧栏树、项目节点、拖拽与键盘排序反馈：`Awaken Design System` 的 `AwakenSidebar` / `AwakenProjectTree`；只通过回调输出完整顺序。
- 首页项目低栏：`Awaken Design System` 的 `AwakenComposerBar` 只渲染受控 `projectPicker`；项目列表、当前选中项和选择/创建回调由 `App.tsx` 注入。
- 文件夹列表、主文件夹徽标与文件夹行菜单：`Awaken Design System` 的 `AwakenProjectFoldersEditor`；创建项目与编辑项目两个 App 级弹窗复用。
- 项目行悬停卡片：`Awaken Design System` 的 `AwakenProjectHoverCard`；用 render prop 交出锚点而不是包裹元素，因为行样式依赖 `.aw-project-node > .aw-project-row` 直接子选择器。
- 在系统文件管理器中定位目录：`awaken:reveal-path` IPC，只接受主窗口发来的绝对路径并在定位前确认目录仍存在；artifact 的 `awaken:reveal-artifact` 绑定 transcript，不适用于项目文件夹。
- durable project/thread数据与按稳定 `projectId` 的重命名：03域存储和本域项目生命周期文档指向的Core owner；Renderer 保存后重新读取项目 authority，下一次 run 才使用新名称作为模型上下文，已经运行中的 run 保持其启动快照。

## 必须保持的规则

1. 切换 workspace/作用域不得让旧 thread 继续把新 run 写入错误项目；独立对话不得回落到记住的默认 workspace。
2. thread 归属来自 FileStore `projectId`，不来自 label、DOM 文本或 Renderer 合成 ID；空 `projectId` 是独立对话，不是待推断的项目。
3. removed/`trash_pending` 语义由 durable project 状态决定，Renderer 本地选择不能覆盖。
4. 未来筛选只改变可见集合，不得改变 project/thread durable ownership。
5. 排序必须提交当时全部 active project 且每个 id 恰好一次；不得因为拖拽或并发刷新丢失项目。
6. 项目批量展开和对话分区展开只属于 Renderer UI 状态，不写入 FileStore 或 localStorage。

## 异常与恢复

- 线程重放失败：保留项目选择并显示notice，不伪造空历史。
- 初次项目列表读取失败：显示空项目集合并记录错误，不回退到旧 localStorage/registry；后续显式刷新或重启可重试。
- thread引用未注册workspace：不得据此激活removed项目；只有显式upsert/重新添加可恢复。
- 选择项目时路径缺失：不猜测workspace，不创建run。
- 排序提交失败或项目集合已变化：回滚乐观顺序、重新读取FileStore并显示notice；不得继续显示未落盘顺序。

## 测试与真实 Desktop

自动化应覆盖项目/线程/独立对话选择、workspace 切换清理、thread 归属、项目重命名及下一轮上下文名称、无项目 run、removed 隐藏、完整集合排序和重启重放。当前主要 owner 是 `apps/desktop/src/renderer/App.test.ts`、`src/runtime/run_service_test.go`、`src/runtime/file_desktop_store_test.go`、`src/server/project_handlers_test.go` 与 `projectWorkspace` tests。

真实Desktop只读复核：

1. 展开两个项目并切换线程，确认active项目与thread归属同步。
2. 选择另一个项目，确认旧workspace的活动上下文不会沿用。
3. 分别点击项目与对话的展开/收起按钮，确认两者状态互不影响；项目按钮一次展开或收起所有项目。
4. 让项目与对话总长度超过侧栏可用高度，确认只有中部出现窄滚动条，顶部入口和底部账户保持固定。
5. 连续点击底部账户按钮，确认个人菜单依次展开、收起且箭头同步翻转；展开后拖宽和缩窄侧栏，确认菜单始终与账户按钮等宽、左右边距相同，并且侧栏不能缩到 228px 以下。
6. 不创建项目，点击 `新建任务` 或“对话”「+」并提交，确认新 thread 只出现在“对话”；重启后仍归在该区。
7. 重启后不得把 localStorage 写入误报为精确选择恢复；按实际行为记录。
8. 把一个顶层项目拖到另一个项目上方或下方，确认插入线、释放后的顺序；重启 Desktop 后确认顺序保持。
9. 回到首页空态，确认输入面低栏以无图标“选择项目”表达尚未绑定项目的全局对话状态；再选择另一个项目，确认项目项带文件夹图标、左侧栏同步选中且旧 thread 上下文没有沿用。悬停作用域控件，确认文件夹图标原位变成圆形 `X`；点击 `X` 后直接回到“选择项目”且菜单不展开；再用键盘聚焦清除按钮确认 `X` 可见可操作。最后从低栏打开「创建项目」，确认出现与侧栏项目「+」相同的名称与多文件夹创建弹窗。
10. 在“对话”分区准备至少三个独立 thread，其中一个保持运行；进入批量管理，确认运行中项禁选、其他项整行可切换、全选不包含运行中项。删除其中包含当前 active thread 的多个会话，核对确认文案、成功后的新建任务空态、失败项保留选择与取消/导航清空选择；重启后已删除 thread 不得复活。
11. 从项目菜单或悬停卡进入「编辑项目」，修改名称并完成保存；确认侧栏、悬停卡、首页项目作用域和文件工作区项目标题同步更新，文件夹顺序、线程归属和项目选择不变；用中文输入法按 Enter 确认候选时不得提前提交。随后在该项目继续一轮任务，确认模型侧 `<environment_context>` 使用新名称；Windows 还需让同一 cwd 分别以盘符/分段大小写、`\\`/`/` 和尾分隔符变化出现，确认仍携带同一项目的新名称。重命名前已经运行中的 run 不被中途改写。重启 Desktop 后确认名称保持。

## 项目状态

- `active`：可创建和运行会话。
- `removed`：从侧栏隐藏；显式重新添加同一路径才允许恢复为active。
- `trash_pending`：禁止新 run，等待 active run 取消、系统废纸篓和 finalize。

只有active project允许新run；未知workspace可在显式upsert时创建。`trash_pending`必须fail closed，不能继续建run或并发开始第二个项目operation。

一个文件夹被多个项目持有时，「这个文件夹还能不能开会话」按整组持有者判定，因为磁盘目录只有一个：任一持有者处于 `trash_pending` 就一起挡住，否则只要有一个 `active` 持有者，这个文件夹就可用。没有任何项目持有的路径不受这道闸门管辖。

## Operation状态

Action：`detach|delete_history|trash_and_purge|delete_thread`。

Status：`accepted|running|succeeded|failed|blocked`。

Trash phase：

```text
waiting_for_runs
  -> trash_claimed
  -> trash_staged
  -> trashing
  -> cleaning
  -> completed

failure -> status=failed, phase=failed，并恢复 previous project state
cancel  -> status=failed, phase=cancelled，并恢复 previous project state
```

`status` 与 `phase` 是两个维度：成功收口为 `status=succeeded, phase=completed`；取消不是 status 枚举，而是上述 `failed/cancelled` 组合。只有创建 operation 的修改动作必须携带 idempotency key；重命名、文件夹挂载/解绑/切主和排序是原子 set，不创建 operation。业务成功以 lifecycle mutation journal-first 提交为准；session 与附件通过 durable cleanup job 重试，不能因为物理清理暂时失败而让 UI 复活。

Renderer收到pending trash operation后持久化tracker并收起项目，不能用固定超时推断结果。只有operation已逻辑提交且project离开 `trash_pending` 才能永久移除；明确失败且project恢复active时立即重新展示并恢复原展开状态。operation查询或项目刷新瞬时失败继续追踪，不能丢tracker或删历史。

## Trash 两阶段与路径身份

作用对象是本次操作指定的那个用户文件夹，两阶段 staging、path fingerprint 复验和系统废纸篓链路与文件夹粒度前完全一致。

Prepare只保存path fingerprint、thread cutoff和operation，不删除历史。active/question/gate run先取消并等到不忙。

每次claim生成新的attempt token，后续attest/stage/begin/complete/fail必须持有当前token，旧worker不能完成新attempt。

Core把原目录原子改名到同卷operation专属staging，并在改名前后复验volume/file identity。目录内普通新增/修改不应误判；同路径被替换成另一个目录必须拒绝。staging保留原文件夹名。

Electron Main只把staging路径交给系统废纸篓，绝不再按原路径删除。`begin-trash` 必须在系统调用前durable记录invocation boundary。只有staging确认消失后，Core才在同一 lifecycle mutation 中把该文件夹从项目解绑并把项目恢复为 previous state。这是项目的最后一个文件夹时，项目回到零文件夹状态。同一条 mutation 里，该文件夹也从其他持有它的项目中解绑：目录已经不存在，别处留着这一行就是一条指向空处的路径。

系统调用明确失败时Core原子恢复原目录和previous project state；若原路径已被另一个目录占用则fail closed，不覆盖、不删除新目录。

## 异常恢复

- crash发生在prepare/claim/stage/trashing/finalize/cleanup任一点，重启从durable operation/job继续；
- idempotent重试返回同operation，不重复删；
- 重命名在 journal 提交后即为业务事实；snapshot 缺失或损坏时从 mutation 重放出最新名称，同名重试不推进 version/updated_at；
- active run未停止返回busy并重试，不向用户暴露原始THREAD_BUSY；
- physical cleanup失败不回滚已经提交的逻辑删除，由outbox重试；
- path identity改变或attempt过期必须结构化失败并保全新目录/历史；
- 文件夹级 trash 失败时该文件夹原样挂回项目，项目恢复 active，历史与磁盘都不变；
- session 工作目录缺失时在 run 解析 scope 时重建，不把 run 留在没有 cwd 的状态。

Renderer owner：`useProjectRegistry.ts` 统一回读项目并投影稳定身份，`projectRunScope.ts` 计算运行作用域；`useProjectOperations.tsx` 统一拥有操作发起、表单状态、跟踪 operation 的轮询与恢复；`ProjectManagementDialogs.tsx` 展示本域确认/编辑界面。文件位于 `apps/desktop/src/renderer/`，未把删除语义或磁盘权限移入 Renderer。

## 公共 API 动作

具体 method、path 与注册条件只查 09 域。项目域提供：列出项目（默认排除 removed）、创建或 upsert 项目、按稳定 ID 重命名、挂载文件夹、解绑文件夹、切换主文件夹、以完整active project id序列替换侧栏顺序、detach 且保留历史和目录、逻辑删除项目历史、prepare 文件夹级 trash-and-purge、列出未终态 trash operation、查询 operation，以及只在合法等待阶段取消 operation。

### 创建与文件夹组成

`POST /v1/projects` 有两种 body 形态，由字段决定：

- `{"workspace_root": "...", "display_name": "..."}`：单文件夹 **upsert**。重新打开一个已知目录时继续复用并重新激活它原来的项目，不会新建重复项目。
- `{"folders": [{"path": "...", "primary": true}], "display_name": "..."}`：多文件夹 **创建**，总是新项目，`project_id` 随机生成。`folders` 顺序即展示顺序；没有任何 `primary=true` 时第一个文件夹成为主文件夹。`folders` 为空数组（或两个字段都不给）也合法，项目就此以零文件夹存在，只靠 `display_name` 立项。

两种形态都返回 `201` 与完整 project。project 的 `folders` 是权威字段，`workspace_root` 只镜像主文件夹路径以兼容既有 wire consumer。

文件夹不被独占：同一个磁盘目录可以同时属于任意多个项目，创建和挂载都不因为它已被别的项目持有而失败。一个目录参与哪些工作由用户决定，存储层不做仲裁。

文件夹级动作都返回 `200` 与更新后的完整 project，都不创建 operation、不需要 `Idempotency-Key`：

| 动作 | body | 语义 |
|---|---|---|
| `POST /v1/projects/{id}/folders` | `{"path": "..."}` | 挂载一个文件夹作为次文件夹；项目此前没有文件夹时，它直接成为主文件夹。目录已属于其他项目不影响挂载 |
| `DELETE /v1/projects/{id}/folders` | `{"path": "..."}` | 解绑，不碰磁盘，也不影响仍持有该目录的其他项目；解绑主文件夹时由剩余文件夹接任，全部解绑后项目回到零文件夹状态 |
| `PUT /v1/projects/{id}/primary-folder` | `{"path": "..."}` | 在已挂载的文件夹之间切换主文件夹 |

`POST /v1/projects/{id}/folders/trash` 的 body 是 `{"path": "..."}`，指明本次进废纸篓的那个用户文件夹。它创建 operation，因此仍然要求 `Idempotency-Key`。

### 重命名

`PATCH /v1/projects/{id}` 接受 `{"display_name":"..."}`，返回 `200` 与更新后的完整 project。Core 去掉名称首尾空白；结果为空返回 `400 PROJECT_NAME_INVALID`。项目不存在返回 `404 PROJECT_NOT_FOUND`，项目处于 `trash_pending` 返回 `409 PROJECT_OPERATION_CONFLICT`。

重命名按稳定 `project_id` 原子 set，不创建 operation，也不需要 `Idempotency-Key`。新名称与当前名称相同是 no-op，不推进 `version` / `updated_at`，也不追加空 mutation；真正变化只推进这三个名称相关事实，不改变 `folders`、`workspace_root`、`state`、`project_order`、thread metadata 或历史。共享同一个文件夹的其他项目不受影响。零文件夹项目使用完全相同的合同。

Desktop 后续创建或继续 run 时，把当前 project authority 的最新 `display_name` 作为 `workspace.project_name` 送入 TaskScope；该字段进入模型上下文，但不参与路径、权限或 identity 解析。名称变化会让后续 run 重建 scope 上下文，不回写既有 transcript。

### 幂等与排序

创建operation的修改请求必须带 `Idempotency-Key`。同 key/同 project/action 返回同 operation；同 key 被其他 operation 占用返回冲突。“删除会话”内部使用稳定 `thread-delete:<thread-id>`，重复请求不重复创建 job。项目排序使用幂等的完整替换 `PUT`，body为 `{"project_ids":[...]}`，不创建operation，也不修改project `version/updated_at`；请求必须包含当前每个active project且每个id恰好一次。

## Worker 内部动作

| 动作 | 责任 |
|---|---|
| `claim-trash` | worker 领取 lease、生成 attempt id，并确认 run 已停 |
| `attest-trash` | staging 前复验目标文件夹的路径身份 |
| `stage-trash` | 原子 rename 到同卷 operation 目录并持久化路径 |
| `begin-trash` | 系统调用前耐久记录 invoked boundary |
| `complete-trash` | 确认 staging 消失后解绑该文件夹并恢复 project state；这是最后一个文件夹时项目回到零文件夹状态 |
| `fail-trash` | 恢复 staging 和 project state，保存稳定错误 |

operation 的目标是一个文件夹，不是整个项目：`complete-trash` 不再 tombstone project，也不再按 cutoff soft-delete 项目历史。

废纸篓真的删掉磁盘目录，所以它对共享文件夹是全局事件：`prepare-trash` 把该文件夹对**每个**持有它的项目围栏起来并停掉锚在它上面的线程，`complete-trash` 把它从每个持有它的项目里一并解绑。失败或取消时这些围栏全部释放。非破坏性的项目级动作（detach 项目、删除历史）只围栏没有其他活跃持有者的文件夹，不牵连别的项目。

除 claim 外的后续请求必须带当前 `attempt_id`。lease 恢复必须重新 claim；旧 attempt 返回 `PROJECT_TRASH_ATTEMPT_INVALID`。

## 领域错误

| code | HTTP | 语义 |
|---|---:|---|
| `PROJECT_NOT_FOUND` | 404 | project 不存在 |
| `PROJECT_OPERATION_NOT_FOUND` | 404 | operation 不存在 |
| `PROJECT_OPERATION_CONFLICT` | 409 | 状态/阶段不允许 |
| `PROJECT_RUNS_BUSY` | 409 | active run 尚未停止 |
| `PROJECT_PATH_FINGERPRINT_CHANGED` | 409 | 路径身份被替换 |
| `PROJECT_TRASH_ATTEMPT_INVALID` | 409 | attempt 已过期/不匹配 |
| `IDEMPOTENCY_KEY_CONFLICT` | 409 | key 属于其他 operation |
| `IDEMPOTENCY_KEY_REQUIRED` | 400 | 修改请求缺 key |
| `PROJECT_PATH_INVALID` | 400 | workspace path 无效 |
| `PROJECT_ORDER_INVALID` | 400 | 排序缺少active project、包含重复/空id或非active project |
| `PROJECT_NAME_INVALID` | 400 | 重命名去掉首尾空白后为空 |
| `PROJECT_FOLDER_NOT_FOUND` | 404 | 目标文件夹不在这个项目里 |

未知错误返回 `INTERNAL_ERROR`；详细错误只写带 operation id 的结构化日志，Renderer 显示稳定 notice。

## FileStore transaction

项目、项目顺序、operation、idempotency index、operation-thread cutoff 和 cleanup jobs 的 authority 是活动 generation 下的 `lifecycle/mutations.jsonl`。每个领域 commit 形成一条包含完整 post-state 的 mutation；`ReorderProjects` mutation保存完整 `project_order`，新增项目排在现有顺序之前，removed项目可保留在内部顺序尾部但不进入active侧栏：

```text
获取 store.lock
  -> append + fsync lifecycle mutation
  -> 更新内存 state
  -> 幂等物化 thread metadata side files
  -> 原子替换 lifecycle/state.json
  -> 释放 lock
```

`state.json` 是可重建快照，不是第二 authority；启动从 journal seq 重放到最新。

`RenameProject` mutation携带重命名后的完整 project post-state。它不携带 `project_order`、thread side-file mutation 或 operation/job，因此重启只重放名称及该次 material change 的 `version/updated_at`；同名 no-op 不写 journal。

文件夹归属只有一处事实：每个 project 自己的 `folders`。存储层不再维护路径到 project 的反向索引；「这个目录属于哪些项目」由 `ProjectsHoldingFolder` 按侧栏顺序扫描 project 得出，可能返回多个。旧 `state.json` 里遗留的 `workspace_index` 字段不再被读取，解码时忽略，无需迁移。禁止先删除 session 目录再提交逻辑 mutation，否则 crash 会造成 UI 历史与物理文件不一致。operation/job ID、时间和 cutoff 必须先生成并写进 mutation，重放不得重新生成。

## Cleanup 与业务完成

`detach` 可同步完成。`delete_history`、`delete_thread` 和 trash finalize 先在 lifecycle mutation 中 soft-delete thread 并创建 cleanup jobs；pending cleanup 大于 0 时 HTTP 可返回 202。

业务完成（logical committed）与物理完成（session metadata/journal/附件清理）分离：

- UI 以逻辑提交和 project durable state 为准；
- cleanup job 幂等 claim/retry；
- 只有已 soft-deleted session 才可物理清理；
- 已逻辑删除的 thread 不能因 physical failure 复活；
- pending cleanup 清零后 operation 进入 `phase=completed, status=succeeded`。

## Renderer tracker

pending trash tracker 至少保存 operationId、UI projectId、backendProjectId、目标 folderPath、label 和原 expanded 状态，并写入 localStorage。缺少 folderPath 的旧条目在解析时被丢弃。启动/重载后继续查询 operation 与 project，判据是「项目是否还挂着这个文件夹」而不是「项目是否被整体移除」：

- pending/unknown：继续低频跟踪；
- committed 且项目已不含该文件夹：清除 tracker，保持移除；
- `status=failed` 且 `phase=failed|cancelled`、project active 且文件夹仍在：清除 tracker 并恢复展示/expanded；
- operation 请求失败或 project refresh 失败：不清 tracker。

`projectWorkspace.ts` 的 reconciliation 纯函数是判断 authority；App 不应散落第二套 phase 集合。

## FileStore 唯一项目 authority

Renderer 启动无条件调用项目列表 API，并只把返回的 stable `project_id` 投影到侧栏。空 FileStore 必须返回 JSON `[]`，Electron Main 和 Renderer 不接受 `null` 作为集合，也不回退到旧 UI 状态。

当前产品不存在旧 Local Storage、workspace registry 或历史 thread workspace 的读取、清理、导入、转换及 upsert 入口。用户重新添加目录时，先通过公共 API取得 FileStore `project_id`，后续生命周期动作只使用该 ID；不得把路径编码的 Renderer ID 当成后端 ID。

同一个文件夹可以出现在多个项目的 `folders` 里，因此 `project_id` 不能从路径推导。新项目使用随机 id；已有 path-derived id 原样保留。加载旧 snapshot 或重放旧 journal 时，没有 `folders` 的项目合成 `[{path: workspace_root, role: "user", is_primary: true}]`，不需要迁移脚本。零文件夹项目的 `workspace_root` 为空字符串、`folders` 为空数组；它的 session 工作目录路径由 `desktopdata.SessionWorkspacePath` 唯一构造，不写入项目状态。

## 安全必须保持的规则

1. 系统 trash 只接收 staging 路径。
2. staging 必须同卷原子 rename。
3. begin-trash 先于系统 trash 调用耐久提交。
4. complete 前必须确认 staging 不存在。
5. original path 已被新目录占用时不覆盖、不删。
6. cutoff 后新建 thread 不被旧 operation 误删。
7. Renderer 不能直接调用文件删除命令。
8. FileStore lifecycle mutation journal-first；snapshot 损坏只能重建，不能反向覆盖 journal。
9. Renderer与localStorage不得成为项目顺序authority；拖拽只产生乐观UI，Core拒绝后必须按FileStore回滚。
10. 项目的文件夹数可以为零；有文件夹时恰好一个是 primary。零文件夹项目的 run 由 `workspace.project_id` 解析到项目 session 工作目录。`workspace_root` 与 `project_id` 同时为空属于独立对话，不创建 project row，也不进入项目生命周期状态机；其 thread/session 契约由 02、03、04 域拥有。
11. 一个磁盘路径可以属于任意多个项目；归属只从各 project 的 `folders` 派生，不存在需要维护一致性的反向索引。判断「这个文件夹还能不能开 run」必须聚合它的全部持有者，而不是任取一个。
12. 项目名称是模型可见上下文而不是授权事实；重命名不得改变 `project_id`、路径 scope、文件夹归属、项目顺序或 thread ownership。

## 多根执行与搜索

- [ ] run 的 readable/writable/output roots 是 `[本次 cwd, ...项目其余文件夹]`，从主文件夹发起时即 `[主文件夹, ...次文件夹]`。
- [ ] 锚在次文件夹上的 run（继续旧线程或切换过主文件夹后）不塌回单根，项目其余文件夹仍在 scope 内。
- [ ] 次文件夹里的读、写、artifact 输出成功；次文件夹仓库的 `.git` 仍然不可写。
- [ ] 不带 `path` 的 `Glob`/`Grep` 覆盖全部 readable roots 并返回绝对路径；单根时仍是 root 相对路径。
- [ ] 嵌套 root 不让同一个文件出现两次。
- [ ] session 工作目录作为 root 时可写，而 `~/.awaken` 下的 `config`、`credentials`、`store-generations`、`memory` 仍然不可写。
- [ ] 给出项目文件夹之外的绝对路径时，读、写、`Glob`/`Grep` 都直接执行且不出现审批。
- [ ] 无论在哪个位置，写 `.git` 内部、`.env`、私钥/凭据文件、shell 配置和 `~/.awaken` 仍被拒绝；读这些文件不受限。
- [ ] 不带 `path` 的搜索不会扩散到项目文件夹之外。

## 用户语义

- [ ] 从 Awaken 移除后目录和历史保留，重启不复活，重新添加可恢复关联。
- [ ] 删除历史后项目和目录保留，UI 立即隐藏历史，后台最终清理 JSONL/附件。
- [ ] active/approval/question run 自动取消，不向用户暴露 `THREAD_BUSY`。
- [ ] 独立“对话”批量管理只允许选择非运行 thread；若确认后出现竞态，Core 按项返回 `THREAD_BUSY`，成功项消失、busy 项保持可见但转为禁选，且不会误删产出文件。
- [ ] 重复请求和响应丢失不会重复删除。
- [ ] 文件夹 Trash 成功后该目录真实进入系统废纸篓、从项目解绑，项目仍然 `active` 且其 Awaken 历史保留。
- [ ] Trash 掉主文件夹后剩余文件夹接任主文件夹；trash 掉最后一个文件夹后项目回到零文件夹状态。
- [ ] Trash 失败后该文件夹原样挂回项目，项目恢复 `active`，thread metadata、SemanticJournal 和附件不变。
- [ ] Trash operation 超过 30 秒仍未终态时，Renderer 继续后台跟踪；随后失败无需重启即可恢复项目和历史，成功保持移除。
- [ ] Renderer 在后台 operation 未终态时重载，能够从持久化 tracker 续接状态，不因轮询或刷新瞬时失败丢失跟踪。
- [ ] Electron userData registry 和 Renderer 项目键即使存在也不参与启动，侧栏不复活非 FileStore 项目；重新添加目录后使用 FileStore stable project ID。
- [ ] Prepare、staged、trashing、finalize、cleanup 五个崩溃点均能重启续跑。
- [ ] 同路径出现不同文件身份时绝不删除新目录或历史。
- [ ] macOS Trash 与 Windows Recycle Bin 都完成真实 smoke。

## 路径与并发安全

- [ ] 同目录普通内容变化不误判为path replacement。
- [ ] 原路径被另一个目录占用时，新目录不进入系统Trash，历史不删除。
- [ ] 旧attempt在新claim后不能attest/stage/begin/complete/fail。
- [ ] begin-trash之前crash可安全重试；之后crash不会再次按原路径trash。
- [ ] cutoff之后创建的thread不被旧operation清理。
- [ ] 同一idempotency key重试返回同operation；冲突key结构化失败。

## 真实Desktop步骤

1. 在专用测试目录创建可识别文件，用「创建项目」一次选入两个文件夹并指定主文件夹，准备至少一个thread。
2. “从Awaken移除”：确认全部文件夹和历史保留，重启不复活，显式重新添加后关联恢复。
3. “删除Awaken历史”：确认项目/文件夹保留，列表立即隐藏历史，重启仍隐藏。
4. 文件夹行“移到废纸篓”：确认pending期间不能新run，系统Trash/Recycle Bin真实出现该目录，成功后项目仍在侧栏、历史保留、只少了这个文件夹。
5. 在次文件夹里让 agent 读写一个文件，并用不带 `path` 的搜索确认两个文件夹都被覆盖。
6. 在侧栏「+」里只填项目名称创建项目，确认它直接出现在列表里；在它下面发起一次会话并确认产出落在 `~/.awaken/sessions/<project_id>/output`；随后加入一个文件夹并确认它成为主文件夹。
7. 用可控失败（权限或测试double）验证文件夹、项目、历史、文件全部恢复；不得拿真实业务目录做失败注入。
8. 重载renderer/重启Desktop验证tracker续接。
9. 在隔离 userData 写入非 FileStore project fixtures，重启确认 Projects 仍只以 FileStore 为准且这些载体不被读取或修改；不得用真实业务目录做测试。
10. 按住一个顶层项目上下拖动，确认插入线和释放后的顺序；用 `Alt + ↑/↓` 复核键盘路径，重启Desktop确认顺序未恢复旧值。
11. 在「编辑项目」里给普通项目和零文件夹项目各重命名一次，确认侧栏与首页项目选择器同步显示 trim 后的新名称；继续原 thread 让 Agent说明当前项目名，确认使用新名称，重启 Desktop 后名称仍保持。

验收报告记录platform、HEAD、operation id、phase序列和最终project state；不要长期保存PID、端口或临时过程截图到知识库。
