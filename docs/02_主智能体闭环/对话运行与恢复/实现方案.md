# 对话运行与恢复 · 实现方案

本文说明代码职责、数据与接口、异常恢复和验证方法。功能范围及用户操作见[需求文档](需求文档.md)。

## 主循环

Agent 按 model response 执行 assistant text、tool calls、Skill catalog call、context estimate/compact 和后续轮次。每次模型调用先完成一次协议 lowering，耐久并 flush 脱敏 `model_request` 后发送完全相同的 prepared body，结束后用同一 request ID 写 nullable `model_usage`。普通工具默认自动；默认 raw Shell 使用当前登录用户本机权限，不进入通用审批。`ask_user` 只承担任务信息 gate；消息发送（包括多人、群、频道、广播和批量发送）没有 Awaken 人工审核状态。run 对外状态只有 `running`、`cancelling`、`finished`、`error`、`cancelled`，不存在通用 `awaiting_approval`。Journal 恢复使用的 terminal payload `status=interrupted` 会投影为公开 `error`/`RUN_ERROR`，不是第六种对外 run 状态。

ToolRuntime 先校验固定 snapshot/provider readiness，再执行 TaskScope、安全决策、broker 和 tool。canonical Outcome 回到模型；UI/replay 使用独立投影。

Hook 更新后的工具输入重新进入 ToolRuntime 的 schema、snapshot/provider readiness、TaskScope 和安全决策，不继承原输入的校验结果。Hook 阻断生成 `denied + side_effect_state=not_started + decision_source=hook` 的 canonical Outcome。Hook additional context 只作为当前 run 的 runtime context block 进入后续请求，不生成第二条 user message；command executor 不通过 Tool Registry，因此不会递归触发 Hook。Subagent 生命周期 Hook 使用父 run Dispatcher 和预算，回执带 `subagent_task_id`，其 additional context 只进入 child；child 内部工具调用仍不触发 user/project Hook。`BeforeFinish` block 把候选回答保留为 non-final assistant 历史，并把有界反馈作为 host-owned untrusted data 注入下一模型边界；每 run 最多两次，第三次写 `hook_reentry_limit` 并强制完成。

## 必须保持的规则

- 同一 run 的 tool/environment snapshot 不变；
- 同一 run 的 Hook snapshot 和 Dispatcher 预算不变；配置或信任变化只影响后续 run；
- Skill hints 不改变权限或工具池；
- side-effect call 必须 append-before-transport；
- model request 必须 prepare once、journal+flush before transport，并以同一 request ID 封口；
- terminal 只能来自 durable run 事实，UI 不自行补成功；
- thread 切换/重开不得改变旧 run provider/readiness 或 Skill 内容。
- 归档历史只通过 root `archived_history` 的精确 archived `thread_id` 读取；不自动注入、不向 child 继承、不把历史内容提升为指令，也不允许模型绕过 Runtime 扫描业务数据根。
- 独立对话不得继承 Renderer 记住的项目路径，也不得被持久化为隐藏项目；同一 thread 的 managed workspace 必须稳定，不同独立 thread 必须隔离。
- 可见媒体序号由宿主从 durable Artifact 投影，模型不得用提示词编号或文件名替代；任意未出现在当前 thread 媒体许可集合中的 `artifact_id` 都不能获得路径能力。

## 失败监督

`FailureSupervisor.BeforeCall` 用单一 `CallAction` 表示执行、阻断或终止 run，不能同时允许和阻断。失败分类元数据持有唯一计数；`AfterOutcome` 只返回实际使用的恢复信息。监督器使用 canonical Outcome：

- validation/policy/not_started：修正输入或换已支持路径；
- needs_auth/runtime：呈现 next action，完成外部准备后新调用；
- unsupported：换 provider/capability 或明确报告缺口；
- retryable transient 且无副作用：有界重试；
- partial/unknown：先检查外部状态并阻止原样重复；
- output schema mismatch/provider contract violation：保留诊断，不生成伪成功。

主模型只返回内部推理、但没有可见正文或工具调用时，不得以 `completed` 结束。宿主在同一 run 内注入一次不可见的继续指令，并保留 provider opaque reasoning 用于同供应商重放；下一轮仍无正文且无工具调用时，以 `empty_response` 失败。该继续计入 max turns，不追加无界重试。

主模型 transport 的错误分类由 05 域拥有：HTTP 非 2xx 保留去敏 `RequestError(status,retry_after)`；尚未取得任何 HTTP 响应的连接失败使用不携带 URL/底层网络详情的 `TransportError`；响应已接受后的 body/EOF/reset 使用 `StreamDisconnectedError`。同一 turn 的重试政策由本域拥有，且不把 reconnect 写入 SemanticJournal：

- 响应前 `TransportError`：run 保持 running，无限等待网络，退避 5s 起倍增到 60s；每次等待发出 live-only `ProviderReconnect(waiting_for_network)`，`maxAttempts=0`；
- 已接受响应但没有协议终止信号的 clean EOF 也属于 `StreamDisconnectedError`：OpenAI Chat 需要 `[DONE]` 或非空 `finish_reason`，OpenAI Responses 需要 `response.completed` / `response.incomplete` 或 `[DONE]`，Anthropic Messages 需要 `message_stop`；不能因为 `Scanner.Err()==nil` 就把半截正文或不完整 tool call 当成成功；
- 尚未开始工具流的 `StreamDisconnectedError`：最多 5 次有界重试，发出 `ProviderReconnect(reconnecting)`；未耐久的文本/思考缓冲丢弃，`resetInProgress=true`，Desktop 恢复 planning/思考中，不提交失败回答；第 5 次重试后的最终失败若仍产生了部分输出，也必须先发 reset frame 再进入唯一 run terminal；
- `429`/`5xx`：同一有界次数，优先遵守 `Retry-After`，单次等待上限 30 秒；
- 成功后发 `ProviderReconnect(recovered)`，继续当前 turn；
- `400/401/403/404`、stream idle timeout、以及工具参数流或 tool call 已经开始后的中断不自动重放；provider-neutral `StreamEventToolCallStart` 本身就是工具流边界，不能等首个非空参数 delta 才标记。

每次真实 provider 尝试仍分别写 model request/usage，最终失败只产生一个 run terminal。`AWAKEN_PROVIDER_RECONNECT` 只存在于 live wire，不进入 transcript/replay。Desktop SSE 订阅中断与 provider 重试不是同一条恢复链，见 [09 HTTP 与 SSE 接口契约](../../09_AGUI与A2UI协议/本地接口与事件协议/实现方案.md) 与 Desktop 客户端。

Context Epoch 投影发生在 provider transport 之前。它失败时使用 `context_epoch_error` terminal reason 与 `CONTEXT_EPOCH_ERROR` code，并呈现 `context preparation failed`；不得包装成 `LLM stream call failed`、`model_error` 或 provider request failure，也不得触发 provider 重试。损坏与唯一允许的旧 writer 归一化边界由[提示词缓存与成本治理](../上下文与用量/实现方案.md#affinity凭据-revision-与-context-epoch)拥有。

Shell 失败的 resource revision 由 `command + workdir` 生成不暴露命令文本的稳定摘要，不同恢复命令不共用粗糙 `unknown` 预算。已观测 mutation 成功，或另一个默认 direct Shell 非检查命令成功且返回 unknown side effects 后，旧 Shell 失败记录可清除，使 `pipeline 缺包失败 -> npm install -> 原样重跑 pipeline` 可以针对新环境恢复；副作用已证明为 none 的不相关只读成功不得清除恢复指令。

单个业务工具的累计失败不直接终止 run：达到单 turn 6 次或单 run 12 次失败阈值后升级为强制 `strategy_change_required` directive；被拒绝的完全相同重复调用返回可恢复 tool result（`same_call_retryable=false`），run 继续。run 只由 run 级预算（max turns / max tool executions）、取消、持久化失败等编排级原因终止。阈值与拦截语义的维护位置见 [工具决策、Outcome 与失败监督](../../04_工具权限与审批/工具发现与执行/实现方案.md)。

已成功的变更不能通过只换 `idempotency_key` 在同一 run 中反复执行。宿主用工具名和排除幂等 token 后的业务参数建立成功变更签名：首次重复返回 `successful_mutation_already_applied`，要求进入下一业务步骤、用只读工具验证，或在确需修正时改变业务参数；模型忽略该拦截再次提交同一变更时，以 `repeated_tool_failure` 终止，且第二次不进入 provider transport。只读调用不受此规则影响；业务参数不同的修正仍可执行。

`ask_user` 是交互门，不属于上述可替换的业务工具：非重试的输入校验失败已经返回当前结构和示例后，模型若再次提交完全相同的无效参数，supervisor 以 `repeated_tool_failure` 终止 run；用户可在新 run 使用正确结构或更换具备兼容结构化工具调用能力的模型。该例外只阻止已证明无进展的相同交互请求，不影响修正参数后的首次调用。

Skill 激活失败使用 Skill load/invocation error 和 diagnostics；旧的“按工具求交”“平台关键字冲突”“资源预加载缺失”不再是通用检查要求。Skill 建议的工具不可用时表现为 provider/tool Outcome。

对 composer 显式 Skill token，失败终态之前已耐久保留完整 `user_message`；多 Skill 激活 records 以单批写入，批次失败时不泄漏部分 `skill_activated`。

## 恢复

服务启动扫描未闭合 journal：补 interrupted terminal、为未闭合 tool call 生成 unknown/blocked recovery，不执行外部调用。live/replay projector 产生同一最终顺序。

## 输入合同

新模型调用使用结构化 `questions`：

- 一次 1–3 个问题；
- 每题 2–4 个明确选项，默认单选；`multi_select=true` 时允许多选；
- `question`、选项 `label` 必填；
- `header`、选项 `description`、`multi_select` 可选；
- Desktop 可以提供“其他”自由文本，但当前没有“只有自由文本、没有选项”的独立题型。

`questions_json` 和裸数组解析仅用于历史兼容，不应继续出现在新 prompt、示例或调用代码中。JSON schema 是新调用的限制来源；兼容解析器对旧载体较宽松，不代表产品合同放宽。

模型可见 schema 只有一个顶层对象和一个必填 `questions` 字段，不使用顶层 `oneOf`。Runtime 在正式 schema 校验前只把历史 `questions_json` 或裸数组载体规范化成当前对象；空对象、混合新旧字段和其他新调用错误不会借兼容路径绕过校验。失败结果会返回当前对象示例；同一非重试输入在收到纠正信息后仍原样调用时，FailureSupervisor 终止该 run，避免交互门无限消耗模型回合。

代码 owner：[`src/tools/ask_user/ask_user.go`](../../../src/tools/ask_user/ask_user.go)。

## 状态与事件流

1. 模型产生 `ask_user` tool call。
2. ToolRuntime 不调用普通 executor，而是构造 question request。
3. [`src/runtime/session.go`](../../../src/runtime/session.go) 登记 pending question，并等待 answered/cancelled resolution 或 run terminal。
4. Desktop 通过 09 协议域定义的 question answer/cancel 动作提交非空回答，或明确表示用户取消本次回答。
5. Session 校验 run/question identity，完成等待；ToolRuntime 生成含 `resolution`、`question_count`，以及 answered 时 `answer_text` 的 canonical outcome。cancelled 是 transport 已完成的正常交互结果，明确告知模型用户未回答且 run 仍活跃，不伪造答案、不触发主 run cancel。
6. 该结果按普通 tool result 进入 journal 和模型续轮。

若 sink 不支持等待、主 run 被 Stop/超时、question identity 不匹配或 answered resolution 的回答为空，runtime 不执行任何替代副作用；pending question 被清理并形成明确失败/运行取消结果。用户主动取消问题属于合法 `cancelled` resolution，不进入这条失败路径。

## 必须保持的规则与边界

- 同一个 pending question 只能以 answered 或 cancelled 完成一次；迟到回答、迟到取消都不得复活已终止 run。
- question request 与 resolved 必须携带同一 run/question identity。
- 用户回答或问题取消必须作为 tool result 回到原 tool call，不能额外伪造 user message 破坏 pairing；cancelled result 不得带虚假 `answer_text`。
- Workbench 必须使用既有 `RunStage`/composer ownership；不得为问答卡新增第二个滚动容器或输入系统。
- 问题卡作为 `composer-dock-stack` gate 出现时，普通 ComposerBar 必须固定保留在其下方；等待回答期间 ComposerBar 沿用当前 run 的 busy 禁用/停止态，不能并发发送第二条用户消息。
- 问题不得承载密码、API key 等敏感凭据收集；凭据入口属于 05 模型配置。

## 自动化

- run 固定 environment/tool availability snapshot，RequestBuilder 与 ToolRuntime 同源；
- registry/PATH 变化不替换当前 run 已固定的 tool schema、runtime/provider identity 和 environment snapshot；MCP adapter 的 live connection/auth state 仍立即改变当前调用结果，model-facing `skill` 调用也按当时 registry 重查定义/正文；
- composer token 校验、inline context、真实 fork child 和 model-facing `skill`；StartRun 到最终 provider request 的合同必须确认当前选择的 Skill ID/source/mode/absolute root/SKILL.md 作为 host-owned block 进入上下文，single/multi/token-only/fork/历史/model-invoked 语义不混同；
- 含 Skill token 的完整 `user_message` 先于预激活耐久化，激活失败保留输入且不写部分/伪 activation，成功执行不重复写入；
- Skill 不改变父 tool snapshot；
- host-owned Memory policy/index/recall block 在请求中保持数据与指令边界，selector 最多 5 条且失败不阻塞主 run，compact 后预算按 11 域复位；原生 child 只继承父已召回的冻结 snapshot，不跑 user-scope selector；
- context estimate/compact、Skill 单包 5k/总计 25k budget、最新 5-of-6 保留、恢复时间顺序和截断块精确 `Read` 源路径提示（`TestCompactInvokedSkillContextEnforcesBudgetsAndKeepsNewest`），以及 tool media storage key、restart 恢复/fork 隔离；
- 低窗口下一批多个媒体 `Read` 只执行剩余预算装得下的前缀，其余合成 `context_admission_exhausted` 且 pairing 仍合法（`TestExecuteToolCallsAdmitsOnlyFittingMediaReads`）；文本 `Read` 不被该入场门拦截；
- 请求投影按当前窗口重算：11 张旧图 + 1 张近尾时本地账仍计媒体，provider clone 只 hydrate 近尾；摘要请求无 image/file payload；14×10 图的超限 tail 被吸收后不再带齐 `DataBase64`；journal replay 只恢复 `storage_key`，重启投影与 live 一致；
- compact 后置条件：摘要成功但重建投影仍高于 auto/block 或未缩 20% 时失败且不切 epoch；三次同类失败才 circuit + `CONTEXT_BLOCKED`；`errors.Is(blocked)` 时 `isPromptTooLongError` 为 false；
- 默认 system prompt 必须把同一任务内已恢复的前序 user/assistant/tool 消息声明为连续历史；“上一个对话”等指代默认落到当前任务最近相关轮次，同时保持供应商 messages 为标准有序 role/content，不下发内部 thread/run/session、时间戳或 message/turn identity；
- root 模型工具池必须暴露 `archived_history` 的 list/read、`thread_id` 寻址、host-managed location 和 untrusted 历史边界；child role 必须隐藏该工具且不继承 service。归档 read 只命中 archived authority，分页/单项上限生效，tool arguments 不返回，当前 journal 只保存无正文读取回执；
- `ContextUsageSnapshot` 七项分类和等于总估算、Memory/Skill 不重复、old record 不补造；provider total/input/output 不覆盖 Core local snapshot；identity 一致的完整主调用 inclusive input 直接驱动 Desktop 当前总输入并与面板输入 Token 相等，provider total/input 与 `sent_estimated_input_tokens` 另驱动 Core 保守阈值并在新 run/旧 thread 的兼容恢复中成对续用；同 epoch 内锚点不得因 pre-epoch admission 与 post-epoch sent estimate 的阶段差异向下回退，必须覆盖 146023/162363/254928/143 这类真实回归并主动压缩；正残差单列“其他/协议开销”，分类显示 reconciliation 后仍与汇总严格相等；缓存与 token/cost 明细紧接分类且没有“上次请求”分界；面板不显示 compact diagnostics 或 failure/invalidation reason，compact 期间保持最后完整快照并仅在成功后的完整 snapshot 原子刷新；失败 compact 后立即检查、完整重启后再检查都必须保持压前值，Journal 中 compact auxiliary usage 后的高位 snapshot 不得在回放中穿透冻结；0 值分类不绘制进度 segment 时，后续 segment 与图例仍按分类语义同色；
- prepare-once exact body、`model_request` fsync-before-send、同 request ID terminal usage、orphan `usage_unknown`、purpose/retry/auxiliary fallback 与 live/replay 聚合；
- DeepSeek/Kimi/火山/custom capability、affinity/credential revision、nullable cached usage、Context Epoch/compact 边界、Kimi provider-opaque state 和大 tool result 首次 admission offload；
- 仅含 thinking/reasoning 但无可见正文、无工具调用的主模型终态不得写入 completed；首次保留同供应商 opaque state 并做一次 host-owned continuation，下一轮正文或工具可继续，连续第二次则以 `empty_response` 失败且不产生 `run_finished`；
- 已成功 MCP mutation 只换 `idempotency_key` 重复调用时，第二次不进入 transport 并返回 `successful_mutation_already_applied`；模型再次忽略时以 `repeated_tool_failure` 终止；改变真正业务参数的修正可继续，重复只读不被误拦；
- ordinary auto、ask_user、needs_auth/runtime/unsupported，以及消息工具不产生审核 gate；
- cancellation、orphan recovery、partial/unknown retry block 和唯一 terminal；Bash `command+cwd` resource revision 不合并不同恢复命令，已观测 mutation 或成功的 Bash 恢复命令后可重跑验证命令，side effects=none 的无关只读成功不清理失败历史；
- live/replay 相同 semantic projection。

## Run 建立的实现

一次 run 固定 thread/workspace、模型 profile、TaskScope、`ExecutionEnvironmentSnapshot`、`RunToolAvailabilitySnapshot` 和 `HookAvailabilitySnapshot`。RequestBuilder 暴露给模型的 tools 与 ToolRuntime 执行的 runtime/provider identity/runtime pointer 来自同一快照；registry catalog、PATH 或 Hook 配置/信任变化只在后续 run 形成新快照。Hook Dispatcher 从该快照按顺序执行同步 command：`RunStart`/`UserPromptSubmit` 可阻断 run 或注入 host-owned untrusted data；`PreToolUse` 位于耐久 tool call 后、真实执行前，可阻断或更新输入；成功/失败 Post 位于耐久 canonical tool result 后；`PreCompact/PostCompact` 分别位于摘要计算前和成功 boundary 后；`SubagentStart/Stop` 由 root 在 child runner 外层触发；`BeforeFinish` 位于无 tool call 候选回答后、run terminal 前；`RunEnd` 位于耐久 terminal 后且不能改写终态。MCP adapter 仍检查 live server state，因此当前 run 中途断线会立即使后续调用返回 needs-auth/runtime/deny/transport failure，但不会换成另一个 provider 或调用旧 session。
