# 插件产品与架构契约

本文是 Awaken 插件（Agent Plugin）能力的唯一权威。插件层是包管理与来源层，不是第二套 Skill runtime 或第二套 MCP runtime。

## 1. 当前支持

用户可在 Desktop 扩展导航「插件」页，以显式动作安装符合 Agent Plugins 1.0.0 的第三方插件目录（root `plugin.json` + 可选 `skills/` + 可选 `mcp.json`）。模型也可通过 strict-v2 `plugin` 工具 inspect 已安装 identity、把完整包 export 到普通作者目录、对候选 source 做零写入 validate，以及在复核后 install/replace。Core `src/plugins` 拥有合规解析、校验、受控导出、安装、状态、启停、升级与卸载，并把启用插件的 Skills / MCP servers 注入既有 08 / 06 运行时。

Workbench 与定时任务 Agent 编辑器还可通过 `@` 选择已启用 Plugin；首页与对话 Composer 同时在 `+` 右侧提供同目录的插件快捷入口，最多预览三个统一拼图默认图标，并可展开只含默认图标与插件名的紧凑完整列表；没有插件时入口仍常驻并显示空状态，定时任务不显示该快捷入口。两种选择都只形成带 `pluginName + pluginDigest` 的结构化 token，不复制插件组件；每次普通 run 或计划触发前，Core 都从 Store 重新确认包仍存在、已启用、digest 未变化且至少有一个可用 Skill/MCP 组件，然后才在 model-facing effective input 注入固定宿主引导。display input、Journal 和 replay 不保存该引导。Plugin Store mutation 通过 composer catalog revision 同时刷新已打开的 `@` 目录和快捷入口，已经开始的 run 继续使用自己的固定工具/技能快照。

### 1.1 包格式

- 只认 plugin root 的 `plugin.json`。`$schema` 白名单仅 `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`；不支持的版本拒绝整个插件。
- `$schema`、`name` 和可选 metadata 按 JSON 原值校验，不以 trim 修复非法包；除规范明确允许忽略的非 object `extensions` 外，字段出现 `null` 不能冒充其声明类型。
- `name`：1–64 字符、`a-z0-9.-`、首尾字母数字、禁 `--` 与 `..`。`name` 同时是 identity 与 `packages/<name>` 目录名。
- 未知顶层字段与非 object 的 `extensions` 报告并忽略；其余 schema 违规 fatal，拒绝插件且不发现组件。
- Skills 只发现 `skills/` 的直接子目录（含普通文件 `SKILL.md` 者），不递归。每个入口按 Agent Skills portable contract 严格要求显式 `name`/`description`、合法名称并与父目录一致；无效 Skill 标记 invalid、报告并跳过，其他 Skills 与 MCP 继续。`skills/` 缺失不是错误；存在但不是目录时仅 Skills 组件 invalid。
- `mcp.json` 为 closed schema，顶层仅 `$schema` + `mcpServers`；`$schema` 必须与 manifest 同版本，否则该插件 MCP 整体停用，Skills 继续。支持 stdio / streamable-http / sse。未知 type、未知字段或跨变体字段使该条目 invalid 并跳过。
- 路径必须 `./` 开头、禁 `..`、禁绝对路径/盘符；经 symlink 解析后必须留在 plugin root。
- 占位符仅 `${PLUGIN_ROOT}`、`${PLUGIN_DATA}`，只在 `args`、`env` 值、`cwd` 单遍展开；`command` / `url` / headers / env 键不展开。`cwd` 只接受 `./`、`${PLUGIN_ROOT}`、`${PLUGIN_DATA}`。stdio `command` 的 `./` 在翻译时落成绝对路径。
- `env` 出现 `PLUGIN_ROOT` / `PLUGIN_DATA` 保留名使该 server invalid。
- `./` stdio command 必须在物化后的包内解析为普通文件；macOS/Linux 还必须保留执行意图。command 作为一个完整 executable token 交给 transport，文件名包含空格时不得拆成 shell command。
- HTTP/SSE 固定 headers 只发送给配置 URL 的同 origin；重定向或 legacy SSE endpoint event 进入不同 origin 时不转发。MCP、OAuth 与宿主生成的同名 header 优先。

### 1.2 安装、升级与卸载

正式路径走 `desktopdata.AwakenHomeRoot()`（`AWAKEN_HOME`）。未注入时 fail closed，不写真实家目录。用户可见路径仍写成 `~/.awaken/...`。

```text
~/.awaken/plugins/packages/<name>/   # PLUGIN_ROOT
~/.awaken/plugins/data/<name>/       # PLUGIN_DATA，跨升级保留
~/.awaken/plugins/.staging/<uuid>/
~/.awaken/config/plugins.json
```

来源：`local_path`（目录或 zip）、`remote_url`（HTTPS zip）、`remote_git`（HTTPS git + 可选 ref/subpath）。安装期零包代码执行。上限：下载 100MiB、解包 500MiB、10000 文件；拒 symlink/hardlink/zip-slip/逃逸。

同名默认 abort；`replace` 把旧包移入平台 Trash，失败回滚且 fail closed。物化与完整导出把普通文件规范化为 owner-only `0600`，把来源中带任一执行位的文件规范化为 owner-only `0700`；本地目录、zip、HTTPS zip、HTTPS Git 与 export 使用同一规则。新 digest 使用 `sha256-v2:`，对 POSIX 相对路径排序后的文件内容 SHA-256 与“是否可执行”共同摘要；既有 `sha256:` 记录按旧 content-only 算法只读兼容，下一次替换升级为 v2。升级时来源与当前安装树均保持相同 digest 才 no-op。

`List`、`Get`、Skill root、MCP config 与 Plugin token 复验都重新计算安装树实际 digest。包内容或 v2 执行意图变化时产生 `plugin_digest_changed` 并 fail closed，不再注入该包的 Skill/MCP；损坏包也不能 export。`PLUGIN_DATA` 必须是 Store data root 内的普通目录，不能以 symlink 指向外部；其解析后路径与 plugin root 解析后路径分别作为 `PLUGIN_DATA` / `PLUGIN_ROOT` 注入。卸载把 packages 与 data 一并移入 Trash，成功后删除状态记录。`plugins.json` 使用与 MCP 相同的锁 + 临时文件 + fsync + 原子 rename；损坏 fail closed，不影响非插件 Skills/MCP 与 Desktop 启动。

Creator 校验调用 `PluginStore.Validate`：source 只进入隔离 `.staging`，另建隔离 validation data directory，复用正式 materializer、`plugin.json` parser、containment、digest、`LoadPackage`、严格 Agent Skills loader 与 `mcp.json` parser，返回 identity、digest、可加载 Skill/server 数和 diagnostics，不写 `plugins.json`、packages/data 或 live runtimes。manifest、来源/materialization 与整体安全错误会使 `valid=false`；按 Agent Plugins failure isolation，单个 Skill、整个 Skills fixed location、单个 MCP server 或顶层 `mcp.json` 无效只报告被跳过/停用的 component diagnostic，不使独立组件不可安装。Creator 仍必须核对所有本次意图组件均进入可加载计数，不能把“包可安装”冒充“每个组件有效”。`plugin action=export` 在 Store lock 内先复验在线包 digest，再把完整包原子复制到此前不存在且位于 store 外的作者目录，保留 Skills、脚本与二进制执行意图，不复制 `PLUGIN_DATA`。安装 action 对 Creator 候选先 validate；`valid=false` 时安装不开始，并把 validation digest 作为正式 materialization 的 expected digest，source 的内容或执行意图在两步间变化会以 `plugin_source_changed` fail closed，不能把旧 dry-run 结论套到新内容。

替换时旧 package 先同盘进入 Store-owned rollback staging，新 package 激活并原子写状态后，旧 package 才进入平台 Trash。任一激活、状态或 Trash 步骤失败都会恢复旧 package 和旧状态；`PLUGIN_DATA` 不参与替换并继续保留。

### 1.3 Skills 注入

`PluginStore.EnabledSkillRoots()` 是 08 域 `plugin` 来源的唯一 root 供给。`AWAKEN_PLUGIN_SKILL_DIRS` 已退役。Catalog ID 为 `plugin__<plugin-name>__<skill-id>`，plugin-name 中的 `.` 规范化为 `-`。`ValidateNameReserved` 拒绝本地包冒用 `plugin__`。激活、预览、`skill_resource_list`、`skill_resource_read` 与 Hook 边界沿用 08 现有契约。Skills 页删除入口对 plugin 来源保持禁用。

### 1.4 MCP 注入

`MergeScoped(plugin, user, project, dynamic)`，plugin 最低。server identity 为 `plugin__<plugin>__<server>`（保留点号），工具为 `mcp__plugin__<plugin>__<server>__<tool>`。由于 plugin server identity 自身包含 `__`，Manager 调用时按当前 server registry 的最长 identity 前缀解析 owner，不能按第一个分隔符截断为 `plugin`。stdio 在配置 env 叠加之后由宿主写入 filesystem-resolved `PLUGIN_ROOT` / `PLUGIN_DATA`。插件配置在 `src/plugins` 完成规范限定的单遍替换后，`MergeScoped` 不再对 plugin scope 执行 user/project 的通用 `${VAR}` 展开；command、URL、headers 与未知 placeholder 保持字面值。启停后 `RestartWithConfig`；消失的 `plugin__` server 从 Manager 移除。连接器「用户安装」排除 `plugin__` 前缀。

插件 MCP stdio 子进程与现有 MCP server 一样未接入 WorkspaceExecutionBroker/Seatbelt，以当前用户身份运行，可读写宿主文件并联网。安装确认必须呈现这一事实；文档不得因“来自插件”宣称额外沙盒。

### 1.5 管理面

```text
GET    /v1/plugins
POST   /v1/plugins/install
GET    /v1/plugins/{name}
POST   /v1/plugins/{name}/enable|disable|upgrade
DELETE /v1/plugins/{name}
POST   /v1/plugins/{name}/servers/{short}/enable|disable
```

store 缺失 → 503 `PLUGINS_UNAVAILABLE`；状态损坏 → 503 `PLUGIN_STATE_CORRUPT`。Desktop 插件页产品交互由 [01 插件页](../01_桌面工作台/扩展管理/插件页产品与架构.md) 拥有。

### 1.6 模型创作面

bundled `plugin-creator` 是模型工作流 owner，本身携带完整 Skill/Plugin 目录说明、资源规划参考、确定性候选脚手架与预检器；它不依赖文字提到另一 Skill 后自动获得其正文。create 与 modify 都在任务 workspace 的完整候选目录完成；modify 固定为 `inspect -> export -> edit -> preflight -> validate -> reviewed replace`。它不定义第二套 schema，也不通过 Bash/文件工具编辑 `~/.awaken/plugins`。候选中的包内 stdio command 必须先完成真实 initialize/tools list；Plugin 中 stdio MCP 没有额外沙盒的事实必须在安装前披露。安装/替换后当前 run 必须停止，只有新 run 的结构化 Plugin 选择、Skill 文件树/资源读取、MCP readiness 与真实无害 tool call 能形成运行验收；不得用 Bash、直接二进制或业务 HTTP 冒充 Plugin 调用。

### 1.7 Composer 选择

- `@` 目录与 Composer 快捷入口只展示当前 enabled、有 digest 且至少有一个可用 Skill/MCP 组件的 Plugin；digest 漂移或组件数为零的包只留在插件管理页展示诊断，不能被计入“可用”或生成 token。WorkBench 同时保留 Computer Use，定时任务不暴露无人值守 Computer Use。
- 首页 `center` 与对话 `dock` 在 `+` 右侧常驻同一有效组件目录的快捷胶囊；胶囊最多预览三个统一拼图默认图标，弹层不提供搜索，只以紧凑的默认图标与插件名行滚动展示全部可用插件；没有可用组件时显示“没有可用插件”，即使插件管理页仍保留一个诊断中的损坏包也不能计入数量。选择复用同一 token producer 和逻辑 caret 插入规则；定时任务与 `embedded` Composer 不渲染该快捷入口。
- catalog revision 同时驱动 `@` 目录与快捷入口重拉；Design System 不读取 Plugin Store，只接收 options/loading/error 和选择回调。
- token 不携带组件路径、Skill 正文、server 配置或工具清单；这些事实只由 Store、Skill Registry 与 MCP Manager 拥有。
- Plugin 被升级、禁用、删除或失去全部可用组件后，旧 token 在模型启动前失败；不按名称回退、不静默选择同名新版本。
- Plugin token 只表达本 turn 的用户选择，不临时启用插件、不绕过 MCP readiness，也不改变已开始 run。

## 2. 当前不支持或已知缺口

- Workbench 与定时任务 Agent 编辑器中的 Plugin `@` 目录、结构化选择，以及保持菜单打开时安装/卸载后的原地刷新，已在当前 macOS Desktop 复验。带真实模型执行、重启恢复，以及完整 2.1 生命周期场景（三种来源、Skill 激活、MCP 工具调用、启停、升级、损坏 fail closed 展示）仍缺少完整实机证据。
- `plugin-creator` 的真实模型 create + modify、dry-run、Trash replace 与新 run 发现/调用尚未在本工作区留下可追溯实机证据。
- 生产 Linux 平台 Trash 不可用时 replace/卸载 fail closed，与 Skill 删除同语义。
- Tool Catalog 的 `SourcePlugin` 仍是预留值，插件 MCP 工具继续以动态 MCP provider 注册，不改 04 来源枚举语义。

## 3. 已确认但尚未实现的设计约束

- 不兼容 legacy manifest（`.codex-plugin/`、`.claude-plugin/`、`.cursor-plugin/`）。
- 不自建 marketplace / registry；不实现 npm 来源。
- 不支持 project scope 插件。
- 不实现 commands/agents/apps/LSP 等非 v1 组件；`extensions` 与全部 extension 目录（含 `io.awaken/`）忽略。
- 不提供插件自动 Hook。插件内 Skill 的 frontmatter hooks 仍只在 composer 显式激活后注册。未来若做必须先改 [04 Hook 契约](../04_工具权限与审批/Hook产品与架构契约.md)。

## 4. 不变量

- 插件层只决定哪些 root / 哪些 server 配置、以什么 identity 进入 08/06；不复制 Skill 激活或 MCP transport。
- 安装不改写用户既有 `~/.awaken/skills`、`mcp-servers.json`、`hooks.json`。
- 对已开始的 run 无影响（工具/技能快照固定）。
- 组件级失败隔离：单 skill / 单 server 失败不拖垮插件；`mcp.json` 顶层失败只停用该插件 MCP。
- 正式路径必须使用 `AWAKEN_HOME`；测试必须隔离临时目录。

## 5. 代码 owner 与测试

- `src/plugins`：manifest / `mcp.json` / containment / store / validate / export / install / remote。
- `src/skills`：plugin root 供给、`plugin__` ID、保留前缀。
- `src/mcpclient`：`ScopePlugin`、`MergeScoped`、stdio `PLUGIN_*` 注入。
- `src/server/handlers_plugins.go`：HTTP。
- `src/tools/plugin`：strict-v2 模型 inspect/export/validate/install surface。
- `cmd/awaken-core/main.go`：Store 注入、启动装配与变更后 reload。
- `src/runtime/run_service.go`：Plugin token 的 run-start 复验与 host-owned model expansion。
- `apps/desktop` + Design System：插件页、`@` provider、token 与 catalog revision 投影。

当前自动化：`go test ./src/plugins/... ./src/skills/... ./src/skillruntime/... ./src/tools/plugin/... ./src/mcpclient/... ./src/runtime/... ./src/scheduledtask/... ./src/server/...`，以及 Desktop/Design System typecheck。它覆盖官方 1.0.0 closed schema 边界、dry-run 零写入、local/zip 物化与 export 执行意图、安装后二进制真实 stdio initialize/tools list/tool call、含 `__` plugin identity 的调用路由、v2/legacy digest、在线树漂移 fail closed、完整导出、digest pin、replace/Trash 回滚、Plugin scope literal placeholder、filesystem-resolved root/data、fixed-origin headers、strict tool definition、Plugin token 当前身份复验、隐藏引导、定时任务持久化和 catalog revision；这些仍不能代替真实模型端到端 Desktop 验收。
