# 连接器验收规范

## 1. 静态复核

1. 从 `src/connectors/source_builtin.go` 数出七个 builtin，不使用文档旧清单。
2. 核对 Desktop MCP/CLI 分类和“Awaken 内置/用户安装”分组仍由 `ExtensionsView.tsx` 实现。
3. 核对 builtin 走 `SaveUserConfig + Manager.Start`，local 走 `InjectDynamic`。
4. 核对 Registry 启动时 active map 为空，且没有从 Manager snapshot 反向恢复 owner。
5. 核对 connector handler 没有启动 OAuth，避免把 `authType` 当成已授权。

## 2. 自动化

```bash
go test ./src/mcpclient ./src/server
npm --workspace @awaken/desktop test -- ExtensionsView.test.ts
npm run typecheck:desktop
git diff --check
```

当前 `src/connectors` 没有独立 `*_test.go`；`ExtensionsView.test.ts` 现有唯一用例测试的是多workspace Skill列表容错，不覆盖七个builtin、MCP/CLI分类、connect/disconnect或restart ownership。因此上面的命令只提供邻近回归，不能称为Connector自动化通过。修改这些事实时必须补connector单元/集成测试；补齐前仅能以代码审计和隔离Desktop人工验收记录。

## 3. 真实 Desktop 只读验收

按根 README 启动 Desktop，在连接器页检查：

- `MCP` 下内建区显示 Puppeteer、Chrome DevTools MCP、Playwright、GitHub 和 context7。
- `CLI` 下显示钉钉CLI、飞书CLI。
- 用户安装 MCP server 与 builtin 卡片分组显示。
- 搜索、分类切换和状态文本可用。

本轮只读验收不点击任何加号/X、不保存 MCP config、不停用/删除 server。builtin 加号会立即覆盖并持久化同名 user MCP config，不是可安全试点的只读控件。

## 4. 需修改状态的验收

只能在可抛弃 userData/workspace 上验证：

1. builtin connect 写入预期 user MCP config，server 从 pending 进入最终状态。
2. builtin disconnect 删除该 config 和 tools。
3. local connect 仅注入 dynamic，restart 后消失。
4. builtin 持久 server restart 后仍在 MCP 列表，但 connector 卡片 owner 不会自动恢复。
5. 同名自定义 user MCP config 在 builtin connect 前必须备份，验证 factory 覆盖的当前行为后恢复隔离环境。

## 5. 失败条件

- builtin 清单与代码不同。
- 把 team remote registry、完整 OAuth、shadowed definition 保留或 restart ownership 写为已支持。
- 把“connect API 返回 200”当成 server 已 connected/已授权。
- 在真实用户 profile 中通过点击 connect/disconnect 完成所谓“只读验收”。
