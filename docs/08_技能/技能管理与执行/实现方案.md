# 技能管理与执行 · 实现方案

本文说明代码职责、数据与接口、异常恢复和验证方法。功能范围及用户操作见[需求文档](需求文档.md)。

## MCP 调用参数

统一 `skill` 工具仍使用 `skill` 和可选字符串 `args`。MCP prompt 的 args 须是命名字符串参数的 JSON 对象文本，例如 `{"name":"Ada"}`；Activator 在访问服务器前解析并校验必填项，将值传给 `McpBodyFetcher.FetchBody`。类型非法或缺少必填参数时不发起远端调用。普通本地 Skill 保留原有自由文本参数；MCP 返回的正文由服务器渲染，不再重复替换。正文、资源 URI 与文本边界见 [MCP 桥接](../../06_MCP运行时/工具与技能桥接/实现方案.md#promptresource-skill-bridge)。`mcp_arguments_test.go` 从实际 CatalogTool.Invoke 入口验证参数传递与失败边界。

## 当前支持

Awaken 把 Skill 视为可发现、可按需读取的完整知识/工作流目录包，而不是一组在启动时注册的新工具或一份孤立 Markdown。目录发现只读取元数据；调用时才读取锚定的 `SKILL.md` 正文。模型可用 `skill_resource_list` 取得不含绝对路径和正文的有界包内文件树，再用 `skill_resource_read` 按需读取 UTF-8 supporting resource。Skill 不改变父 run 已固定的工具可用性快照。

Registry 对本地来源刷新维护稳定的工具状态指纹：相同来源、相同 `SKILL.md` 内容的连续 reload 不发布无差异 `onChange`。指纹只覆盖模型可见 Catalog 和调用所需的真实 binding；最近调用时间、connector/MCP readiness 诊断等展示或执行提示不触发统一 `skill` 工具重注册。正文仍不进入模型上下文，但其内容摘要属于调用 binding，因此正文变化即使没有改变名称或说明，也会发布一次真实变更。

run 的 `ExecutionEnvironmentSnapshot` 只把本地发现合同中的 source + 绝对路径根记为有界元数据（最多 64 项），用于重现环境来源。生成快照不遍历包、不读取 `SKILL.md`、不预加载上下文，也不执行 scripts/hooks；MCP 动态 Skill 没有本地根，不伪造路径元数据。根元数据不是读取或执行授权。

frontmatter `hooks` 当前接入 04 域统一 HookRuntime，但只在 composer 显式选中的 Skill 已完成耐久 `skill_activated` 后注册到当前 run。目录发现、Skills 页面预览、安装/同步和模型自行调用 `skill` 都不注册或执行 Hook。command 入口必须是包内相对路径，激活时经过 package realpath 与逃逸校验；注册后只对后续边界生效，不追溯 `RunStart`/`UserPromptSubmit`，下一 run 必须重新明确选择。项目 Skill 的本次 composer 选择是 run-scoped 执行授权，不形成永久项目 Hook trust。

composer 只有 Skill token、没有附加文字时，耐久/展示 user message 仍保存为空；Host 仅为 provider 请求补入稳定的最小任务句，并把完整 Skill 正文维持在 host-owned system context。这避免上游拒绝空 user message，同时不伪造用户写过的文字。

### 来源与优先级

同名 Skill 按以下高到低优先级 first-wins：

1. `managed`；
2. `project`；
3. `additional`；
4. `user`；
5. `plugin`；
6. `agents`；
7. `mcp`；
8. `bundled`；
9. `legacy`。

`agents` 是 `.agents/skills` 的只读发现来源：它发现用户级 `~/.agents/skills` 和项目级 `<workspace>/.agents/skills` 中的包，但 Skill Registry 和 Skills 页面不参与这些包的安装/删除生命周期，也不迁移或覆盖原有包。连接器域是一个显式的外部 owner：Awaken-managed 钉钉/飞书 CLI 安装会把固定版本、经过校验的官方 `dws`/`lark-*` 包写入用户级目录；进入目录后仍只按 `agents` 来源发现和读取，不能通过通用 Skill 删除 API 管理。

每个目录内确定性排序；同名或 realpath 冲突的低优先级条目仍保留 `shadowed` 诊断，不会悄悄消失。

source root 层先做 canonical realpath 去重：同一真实目录被多个来源配置命中时（例如 project workspace 等于用户 home 使 project/user 技能目录重合，或某来源 root 是另一来源 root 的 symlink），该目录只被最高优先级来源发现一次，不产生整批 `shadowed` 重复卡片。`shadowed` 只用于真正不同的包发生同名或同 realpath 竞争。

默认目录：

| 来源 | 当前目录或配置 |
| --- | --- |
| `managed` | `AWAKEN_MANAGED_SKILL_DIRS`；未设置时 macOS `/Library/Application Support/Awaken/skills`、Windows `%ProgramData%/Awaken/skills`、Linux `/etc/awaken/skills`；平台默认不可解析时回退 `~/.awaken/managed/skills` |
| `project` | 项目全部已挂载文件夹的 `<folder>/.awaken/skills`，主文件夹优先，随后按项目文件夹顺序 |
| `user` | `~/.awaken/skills` |
| `agents` | 全局 `~/.agents/skills`（macOS `/Users/<用户名>/.agents/skills`、Windows `%USERPROFILE%\.agents\skills`）和项目级 `<workspace>/.agents/skills`；只读兼容来源，不迁移、不覆盖 |
| `additional` | `AWAKEN_ADDITIONAL_SKILL_DIRS` 的 OS path-list |
| `plugin` | Core `PluginStore.EnabledSkillSelections()`：每个启用、完整性有效且 component desired/configuration 可运行的精确 Skill package root。`AWAKEN_PLUGIN_SKILL_DIRS` 已退役；测试通过 `skills.SetPluginSkillSelections` 注入。单个 component override 不再要求停用整包 |
| `bundled` | Core 读取 `AWAKEN_BUNDLED_SKILL_DIRS` 的 OS path-list；Desktop 清除继承值后固定注入 `~/.awaken/skills/system-skills`，Core 自身没有隐式 fallback |
| `legacy` | `AWAKEN_LEGACY_COMMAND_DIRS`，以及 project/user 的 `.awaken/commands` 兼容位置 |
| `mcp` | 由 MCP bridge 动态注册，不对应本地安装目录 |

plugin 来源继续完整进入统一 Registry 与 model-facing Catalog；技能页和 `/` 对该来源的隐藏只是 Desktop 产品入口策略。`EnabledSkillSelections()`、精确 package root、`sourceOrigin="plugin"`、Catalog ID 与模型侧 `skill` 调用均不得因入口分离而删除或改写。

project 来源以一个项目的完整文件夹组作为发现边界：主文件夹的 `.awaken/skills` 先加载，其他文件夹按项目持久化顺序随后加载。同一项目的不同文件夹出现同 ID 时，主文件夹优先；若主文件夹没有该 ID，则较早的次文件夹优先，其他定义保留 `shadowed` 诊断。每个定义的 `ProjectPath` 保留它实际来自的文件夹，因此 Desktop 和模型轻量 Catalog 都能说明来源；完整 `SKILL.md` 仍只在预览或调用时从该锚点重读。

`agents` 与 `legacy` 是独立兼容来源，仍只锚定项目主文件夹和用户级目录；本轮多文件夹扩展不把次文件夹的 `.agents/skills` 或 `.awaken/commands` 并入 project Skill。切换主文件夹会改变同 ID project Skill 的优先顺序，也会同步改变项目级 agents/legacy 锚点。项目组成语义由 [项目生命周期与删除](../../01_桌面工作台/项目管理/实现方案.md) 拥有。

`legacy` 兼容嵌套包和无 frontmatter 的平面 Markdown；新包应使用目录中的 `SKILL.md`。

`system-skills` 是大小写不敏感的保留目录名。project、user、managed、additional、plugin 等普通 source root 扫描到这个直接子目录时必须跳过，不能把它报告成 invalid Skill；Desktop 同时把 bundled source root 直接指向该目录内部，因此其中的直接子包仍按 bundled 正常加载。这个双层合同防止 `~/.awaken/skills` 的 user 扫描与 Desktop bundled 扫描重复发现同一批包。

Desktop 从应用资源同步 bundled 根，内部 `.manifest.json` 不进入 Core、模型、Journal 或 Renderer。同步细节与失败降级由 [技能页产品与架构](需求文档.md) 拥有。

仓库当前随附 `word` / `excel` / `ppt` / `pdf` / `code-search` / `PDF_Max` / `skill-creator` / `plugin-creator` 八个 bundled Skill 包（`apps/desktop/resources/system-skills`）。三个 Office 包继续以 Awaken 当前 `Bash`、文件工具、依赖恢复与 `artifact_publish` 为宿主合同，不注册或恢复已退役的 typed Office runtime：

- `word` 提供中文任务路由、创建/高保真编辑 references，以及按 route 的能力探测、安全 OOXML 解包/打包、保守 run 合并、结构/关系校验、独立 LibreOffice profile 接受修订和逐页渲染脚本；DOCX/DOTX 阅读固定使用包内纯标准库 `read_docx.py`，输出 Markdown、结构化 blocks、warnings 与 stats，不再让模型在 Pandoc、MarkItDown、LibreOffice 或第三方 Python reader 之间试错；
- `ppt` 提供中文创建/模板编辑/设计/三层 QA 路由，以及按 route 的绝对执行计划、安全 OOXML 解包/打包、页面/关系/content-type/shape-ID/常见图表校验、严格逐页渲染和缩略图网格脚本；
- `excel` 提供中文创建/编辑/公式/财务模型路由，以及按 route 的绝对执行计划、表头候选/列类型/零值/混合类型输入剖面、工作簿公式缓存/错误/宏/外链/高风险函数检查和独立 LibreOffice profile 重算脚本。重算只接受 `.xlsx`，外链、宏和模板文件不通过普通重算路径静默降级。

这些脚本只在 Agent 按 Skill 正文明确调用 `Bash` 后执行；discovery、Desktop 同步和 Skill 激活不会运行脚本、探测依赖或安装软件。三个 Office doctor 均按 route 分别报告 readiness，并返回 Python 版本、最低 3.9 合同、dependency root 和本轮可复用的绝对 executable plan；未选路线的缺失依赖不能把当前路线整体判为不可用，也不能诱导 Agent 安装无关依赖。缺失依赖由 Agent 根据目标 route 的真实 doctor/命令错误使用当前 `dependency_install` 候选计划或普通 `Bash` 恢复。JSON helper 不允许用 `tail/head/grep` 等管道截断或覆盖退出码，wrapper 失败也不允许退化为裸 LibreOffice/Poppler 命令。Word reader 的 warning 是语义覆盖边界：图片、空间布局、复杂公式、修订、文本框或嵌入对象未被完整解释时，Agent 必须补视觉路线或限定结论，不得把线性提取冒充完整理解。结构校验、LibreOffice 重算/渲染与逐页图片分别证明不同层次，均不能单独证明业务内容正确；用户需要的新建／编辑文件仍需位于 output root 并显式 `artifact_publish`；只读问答说明实际覆盖范围，不为完成 Skill 而另造文件、重算原工作簿或发布原件。

`pdf` Skill 的阅读入口固定为 `Read`：未知页数时首次优先显式传 `pages: "1-10"`；若模型省略，宿主也会把长 PDF 的渲染页路线自动归一化为首段 `1-10` 并返回成功 Outcome，`route=native_pdf` 则代表原生整份已完整交给模型；再按 `route/page_count` 继续剩余范围，不用失败调用探测页数。当前模型既无原生 PDF 又无视觉时，`Read` 返回 `model_pdf_unsupported`，Skill 正文要求立即停止阅读类任务并请用户换模型，禁止用 Bash/`pip`/`venv`/Poppler/OCR 或其他 Office Skill 依赖绕过。合并、拆分、新建、填表等加工/生成路径仍可按正文使用 Bash，但不能用来冒充“已读懂”用户点名的 PDF。

`PDF_Max`（调用 ID：`pdf-max`）只承接 Typst 精排**生成**；正文含同样的阅读硬停，且生成后 `Read` 视觉复核若遇 `model_pdf_unsupported`，只允许声明跳过复核并建议换模型，不得为复核安装 Typst/Python/Poppler/OCR 绕过。

`code-search` 固定为 inline 主上下文，以 `WebSearch` 定位公开资料，需要原文核验且当前 run 可用时使用 `WebFetch`；工具不可用时限定结论，不把摘要当全文。不注册独立基础工具，也不调用已弃用的 Exa code-context 工具；只有 subagent 产品入口和真实 Desktop 验收完整后才能评估迁移为 fork。`PDF_Max` 负责专业长文档、Markdown 精排、论文/简历和用户明确要求的 Typst/PDF 幻灯片，通用 PDF 加工仍由 `pdf` 拥有；包内不携带 Typst CLI，Agent 按正文检查固定 Awaken toolchain 路径和系统 PATH，缺失时显式安装固定受测版本。包进入 Catalog 只证明发现和加载合同成立；真实模型端到端验收状态以 [验收规范](实现方案.md) 为准。

`skill-creator` 与 `plugin-creator` 只拥有模型侧创作编排，不拥有第二套 schema、路径或安装实现。两者本身是包含 `SKILL.md`、`references/` 与 `scripts/` 的完整 bundled Skill 包：按任务选择有价值的资源，用包内确定性脚手架建立候选并做标准预检；简单技能可以只有 SKILL.md，不为目录数量强制扩展工作。Skill 修改固定先经 `skill_package_export`；Plugin 默认也通过 `plugin action=export` 修改候选，再分别用 `skill_install validate_only=true` 或 `plugin action=validate` dry-run 并进入既有安装器。只有用户在当前请求明确授权修改准确的已安装 Plugin 时，`plugin-creator` 才可固定修改前 digest，通过插件仓库的 TaskScope 例外以 `Read` + `Edit` / `Write`（或必要时当前用户 `Bash`）写该 `PLUGIN_ROOT`，并以 `plugin action=commit` 完整校验、CAS 签收；它不直接编辑 `PLUGIN_DATA` 或 `plugins.json`。任何结构校验或 commit 成功都不冒充新 run 中的真实行为验收。

### 按需工作流与辅助脚本

内置 Skill 的 SKILL.md 保留准确触发、路线表、共同边界和分路线完成条件；具体创建／编辑／安装／恢复／QA 步骤由入口链接的 supporting resources 拥有。目录元数据不重复排列全部能力；正文激活不预加载这些参考。保持既有 Skill ID（包括兼容名称 PDF_Max），不因重排正文改变来源或权限。

PDF 表单工具通过 pypdf >= 6.10 的字段／widget 页面查询返回真实页码：每个可见字段每页一行，完整层级名为 field_id，无法定位时 page 为 null 并带 warning。填表拒绝未知字段、错误页码、同字段冲突值、无值请求及已有输出；重复字段更新全部 widget 页面，写出前回读字段值。成功 JSON 的 fields/pages 用于核对实际处理范围与视觉检查。字段定位由 `pdf/scripts/form_fields.py` 共享，入口／填写流程由包内 `pdf/references/forms.md` 路由。只看首页不能证明多页填写成功。

Typst 规划器的 enhancement_decisions 输入包含当前 plan.decision_context、accept 和 reject ID 数组。context 绑定不含决策的任务清单、目录内容及 Typst 版本；接受与拒绝不能重叠，未知 ID、过期 context 被拒绝。仅当前匹配且不违反约束的接受项进入 enhancements，拒绝项进入 exclusions，剩余候选继续确认；原有冲突组不被确认绕过。包内 `PDF_Max/references/路线规划.md` 拥有模型填写示例，旧计划只提供复用提示，不提供自由命令或确认授权。

两个 Creator 预检器识别 Markdown 链接、代码／引号内完整 Unicode 包内路径与常规相对路径，支持空格和 URL 编码，区分外部绝对路径／URL，不从其中截取 scripts 或 references。解析后仍检查包内 containment；结构预检不替代 Core YAML 校验。两个可独立分发的包各自携带此逻辑，由同一组行为用例验证。

### 状态

目录状态只有：

- `loaded`：结构合法，可供目录和调用链使用；
- `invalid`：无法形成合法 Skill；
- `shadowed`：被更高优先级同名或同 realpath 条目覆盖；
- `disabled_by_policy`：命中明确的 source policy。

Connector、MCP、runtime、工具或资源 readiness 只形成执行提示/诊断，不会把结构合法包置灰。旧 `available/unavailable` 及“缺依赖即禁止激活”不再是当前契约。

### Frontmatter

当前宽松解析以下常用字段及 camelCase/kebab-case 别名：

- `name`、`description`、`when_to_use`；缺少名称/说明时可由路径或正文首段兜底；
- `allowed-tools`、`arguments`、`user-invocable`、`disable-model-invocation`；
- `context`、`agent`、`model`、`effort`；
- `hooks`、`paths`、`shell`、`awaken`；
- 旧 `required*` 字段。

未知 frontmatter 原样保留，非通用 `required*` 产生 warning 而不是激活检查要求。`allowed-tools`、required tools/capabilities/runtime 只是模型选择提示和执行 receipt，不是权限声明，也不与父 run 工具池求交。

现有 project/user/managed/additional/agents/bundled 与 legacy 来源继续使用宽松兼容解析，以免旧包因宿主升级失效；缺少 description 时可从正文产生 warning fallback，普通来源名称仍可规范化为稳定 ID。这个兼容边界不等于 portable Agent Skills 校验。新 `skill_install` 候选与 plugin 来源 Skill 必须显式声明 `name`、`description`，`name` 为 1–64 位小写 ASCII 字母/数字/单连字符并与父目录完全一致，`description` 为 1–1024 字符；可选 `license` 出现时必须是字符串，`compatibility` 必须是非空的 1–500 字符字符串，`metadata` 必须是 string->string map，`allowed-tools` 必须是空格分隔字符串。可选字段显式写成 `null` 不等于省略，必须按类型错误拒绝。Awaken 已有扩展 frontmatter 仍由宽松 parser 原样保留，但不能代替或改变这些标准字段的语义。任一不合规 plugin Skill 只标记 invalid 并按组件边界跳过，不能用目录或正文 fallback 冒充 Agent Plugins 合规。

### Desktop 只读预览

`GET /v1/skills` 为所有非 MCP 且拥有本地入口文件的目录条目返回不透明 `catalogEntryId`，包括 Awaken 内置 bundled 来源。该值只标识一次具体 source/root/entrypoint 组合，不包含可供 Renderer 拼接或授权读取的路径语义；MCP 动态 Skill 没有本地 `SKILL.md`，不返回该值，也不能通过公开预览 route 匹配。Renderer 点击后通过 `POST /v1/skills/preview` 提交 `catalogEntryId` 和可选 `projectRoot`，Core 必须重新执行当前来源发现并匹配条目，不能把客户端传入的路径作为读取依据。

一个项目有多个文件夹时，目录请求按主文件夹优先重复提交 `projectRoot`；Core 在一次 Preview discovery 中合并这些 roots，不能由 Renderer 分别加载后自行裁决同名优先级。model-facing Catalog 对 project 条目包含名称、说明、`when_to_use`、`source=project` 与实际 `source_path`；该轻量来源不授予额外路径权限，也不替代 TaskScope 已固定的项目文件夹组。

匹配后 Core 再次校验 host-owned source root、package realpath、直接子包边界、symlink escape、普通文件、UTF-8 和 2 MiB 上限，再从锚定根读取 `SKILL.md` 并列出最多 512 个包内条目。响应包含：

- `frontmatterRaw`：含原始 `---` 分隔线、字段顺序、注释与未知字段的原文；
- `bodyMarkdown`：frontmatter 结束后的完整正文；
- `resources`：仅含 package-relative `path`、`kind` 与普通文件字节数的稳定文件树元数据；
- `resourcesTruncated`：包内条目超过 512 时为 true。

正常 `SKILL.md` 不截断；超过上限、文件消失、非 UTF-8、身份过期或锚点变化必须返回明确错误。资源树只读取目录项 metadata，不读取 references/assets 正文，不执行 hooks/scripts/命令，不替换变量，也不解析正文中的相对资源。Desktop 渲染安全边界与交互由 [技能页产品与架构](需求文档.md) 拥有。

## 必须保持的规则

- 不根据 Skill 文本扫描平台关键字并拒绝加载。
- 不因 Skill 声明某工具而扩大权限，也不因 `allowed-tools` 收窄父 run 快照。
- 不把未知字段丢弃后再伪装成完整兼容。
- 本地包不得冒用 `mcp__` 动态命名空间或 `plugin__` 插件命名空间。
- plugin 来源条目的 Catalog ID 固定为 `plugin__<plugin-name>__<skill-id>`；`<plugin-name>` 取 `packages/<name>` 目录名，其中的 `.` 规范化为 `-`。展示名保留 skill 短名。
- 环境快照中的 Skill root 只是有界来源元数据，不得触发 discovery、preload、resource read 或脚本执行。
- project/user 的同 ID 包继续覆盖 bundled；bundled 条目保留 `shadowed`，覆盖包从磁盘删除并刷新目录后自动恢复为 `loaded`。
- `catalogEntryId` 不是文件 capability；预览必须基于当前 discovery 重新解析条目并重复路径安全校验，Renderer 不直接读取 `skillFilePath`。
- 预览响应不得为了大小限制返回半份 frontmatter 或半份正文；超过 2 MiB 必须整体失败。

## 调用与正文加载

模型调用触发规则是宿主 Prompt 契约，不是宿主侧词法/语义匹配，且只有维护位置文本，不在多处重复维护：`catalog_tool.go` 的模型描述在目录清单前固定携带完整触发规则——用户显式点名 Catalog 中可用的 model-invocable Skill 时必须调用；任务明显匹配某个 Skill 的描述时，调用它是阻塞性要求（必须在该部分任务的普通工具动作之前完成）；多个 Skill 匹配时选择覆盖任务所需的最小集合并声明顺序；已在上下文中的 Skill 不重复调用；没有匹配时按正常工具流程执行，不为了调用而调用。这份规则置于 Catalog 的 1% 预算之外，且随统一 `skill` 工具的 schema 每轮请求一起真实注入，不依赖静态系统提示词的一次性内容。系统提示词的“Skill 选择与调用”节只做一句指向，不重复列出规则；File Tool Priority 中 Office 产物一条据此把 typed artifact provider 定位为匹配 Skill 未规定路径时的执行载体，而不是排在 Catalog 匹配之前的默认选择。自然语言点名仍由模型发起 `skill` 工具调用，其 runtime provenance 是 `InvocationModel`，不会绕过 `disable-model-invocation`；只有 Composer/Slash 结构化 token 预激活才是 `InvocationUser`。是否真正匹配仍由模型判断，宿主不做候选生成或子串匹配。

调用有两条入口：

- 用户显式 Slash token：即使 `disable-model-invocation` 为真仍可调用；
- 模型调用统一 `skill` 工具：`disable-model-invocation` 为真时拒绝。

Runtime 以 token 中的 Skill ID 查当前 registry，并核对当前来源与锚定路径；renderer 路径不是授权来源。激活成功后才更新最近调用时间。

正文在调用时从锚定 `SKILL.md` 或 MCP body fetcher 重新读取。注入上下文包含正文、包根和锚定路径，便于后续按需重读；Windows 的本地包根在模型正文和 `${AWAKEN_SKILL_DIR}` 替换中统一使用正斜杠，既保持绝对路径身份，也避免 POSIX Shell 把反斜杠当转义字符。安装时或目录发现时不 preload 全包资源。

用户从 composer 选择 Skill 时，成功的预激活还会产生 host-owned `ComposerSkillSelection`。该绑定只在当前 run 有效，包含 `skill_id`、registry 校验后的 `source`、`activation_mode`、`invocation=user_composer`、Skill 绝对包根和 `SKILL.md` 绝对路径。

定时任务的 Agent 编辑器复用同一 Slash provider 和结构化 token，而不是把 Skill 名称写成普通 prompt 文本。任务定义可以持久保存 token identity，但不保存 Skill 正文；每次计划触发都把 token 作为该次新 run 的 Composer 选择重新预激活，并重新核对当前 Registry、来源和锚定路径。因删除、禁用用户调用或换源而失效的 token 必须让该次定时 execution 失败，不能静默回退到同名或模型自行选择的 Skill。提醒任务不接受 Composer token。

RequestBuilder 在 Skill 正文之后追加该选择块，因此正文不能伪造宿主选择。单选时，用户说“这个”或“刚选的 Skill”直接指向该 identity；多选时按 token 顺序保留并标记单数指代歧义。历史恢复、model-invoked Skill 和 fork child 可持有各自 SkillContext，但不会冒充父 run 的本轮 composer 选择。

## 包资源

`skill_resource_list` 对本地目录包提供只读资源发现：

- 输入 `skill_id` 与可选 package-relative `prefix`，拒绝绝对路径和 `..`；
- 重新校验 Registry 记录的 source root、包 realpath、单层子包边界和当前 workspace project 身份；
- 返回最多 512 个 package-relative 条目，每项只有 `path`、`kind`、`size_bytes`，不返回绝对路径或正文；
- project/user/managed/additional/plugin/bundled/agents/nested legacy 可列出；flat legacy 只返回自身入口，MCP 动态 Skill 不提供本地文件树；
- 列出目录不执行脚本、不读取 references/assets 正文，也不形成新的路径授权。

`skill_resource_read` 对包内文本资源提供专用读取边界：

- discovery 在 `SkillDefinition.SourceRoot` 记录 host-owned source root，并同时固定包 `ResolvedRootDir`；读取时重新解析当前包 realpath，包根改变即拒绝；
- project/user/managed/additional/plugin/bundled 和 nested legacy 都从 source-root `os.Root` 打开，包必须是该授权 root 的单层子包；flat legacy command 与 MCP Skill 不暴露本地包资源；
- 拒绝 symlink escape、目录、特殊文件和包外路径；
- 单文件最大 2 MiB；
- 只返回 UTF-8 文本；二进制返回 `skill_resource_binary`，调用者改用对应 file/artifact 工具。

`skill_resource_read` 不返回二进制字节；binary assets 仍转交匹配的 file/artifact provider，并继续受其 TaskScope/readiness 契约约束。

## 工具与依赖语义

Skill 激活不会修改 `RunToolAvailabilitySnapshot`，也不会注册 per-Skill 工具。`allowed-tools`、required tools/capabilities/runtime、connector/MCP readiness 都只作为选择提示、诊断或 receipt。真正能否执行由父 run 的固定工具快照、provider readiness 和被选工具的实际合同决定；Skill 不得通过正文扩大 typed provider 的权限，但默认 raw Shell 本身就是当前登录用户的本机执行面，不要求 Skill 专项授权。

这意味着“Skill 可加载”与“它建议的某个执行路径当前可用”是两件事；后者失败时返回结构化工具结果，不回写成 Skill `unavailable`。

Skill 包中的 `.py`/`.mjs`/`.sh` 等脚本在 discovery、安装或激活时都不由宿主自动执行。它们在用户/模型根据 Skill 工作流显式发出 Shell 调用时，以当前登录用户的真实本机环境执行。这条路径可以读写 Skill root、用户缓存和 workspace 外目录，也可以访问网络；它不再依赖 private Workspace staging、Seatbelt 或 TaskScope 先行批准。Shell receipt 只证明直接本机进程事实，不冒充全部脚本副作用的可恢复保证。

首次初始化由 Skill 正文指导 Agent 自行执行，例如在包根 `npm install` 或 `pip install`。依赖可驻留在用户级 Skill 目录中供后续 run 复用；Awaken 不需要根据 `package.json`、requirements 或某个 Skill ID 建立私有安装器。

## SemanticJournal、压缩与重启

成功激活在执行前写入 `skill_activated`；资源读取写 receipt。inline Skill 上下文可从耐久记录重建：

- V2 压缩不按最近顺序删除 active Skill，也不再使用独立 5K/25K 配额；
- 每个完整正文降为包含 Skill ID、正文 digest、锚定 `SKILL.md` 路径和强制重读提示的有界 ref，统一参与完整请求 10% 分配；
- 服务重启先恢复 `skill_activated`，再以最新合法 `context_compacted_v2` 的 Skill refs 安装压后投影，边界后的 activation 继续追加；
- feature flag 回退 v1 时仍可读取旧 `context_compacted`/activation 记录。

fork 的正文属于 child，不注入父 run 的后续上下文；父子调用记录不得互相污染。

## Inline

inline 激活把调用时读取的 Skill 正文和包根加入当前 run 的上下文块。它继承父 run 已固定的模型、工具可用性快照、环境快照、TaskScope 与取消边界；Skill 元数据不能扩大或收窄这些边界。环境快照中的 source/root 只用于记录本地发现来源，不代替调用时的锚定资源读取。

bundled `code-search` 当前固定使用 inline 主上下文。原生 Subagent 已有独立任务运行时和 Desktop 入口，但尚未把 Skill fork 迁移到同一 manager；该 Skill 在统一底座和对应真实 Desktop 验收完成前不迁移为 fork，后续迁移必须同时复核父子上下文隔离、工具继承、来源回传和取消行为。

正式原生 Subagent 的任务注册、并发、控制、持久事件和 Desktop UI 合同由 [原生 Subagent 产品与架构契约](../../02_主智能体闭环/子智能体协作/实现方案.md) 拥有。Skill fork 当前仍保持同步专用链路，不能把两个生命周期或事件 family 混写为同一能力。

## Fork

`context: fork` 当前创建真实 child agent，不再静默降级为 inline。run-scoped `ChildAgentStarter` 优先于 Manager fallback；没有 starter 时返回 `skill_fork_unavailable`。

handoff 包含正文、根目录、锚定路径、参数、agent/model/effort 和工具提示。child 拥有独立上下文，父 run 只接收明确的 child 结果；父 run 的后续 SkillContextBlocks 不混入 child 正文。父子工具能力仍由创建 child 时的显式继承/收窄契约决定，Skill 文本本身不是权限。child 获取的 pinned environment 元数据不授权它预加载根内其他 Skill 或绕过 TaskScope/resource reader。

## MCP 动态 Skill

MCP bridge 把 server 的 prompt/resource 动态注册为 `mcp__<server>__...` Skill：

- 注册时只持有目录元数据和 body fetcher；
- 调用时才请求 prompt messages 或读取 resource 正文；
- server disconnect/disable/reconcile 时注销动态条目；
- re-register 保留进程内最近调用时间；
- MCP readiness 不作为本地 Skill 的加载检查要求；
- MCP 正文中的 shell 文本只是说明，宿主不会在 bridge 内直接执行。

MCP Skill 依旧通过统一 `skill` 工具调用；它不会绕过 MCP transport、认证或 ToolRuntime。

## 执行模式与MCP来源边界：必须保持的规则

- fork 缺少 child starter 时必须显式失败，不能回落 inline。
- MCP server 离线时必须移除其 tools 和动态 Skills，不能继续调用旧 fetcher。
- MCP Skill 不改变父 run 的工具池，也不反向控制 server lifecycle。
- MCP 动态 Skill 没有本地 Skill root；不得为了环境快照 identity 伪造本地路径。

## 执行模式与MCP来源边界：代码位置

- `src/skillruntime/manager.go`：inline/fork 调度与 receipt。
- `src/agentcore/agent.go`、`runner.go`：真实 child-agent handoff。
- `src/skills/mcp_bridge.go`：MCP prompt/resource 动态注册和注销。
- `src/mcpclient`：MCP transport、认证、tool/provider 生命周期。

## 内置资源同步

Desktop 在启动 Core 之前同步内置资源：

```text
开发版 <appPath>/resources/system-skills
安装版 <resourcesPath>/system-skills
                    │
                    ▼
        ~/.awaken/skills/system-skills
                    │
                    ▼
 AWAKEN_BUNDLED_SKILL_DIRS（Desktop 固定注入）
                    │
                    ▼
        Core 现有 /v1/skills Catalog
```

Desktop 先清除登录环境继承的 `AWAKEN_BUNDLED_SKILL_DIRS`，再注入上述产品固定目标，Shell profile 不能改变产品内置来源身份。同步不新增 HTTP route、Core 特权或 Renderer 文件访问能力。

目标中的 `.manifest.json` 是 Desktop 内部协议，`schemaVersion` 固定为 `1`，包含 `appVersion` 和按 POSIX 相对路径排序的 SHA-256 文件表。每次启动都重新扫描源与目标；清单文件本身不能代替实际文件核对。缺失、修改、额外文件或版本变化都会触发完整目录替换。

同步只接受真实目录和普通文件，拒绝 symlink、特殊文件和源中的保留 `.manifest.json`。更新使用目标同父目录下的 staging、backup 与 rename；中断遗留会在下一次启动先恢复，交换失败则恢复最后完整目标。

## 自动化

至少覆盖：

- plugin 来源只来自 `skills.SetPluginSkillSelections` / `PluginStore.EnabledSkillSelections()`，不再读取 `AWAKEN_PLUGIN_SKILL_DIRS`；逐 component disable 必须从 discovery 移除准确 package；plugin Catalog ID 为 `plugin__<plugin-name>__<skill-id>`，`ValidateNameReserved` 拒绝本地包冒用 `plugin__`；
- Plugin Skill 不得生成普通 user/project Skill 副本；Plugin Console、HTTP 和 Desktop bridge 均不暴露复制或 fork 安装入口；
- 多来源路径、确定性优先级、同名/realpath shadow、无 Core bundled 隐式 fallback；多文件夹项目必须验证主文件夹优先、次文件夹按项目顺序发现、同 ID 次文件夹保留 shadowed、独有 Skill 保留真实 `ProjectPath`，同时证明次文件夹 `.agents/skills` 未被误并入 project 来源；`system-skills` 大小写保留目录在普通来源中直接跳过，而 bundled root 指向其内部时加载直接子包；project/user 覆盖 bundled、bundled 保留 shadowed，移除覆盖后恢复；
- 兼容来源继续覆盖宽松 frontmatter、未知字段保留、四种状态和 source policy；新 `skill_install` 候选与 plugin 直系 Skill 必须额外覆盖 Agent Skills portable metadata：显式 `name`/`description`、合法 name、目录名匹配，`license` 字符串、1–500 字符 `compatibility`、string->string `metadata`、字符串 `allowed-tools`，并覆盖错误类型、超长、空值与显式 `null`；plugin 中单个不合规 Skill 只跳过该组件、不拖垮其他有效 Skill 或 MCP；
- Skill 正文中的 npm/pip、`generate.py`、`soffice`、`pdftoppm`、prompt-injection、删文件或群发文字都只是工作流内容，不在 discovery 阶段置灰/改写正文/执行包内脚本；当前负面回归是 `TestImplementationWordsAndScriptsDoNotDisableSkill`；
- 单一 `skill` 目录预算、用户/模型调用边界、调用时正文重读；`TestRequestBuilderInjectsSkillTriggerRulesAndCatalogIntoFinalToolSchema` 直接检查最终 provider request 的 `skill` tool schema，必须同时携带唯一一份固定触发规则、model-invocable Catalog 条目，并排除 `disable-model-invocation` Skill；触发规则本身不参与 Catalog 预算测试；
- Skill Registry 与统一工具注册的幂等性：同一 source、同一内容的连续 local reload 不触发 `onChange`，`MarkInvoked` 和 readiness 诊断不改变工具状态指纹；Manager 连续 `RefreshTools` 和无差异 reload 保持同一 `RegistrationID`/Registry generation，真实 Catalog 变化和正文-only 调用 binding 变化分别产生新执行 pin；

## 安装边界的实现

`validate_only=true` 使用与正式安装完全相同的严格 Agent Skills entrypoint、Awaken 兼容字段解析、ID、保留名称、包上限和 target resolver，并检查 target 是否已存在：新候选必须显式包含 `name`/`description`，名称符合 portable 格式并在目录/zip 来源中与包目录一致；可选 `license`、`compatibility`、`metadata`、`allowed-tools` 同样按标准类型与长度校验，显式 `null` 不能冒充省略，不再接受从正文或目录推导 portable metadata。`abort` 命中同 ID 时直接返回 `skill_install_already_exists`，只有显式 `replace` 才返回 `target_exists=true/would_replace=true`。成功只返回 `validated`、Skill identity、文件数、总字节数与 proposed `root_dir/SKILL.md`，不创建目录、不替换、不进入 Trash、不 reload Registry。Creator 的零依赖 Python 脚本只负责快速结构/资源预检，不能替代这条由 Core 真实 YAML parser 拥有的规范检查要求。Creator 不能把 proposed target 反写成候选 source；正式安装必须重新提交原候选源，并由安装器再次解析，防止 dry-run 后候选变化被静默信任。

Desktop 删除使用 `DELETE /v1/skills/{id}`，请求同时携带 host-facing `sourceOrigin` 与项目根。Core 不信任 Renderer 展示的 `rootDir/skillFilePath`，而是根据 project/user 安装根重新发现并锚定对应包；只允许删除该根的直接子目录。确认删除后，完整包同步移出 `.awaken/skills` 并进入平台 Trash，成功响应前重载当前 Registry；Trash 不可用、包是 symlink/特殊文件、来源不是 project/user、包已不存在或路径不属于受控安装根时均 fail closed，不回退永久删除。plugin 来源由 [14 插件](../../../README.md#14_插件) 拥有生命周期，Skills 删除 API 拒绝该来源。删除不会从已完成 run 的历史记录中抹除既有 `skill_activated` 事实；后续新 run 与目录刷新不再看到该包。

## 技能管理界面的实现

- `sourceOrigin="bundled"` 只进入 Awaken Skills，来源标签为“Awaken 内置”；
- project 条目进入项目视图，并按稳定 `project_id` 分组；文件夹卡使用项目 `display_name`，不再用主文件夹 basename 伪装项目名。创建项目后立即出现卡片，零文件夹项目也显示 `0 Skill`；
- user 条目进入全局视图；MCP 与 plugin 以外的其他动态/外部来源继续在全局视图的既有分区展示；`sourceOrigin="plugin"` 不进入四个技能视图、搜索结果、数量、空态或预览状态，其组件列表、预览、启停、配置与使用生命周期统一由[插件页](../../14_插件/插件管理与运行/需求文档.md)的 Plugin Console 拥有；
- `sourceOrigin="agents"` 进入 Agents Skills 视图，展示来自 `~/.agents/skills` 与 `<workspace>/.agents/skills` 的包；所有条目直接汇入同一个 Skill 卡片网格，不展示来源根标题、路径、数量徽标、折叠按钮或外层分组卡片。来源根只保留给 Catalog identity、搜索和项目级预览请求；agents 来源是只读兼容来源，可预览 `SKILL.md`，预览中不提供删除；
- bundled 同样只读；project/user 只有进入 `SKILL.md` 预览后才显示删除入口。任何来源的小卡片都不承载删除按钮，MCP 动态 Skill 没有本地文件，不提供详情按钮；
- 拥有本地 `SKILL.md` 和 Core `catalogEntryId` 的卡片主体是可聚焦的详情按钮；开关是独立兄弟操作，不会打开详情；
- 安装弹窗只提供 project/global，不允许把上传内容安装成 bundled；选择普通 `SKILL.md`/Skill ZIP 时继续在所选范围安装，选择插件 ZIP 时不得生成普通 Skill 卡片，而要保留同一已选 ZIP、切换到插件页安装弹窗并执行插件校验；Core 的 `PLUGIN_PACKAGE_SELECTED` 是最终边界，Renderer 不按展示路径或文件名猜包类型；
- 资源根随附 `word` / `excel` / `ppt` / `pdf` / `code-search` / `PDF_Max` / `skill-creator` / `plugin-creator` 八个 Skill 包；三个 Office 包使用中文主流程和按需 references，并随附 Awaken 自有的 doctor、Office/OOXML 校验与重算/渲染脚本。Word 的“接受全部修订”使用独立 LibreOffice profile 输出新文件，超时或任何 Word 文档部件仍残留修订节点必须失败；PPT 渲染拒绝非空旧预览目录并核对注册/渲染页数；Excel 重算只接受 `.xlsx`，在临时副本成功写回后原子替换目标，外链、宏和模板不静默降级。脚本只在 Agent 明确调用 `Bash` 后执行，Desktop 同步/发现/预览均不执行包代码；当前 macOS Desktop 验收基线已覆盖 Word、Excel、PPT 的模型实际生成、内容/结构/视觉 QA、`artifact_publish` 交付卡片和正式关闭/重开后的原线程回放；`code-search` 以内联上下文编排现有 `WebSearch`；`PDF_Max` 不携带 Typst 二进制，由 Agent 按正文检查固定 Awaken toolchain 路径和系统 PATH，缺失时安装固定受测版本；两个 Creator 自身都是带 `references/` 与 `scripts/` 的完整 Skill 包，提供确定性脚手架和预检器，再编排 Core typed 生命周期。`skill-creator` 与 Plugin 默认修改仍走受控导出、dry-run 和安装/替换；用户明确授权时，`plugin-creator` 还可直改准确 `PLUGIN_ROOT`，随后以旧 digest commit 签收，但仍不能直接编辑 Desktop-owned bundled 同步目标、`PLUGIN_DATA` 或 `plugins.json`；
- bundled 目录为空时显示“内置 Skills 未就绪，重启 Awaken 后重试”，不影响其他视图和 Desktop/Core 启动。
- Skill 一级导航、卡片、预览、工具轨迹、Slash 列表以及选择后的 Composer/Prompt token 统一使用打开的书图标；不得在这些入口重新使用六边形、扳手或包裹盒。
- Skills 页面由最外层 Desktop 内容区拥有唯一纵向滚动；居中的内容层只负责最大宽度与左右留白，不拥有独立滚动，因此页面滚动条始终贴近内容区右边界，而不会随内容列向内缩进。滚动 owner 使用对称的稳定 scrollbar gutter：无滚轮与有滚轮状态预留相同空间，切换来源或搜索结果导致纵向溢出变化时，标题、工具栏和卡片网格不得发生横向位移。
- Skills 工具栏缩窄时保持四个来源标签单行完整显示，搜索框在 `360px` 到 `160px` 之间优先随可用宽度收缩；视口进入窄屏断点后，标签和搜索框再切换为上下两行，避免用标签换行承担搜索框的固定宽度。
- Awaken、项目、全局与 Agents 的 Skill 条目全部直接消费 Design System `AwakenSkillCard`，不保留 Desktop 私有卡片实现。卡片固定为 `78px` 高，图标为 `36px`，描述只显示一行并截断，右侧使用 compact 开关；来源以弱化小字紧跟 Skill 名称，不显示“可预览 SKILL.md”文案，也不显示删除操作。内容长度或来源类型不得改变卡片高度。
- Skills 页面可见期间，Renderer 每秒先刷新 active project 实体，再对每个项目把主文件夹优先的完整 folder roots 作为一次 Skill Catalog 请求；Core 每次从本地来源重扫并统一裁决同名优先级。因此项目新建、挂载/解绑/切主，以及 Finder、终端或其他进程对任一文件夹 Skill 包的新增与删除都会自动反映到项目卡片、数量和已打开窗口，不要求用户点击刷新。后台同步失败时保留最后一次成功快照，工具栏刷新仍作为显式重试入口；若当前预览条目从 Catalog 消失，项目预览回到同一个项目列表/空态，独立预览则关闭。
- Desktop 项目 Skills 视图与 Design System 的 Skills 组合都直接消费原子 `AwakenFolder`，使用 `dense` 尺寸并按可用宽度自动填充列；无论只有一个还是多个项目，文件夹都必须从容器左侧开始、按从左到右的项目顺序排列，让宽屏优先容纳更多项目，不得因空列折叠而将少量项目居中。文件夹名称在卡面和辅助技术 `aria-label` 中表达，按钮不添加会触发操作系统原生悬浮提示的 `title`。点击文件夹打开受控的 `AwakenProjectSkillsDialog`，主页面不再向下追加项目详情面板。项目名称只在窗口标题中出现；内容区默认只显示“文件夹数量 + 主文件夹名称”的紧凑摘要和 Skill 总数，点击摘要后由紧凑 `AwakenPopover` 提供“全部文件夹”和按主文件夹优先排列的各文件夹筛选项，只展示名称、主标记和 Skill 数量，任何绝对路径都不进入可见 UI。所有文件夹无论 Skill 数是否为零都保持可选择；选择文件夹后窗口只显示其 Skills，零 Skill 文件夹显示明确空态，选择“全部文件夹”恢复聚合视图。每张 Skill 卡只以文件夹名称轻量标出真实来源，主/次关系由文件夹 Popover 统一表达。项目窗口与记忆库浏览采用相同的持续挂载模式：点击卡片主体时保留同一个 Dialog 节点、遮罩和稳定尺寸，只把列表内容切换为 `SKILL.md` 预览；关闭预览后在同一窗口切回原项目列表并恢复卡片焦点，不卸载项目窗口，也不在主页面上另开第二个 Dialog。独立预览直接消费 Design System `AwakenSkillPreviewDialog`；项目窗口内的预览消费同目录导出的 `AwakenSkillPreviewContent` 与 `AwakenSkillPreviewDeleteButton`，两条路径不保留 Desktop 私有预览 DOM 或视觉 CSS。project/user 的删除入口只出现在预览底部；project 删除确认继续在同一项目窗口内切换，取消或成功删除并刷新后返回原项目列表。这些 Design System 组件只拥有 UI，项目数据、预览读取、删除、启停与过期请求隔离仍由 Desktop 注入。
