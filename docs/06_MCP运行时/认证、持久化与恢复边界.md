# MCP 认证、持久化与恢复边界

## 1. 权威范围

本文档唯一定义 MCP OAuth 骨架、凭据存储、Desktop 当前可用性、disable 持久性、401 处理和恢复分类。安全凭据的通用 Desktop `safeStorage` 状态机由 `05_模型与供应商配置` 持有；本文档只记录 MCP 的 Go credential store。

## 2. 已实现的认证组件

`src/mcpclient` 已实现：

- OAuth 2.0 authorization-code handler 和 PKCE 所需 SDK 组装。
- 保护资源/授权服务器 metadata discovery。
- 预注册 client ID/secret 或 dynamic client registration 的 SDK 配置入口。
- `CredentialStore` 接口、内存实现与生产 `PersistentCredentialStore`。
- token refresh 后把新 token source 持久化回 store。

生产 `buildMCPManager` 安装 `PersistentCredentialStore`。该 store 把非秘密 metadata 写入 Desktop data 下的 `connector_accounts` SQLite，把 token source JSON 交给系统 keyring（service `awaken-mcp`），不把 token 明文写入 MCP JSON 配置。

OAuth handler当前只装入 `http` 的 Streamable HTTP transport。`sse` 虽是生产支持transport，但 `buildTransport` 不把OAuth handler传给legacy SSE client；不能宣称SSE可用持久token完成认证/刷新。

## 3. Desktop 当前认证限制

OAuth 端到端流程需要 Desktop 通过 `Manager.InstallAuthFetcher` 提供 `AuthorizationCodeFetcher`，用于打开浏览器并接收 loopback callback。当前生产 Desktop 和 `cmd/awaken-core` 没有安装这个 fetcher。

因此，调用 09 协议域定义的 MCP 认证动作会得到 HTTP 409 和 `AUTH_FETCHER_REQUIRED`。

这是当前产品限制，不是用户通过重试或编辑 JSON 可修复的短暂错误。已在persistent store中存在且仍可用的token source只会被Streamable HTTP transport重建；SSE不接OAuth handler。需要新授权或交互式重授权时仍会遇到fetcher缺口。

Connector `authType` 目前也只是 metadata。Connector connect 动作不会主动完成 OAuth；它直接创建/持久化 MCP 配置，method/path 只查 09 route 清单。

## 4. 401 与 `needs-auth` 的实际语义

Manager 在 **initialize/connect** 阶段使用 `isAuthError` 识别 401、unauthorized 和 needs-auth 文本，并将 server 改为 `needs-auth`。该状态下：

- `McpToolAdapter.CheckPermission` 返回 `needs_auth`。
- `Manager.CallTool` 返回 `NeedsAuthError`。
- 工具不应进入通用 approval。

但是，已处于 `connected` 的 server 在 **tool call** 期间返回 401/expired session 时，`Manager.CallTool` 当前只把 SDK error 向上返回，不会更新 managed server 状态，也不会自动反注册工具。旧规范中的 `connected -> needs-auth on 401` 尚未完成。

工程上不得仅根据 `isAuthError` 已存在就声称 tool-call 401 闭环已实现。

## 5. disable 与其他持久化语义

| 事实 | 当前行为 |
| --- | --- |
| user/project server 配置 | 写入 JSON，跨重启 |
| OAuth metadata/token | SQLite + 系统 keyring，跨重启 |
| `Disable(name)` | 仅 Manager 内存状态，不回写 `enabled:false` |
| dynamic server | 仅当前进程 |
| connector active ownership | connector registry 内存，详见 07 域 |

因此用户在 Desktop 点击“停用”后，当前进程中会保留配置但卸载工具；重启 Desktop 后配置会再次被加载和连接。删除配置可以持续移除server配置，但当前DELETE/connector disconnect都没有调用 `PersistentCredentialStore.ClearTokenSource`：SQLite/keyring中的同名OAuth凭据仍保留，同名server以后重建时可能复用旧token。配置删除和凭据清除不是同一能力，后者当前没有接入产品删除链。

## 6. 异常分类与恢复

| 类型 | 可观测结果 | 当前恢复方式 |
| --- | --- | --- |
| 配置无效 | API 拒绝，或启动合并时 warning/过滤 | 修正唯一 transport 和必填字段 |
| 网络/子进程失败 | `pending` 重试后 `failed` + `errorReason` | 修正外部环境，再 enable/reconnect |
| 握手需授权 | `needs-auth` | 当前 Desktop 无完整授权入口；记录能力缺口 |
| tool call 返回 401 | tool error，server 可能仍显示 connected | 不做无限重试；记录状态迁移缺口 |
| Desktop 停用后重启又连接 | 配置仍存在 | 这是当前非持久 disable 语义，不用文档掩盖 |
| 删除server后同名token仍存在 | 配置消失，credential store未清理 | 当前无产品清理链；重建同名server前按遗留token风险处理 |

## 7. 不可绕过的边界

- token/secret 不得写入文档、日志、MCP 配置示例或 Desktop renderer state。
- 没有安装 auth fetcher 时必须 fail closed，不得伪造授权 URL 或把“已打开浏览器”当作 token 已获得。
- 不得将通用工具 approval 用于代替 OAuth；缺授权是 `needs_auth`，不是请求用户批准一次工具调用。
- 重试必须受连接状态和外部条件限制，不能对已发生外部副作用的 MCP tool 盲目重放。
