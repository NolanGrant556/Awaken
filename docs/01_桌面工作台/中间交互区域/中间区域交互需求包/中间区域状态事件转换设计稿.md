# 中间区域状态事件转换设计稿

## 1. 文档目的

本稿用于补齐中间区域在实现前缺失的“状态 / 事件 / 转换”设计，不直接给出代码方案，也不替代验收文档。

它解决的问题是：

- 中间区域已经不是单一 scroll 算法问题；
- 当前行为分散在 narrative 渲染、scroll controller、CSS sticky、composer inset、approval stack、overlay 等多个层次；
- 如果没有统一状态和事件模型，后续改动仍会反复出现“修一处，另一处又坏”。

本稿的目标是给后续实现一个统一前提：

**以后凡是改中间区域，都先回答“在改哪个状态、由什么事件触发、会触发哪些合法转换”。**

## 2. 适用范围

本稿适用于 Workbench 中间区域主链路：

```text
WorkbenchShell
  -> RunStage
    -> ExecutionFeed
      -> execution-turn-section
        -> execution-turn-header
        -> execution-turn-body
    -> ComposerDock
    -> overlay
```

覆盖的主要行为：

- center composer 与 dock composer 切换
- prompt anchor
- sticky prompt ownership
- latest output follow
- 用户暂停 follow 与恢复
- composer inset / output gap / latest turn min-height
- turn marker rail
- prompt bubble 折叠展开
- return-to-latest affordance
- approval / runtime panel 对底部布局的影响
- thread switch / replay / reconnect 对中间区域状态的影响
- work packet 聚合对象的显示状态

不覆盖：

- 右侧 inspector 详情逻辑
- 模型设置、workspace picker、项目树等非中间区域主链路
- markdown 具体渲染细节本身，除非它改变中间区域布局和滚动语义

## 3. 设计原则

### 3.1 RunStage 是唯一滚动与定位容器

中间区域所有与滚动、吸底、overlay、anchor、marker、return affordance 相关的语义，都必须建立在 `RunStage` 的唯一滚动容器之上。

### 3.2 Prompt 属于 Turn

prompt 不是独立浮层，也不是 feed 外同步副本。它始终属于对应 turn，并与 thinking、tool、approval、file change、answer 组成一个完整叙事单元。

### 3.3 用户意图优先于被动布局变化

用户主动滚动、点击 marker、点击恢复按钮、切换线程，优先级高于：

- markdown 渲染完成
- ThoughtTrace 增高
- prompt 展开
- approval / runtime panel 出现或消失
- composer 多行增高
- viewport resize

后者只能改变布局事实，不能直接改写用户意图状态。

### 3.4 所有底部空间共用同一布局事实

以下概念必须建立在同一底部事实之上，而不是各算各的：

- composer inset
- output gap
- native scroll bottom
- latest output tail 可见空间
- marker rail bottom
- return-to-latest 按钮相对 composer 的位置

### 3.5 return-to-latest 是恢复入口，不是布局事实

return affordance 只表达“恢复 follow”的用户入口，不参与：

- composer 高度测量
- safe area
- output tail
- scroll bottom

### 3.6 被动壳与交互策略分离，但交互策略必须系统化

设计系统组件可以继续保持 UI-only；但 Desktop renderer 不能继续只靠零散 `ref + effect + CSS variable` 维持复杂交互，必须有一份正式状态模型作为约束。

## 4. 状态分层

中间区域状态分为 5 层：

1. 叙事身份状态
2. 用户意图与 follow 状态
3. 布局事实状态
4. 局部交互对象状态
5. 恢复与切换状态

这些状态里，有些是“规范状态”，有些是“派生状态”。

### 4.1 规范状态

规范状态是中间区域真正要维护的第一等状态。

| 状态名 | 类型 | 含义 | 推荐 owner | 允许由谁改变 |
|------|------|------|-----------|-------------|
| `stageMode` | `center \| dock \| history` | 当前中间区域主显示模式 | Desktop renderer | runtime / thread / narrative 事件 |
| `latestTurnId` | `string \| undefined` | 最新 prompt 所属 turn | narrative grouping | prompt 提交 / transcript replay |
| `currentTurnId` | `string \| undefined` | 当前 sticky / marker 代表的 turn | scroll controller | anchor、scroll、marker jump、thread restore |
| `pendingPromptAnchorTurnId` | `string \| undefined` | 仍需锚定到顶部的新 turn | scroll controller | run requested / rerun / thread switch |
| `followMode` | `anchoring \| following_latest \| paused_by_user` | latest output 跟随主状态 | scroll controller | 直接用户事件、run 启动、thread switch |
| `resumeIntent` | `none \| wheel_down \| touch_to_latest \| scroll_to_tail \| return_button` | 用户是否明确表达恢复意图 | scroll controller | 用户直接事件 |
| `programmaticScrollReason` | `none \| anchor_prompt \| follow_latest \| marker_jump \| thread_restore` | 当前程序滚动原因 | scroll controller | 仅系统主动滚动 |
| `promptBubbleModeByTurnId` | `Record<string, "collapsed" \| "expanded" \| "internal_scroll">` | 每个 prompt bubble 的显示模式 | Desktop renderer / prompt UI bridge | prompt 直接交互 |
| `returnToLatestState` | `hidden \| visible` | 恢复 follow 的显式入口是否显示 | overlay policy | followMode、run status、tail proximity |
| `workPacketModeById` | `Record<string, "summary" \| "collapsed" \| "expanded" \| "internal_scroll">` | 长 trace 聚合对象状态 | narrative interaction layer | work packet 直接交互 |
| `recoveryMode` | `idle \| switching_thread \| replaying \| reconnecting` | 当前是否处于恢复路径 | Desktop renderer | thread switch / replay / reconnect |

### 4.2 布局事实状态

布局事实状态描述的是“当前可测量现实”，它们不是用户意图。

| 状态名 | 类型 | 含义 | 来源 |
|------|------|------|------|
| `runStageViewportHeightPx` | `number` | RunStage 当前可视高度 | `ResizeObserver` |
| `composerInsetPx` | `number` | composer 实际占用内容高度 | dock 测量 |
| `outputGapPx` | `number` | output 与 composer 间目标安全间距 | 设计常量或派生 |
| `composerSafeAreaPx` | `number` | inset + gap 的安全空间 | 布局派生 |
| `latestTurnMinHeightPx` | `number` | latest turn 为 anchor + 尾部可读性预留的最小高度 | viewport + inset + gap 派生 |
| `latestOutputTailBottomPx` | `number` | latest answer 底部真实位置 | DOM 测量 |
| `anchorOffsetPx` | `number` | prompt anchor 顶部偏移 | RunStage CSS / measurement |

### 4.3 派生状态

以下状态不建议独立持久保存，应由规范状态和布局事实推导：

- `showTurnMarkerRail`
- `activeMarkerId`
- `isNearLatestTail`
- `isAtNativeScrollBottom`
- `canAutoFollow`
- `showCenterComposer`
- `markerRailMode`
- `returnButtonBottomPx`

## 5. 当前实现与目标状态的映射

为避免后续实现讨论失焦，先明确当前 `main` 已有状态与目标状态的关系。

| 当前实现中的概念 | 当前载体 | 在目标模型中的对应物 | 问题 |
|------|------|------|------|
| `pendingPromptAnchorRef` | ref | `pendingPromptAnchorTurnId` | 当前只有 bool，没有 turn 语义 |
| `followLatestOutputRef` | ref | `followMode=following_latest` | 当前只是布尔位，语义不够完整 |
| `latestOutputFollowPausedByUserRef` | ref | `followMode=paused_by_user` | 与 resumeIntent 分散 |
| `latestOutputFollowResumeIntentRef` | ref | `resumeIntent` | 当前只有少量来源，不够完整 |
| `programmaticRunStageScrollTopRef` | ref | `programmaticScrollReason` | 只记数值，不记滚动意图 |
| prompt 展开状态 | `AwakenUserPromptBlock` 内部 state | `promptBubbleModeByTurnId` | 没纳入中间区域系统模型 |
| return affordance | 未落地 | `returnToLatestState` | 当前缺正式对象 |
| work packet 折叠状态 | 未落地 | `workPacketModeById` | 当前缺正式对象 |

## 6. 事件模型

中间区域事件分为 4 类：

1. 用户直接事件
2. runtime / narrative 事件
3. 被动布局事件
4. 恢复路径事件

### 6.1 用户直接事件

这些事件可以改变用户意图状态。

| 事件名 | 说明 | 可以改变的状态 | 不应直接改变的状态 |
|------|------|---------------|------------------|
| `submit_prompt` | 提交新 prompt | `latestTurnId`、`pendingPromptAnchorTurnId`、`followMode` | `promptBubbleModeByTurnId` |
| `wheel_history` | 向历史方向滚动 | `followMode`、`resumeIntent` | `latestTurnId` |
| `wheel_latest` | 向最新方向滚动 | `resumeIntent` | `currentTurnId` 以外的叙事身份 |
| `touch_history` | 触控向历史方向移动 | `followMode`、`resumeIntent` | `latestTurnId` |
| `touch_latest` | 触控向最新方向移动 | `resumeIntent` | `pendingPromptAnchorTurnId` |
| `pointer_down_in_feed` | 用户直接操作中间内容 | `followMode` | `composerInsetPx` |
| `click_turn_marker` | 点击旧 turn marker | `currentTurnId`、`followMode`、`resumeIntent` | `latestTurnId` |
| `click_return_to_latest` | 点击恢复按钮 | `resumeIntent`、`followMode` | `promptBubbleModeByTurnId` |
| `expand_prompt` | 展开 prompt bubble | `promptBubbleModeByTurnId` | `followMode` |
| `collapse_prompt` | 收起 prompt bubble | `promptBubbleModeByTurnId` | `followMode` |
| `scroll_prompt_internal` | prompt 内部滚动 | `promptBubbleModeByTurnId` | `followMode` |
| `expand_work_packet` | 展开工作包 | `workPacketModeById` | `followMode` |
| `collapse_work_packet` | 收起工作包 | `workPacketModeById` | `followMode` |
| `switch_thread` | 切换线程 | `recoveryMode`、`currentTurnId`、`followMode` | 历史 turn 的 prompt 模式不应串线 |

### 6.2 runtime / narrative 事件

这些事件主要改变叙事身份状态和 feed 内容，不应直接覆盖用户意图。

| 事件名 | 说明 | 主要影响 |
|------|------|---------|
| `run_requested` | 用户发起 run | 创建 latest turn，进入 pending anchor |
| `run_created` | runtime 返回 run / thread | 确认 thread / run 身份 |
| `narrative_item_appended` | thinking / tool / answer 增长 | 更新 latest turn body |
| `approval_requested` | 审批出现 | 影响 composer stack 和 narrative item |
| `approval_resolved` | 审批结束 | 影响 approval narrative 与 stack |
| `run_finished` | run 正常结束 | latest turn 转 terminal |
| `run_cancelled` | run 取消 | latest turn 转 terminal |
| `run_error` | run 错误终止 | latest turn 转 terminal |

### 6.3 被动布局事件

这些事件只能更新布局事实，不应直接重写用户意图。

| 事件名 | 说明 | 允许影响 | 禁止影响 |
|------|------|---------|---------|
| `composer_height_changed` | composer 多行或 panel 高度变化 | `composerInsetPx`、`composerSafeAreaPx`、`latestTurnMinHeightPx` | 不得直接把 `followMode` 改回 following |
| `viewport_resized` | RunStage 高度变化 | `runStageViewportHeightPx`、marker 容量 | 不得清空 `paused_by_user` |
| `latest_turn_height_changed` | latest turn body 高度变化 | `latestOutputTailBottomPx`、`latestTurnMinHeightPx` | 不得直接恢复 follow |
| `prompt_height_changed` | prompt 展开或收起引发高度变化 | `latestTurnMinHeightPx`、anchor 相关测量 | 不得被视为 resume intent |
| `markdown_layout_stabilized` | markdown 渲染完成 | `latestOutputTailBottomPx` | 不得直接改变 `resumeIntent` |

### 6.4 恢复路径事件

这些事件决定状态初始化和清理边界。

| 事件名 | 说明 | 主要影响 |
|------|------|---------|
| `thread_switch_started` | 开始切线程 | `recoveryMode=switching_thread` |
| `thread_replay_started` | 开始重放 transcript | `recoveryMode=replaying` |
| `thread_replay_completed` | 重放完成 | 重建 `latestTurnId`、`currentTurnId` |
| `reconnect_started` | SSE 中断恢复 | `recoveryMode=reconnecting` |
| `reconnect_resumed` | live tail 恢复 | 保持 turn / follow 语义连续 |

## 7. 关键转换规则

### 7.1 空态到第一轮运行

前置：

- `stageMode=center`
- 无 active run

触发：

- `submit_prompt`

状态变化：

- `stageMode -> dock`
- `latestTurnId = newTurnId`
- `pendingPromptAnchorTurnId = newTurnId`
- `followMode = anchoring`
- `resumeIntent = none`
- `returnToLatestState = hidden`

禁止副作用：

- 不得因为 composer 切换为 dock 就立即视为“用户暂停 follow”

### 7.2 新 turn 替换旧 sticky ownership

前置：

- 已存在旧 `currentTurnId`
- 新 prompt 提交

触发：

- `run_requested`

状态变化：

- `latestTurnId = newTurnId`
- `pendingPromptAnchorTurnId = newTurnId`
- `followMode = anchoring`

完成条件：

- 最新 prompt 完成 anchor 后，`currentTurnId` 必须交接到 `latestTurnId`
- `pendingPromptAnchorTurnId -> undefined`
- 若 latest turn 已有 body output，则 `followMode -> following_latest`

禁止副作用：

- 旧 turn sticky header 不得继续占据顶部所有权

### 7.3 用户暂停 latest follow

前置：

- `followMode = following_latest`

触发：

- `wheel_history`
- `touch_history`
- `pointer_down_in_feed`
- `click_turn_marker`

状态变化：

- `followMode -> paused_by_user`
- `resumeIntent -> none`
- `returnToLatestState -> visible`，若 latest run 仍在输出

禁止副作用：

- 被动布局变化不得触发同样的状态转换

### 7.4 用户恢复 latest follow

前置：

- `followMode = paused_by_user`

触发：

- `click_return_to_latest`
- `wheel_latest`
- `touch_latest`
- `scroll_to_tail`

状态变化：

- `resumeIntent` 记录明确来源
- 当且仅当满足“接近 latest tail 且位于 native scroll bottom”时：
  - `followMode -> following_latest`
  - `resumeIntent -> none`
  - `returnToLatestState -> hidden`

禁止副作用：

- `composer_height_changed`
- `prompt_height_changed`
- `markdown_layout_stabilized`

以上事件都不得单独触发恢复。

### 7.5 prompt 展开 / 收起

前置：

- 存在可展开 prompt

触发：

- `expand_prompt`
- `collapse_prompt`

状态变化：

- `promptBubbleModeByTurnId[turnId]` 更新
- 布局层触发 `prompt_height_changed`

允许影响：

- 重新测量 anchor / latest turn min-height

禁止副作用：

- 不得把 prompt 展开视为用户想恢复 latest follow
- 不得因为 prompt 收起就清除 `paused_by_user`

### 7.6 composer 高度变化

前置：

- `stageMode=dock`

触发：

- 输入框多行
- runtime panel 出现或消失
- approval card 出现或消失

状态变化：

- 更新 `composerInsetPx`
- 重新派生 `composerSafeAreaPx`
- 重新派生 `latestTurnMinHeightPx`

禁止副作用：

- 不得改写 `resumeIntent`
- 不得把 `followMode=paused_by_user` 强行恢复

### 7.7 turn marker 跳转

前置：

- marker rail 可见

触发：

- `click_turn_marker`

状态变化：

- `currentTurnId = markerTurnId`
- `followMode -> paused_by_user`
- `resumeIntent -> none`
- `programmaticScrollReason = marker_jump`

禁止副作用：

- 不得把 `latestTurnId` 改成旧 turn

### 7.8 thread switch / replay / reconnect

前置：

- 用户切线程或系统恢复运行

触发：

- `switch_thread`
- `thread_replay_started`
- `reconnect_started`

状态变化：

- `recoveryMode` 更新
- `currentTurnId` 和 `latestTurnId` 由 replay 后的 narrative 重建
- `followMode` 需按恢复类型初始化，而不是沿用旧线程的 UI 状态

建议规则：

- thread switch 默认不带待 anchor 语义
- replay 恢复优先重建 turn 身份，再决定是否跟随 tail
- reconnect 不得把中断误判为普通失败，并破坏当前 narrative 连续性

## 8. 不变量

后续实现必须满足以下不变量：

1. `latestTurnId` 只能来自 prompt turn 顺序，不能来自 marker 点击。
2. `currentTurnId` 可以被滚动、anchor、marker jump、thread restore 改变。
3. `paused_by_user` 只能由直接用户事件进入，不能由被动布局事件进入。
4. `paused_by_user` 也只能由明确 resume intent + tail 条件满足后退出。
5. prompt 展开 / 收起是布局变化，不是 follow 意图。
6. return-to-latest 是 overlay 恢复入口，不参与 composer inset 和 safe area。
7. work packet 的展开 / 收起不应改写 latest follow 语义，除非它本身属于用户阅读历史的直接操作。
8. thread replay 必须优先恢复叙事身份，再恢复滚动行为。

## 9. 推荐的职责归属

| 层级 | 应负责什么 | 不应负责什么 |
|------|-----------|-------------|
| 设计系统 | 结构容器、视觉样式、局部可复用交互表面 | runtime 状态、跨 turn follow 策略 |
| narrative projector | 叙事 item 类型、turn 分组输入材料、work packet 对象生成 | DOM scroll、sticky ownership |
| scroll / interaction controller | current/latest turn、followMode、resumeIntent、layout facts、overlay 显示条件 | narrative item 具体渲染 |
| App 编排层 | 组合容器、接 runtime 事件、分发 thread/replay/approval 路径 | 大量内联交互规则分支 |

## 11. 本稿对后续实现的直接约束

后续任何中间区域改动，如果涉及：

- sticky ownership
- latest output follow
- prompt 折叠展开
- return-to-latest
- composer inset
- marker 跳转
- replay / reconnect
- work packet

都应先回答下面 3 个问题：

1. 这次改动触碰的是哪个规范状态？
2. 这个状态只能被哪些事件改变？
3. 这次改动是否错误地让被动布局事件改写了用户意图？

如果答不清楚，就不应直接进入实现。

## 12. 下一步建议

基于本稿，后续工作顺序建议是：

1. 先用本稿复核当前 `main` 缺了哪些正式状态对象。
2. 再单独写“Phase 1 sticky / anchor 状态实现稿”。
3. 再单独写“Phase 2 composer inset / latest tail 实现稿”。
4. 再单独写“Phase 3 user intent / follow 状态机实现稿”。
5. return-to-latest 与 work packet 继续保持单独阶段、单独验收。

这样做的目标不是一次性设计完整系统，而是先把“以后不能再混着改”的边界明确下来。
