# 会话存储从工作区迁移到桌面全局目录方案

## 摘要

当前 Awaken 把对话记录默认写入 `workspace/.awaken/transcripts/*.jsonl`。这套实现便于开发期按工作区恢复线程，但它不符合成熟桌面产品的默认用户预期，也不符合我们想对标的 Codex Desktop 方向。

本方案的核心决策是：

- **会话历史从工作区本地存储，迁移为 Desktop 应用全局存储**
- **工作区只保留项目级资产，不再默认承载聊天历史**
- **线程与工作区改为“关联关系”，而不是“同目录关系”**
- **MCP 配置、OAuth 凭据、浏览器态、桌面配置与会话历史建立统一的数据分层**
- **不兼容旧 workspace 历史，直接切换到 Desktop 全局存储**

目标不是简单换个路径，而是把 Awaken 的线程、恢复、删除语义、跨平台一致性，以及 MCP / Connector 的登录态持久化，一次性收口到正式桌面产品架构上，同时保持当前正常使用的核心能力不被破坏。

## 为什么必须改

### 1. 当前行为更像开发态，不像产品态

现在的会话历史写在项目目录里，会导致几个直接问题：

- 污染用户项目目录
- 容易被误提交到 git
- 删除或移动项目目录时，会把会话历史一并带走
- 多项目历史天然分散，难以统一管理
- 线程恢复依赖“扫工作区”，不是依赖正式的全局索引

这套方案作为开发期过渡实现可以接受，但不适合作为 Awaken 的长期产品默认行为。

### 2. 它和 Desktop 其他数据归属已经不一致

Awaken Desktop 自己的桌面配置已经是 app-global：

- `last-workspace.json`
- `workspace-registry.json`
- `config/model-profiles.json`

这些都放在 Electron `userData` 目录里，而不是工作区目录里。只有会话历史仍然写入 workspace，这是明显的架构不一致。

### 3. 对标 Codex Desktop，方向也不对

基于当前这台机器上的本地观察，Codex 的数据明显是 app-global 的，而不是 project-local 的。可见数据包括：

- `~/.codex/session_index.jsonl`
- `~/.codex/sessions/`
- `~/.codex/state_5.sqlite`
- `~/Library/Application Support/Codex`
- `~/Library/Application Support/com.openai.codex`

这说明 Codex 把“会话历史”和“桌面应用数据”视为同一类产品级数据，而不是把聊天记录散落到每个项目目录里。Awaken 如果要对标这一路线，会话存储必须调整。

### 4. 当前问题不是“完全没落盘”，而是“落盘边界不完整”

这件事不能粗暴理解成 Awaken 完全没有持久化。当前真实情况是：

- **会话历史**：会落盘，但落在 workspace 里
- **MCP 配置**：会落盘，例如 `~/.awaken/mcp.json`
- **Desktop 配置**：会落盘，例如 `last-workspace.json`、`workspace-registry.json`、`model-profiles.json`
- **OAuth 凭据 / token**：默认仍是内存态，不保证跨重启持久化

所以问题本质不是“有没有存”，而是：

- 有的数据已经存了，但**存错了层**
- 有的数据存了，但**归属分散**
- 有的敏感状态压根还没有正式持久化闭环

这也是为什么本方案必须从“单纯调整 transcript 路径”，升级为“Desktop 全局数据分层重构”。

## 对标 Codex 的参考模型

基于当前机器上可见的 Codex 数据，本方案提炼出 3 个非常明确的对标观察。

### 观察 1：Codex 的线程索引是全局索引，不依赖项目目录

本机可见：

- `~/.codex/state_5.sqlite`
- `threads` 表

该表可见字段包括：

- `id`
- `rollout_path`
- `cwd`
- `title`
- `archived`
- `preview`
- `git_sha`
- `git_branch`
- `model_provider`

这里最关键的是：Codex 用 `cwd` 记录线程关联的工作目录，而不是把线程文件物理放进那个项目目录里。这说明：

- 线程的“归属项目”是元数据
- 线程的“物理存储位置”是全局应用数据

Awaken 如果要对标，就必须采用同样的分层思想。

### 观察 2：Codex 既有索引，也有原始会话文件

本机可见：

- `~/.codex/session_index.jsonl`
- `~/.codex/sessions/YYYY/MM/DD/rollout-....jsonl`
- `~/.codex/archived_sessions/...`

这说明 Codex 不是单纯依赖一个 sqlite，也不是只靠一个 jsonl，而是分成：

- **索引层**
- **原始会话层**
- **归档层**

这和 Awaken 当前“直接把 transcript 当成主要恢复入口”的做法有本质不同。

### 观察 3：Codex 的浏览器态和会话态都有正式 app-global 底座

本机可见：

- `~/Library/Application Support/Codex`
- 其中包含 `Cookies`、`Local Storage`、`Session Storage`、`Preferences`
- 另有 `~/Library/Application Support/com.openai.codex`

这至少说明：

- Codex 的产品状态不是靠“纯内存”维持
- 浏览器/网页登录相关状态拥有正式持久化基础设施
- 它的产品级状态管理是一套完整的桌面应用数据系统，而不是零散临时文件

Awaken 现在在这方面的差距主要有两类：

- 会话历史放错层
- OAuth / Connector 凭据默认未持久化

## 当前代码现状

### Awaken 当前对话记录路径

当前代码直接把 transcript 路径拼为：

`<workspaceRoot>/.awaken/transcripts/<thread_id>.jsonl`

现状代码位置：

- `src/runtime/transcript_store.go`
- `transcriptPath(workspaceRoot, threadID string)`

### 当前线程恢复机制

当前 `RunService.ListThreads()` 并不是从一个全局线程库读取，而是：

1. 先看内存中的线程
2. 再按 `defaultWorkspace + historyWorkspaces` 遍历
3. 进入每个工作区的 `.awaken/transcripts/` 扫描 durable thread

这意味着：

- 线程列表依赖工作区搜索顺序
- 线程恢复依赖工作区是否仍存在
- 历史线程不是“系统统一资产”，而是“工作区附属物”

### 当前删除语义

当前删除线程时，会直接删除工作区里的 transcript 文件：

`os.Remove(transcriptPath(workspace.WorkspaceRoot, threadID))`

这进一步说明线程本体今天仍然是 workspace-local 的。

### 当前 MCP 配置与 OAuth 凭据状态

当前 MCP / Connector 相关状态是分裂的：

- 用户级 MCP 配置落在 `~/.awaken/mcp.json`
- 项目级 MCP 配置落在 `<workspace>/awaken.mcp.json`
- Desktop 自己的配置落在 Electron `userData`
- OAuth token 默认在 `InMemoryCredentialStore`

这意味着：

- “这个 MCP 怎么连”会被记住
- “这个 MCP 是否已经登录”未必会被记住
- Desktop 级体验和 runtime 级实现之间，仍缺一层统一的产品级数据治理

### 当前模型调用链状态

当前模型调用链本身并不依赖 `workspace/.awaken/transcripts` 这个目录位置，但它依赖“线程恢复出来的对话内容是否完整、顺序是否正确、上下文状态是否可恢复”。

当前链路大致是：

1. Desktop 从 `model-profiles.json` 读取默认模型配置
2. `StartRunRequest` 带上 `model_profile`
3. `RunService.StartRun()` 创建或恢复线程
4. 若是旧线程恢复，会把 transcript 中的消息重新塞回 `agent.GetConversation().Context`
5. `RequestBuilder` 基于当前 conversation 构建 `ContextEnvelope`
6. `ContextWindowState` 基于 envelope 计算 token 估算、warning、auto-compact、block 阈值
7. runner 再据此发起模型请求、触发压缩、或阻断

因此，线程存储改造虽然不是“模型提供商改造”，但它会直接影响：

- 下一次模型调用拿到的历史消息
- 模型请求的上下文长度估算
- 自动压缩触发时机
- 压缩后的连续性

### 当前上下文管理状态

当前上下文管理不仅依赖原始消息，还依赖 transcript 中恢复出的附加状态，包括：

- `CompactBoundaryID`
- `LastContextWindowState`
- terminal event 上的 context estimate
- tool result pairing

当前 `loadRestoredTranscript(...)` 会恢复这些信息，测试也明确覆盖了：

- compact boundary 恢复
- context window 估算状态恢复
- tool-result 配对恢复
- 重启后 conversation 恢复

这意味着：如果这次只顾着把线程文件换到全局目录，却没有把这些语义一起迁过去，就会直接伤到上下文管理，而不只是伤到左侧栏显示。

## 本方案的目标原则

### 原则 1：聊天历史默认属于 Awaken，不属于项目目录

Awaken 是桌面工作台，不是项目内聊天脚手架。默认历史应当属于用户的 Awaken 应用数据，而不是属于某一个仓库或文件夹。

### 原则 2：项目级数据与应用级数据分层

未来要严格区分两类数据：

**项目级数据**

- `awaken.mcp.json`
- `.awaken/skills/`
- 未来如有必要的项目级 agent 资产

**应用级数据**

- 会话历史
- 线程索引
- 原始运行日志与事件流
- 全局收藏/置顶/归档
- 全局搜索索引
- 恢复状态
- 桌面配置与用户偏好
- 用户级 MCP 配置
- OAuth 凭据 / token / 浏览器态
- 连接器授权账户信息

### 原则 2.1：敏感凭据与普通配置分层

未来还要把应用级数据继续拆为两类：

**普通配置 / 索引**

- 线程索引
- 线程 transcript
- MCP 服务器配置
- workspace 注册表
- model profile 非敏感字段

**敏感凭据**

- OAuth access token
- OAuth refresh token
- Connector 登录凭据
- API key 密文

普通配置可以进入 sqlite / json 文件，敏感凭据必须走系统安全存储或等价加密存储层。

### 原则 3：线程归属通过元数据表达，不通过磁盘位置表达

线程“属于哪个工作区”应该是线程记录里的字段，而不是通过“文件存在哪个目录”来表达。

### 原则 4：Mac 和 Windows 共享同一套上层模型

不要为 Mac 和 Windows 维护两套会话语义。两端只允许在“系统路径基座”上不同，上层数据模型、迁移逻辑、恢复逻辑和删除逻辑必须一致。

## 目标存储布局

### Desktop 全局根目录

Awaken Desktop 已经把 `userData` 设置为：

- `Mac`：`~/Library/Application Support/@awaken/desktop`
- `Windows`：`%APPDATA%\\@awaken\\desktop`

本方案要求会话历史统一落在这棵目录下。

### 目录职责说明

#### `config/`

存放非敏感、可编辑、可导出的 Desktop 配置：

- 用户级 MCP 服务器配置
- 用户级 connector 配置
- 模型配置的非敏感部分

#### `data/threads/`

存放线程 transcript 原始文件，是 Awaken 对应 Codex `sessions/` 这一层的主要映射。

#### `data/threads.sqlite`

存放线程列表与恢复索引，是 Awaken 对应 Codex `state_5.sqlite` / `session_index.jsonl` 这一层的主要映射。

#### `data/auth/`

存放非敏感授权元数据，例如：

- 哪个 server 绑定过哪种授权方式
- 上次授权时间
- token 到期时间
- 显示名称
- provider 标识

注意：这里不应该明文存 access token / refresh token。

#### `secure/`

这里只保存与系统安全存储交互所需的桥接状态或引用元数据，不保存明文密钥。

真正的凭据应进入：

- `Mac`：Keychain
- `Windows`：Credential Manager / DPAPI

## 需要一起治理的 5 类数据

为了避免后续再次把不同问题混在一起，本方案明确区分 5 类数据。

### 1. 线程历史

内容：

- 用户消息
- 助手消息
- 工具调用
- 运行事件
- 审批事件
- 工件事件

目标归属：

- `Desktop 全局`

目标形态：

- `threads.sqlite` + `thread_<id>.jsonl`

### 2. 项目级 Awaken 资产

内容：

- `awaken.mcp.json`
- `.awaken/skills/`
- 未来项目级 agent 资产

目标归属：

- `workspace 本地`

### 3. 用户级 MCP / Connector 配置

内容：

- 用户主动配置的 MCP server
- 用户级 connector 来源配置

目标归属：

- `Desktop 全局 config/`

兼容来源：

- `~/.awaken/mcp.json`
- `~/.awaken/connectors.json`

### 4. OAuth 凭据 / 登录态

内容：

- access token
- refresh token
- token source
- 账户绑定关系

目标归属：

- `Desktop 全局 secure + auth metadata`

### 5. 浏览器态 / Web 登录态

内容：

- Cookie
- Session Storage
- Local Storage
- 与网页登录相关的宿主状态

目标归属：

- `Desktop 应用 Web 容器用户数据`

这层不一定和 MCP OAuth 是同一套实现，但它们共同构成了“重启后还记得登录态”的产品体验闭环。

## 目标数据模型

### 1. 线程索引：`threads.sqlite`

建议新增一个全局线程索引库，负责解决“查找、排序、筛选、归档、恢复”问题。

建议至少包含这些字段：

- `thread_id`
- `title`
- `workspace_root`
- `scope_id`
- `latest_run_id`
- `created_at`
- `updated_at`
- `archived_at`
- `deleted_at`
- `last_message_preview`
- `last_error_state`
- `pinned`
- `source_kind`
  - `desktop_global`

索引库的职责是：

- 快速列出线程
- 支持跨项目统一排序
- 支持按 workspace 过滤
- 支持未来的搜索、置顶、归档

### 2. 原始 transcript：`data/threads/thread_<id>.jsonl`

保留 append-only `jsonl` 思路，不要把所有细粒度事件全部塞进 sqlite。

原因：

- 当前 transcript 结构已经稳定
- 事件流天然适合顺序追加
- 出问题时更易排查和导出
- 重放线程时不需要先从关系表重新拼装

这层负责保存：

- `thread`
- `message`
- `event`
- `tool result`
- `attachments metadata`

### 3. 附件与导出

如果未来要支持真正的会话级附件快照、导出包、长期归档，建议预留：

- `data/attachments/`
- `data/exports/`

本轮不一定实现完整能力，但目录和模型需要预留。

### 4. 授权账户索引：`data/auth/connector-accounts.sqlite`

建议新增授权账户索引，负责管理：

- 哪个 MCP / Connector 使用了哪种授权方式
- 对应展示名称
- provider / serverName
- 上次授权成功时间
- token 预计过期时间
- 是否需要重新授权
- 是否有系统安全存储引用

建议字段至少包括：

- `account_id`
- `provider_kind`
- `server_name`
- `connector_id`
- `display_name`
- `auth_type`
  - `oauth2`
  - `api_key`
  - `browser_session`
- `credential_ref`
- `last_authorized_at`
- `expires_at`
- `needs_reauth`
- `created_at`
- `updated_at`

### 5. 敏感凭据引用：系统安全存储

本方案不建议把 OAuth token 明文写进 sqlite 或 json。

建议采用：

- `Mac`：Keychain item
- `Windows`：Credential Manager / DPAPI protected blob

Awaken 本地只保存一个 `credential_ref`，用于定位系统级安全存储中的实际凭据。

## 工作区目录未来还保留什么

本方案不是要删除 `.awaken/` 这个概念，而是要缩小它的职责。

### 工作区应继续保留

- `.awaken/skills/`
- 未来显式项目级 Awaken 资产
- 用户明确选择“导出到项目目录”的内容

### 工作区不应默认保留

- 聊天历史 transcript
- 会话恢复主数据
- 线程索引
- 用户级 OAuth 登录态
- 用户级 MCP server 凭据

### 项目级会话导出

如果用户确实希望“把某个线程跟项目一起保存”，那应该是显式操作，例如：

- 导出为 Markdown
- 导出为 JSONL
- 导出为审计包

而不是把所有运行历史默认写进项目目录。

## 对运行时的影响

### 1. `transcriptPath(...)` 不再接受 `workspaceRoot`

当前：

- transcript 物理位置依赖 `workspaceRoot`

目标：

- transcript 物理位置依赖 `userData/data/threads`
- `workspaceRoot` 只作为线程元数据字段参与索引

这意味着 `transcriptPath` 需要重构为由全局存储根生成，不再由 workspace 派生。

### 2. `ListThreads()` 不再扫工作区目录

当前 `ListThreads()` 会遍历：

- `defaultWorkspace`
- `historyWorkspaces`

然后去每个 workspace 扫 durable thread。

目标是：

- 线程列表直接读全局索引
- workspace 只作为筛选条件，不作为扫描入口

这样才能真正做到：

- 跨项目统一线程列表
- 切换 workspace 不影响历史可见性
- 删除某个 workspace 不会直接让线程“消失”

### 3. `GetThreadTranscript()` 直接读全局存储

当前它会先尝试从内存命中，否则再按 workspace fallback 搜索。

目标应改成：

- 先查全局索引得到线程记录
- 再用 `thread_id` 直接定位 transcript 文件

### 4. `RenameThread()` / `DeleteThread()` 改为操作全局线程存储

当前删除线程会删除某个工作区下的 transcript 文件。

目标应改成：

- 修改全局索引
- 删除或归档 `data/threads/thread_<id>.jsonl`
- 与 workspace 目录解绑

### 5. `RunService` 需要显式依赖 `ThreadStore`

当前 `RunService` 把“线程恢复”和“workspace 搜索”耦合在一起。

目标应改成：

- `RunService` 依赖抽象的 `ThreadStore`
- `ThreadStore` 屏蔽底层是 sqlite + jsonl
- `WorkspaceConfig` 仅作为运行上下文字段

这样未来 Desktop、CLI、导入器、归档器都能复用同一套线程存储接口。

### 6. MCP / Connector runtime 需要显式依赖 `CredentialStore`

当前 `Manager` 默认装配的是 `InMemoryCredentialStore`。

目标应改成：

- 启动 Desktop runtime 时，显式注入 `PersistentCredentialStore`
- Desktop 负责初始化系统安全存储桥接
- runtime 通过统一接口拿 token source

这样“应用重启后仍记得登录态”才会真正成立。

### 7. 模型调用恢复路径必须保持不变

这轮改造后，下面这条链必须继续成立：

1. 选中某个线程
2. 恢复该线程的历史消息
3. 把消息重新灌回 `Conversation.Context`
4. 下一次 `RequestBuilder.BuildContextEnvelope(...)` 拿到完整历史
5. 新一轮模型调用在连续上下文上继续执行

也就是说，虽然 transcript 的**物理位置**要改，但 transcript 对 `RunService.StartRun()` 的**恢复语义**不能丢。

### 8. 模型配置本身不应被本轮改动

当前模型配置已经是 Desktop app-global：

- `config/model-profiles.json`
- API key 走 `safeStorage`

这部分不是本轮重构的目标，不应该因为线程迁移而改变：

- 默认模型选择
- 模型启用/禁用
- API key 保存方式
- `model_profile` 注入到 runtime 的方式

换句话说，本轮要改的是“线程历史和授权状态存储”，不是“模型配置体系”。

### 9. 上下文管理必须保持 3 个关键语义

#### 语义 A：历史消息顺序不变

模型下一轮请求必须看到与原线程一致的用户/助手/工具消息顺序，否则会造成：

- 回答断层
- 工具结果脱链
- 历史推理失真

#### 语义 B：tool-result pairing 不变

如果恢复后的历史打破 tool call / tool result 配对，会直接影响：

- conversation 校验
- 继续调用模型时的上下文正确性
- 压缩器的结构化摘要质量

#### 语义 C：compact boundary 与 context state 不变

如果新存储层丢掉：

- `CompactBoundaryID`
- `LastContextWindowState`
- terminal context estimate

就会导致：

- token 估算偏差
- auto-compact 过早或过晚
- reactive compact 行为不稳定
- 已压缩线程在恢复后再次压缩时出现失真

因此，新的全局 `ThreadStore` 不只是要“能读回聊天文本”，还要能恢复上下文管理语义。

## 对模型调用与上下文管理的影响

### 1. 这轮不是改模型能力，但它会改模型调用前置条件

模型提供商、模型列表、API key、temperature、max tokens 这些并不是本轮的主改动对象。

但每次模型调用之前，系统都要先回答两个问题：

- 这个线程现在的完整对话历史是什么
- 这个线程现在的上下文窗口状态是什么

而这两个问题今天都和 transcript 恢复高度耦合，所以这轮改造一定会波及模型调用前置条件。

### 2. 如果改坏，会出现什么现象

如果线程全局化做错，最容易出现的模型层异常不是“模型接口 500”，而是下面这些产品级异常：

- 切到旧线程后，模型像“失忆”了一样继续回答
- 明明同一个线程，续问时前文丢失
- token 估算异常，context windows 数字失真
- auto-compact 提前触发或完全不触发
- 压缩后线程恢复正常，重启后再打开却异常
- 工具结果不连贯，导致模型读到的历史逻辑断开

### 3. 本轮必须保护的模型调用能力

即使放弃旧 workspace 历史兼容，以下能力也必须保持：

- 新线程从创建到连续多轮对话都正常
- 新线程重启 Desktop 后再打开，仍能连续上下文继续对话
- 附件型输入在恢复后不破坏后续模型调用
- 选中的 `model_profile` 继续正确注入 runtime
- `ContextEstimated`、warning、auto-compact、block 行为保持现有语义

### 4. 对上下文压缩的特殊约束

上下文压缩比普通线程恢复更敏感，因为它不仅依赖文本，还依赖结构化状态。

新的全局 transcript / thread store 至少要保证：

- 压缩摘要消息能被恢复
- compact boundary 可恢复
- terminal event 里的 context payload 可恢复
- 压缩后的 model-view 消息切片语义不变

否则即使普通线程“看起来能打开”，长对话场景也会在真实运行时出问题。

## 授权状态与敏感凭据持久化

### 1. 这不是线程问题，但必须一起收口

如果只迁移线程历史，而 OAuth 凭据仍然是内存态，那么用户仍会遇到：

- MCP 配置还在
- 会话历史还在
- 但是 Slack / GitHub / Notion 又要重新登录

这会让产品体验看起来仍然“不完整”。

所以线程全局化和授权状态持久化，应该视为同一轮产品化重构的上下游，而不是两条完全无关的路线。

### 2. 目标授权分层

未来要分 3 层：

#### 层 A：连接配置

描述“怎么连”：

- server name
- transport
- command / url
- args
- header helper

存储位置：

- `config/mcp-servers.json`
- 项目覆盖仍可来自 `awaken.mcp.json`

#### 层 B：授权元数据

描述“谁登录过、是否快过期、UI 如何展示”：

- display name
- provider
- expires_at
- needs_reauth
- last_authorized_at

存储位置：

- `data/auth/connector-accounts.sqlite`

#### 层 C：敏感凭据

真正的：

- access token
- refresh token
- API key
- browser session credential handle

存储位置：

- `Mac Keychain`
- `Windows Credential Manager / DPAPI`

### 3. 推荐实现策略

#### Mac

- token 明文不入 json / sqlite
- 使用 Keychain 保存凭据
- Awaken 本地只保留 `credential_ref`

#### Windows

- 优先使用 Credential Manager
- 或将 blob 交给 DPAPI 加密后落盘
- 同样只在 Awaken 索引层保存引用和元数据

### 4. 启动与恢复流程

#### 启动时

1. Desktop 初始化 `userData/config`
2. Desktop 初始化 `ThreadStore`
3. Desktop 初始化 `CredentialStore`
4. runtime 注入 `PersistentCredentialStore`
5. MCP / Connector manager 读取服务器配置
6. 若 server 需要认证，则从凭据层恢复 token source

#### 首次调用工具时

- 若 token 有效：直接调用
- 若 token 缺失：标记 `needs_reauth`
- 若 token 过期但可刷新：后台刷新
- 若刷新失败：提示重新授权

### 5. UI 展示规则

Desktop 不应只显示“已配置”，还要显示：

- `已配置`
- `已连接`
- `已授权`
- `授权已过期`
- `需要重新登录`

这样用户才能区分：

- MCP 配置还在
- 但登录态没恢复

## 对 Desktop 的影响

### 1. 左侧线程列表会更像正式产品

左侧栏未来应从“当前工作区历史”升级为：

- 全局线程视图
- 可按项目过滤
- 可按最近使用排序
- 可置顶、归档、搜索

这比今天按 workspace 扫 transcript 的方式更像 Codex，也更像一个真正的 Desktop 工作台。

### 2. `last-workspace.json` 与 `workspace-registry.json` 继续保留

这两份桌面配置仍然是有价值的，但它们只负责：

- 默认打开哪个 workspace
- 曾经打开过哪些 workspace

不再承担“线程历史入口”的职责。

### 3. 恢复逻辑要从“恢复工作区”改成“恢复线程 + 工作区关联”

重启 Desktop 后，恢复逻辑应优先是：

1. 找到上次活动线程
2. 读取线程元数据中的 `workspace_root`
3. 再恢复相关 workspace 选择与运行上下文

而不是今天这样：

1. 先恢复 workspace
2. 再去 workspace 下找 transcript

### 4. 设置页与扩展页会变得更一致

未来 Desktop 的设置/扩展能力应统一表达：

- 线程历史属于 Desktop
- 用户级 MCP 配置属于 Desktop
- OAuth 登录态属于 Desktop
- 项目级覆盖属于 workspace

这会让用户更容易理解：

- “这个项目自己的配置是什么”
- “这个桌面应用自己记住了什么”

### 5. 左侧线程与模型连续性要保持解耦

用户不应该因为线程存储迁移，就感知到：

- 模型被重置
- 上下文连续性变差
- 历史对话突然无法续问

所以左侧线程列表的重构必须以“模型连续性不变”为前提，而不是只以“列表展示正确”为前提。

## 对用户体验的影响

### 1. 好处

- 项目目录更干净
- 不再担心 transcript 进 git
- 跨项目线程统一可见
- 用户更容易理解“Awaken 的历史都在应用里”
- 删除项目文件夹时，不会意外丢失会话

### 2. 变化点

- 用户不能再直接去项目目录里翻所有聊天历史
- 某些依赖 `.awaken/transcripts` 的手工操作路径会失效
- 某些过去依赖“重启后重新授权”的奇怪现象会消失
- 设置 / 扩展页会开始承担更正式的数据治理职责

因此需要配套能力：

- 会话导出

## 迁移方案

### 迁移原则

- 不兼容旧 workspace transcript
- 不做双读
- 不做后台导入
- 直接切到新的 Desktop 全局存储
- 现有正常能力必须保持可用

### Phase 1：引入全局存储骨架

新增：

- `userData/data/threads.sqlite`
- `userData/data/threads/*.jsonl`
- `userData/data/auth/`
- `userData/config/mcp-servers.json`

这一阶段先不迁移 UI，只打底座。

### Phase 2：直接切换线程写入与读取

运行规则改为：

- 新线程：只写全局目录
- 线程列表：只读全局索引
- transcript 回放：只读全局 transcript

这一步的目标是：

- 新数据不再污染工作区
- 线程恢复路径变得单一
- 不再依赖 workspace 搜索历史 transcript

### Phase 3：引入持久化 `CredentialStore`

新增：

- `PersistentCredentialStore`
- `AccountMetadataStore`
- 系统安全存储桥接

运行规则改为：

- OAuth token 成功获取后立即持久化
- Desktop 重启时自动恢复 token source
- 无法恢复时再进入 `needs_reauth`

### Phase 4：清理旧实现残留入口

切换完成后：

- `appendUserTranscriptRecord`
- `appendConversationTranscript`
- `appendRunEventTranscript`

全部改为写入全局 transcript store，并移除任何基于 workspace transcript 的恢复路径。

### Phase 5：统一 Desktop 数据治理入口

在设置或扩展管理区域引入更清晰的状态展示：

- 线程历史存储位置
- 用户级 MCP 配置来源
- 项目级覆盖来源
- 授权账户列表
- 需要重新授权的连接

## 跨平台路径契约

### Mac

- App 全局根目录：`~/Library/Application Support/@awaken/desktop`
- 会话历史：`~/Library/Application Support/@awaken/desktop/data/threads/`
- 线程索引：`~/Library/Application Support/@awaken/desktop/data/threads.sqlite`
- 用户级 MCP 配置：`~/Library/Application Support/@awaken/desktop/config/mcp-servers.json`
- 授权元数据：`~/Library/Application Support/@awaken/desktop/data/auth/connector-accounts.sqlite`
- 敏感凭据：`Mac Keychain`

### Windows

- App 全局根目录：`%APPDATA%\\@awaken\\desktop`
- 会话历史：`%APPDATA%\\@awaken\\desktop\\data\\threads\\`
- 线程索引：`%APPDATA%\\@awaken\\desktop\\data\\threads.sqlite`
- 用户级 MCP 配置：`%APPDATA%\\@awaken\\desktop\\config\\mcp-servers.json`
- 授权元数据：`%APPDATA%\\@awaken\\desktop\\data\\auth\\connector-accounts.sqlite`
- 敏感凭据：`Windows Credential Manager / DPAPI`

### 统一规则

- 上层模型一致
- 仅系统路径前缀不同
- 不维护 mac/windows 双主线实现

## 风险与注意事项

### 1. 旧历史会直接被放弃

本方案明确不兼容旧 workspace transcript，因此必须接受：

- 旧的 `.awaken/transcripts` 不再作为正式历史来源
- 用户升级后看不到旧 workspace 历史
- 任何仍依赖旧 transcript 的手工流程都将失效

这不是 bug，而是明确的产品取舍。

### 2. 线程与 workspace 解绑后，某些运行恢复要更谨慎

线程还在，不代表原 workspace 还在。恢复时要区分：

- 线程历史可读
- workspace 当前可访问

两者不能混为一谈。

### 3. 项目内协作场景会改变预期

过去把 transcript 放在 workspace 里，某种程度上会让“项目跟历史一起走”。改成 app-global 后，这种副作用会消失。

这是正确方向，但要承认它改变了少量用户的旧习惯，因此必须提供显式导出能力。

### 4. 授权状态迁移的兼容期会更长

虽然线程历史不做兼容，但 OAuth 凭据仍然不能简单从内存迁移到磁盘，因为：

- 当前很多 token 根本没有 durable source
- 有的 provider 只给短期 token
- 有的 provider 需要 refresh token 才能恢复

所以授权持久化的首批目标不是“百分百无感迁移”，而是：

- 新授权立即持久化
- 老授权在重新登录后进入新体系
- 重启后尽量不再丢登录态

## 验收标准

### 功能验收

- 新会话不再写入 `workspace/.awaken/transcripts`
- 新线程统一写入 `userData/data/threads`
- 重启 Desktop 后，线程列表从全局索引恢复
- 切换 workspace 不影响历史线程可见性
- 删除某个 workspace 目录后，线程历史仍可见
- 删除线程时，不再操作工作区内 transcript 文件
- 新线程重启后再次续问，模型仍能接上前文
- `model_profile` 选择与运行时注入行为不变
- `ContextEstimated`、warning、auto-compact、block 行为与当前一致
- 需要 OAuth 的 MCP / Connector 在重启后能恢复已持久化的登录态
- UI 能明确区分“已配置”和“已授权”

### 非兼容验收

- 旧 workspace 下的 transcript 不再进入正式线程列表
- 系统不再 fallback 读取 `workspace/.awaken/transcripts`
- 新线程完全独立于旧 workspace transcript
- 旧的 `~/.awaken/mcp.json` 仍可读取并迁移到新的 Desktop config 层
- 已经重新授权过的新账户可在重启后恢复

### 跨平台验收

- Mac 路径写入正确
- Windows 路径写入正确
- 两端线程恢复与删除语义一致
- 两端线程恢复后的模型连续性一致
- 两端授权元数据结构一致
- 两端敏感凭据都不以明文形式落在普通配置文件中

### 安全验收

- access token / refresh token 不出现在 `threads.sqlite`
- access token / refresh token 不出现在 `thread_<id>.jsonl`
- access token / refresh token 不出现在普通 `config/*.json`
- 删除账户时，系统安全存储中的对应凭据一并清除

### 上下文管理验收

- 恢复后的 transcript 仍通过 tool-result pairing 校验
- compact boundary 恢复正确
- `LastContextWindowState` 恢复正确
- 已发生过压缩的线程在重启后继续对话，不出现上下文断层

## 推荐实施顺序

1. 抽象全局 `ThreadStore`
2. 新增 `userData/data` 路径与初始化
3. 建立 `threads.sqlite` 索引
4. 新线程切到全局写入
5. 左侧线程列表切全局索引
6. 重启恢复切全局 transcript
7. 抽象 `PersistentCredentialStore`
8. 打通系统安全存储桥接
9. 设置/扩展页接入授权状态展示
10. 清理旧代码路径与导出能力

## 本轮明确不做

- 不在本轮把 transcript 改成纯 sqlite
- 不在本轮为旧 `.awaken/transcripts` 提供兼容恢复
- 不在本轮引入云同步
- 不在本轮实现团队共享线程库
- 不在本轮承诺所有旧 OAuth 登录态都可自动迁移
- 不在本轮把所有 CLI / 非 Desktop 路径统一到同一个存储后端

## 结论

这不是一个“把文件从 A 挪到 B”的小修，而是 Awaken 从开发态线程恢复方案，走向正式 Desktop 会话系统与正式 Desktop 状态治理系统的关键一步。

如果 Awaken 要对标 Codex Desktop，至少要同时满足两件事：

- 会话历史默认成为 **应用级全局资产**
- MCP / Connector 的授权状态成为 **应用级可恢复资产**

同时，本方案额外确立一个强约束：

- **可以放弃旧历史兼容，但不能破坏当前正常使用的核心功能**

这里的“核心功能”至少包括：

- 新线程创建
- 左侧线程列表显示
- 线程切换与 transcript 回放
- 重启后恢复当前线程
- 重启后继续模型对话的连续性
- 线程重命名与删除
- 模型配置继续正常调用
- 上下文估算、压缩、阻断继续正常
- MCP 配置继续可用
- 已完成持久化的新授权能跨重启恢复

因此，本方案应作为 Awaken 后续：

- 线程系统
- 左侧栏历史
- 跨项目恢复
- MCP / Connector 登录态
- 导出归档
- 桌面产品化

的统一基线。
