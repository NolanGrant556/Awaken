# MCP 运行时验收规范

## 1. 验收范围

本文档负责 MCP 配置、transport、状态机、工具注册、认证限制和 Skill bridge 的最小复核集。结论必须使用当前 `HEAD` 的执行结果，不接受旧任务清单或过期截图代替。

## 2. 静态复核

- 配置只宣称 `stdio/http/sse` 为生产支持。
- `cmd/awaken-core/main.go` 若仍未注入 `WithInProcRegistry`，文档必须保留 in-process 未接线结论。
- Desktop/main 若仍未调用 `InstallAuthFetcher`，必须保留 `AUTH_FETCHER_REQUIRED`。
- `CallTool` 若仍没有写回 server state，必须保留 connected-tool-call 401 缺口。
- `Disable` 若仍没有回写 config，必须保留“重启后重新加载”边界。
- `FetchPromptBody` 若仍固定 nil arguments/只返回 description/不调 resources/read，不得宣称 Skill bridge 完整。

## 4. 真实 Desktop 验收

按根 README 正式入口启动，在“连接器 > MCP”进行：

1. 确认“Awaken 内置”和“用户安装”分组可见。
2. 只读检查已存在 server 的 name、transport、scope、state 和 error reason。
3. 打开设置对话框时，可检查工具/日志，但不保存、不删除、不切换 enable/disable。
4. 如验证配置、连接、停用或删除，必须使用可抛弃 workspace 和隔离 Desktop profile，并在测试后核对配置和子进程清理。

本轮文档验收不允许点击连接、断开、配置、停用、删除或授权，因为这些操作都会修改 userData 或外部进程状态。

## 5. 验收失败条件

出现任一情况必须判定未通过：

- 文档或 UI 把 WS、生产 in-process、完整 OAuth 或跨重启 disable 写为已支持。
- server 失败导致整个 runtime 不可用。
- server 离线后 `mcp__{server}__*` 工具仍可被新 run 看到。
- 机密凭据出现在 JSON 配置、日志、SSE 或截图。
- Desktop 真实行为与文档不一致，但验收者仅修改文档掩盖差异。
