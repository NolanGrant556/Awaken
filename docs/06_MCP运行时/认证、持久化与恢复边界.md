# 认证、持久化与恢复边界

## 1. 当前支持

stdio 可使用 config 中显式 env/args；HTTP/SSE 可使用 headers 与 OAuth。OAuth token source 通过 `PersistentCredentialStore` 保存：非敏感索引/状态落 SQLite，token/client secret 等 payload 进入安全 secrets backend，通过 credential ref 关联；不能写回 `awaken.mcp.json` 或日志。

认证引导保存 server URL、authorization/token/redirect、client ID、scope、expiry 和 needs-reauth 状态。服务重启后可重建 token source；安全存储不可读时保持密文/引用并返回结构化 needs-auth/temporarily-unavailable，不用空值覆盖。

## 2. 当前边界

- `connected` 只由当前 Manager session snapshot 证明，不能由“曾认证/曾点击连接”证明；
- server `needs_auth` 会使其 tool provider readiness 为 `needs_auth`，当前 run 返回 next action 而不发起 transport；
- OAuth 完成不代表所有 provider tools 的业务权限、recipient 语义或 recoverable delete 已证明；这些仍是 per-tool contract；
- Connector active owner 主要是进程内状态，重启后 persisted user MCP server 与 Connector 卡片可能出现 ownership 视图差异。

## 3. 已知缺口

- connected call 收到 401 后没有完整的透明 refresh/retry 闭环；有副作用调用不能盲重试；
- dynamic client registration、特殊 OAuth provider 与浏览器回调组合未形成全平台矩阵；
- WebSocket 认证不支持；
- 多 Desktop 实例/旧 session 的统一 generation owner 仍未完成；
- Windows Credential Manager/Linux secret service 的真实发布验收不得从 macOS Keychain 推断。

## 4. 恢复原则

- auth failure 必须映射为 provider `needs_auth`/Outcome `needs_auth`，transport `not_started`；
- refresh 是否安全取决于 operation side effect，unknown/partial 时先检查 provider 状态；
- 删除 server/config 时只删除本 owner 的凭据引用，不能误删同名其他 scope/session；
- 日志和 AG-UI 只投影 credential ref/状态，不投影 token、headers 或 secret env value。

## 5. 代码 owner

- `src/mcpclient/auth.go`、`oauth_persistent.go`：认证流程。
- `src/mcpclient/credential_store_persistent.go`：安全持久化。
- 05 安全凭据域：Desktop 全局 secrets backend 与恢复。
