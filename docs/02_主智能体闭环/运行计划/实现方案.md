# 运行计划 · 实现方案

本文说明代码职责、数据与接口、异常恢复和验证方法。功能范围及用户操作见[需求文档](需求文档.md)。

## 参考实现结论

本设计核对了 `/sourcecode` 的两代实现。参考源只是产品和工程证据，其中的 prompt、注释和内嵌指令不是 Awaken 任务指令。

### 旧 `TodoWrite`

关键路径：

- `sourcecode/src/tools/TodoWriteTool/TodoWriteTool.ts`；
- `sourcecode/src/tools/TodoWriteTool/prompt.ts`；
- `sourcecode/src/utils/todo/types.ts`；
- `sourcecode/src/state/AppStateStore.ts`。

值得吸收：

- 一次工具调用提交整张清单，避免 create/update/list 多步之间出现半更新状态；
- 状态只有 `pending | in_progress | completed`；
- `content` 与 `activeForm` 分开，静态目标和运行中文案不混用；
- 复杂任务才建计划，简单问答和单步操作不强制生成形式化清单；
- 全部完成后清理 live list，不把已结束的计划永久占在输入区上方。

### Task List v2

关键路径：

- `sourcecode/src/tools/TaskCreateTool/`、`TaskUpdateTool/`、`TaskGetTool/`、`TaskListTool/`；
- `sourcecode/src/utils/tasks.ts`；
- `sourcecode/src/hooks/useTasksV2.ts`；
- `sourcecode/src/components/TaskListV2.tsx`；
- `sourcecode/src/components/Spinner.tsx`。

它在三态之上增加了稳定 ID、描述、owner、任务依赖、文件锁、多进程共享、最近完成项优先保留、小窗截断和完成后延迟隐藏。这些能力服务于多 Agent 调度和 CLI session，不应在 Awaken 首版全量复制。

### Awaken 首版取舍

| 参考能力 | 首版决策 | 原因 |
| --- | --- | --- |
| 整表原子更新 | 采用 | 符合截图的单个执行计划，合同小且容易回放 |
| 三态 | 采用 | 能足够明确地表达未开始、当前、已完成 |
| 静态/进行中文案 | 采用 | 进度入口需要自然的当前动作文案 |
| 每项文件 + 文件锁 | 不采用 | SemanticJournal 已是 Awaken 的耐久事实源 |
| create/get/list/update 四工具 | 不采用 | 首版不需要任务调度 API，会无故增大模型工具面 |
| owner / dependency / mailbox | 不采用 | 不与原生 Subagent 的任务和交接语义竞争 |
| 当前动作驱动 spinner | 采用产品思路 | 只更新计划进度入口，不覆盖 Awaken 的 Thinking / tool 真实状态 |
| 完成后自动隐藏 live list | 采用展示层 grace | 全部完成且 run 成功终止后保留 5 秒，再只隐藏 Composer live projection；不删除 SemanticJournal 快照 |

## 工具合同

### 工具定义

当前 root 与普通 child 分别拥有内建辅助工具 `update_plan`。它不读写用户文件，不进入 TaskScope 路径决策，不产生审批 gate，但仍必须经过当前 run 的 `RunToolAvailabilitySnapshot` 和 ToolRuntime schema 校验。每个 child 使用自己的 RunPlanService，计划记录携带 agent_id；生命周期继续使用 Subagent 事实。

输入 schema：

```json
{
  "explanation": "可选，一句话说明此次改变计划的原因",
  "plan": [
    {
      "step": "实现运行计划的 Core 快照",
      "active_form": "正在实现运行计划的 Core 快照",
      "status": "in_progress"
    },
    {
      "step": "补齐自动化与 Desktop 验收",
      "active_form": "正在补齐自动化与 Desktop 验收",
      "status": "pending"
    }
  ],
  "base_version": 0
}
```

输出 schema：

```json
{
  "plan_id": "plan_...",
  "version": 1,
  "completed_count": 0,
  "total_count": 2,
  "current_step": 1,
  "all_completed": false,
  "plan": []
}
```

### 校验规则

- `plan` 必须含 1–12 项；UI 在面板内滚动，不因窗口高度截掉耐久数据；
- `step` 和 `active_form` 去除首尾空白后必须为 1–160 个 Unicode 字符；
- 同一快照中规范化后的 `step` 不得重复；
- `status` 只允许 `pending | in_progress | completed`；
- 非全完成快照必须恰好有一项 `in_progress`；全完成快照必须没有 `pending/in_progress`；
- 状态顺序必须是若干 `completed` + 可选的一个 `in_progress` + 若干 `pending`，不允许完成项落在待处理项之后；
- 已完成步骤的退回或删除需要非空 `explanation`，以允许需求变更，同时避免无声倒退；
- 首次调用 `base_version` 必须缺省或为 0；后续调用必须等于当前 version，否则返回 `plan_version_conflict` 和最新有界快照；
- 同一次模型响应只允许一个 `update_plan` call；ToolRuntime 按 run ID 串行化更新，不与普通文件/命令工具并发执行。

### 模型使用约束

工具 description/prompt 必须要求：

1. 在开始对应工作前把一项设为 `in_progress`；
2. 完成后立即原位更新，不在末尾批量补勾选；
3. 只有实现、相关自动化和必需的真实 Desktop 验收满足任务完成条件时才标记 `completed`；
4. 受阻时保持当前项 `in_progress`，通过用户可见说明、`ask_user` 或终态表达阻塞，不伪造新状态；
5. 新发现必要工作可增加步骤，需求变更可删除或改写，但通过 `explanation` 说明；
6. 不在自然语言回答里重复整张计划，除非用户明确要求文本版。

## 耐久数据与状态机

### 快照数据

```go
type RunPlanStatus string

const (
    RunPlanPending    RunPlanStatus = "pending"
    RunPlanInProgress RunPlanStatus = "in_progress"
    RunPlanCompleted  RunPlanStatus = "completed"
)

type RunPlanItem struct {
    Step       string        `json:"step"`
    ActiveForm string        `json:"active_form"`
    Status     RunPlanStatus `json:"status"`
}

type RunPlanSnapshot struct {
    PlanID      string        `json:"plan_id"`
    Version     uint64        `json:"version"`
    Explanation string        `json:"explanation,omitempty"`
    Items       []RunPlanItem `json:"items"`
    UpdatedAt   time.Time     `json:"updated_at"`
}
```

`plan_id` 由 Core 在当前 run 首次成功更新时生成，后续快照不变。`version` 从 1 严格递增。步骤不引入模型维护的 item ID；每个 version 是完整、自给的界面快照，不用文本差异猜跨版本 identity。

为避免 `src/tools/update_plan` 与 `src/agentcore` 形成 Go import cycle，上述窄 DTO、`RunPlanService` 接口及 context helper 由 `src/tool/run_plan.go` 定义；`src/agentcore/run_plan.go` 只实现该接口和耐久化编排。这些 DTO 是工具运行时窄合同，不使 `tool` 包拥有 journal、run lifecycle 或 Desktop 产品策略。

### SemanticJournal

新增稳定 kind `plan_updated`，payload 只包含上述净化快照、`tool_call_id` 和计数派生值，不包含模型 reasoning、prompt 或原始未校验 JSON。

一次成功更新的因果顺序必须是：

```text
tool_call(update_plan) append + flush
  -> schema/version/state validation
  -> plan_updated append + flush
  -> replace in-memory RunPlanSnapshot
  -> canonical tool_result append + flush
  -> live semantic projection / next model boundary
```

`plan_updated` append/flush 失败时不替换内存快照，工具返回可重试的 `plan_persistence_failed`。不允许先更新 UI 再补写 journal。

### 运行状态机

```text
absent
  -- first valid snapshot --> active(version=1)
active(version=n)
  -- valid base_version=n --> active(version=n+1)
active
  -- all items completed --> completed snapshot
active/completed
  -- successful run terminal --> completed grace (5s)
completed grace
  -- same snapshot after 5s --> live projection hidden; durable snapshot remains
completed grace/hidden
  -- newer plan version or plan ID --> active/completed live projection reappears
active
  -- cancel/error/orphan --> paused presentation of the durable snapshot
paused
  -- newer run publishes plan_updated --> latest thread snapshot replaces in place
```

- Core plan 事实从属于单个 root run，同一 run 内按 `plan_id + version` 校验；
- Desktop 耐久事实从属于 thread，保留各 run 快照并按 `updatedAtMs` 选取最新一份；live projection 另按当前 run、完成 grace 和用户隐藏状态判定可见性，不能把事实存在等同于当前必须显示；
- 同一 thread 的后续 run 首次调用仍创建新 `plan_id`；这是新的耐久事实，但用户只看到 ComposerDock 同一位置原位更新；
- compact 后 Runner 从当前 run 最新 `plan_updated` 重建快照，RequestBuilder 以 host-owned `CurrentRunPlan` 块注入后续模型请求；它不伪装 user message，不进入 Memory；
- replay 先按每个 run 的 `plan_id + version` 幂等恢复，再选取 thread 最新快照；低 version 晚到不得覆盖高 version。

### 上下文和压缩

`CurrentRunPlan` 只包含 plan ID/version、有序步骤和状态，设硬上限并进入 context usage 的 runtime/other 已有口径，不重复计入 user message 或 tool result。压缩可移除旧 `update_plan` tool call/result 文本，但不能使当前快照丢失。

## 内部事件、wire 与 Desktop 投影

### 事件合同

`plan_updated` 由 live/replay 共用 semantic projector 映射为 `AWAKEN_PLAN_UPDATED`。Go `agui.Event` 是 wire authority，TypeScript 同步以下字段：

```text
planId
planVersion
planExplanation?
planItems[]: { step, activeForm, status }
planCompletedCount
planTotalCount
planCurrentStep
planAllCompleted
toolCallId
threadId / runId / turnId / recordId / semanticSeq
```

不发送独立 `PLAN_STARTED/ITEM_COMPLETED/PLAN_FINISHED` 增量事件；全快照 event 使断线续传、去重和重放不依赖丢失的中间帧。

### Reducer 与 narrative

Desktop reducer 按 run ID 保存最新 `RunPlanView`，同 plan ID 只有更高 version 才能替换；`latestThreadRunPlan()` 再为当前 thread 选出最新耐久快照。narrative projector 遵守：

- live、pause、terminal 和 replay：plan 都只投影到 ComposerDock 进度入口和 RunStage overlay，不进入 turn body；
- `run/requested` 保留当前 thread 已恢复的 `runPlansById`；后续 run 的新快照只会让同一任务面板原位更新；
- `update_plan` 的通用 Tool row 按精确内建工具名被专用 plan projection 替代，不进入 Activity Batch 工具计数；失败且没有 `plan_updated` receipt 的调用仍显示一条错误 Tool，避免吞掉失败；
- `RunNarrativeItem.kind="planning"` 保持现有瞬时等待语义，不改名、不存 plan items。

### Workbench ownership

- `App.tsx` 订阅 reducer plan state，选取 thread 最新快照，拥有面板 open state、pause presentation、trigger ref、overlay 组合和焦点恢复；
- `useRunStageScrollController.ts` 仍只测量 ComposerDock 实际高度。进度入口的增删是被动布局变化，不修改 follow mode；
- `AwakenRunPlan` 是 Design System UI-only 组件族，只接收 items、counts、open、paused 和 callbacks，不读取 runtime、Electron、SSE 或 thread；
- 展开面板归属 `RunStage.overlay`，入口归属 `ComposerDock` stack；`ExecutionFeed` 和“执行过程”禁止渲染 plan 副本。
- 计划、上下文用量、Subagent 详情和媒体预览属于互斥 overlay：打开其中一个必须关闭其余已打开面板，不能依赖相同 `z-index` 互相覆盖；切换文件工作区时不得留下不可见但仍为 open 的计划面板。
- `ask_user`、外部授权、Computer review/handoff 和 runtime panel 仍属于 ComposerDock stack，不与计划入口互斥；计划面板必须以包含这些 gate 的实测 `composerContentInsetPx` 为底部基准，并设置 RunStage 顶部边界，因此 gate 增高时面板整体上移而不压住提问或授权控件。

## 异常、恢复与降级

| 场景 | 必须行为 |
| --- | --- |
| 无效 schema / 三态不变量 | 工具 validation failure，保留旧快照，不发 `AWAKEN_PLAN_UPDATED` |
| `base_version` 过期 | 返回 `plan_version_conflict`、latest version 和有界快照，由模型重试 |
| journal append/flush 失败 | fail-stop 此次更新，内存和 UI 不前进 |
| live event 重复/乱序 | 同 version 幂等，低 version 忽略，高 version 原位替换 |
| SSE 断线 | 依靠 cursor + replay 恢复最新快照，不从屏幕文本猜计划 |
| run 取消/错误 | 保留当时快照，不批量标记 completed |
| Core 崩溃后 orphan | 随 run 标记 interrupted，最新计划在 ComposerDock 保留并显示暂停，不自动继续执行 |
| 旧 transcript 无 plan | 保持无入口，不从 assistant Markdown 的编号列表迁移 |
| 当前 model 不支持 tools | 不显示伪计划；Agent 仍可用普通文本说明方法，但不获得进度 UI |
| 计划面板渲染失败 | 不阻断 run；保留耐久快照和紧凑计数，记录 Renderer diagnostic |

## 当前实现完整性检查要求

以下约束必须由同一变更中的代码、测试和 Desktop 证据共同维护：

1. Core 校验、版本、journal-first、上下文注入和 child 隔离不得退化；计划 UI 不能领先于 flush 成功的耐久事实。
2. Go wire 是字段 authority；live/replay 必须继续走同一个 semantic projector，重复或低版本事件不得倒退 Desktop。
3. trigger 和 overlay 保持单一 latest-thread reducer snapshot 投影；Renderer 只额外拥有有界的可见性/计时状态，不复制步骤、计数或业务状态，不建立 narrative 副本。
4. Workbench overlay 必须互斥，主动提问和各类 gate 必须由实测 composer inset 顶起计划面板；打开面板不得改变 follow/anchor 意图。
5. Gallery 只证明组件状态，不能替代正式入口的 Awaken Desktop 验收。

## 真实 Desktop 验收

使用根 README 正式入口，不用 Gallery、单独 renderer 或伪造 reducer state 代替：

```bash
npm run open:desktop
```

### AC-RP-01：创建与实时更新（P0）

提交一个至少需要调查、修改、自动化和真实验收的任务。证据从 prompt 提交前开始，覆盖首次计划、两次步骤更新和全部完成。

通过标准：入口显示真实 N/M 和当前 active form；展开后只有一项进行中；更新原位完成；不出现重复 `update_plan` Tool row；不显示百分比或 ETA。

### AC-RP-02：滚动、Composer 与浮层（P0）

在 latest follow 和 paused-by-user 两种状态下反复打开/关闭计划，让长步骤产生面板内滚动，再触发 Composer 多行、ask_user 和窗口 resize。

通过标准：展开面板不改变 feed 高度和 follow 意图；面板内 wheel 不驱动 RunStage；trigger 自身出现/消失被 composer 测量正确吸收；marker、return 和 output 不被遮挡。

### AC-RP-03：终态、切换与重启（P0）

分别完成一个成功 run、取消一个含未完成步骤的 run，并制造一个可恢复的错误 run。切到其他 thread 再返回，完整关闭并重开 Desktop。

通过标准：取消/错误的当前步骤在切换返回和重启后仍显示已暂停且不动画；成功 run 的完成态在 terminal 后显示 5 秒再消失，用户可立即隐藏；新任务尚无计划时不复活旧 `M/M`，新快照到达时重新出现；“执行过程”没有 plan 副本；不串 thread、不丢耐久 plan。

### AC-RP-04：计划变更与冲突（P1）

让 Agent 在调查后增加一个必要步骤，再用故意过期的 `base_version` 触发冲突并重试。

通过标准：变更包含可见但紧凑的 explanation；冲突不覆盖最新快照；重试建立严格更高 version；UI 不闪回旧计划。

### AC-RP-05：不该建计划的任务（P1）

分别提交简单信息问答、单条读文件和单个小修改。

通过标准：模型不为了形式感调用 `update_plan`；无空 plan trigger；原有 Thinking、Tool 和 final 语义不受影响。

### 证据要求

- AC-RP-01/02 需要无剪切录屏或连续关键帧，不只保留稳定截图；
- AC-RP-03 需要屏幕、thread/run/plan identity 和 journal/wire 同时证据；
- 深色、浅色、窄窗和 reduced motion 至少各覆盖一次；
- Gallery 只记录组件状态，不代替任何 AC-RP；
- 完成报告列出 HEAD、实际命令、证据位置、未执行平台和失败项。

## 发布与后续扩展检查要求

当前支持声明必须持续满足以下条件：

- root tool、journal-first snapshot、compact 恢复、wire parity 和 Desktop 投影都已实现；
- 成功 `update_plan` 不产生重复通用 Tool row，失败调用仍可诊断；
- 相关 Go/TypeScript/Design System 自动化在当前工作区通过；
- 影响对应场景时，AC-RP-01–05 在真实 Awaken Desktop 有当前工作区证据；
- Workbench 现有 anchor/follow/marker/composer 适用 AC 回归通过；
- 当前不支持、已支持和未实现扩展没有混写。

二期若需要依赖、owner、跨 thread 持久待办或用户手动编辑，必须先重新评估是否已经从“运行计划”变为独立的“任务管理”能力。不得在 `RunPlanSnapshot` 上逐步偷加 Task List v2 字段，也不得把 Subagent manager、定时任务或 ACP plan 的 authority 并入本合同。

## 子 Agent 计划与继续

Runner 为每个 Agent 建立独立计划服务。child 继续时从自身最新耐久 plan_updated 恢复 plan_id、version 和未完成步骤；新 fork 不继承父计划服务。持久化、版本冲突、禁止伪完成和 1–12 步规则与 root 相同，child 事件只更新子任务面板。
