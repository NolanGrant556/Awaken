# 计算机操作能力当前支持边界

## 1. 权威范围

本文唯一拥有 Awaken 当前是否具备原生 OS Computer Use、哪些邻近能力不能混同，以及当前验证方法。不负责未来架构；未来约束见 [计算机操作能力设计契约](./计算机操作能力设计契约.md)。

## 2. 当前产品事实

截至当前代码，Awaken 没有原生 Computer Use 能力。用户不能让 Agent 通过 Awaken 自有的受控运行时观察整个桌面、定位窗口/AX 元素、发送鼠标键盘输入、接管/归还控制权或重放 GUI 轨迹。

代码中当前不存在：

- `src/computer` 或等价 Computer domain/runtime；
- `LaneComputer`、`ComputerExecutor` 或 run-scoped `ComputerSession`；
- `computer_observe`、`computer_act`、`computer_verify`、session/takeover 工具；
- Computer observation/action/review/control-transfer/verification 语义记录与 AG-UI 事件；
- Computer HTTP route、lease/fencing/state store、截图 Blob Store 或 trajectory recorder；
- Desktop Computer 画面、专用高风险 review、takeover 控制或轨迹播放器。

因此产品文档、UI 文案和 Agent prompt 都不能宣称“可操作任意本机应用”“可看屏幕并点击”或“具备原生 Computer Use”。

## 3. 邻近能力不是 Computer Use

| 当前能力 | 为什么不等同于原生 Computer Use |
| --- | --- |
| MCP 浏览器/自动化 server | 它们是外部 MCP 工具，受各 server transport 和工具合同约束；Awaken 没有统一 Computer session、lease、fencing、takeover 或 GUI 轨迹 |
| Connector | 连接器只是 MCP/CLI 来源与生命周期入口，不授予 OS 全局观察和输入能力 |
| Shell 本机执行 | shell 是字符串命令执行面，不是窗口、AX、截图、动作验证或 OS sandbox |
| typed 文件工具 | 只操作明确文件边界，不观察或控制 GUI |
| Electron Desktop 自身 | 应用能显示 UI、打开经复验的 artifact，不代表 Agent 能控制其他应用 |
| 测试使用的 Browser/Computer Use 工具 | Codex 验收基础设施属于开发者外部工具，不是 Awaken 产品 runtime 能力 |

当某个 MCP server 自己提供截图或点击工具时，当前只能称“通过该 MCP server 调用其工具”；不能上升为 Awaken 已实现统一 Computer Use 架构。

## 4. 当前支持与不支持

当前支持：

- 通过正式 Tool/Connector/MCP/Skill 入口执行各自已经注册的能力；
- 由外部测试工具操作 Awaken Desktop 完成真实验收；
- 把 [计算机操作能力设计契约](./计算机操作能力设计契约.md) 作为未来实现的强约束。

当前不支持：

- 原生全桌面截图、AX tree、窗口枚举或坐标 grounding；
- 原生 mouse/keyboard/scroll/drag/type action；
- 独占桌面租约、fencing token、control epoch 和崩溃恢复；
- Computer 高风险动作 review 或 human takeover；
- 多模态 tool-result 截图闭环、加密媒体 Blob、轨迹审计和只读 replay；
- VM/Sandbox、远程桌面池、多租户 Computer data plane；
- 无人值守金融交易、外部发布、批量删除或凭据/验证码读取。

## 5. 异常与用户恢复

如果任务需要操作未被现有 typed tool、MCP 或 Connector 覆盖的 GUI，当前正确结果是明确报告“不支持或缺少对应工具”，并让用户手动完成或安装/配置一个有明确合同的扩展。不得：

- 静默改用 shell 拼接 GUI automation；
- 假装浏览器 MCP 可以控制整个 OS；
- 让模型输出坐标后由不受控脚本执行；
- 复活通用 ApprovalCard 来掩盖没有 Computer policy/runtime 的事实；
- 把设计契约中的未来 API 写入当前 route 或 event 清单。

## 6. 验证方法

### 6.1 静态

```text
rg -n "LaneComputer|ComputerExecutor|computer_observe|computer_act|computer_verify" src apps/desktop
rg -n "computer_session|computer_observation|computer_action|computer_control_transfer" src apps/desktop
```

预期没有生产实现命中；若未来出现命中，必须继续核对注册、route、事件、Desktop UI、lease/fencing 和测试，不能以单个类型名判定能力已落地。

### 6.2 自动化

运行项目全量 Go、Desktop typecheck 和相关测试，确认当前产品没有因文档整理被改变。本文没有 Computer 专项自动化，因为该能力尚未实现；未来实现前必须先按设计契约第 14 节建立测试矩阵。

### 6.3 真实 Desktop

按根 README 正式入口打开 Awaken，只读确认工具、连接器、Skill 和 Workbench 中没有原生 Computer 控制入口。不要因为 Codex/测试代理能操作这个窗口，就把该外部验收能力归入 Awaken。

## 7. 变更门槛

只有同时具备以下证据，才能把某项从“不支持”迁入当前能力：

1. 代码 owner 和注册路径真实存在；
2. Tool/Runtime、安全状态机和持久化符合设计契约；
3. 自动化覆盖正常、失败、取消、崩溃和并发边界；
4. 正式 Desktop 中完成真实任务并保留验收证据；
5. 相关 01/02/03/04/09 权威文档同步更新。
