# 实施顺序与验收策略

## 1. 原则

Workbench 中间区域不能按“大计划一次性全量落地”的方式推进。后续必须遵循：

- 每次只修改一个行为轴：sticky/anchor、latest follow、return affordance、transcript replay、work packet 不能在同一刀里混改。
- 每刀必须能独立回滚。
- 如果真实 Desktop 出现滚动或布局破坏，应撤回该刀，而不是继续在坏状态上叠补丁。
- 静态测试、typecheck、截图脚本通过只能说明代码基本可运行。
- 真实中间区域滚动手感、composer 多行跟随、输出与输入框间距，必须由真实 Desktop 验收决定。
- 视觉按钮需求不得和 scroll controller 状态机重构绑定提交。

## 2. 必须使用真实 Desktop

涉及中间区域布局、滚动、锚定、follow、composer、turn marker 的改动，必须使用：

```bash
npm run open:desktop
```

并确认窗口 ready、可见、尺寸足够。浏览器打开 `127.0.0.1:5174` 不能代表 Desktop 验收，因为 renderer 依赖 Electron bridge。

关闭时使用：

```bash
npm run close:desktop
```

## 3. 真实交互通道

动态交互验收指定使用真实 Awaken Desktop。允许两种等价通道：

1. 自动操作通道：具备 Computer Use、系统级 UI 自动化或等价真实桌面控制能力时，由 Agent 操作真实 Electron 窗口，并保存录屏 / 关键帧 / manifest。
2. 人工操作通道：缺少真实桌面操作能力时，Agent 必须输出可执行验收脚本和阻塞条件，由用户或另一个具备桌面控制能力的验收者在真实 Awaken Desktop 中操作，并把录屏 / 关键帧保存到验收文件夹。

缺少真实桌面操作能力的 Agent 不能声明“动态验收通过”，只能声明“静态检查通过，等待真实 Desktop 验收”。

## 4. 最小 P0 验收链路

1. 打开 Awaken Desktop，确认 center composer。
2. 发送第一条短 prompt，确认 prompt 置顶、dock composer 出现。
3. 发送第二条短 prompt，确认最新 prompt 置顶，旧 turn 不遮挡 answer。
4. 发送两条多行 prompt，确认多行 bubble 不破坏 sticky/anchor。
5. 发送第三条 prompt，确认 turn marker 出现。
6. 点击旧 marker，确认跳转与 active marker 同步，且 latest follow 暂停。
7. 运行长输出任务，向上滚动暂停 follow。
8. 输出继续增长时不自动拉回，并显示“回到最新输出” affordance。
9. 点击“回到最新输出”或向下滚回 final output bottom 后，follow 可恢复。
10. run 完成后 final output 与 dock composer 保持稳定避让。
11. 运行包含大量工具调用、文件变更或执行日志的任务，确认长 trace 聚合为可展开 work packet。

## 5. 截图、录屏与 manifest

至少保留：

```bash
npm run capture:workbench -- --state center --no-open
npm run capture:workbench -- --state dock --no-open
npm run capture:workbench -- --state marker --no-open
```

涉及视觉变更时使用：

```bash
npm run capture:workbench:vrt
```

所有涉及 Workbench 中间区域交互、滚动、锚定、follow、composer、marker、prompt bubble 或 work packet 的 PR，必须保存真实 Desktop 录屏或关键帧证据到固定目录：

```text
docs/01_桌面工作台/中间交互区域/验收文件夹/
```

PR 描述中必须列出对应录屏 / 截图 / manifest 路径。只贴临时目录截图或只说明“本地看过”不算通过验收。

## 7. 推荐实施顺序

### Phase 1：修复 P0 sticky/anchor 状态模型

目标：解决 WBI-001 / WBI-002。

验收：连续多行 prompt、两轮以上 run、旧 header 不遮挡、新 prompt 置顶。

### Phase 2：统一 composer inset / latest tail follow

目标：解决 WBI-003。

验收：长输出、runtime panel、approval prompt、composer 高度变化后，final output 与 composer 保持稳定间距。

### Phase 3：补强 user intent / follow 状态机

目标：解决 WBI-004。

验收：用户向上滚动暂停、被动内容增长不恢复、明确向下回 tail 才恢复。

### Phase 4：单独实现 return-to-latest affordance

目标：按 [回到最新输出按钮需求](回到最新输出按钮需求.md) 实现按钮。

验收：AC-007、AC-008、AC-008A。

### Phase 5：落地 collapsed work packet

目标：解决 WBI-008。

验收：长工具调用、文件变更、执行日志聚合为可展开 work packet，且不破坏 anchor/follow/composer/marker。

### Phase 6：恢复低风险结构重构

目标：继续治理 `App.tsx`。

验收：每一刀保持 DOM / key / behavior 不变，并执行相关 AC。

## 8. 静态检查

每个阶段至少运行：

```bash
npm --workspace @awaken/desktop run test
npm run typecheck:desktop
git diff --check
```

如果改动 design-system 文件，还需运行：

```bash
npm run smoke:ui
```

如果改动 runtime / protocol-adjacent event handling，再运行相关 Go 测试。
