# 用量查询合同

> 官方资料复核日期：2026-08-11

本文件统一定义 Awaken 如何判断和接入供应商的用量、余额、成本与套餐额度查询。它不把“能拿到 token usage”误写成“能查余额”，也不把厂商控制台能力误写成普通 API Key 可调用的公开 API。

## 1. 五类查询路径

| 类别 | 含义 | 常见凭据 | 可回答的问题 |
| --- | --- | --- | --- |
| A. 推理响应 usage | 每次 Chat、Responses 或 Messages 返回的本次请求消耗 | 推理 Key | 本次 input/output/cached/reasoning token；不能回答账户余额 |
| B. 同 Key 账户或套餐查询 | 厂商允许用推理 Key 或套餐 Key 请求余额/窗口额度 endpoint | 推理 Key 或套餐 Key | 可用余额、5 小时/周窗口、重置时间等 |
| C. 组织管理 API | 推理 API 之外的组织级用量与成本报表 | 独立 Admin API Key | 组织聚合用量、成本、时间桶、项目或 Key 维度 |
| D. 云账号控制面 | 云厂商的账单、监控或套餐管理 API | OAuth、服务账号、RAM AccessKey、AK/SK | 项目监控、云账单、套餐/席位用量；通常不是推理 Key |
| E. 仅控制台或合同未公开 | 官方 UI 能看，但没有足够稳定的公开请求合同 | 登录态或未知 | 只能引导用户查看控制台，不得自动探测私有接口 |

同一厂商可同时存在多类路径。Awaken 必须按 `provider_id + access_type + region + credential_scope` 保存查询合同，不能凭 Base URL 或 Key 前缀之外的猜测跨类复用。

## 3. MiniMax 两套凭据与用量查询

MiniMax 的普通开放平台 API 与 Token Plan/Coding Plan 是两套独立计费身份。官方 FAQ 明确说明订阅 Key 与普通按量 API Key 不能混用；达到套餐限额后切换到普通 Key，实际是从套餐额度切到按 token 消耗开放平台账户余额，不是同一个 Key 自动更换计费方式。

| 用户配置入口 | Awaken identity | 用户填写的凭据 | 推理计费与逐次数据 | 同 Key 管理查询 | UI 应表达 | Awaken 当前 |
| --- | --- | --- | --- | --- | --- | --- |
| MiniMax API | `provider_id=minimax`、普通 API access type | 普通按量 API Key | 按实际 token 消耗账户余额；Chat/Responses/Messages 响应中的 usage 只描述本次请求 | 官方 CLI 对 `sk-api-` Key 选择 `{api-region-base}/account/query_balance`，读取 `available_amount` 等账户金额字段 | 本次 input/output/cached token；若余额查询接入，再单独显示账户余额/币种/查询时间 | 逐次 usage 可记录；账户余额查询尚未接入，不得显示 Token Plan 的 5 小时/周额度 |
| MiniMax Token Plan | `provider_id=minimax-token-plan`、Plan access type | Token Plan 订阅 Key | 消耗套餐内 Token Plan 额度，超额可按官方规则使用已购积分 | `GET https://www.minimaxi.com/v1/token_plan/remains`；国际区对应 `www.minimax.io` | 5 小时额度、周额度、重置时间、无限状态；不是货币余额，也不按 token 单价自行折算 | 已接入文字模型 `general` 的套餐窗口 |

必须按以下顺序路由：

1. 读取 profile 已保存的 `provider_id`、`access_type`、`region` 和 `credential_scope`，不从模型名或 Base URL 猜测。
2. `minimax-token-plan` 只请求 Token Plan remains；`minimax` 只记录推理响应 usage，并仅在账户余额 typed schema 已实测、已接入后请求 account balance。
3. 不能因为一个端点返回 401/403/404 就自动用同一 Key 试另一个端点；这类响应优先解释为凭据类别、区域、权限或计划不匹配，而不是“余额/额度为 0”。
4. 旧 profile 缺少 access type 或 credential scope 时，要求用户重新选择“MiniMax API”或“MiniMax Token Plan”入口；不得以 Key 前缀作为唯一迁移依据。官方 CLI 的 `sk-api-` 分支可作为厂商实现证据，但 Awaken 的用户合同仍以显式入口为准。
5. 两套查询结果分别缓存，cache identity 至少包含 provider、access type、region、credential revision 和查询合同版本；不得把套餐窗口快照显示在普通 API profile 上。

这也解释了“用户已经填写 MiniMax API Key，但用量查询显示套餐额度”为什么是错误设计：普通 API Key 当前只能可靠提供逐次 usage；若 Awaken 尚未接入 `/account/query_balance`，应明确显示账户余额查询暂不可用并提供控制台入口，不能用 `/v1/token_plan/remains` 补位。

## 4. Kimi Coding 为什么能查

Kimi Coding 的 `/usages` 不是根据页面逆向猜出的接口：

- [Kimi 官方论坛开发者支持答复](https://forum.moonshot.ai/t/error-code-429-were-receiving-too-many-requests-at-the-moment/191/7) 给出 `GET https://api.kimi.com/coding/v1/usages`、Bearer Key、5 小时窗口与 `remaining/resetTime` 等字段，并注明这是 legacy/experimental 接口；同一官方讨论进一步说明 `100`、`33` 这类数值是 token 限额百分比，不是实际 token 或请求数。
- [Moonshot 官方 `kimi-code` 源码](https://github.com/MoonshotAI/kimi-code/blob/main/packages/oauth/src/managed-usage.ts)仍以 `https://api.kimi.com/coding/v1` 为根请求 `/usages`，解析 weekly、window 与 `boosterWallet`。
- [Kimi Code `/usage` 命令文档](https://moonshotai.github.io/kimi-code/zh/reference/slash-commands.html)证明官方客户端向用户展示套餐使用情况。

因此 Awaken 可以把它作为“官方一方实现可证、稳定性低于正式公开 API reference”的套餐查询能力，而不能把它描述为普通 Moonshot Open Platform 的稳定余额 API。当前 Awaken 只归一化周窗口和 300 分钟窗口，且显示名使用“请求”，没有表达百分比语义；后续必须修正单位/名称，若加入 `boosterWallet`，还要同步 UI 字段、过期时间与测试。

## 5. 各厂商可实施路线

### 5.1 可沿现有余额 fetcher 扩展

- MiniMax API：按官方 CLI 当前 region 选择 `https://api.minimaxi.com` 或 `https://api.minimax.io`，普通 API Key 请求 `/account/query_balance`；先用真实 Key 实测响应，再固化 typed schema。
- MiniMax Token Plan：已接入。套餐 Key 请求 `/v1/token_plan/remains`，文字模型 profile 只展示 `general` 的“5 小时额度”和“周额度”；`video` 等非文本资源桶属于媒体工具，不混入文字模型卡片。公开 FAQ 使用 `https://www.minimaxi.com`/`https://www.minimax.io`；Awaken 只根据 profile 的明确中国区/国际区 identity 选择这两个查询 host，不从推理 Base URL 盲拼。计数型套餐使用供应商返回的 usage/total；`total_count = 0` 的时间型套餐使用供应商返回的 remaining percent，不把 `0 / 0` 当真实额度；当前实测 `status=3` 对应供应商控制台的“无限”，必须保留为无限语义。
- GLM Coding Plan：按中国区/国际区 host 请求官方插件使用的 model usage、tool usage 与 quota limit endpoint；鉴权不是 Bearer，必须单独建合同与测试。

这些候选接口虽然使用用户持有的 API/套餐凭据，也仍需先完成凭据类型识别、错误分类、区域测试和响应 schema 固化，不能仅因 curl 成功就宣称产品支持。

### 5.2 必须新增管理凭据模型

- Google：新增 project ID + OAuth/服务账号凭据，仅查询 Cloud Monitoring 的 usage/quota 指标；预付余额仍引导 AI Studio。
- Qwen/阿里云：新增 AccessKey/Secret 与 RAM 权限；用户先启用高级模型监控并提供私有 Prometheus HTTP API 地址后，可查询 `model_usage`，再按需用 BSS 查询云账号余额/账单。Token Plan 管理 API 只有在官方请求合同完整后再接入。
- Doubao/Volcengine：新增火山 AK/SK 和 Ark 管理 API 签名层，区分按量、Coding Plan、Agent Plan 与席位维度。

这些凭据权限高于普通推理 Key，不得塞进现有 inference credential 字段，也不得发送到 Renderer。默认采用只读最小权限，并在 UI 明确说明“模型推理凭据”和“用量管理凭据”的差异。

## 6. 实现与错误语义

- 查询结果至少带 `source`、`queried_at`、`credential_scope`、`region`、原始币种/单位和窗口重置时间；未知字段保持 null，不用 0 代替。
- 对管理查询设置短 TTL，避免页面刷新制造限流；过期数据必须显示查询时间，不能伪装实时值。
- 401/403：区分错误凭据类别、区域不匹配、权限不足和套餐不可用；不得显示“余额为 0”。
- 404：先检查 endpoint 版本、host 与计划类型，不自动遍历私有路径。
- 429：保留重试时间与限流来源，不把“查询受限”写成“额度耗尽”。
- 5xx/网络错误：可保留最后一次成功快照并标为陈旧；不得用旧数据覆盖新账户。
- 任何管理查询都不计作模型请求，不写入生成 token 成本；其审计记录与推理 usage 分开。
