# 模型配置与调用

## 1. 权威范围

本文是 Awaken 当前模型目录、profile、会话模型选择、推理强度、能力验证和 run 注入链的唯一权威。模型与 Agent Plan API key 的文件格式、权限和恢复由[安全凭据存储与恢复契约](安全凭据存储与恢复/架构与恢复契约.md)拥有；Composer 通用输入由[输入、斜杠菜单与附件](../01_桌面工作台/中间交互区域/输入、斜杠菜单与附件.md)拥有；prompt cache 与用量由[提示词缓存与成本治理](../02_主智能体闭环/提示词缓存与成本治理.md)拥有。

## 2. 用户入口

“设置 > 模型”使用两层导航。模型页左侧固定分成三个互相独立的接入类型：

| 接入类型 | 当前 provider |
| --- | --- |
| Coding Plan | Kimi Coding Plan、火山 Coding Plan、Qwen Token Plan |
| API | Kimi、MiniMax、GLM、Qwen、Doubao Ark、DeepSeek |
| Agent Plan | 火山 Agent Plan |

右侧每个接入类型固定包含两个二级页面：

- 连接配置：Coding Plan 显示“配置 Token”，API 显示“配置 API Key”，Agent Plan 显示“配置账户”；当前类型的 provider 以固定三列、统一高度的紧凑卡片展示官方产品 Logo、名称和“配置”动作。点击卡片在屏幕中央打开配置弹窗，连接状态紧邻供应商名称右侧，模型和密钥位于首层，Base URL、输入能力和付费能力验证收进“高级设置”，不在主页面纵向展开大表单。弹窗采用紧凑品牌头、稳定间距的表单区和单行底部操作栏，按内容自然增高并限制最大高度，超出时只滚动弹窗内容。
- LLM 设置：只展示当前类型已经配置的模型卡片，并显示对应产品 Logo；标题固定按“厂商名：模型 ID”单行展示，管理默认模型、启停、上下文、输出上限和删除。接入类型与 Function Calling 能力不作为卡片标签重复展示；上下文、自动压缩阈值与输出上限收在低高度的卡片参数区，自动压缩阈值的标题与数值在所属参数列水平居中。页面使用窄类型导航、紧凑页头和受控内容宽度，不随宽窗口无限拉伸，也不再把三类 profile 混成公共表格。

供应商 Logo 作为本地静态资源随 Design System 打包，Renderer 不在运行时请求远程图片；同一套 Logo 同时用于连接卡片、LLM 设置卡片、Composer 当前模型按钮、模型选择器和推理强度二级面板标题。连接配置区固定为三列、统一卡片高度，入口只展示 Logo、供应商名称和“配置”动作；API 类型已经由左侧接入分类明确，厂商名称和配置弹窗标题不再重复附加 `API` 后缀。连接状态只在居中配置弹窗标题区、紧邻名称右侧展示，不在入口卡片重复展示模型数量。连接卡片和 LLM 卡片统一使用纯色表面与细边框，不使用渐变炫光、悬浮阴影或上浮位移。Logo 使用带细边框的浅色内衬容器，品牌图保持克制比例；Kimi 官方 App Icon 因原图自带安全留白而使用更高的容器占比，不裁切官方资源。位图至少使用 640 × 640 原图，其余使用可缩放 SVG。Kimi 与 Kimi Coding Plan 共用从官方 Kimi App 提取的 1024 × 1024 App Icon；Qwen 与 Qwen Token Plan 共用 Qwen Logo；Doubao Ark 使用 Doubao Logo，火山 Coding Plan 与火山 Agent Plan 使用火山引擎 Logo。资源与来源清单由 `Awaken Design System/src/assets/model-providers/README.md` 维护。

推理强度不在设置页配置。Composer 是唯一面向用户的 effort 入口，按 thread 保存当前模型的 `low | high | max` 选择；模型设置页不显示 profile 默认 effort。

`ModelAccessType` 的当前产品值为 `coding_plan | api | agent_plan`。存量 provider ID 和 profile ID 保持不变；旧 `coding_preset` 仅作为读取兼容信号，不再是 UI 分类。

### 2.1 保存、连接与 effort 验证

1. Renderer 从 Main 取得非敏感 provider catalog 和 profile 摘要。
2. `测试连接` 发送最小聊天请求，只证明 endpoint/key/model 可以响应，不验证工具调用或 effort 档位；测试中按钮显示进行态，完成后在当前供应商弹窗内明确保留成功或失败结果，直到用户修改连接参数、重新测试或关闭弹窗。当前模型目录与自定义模型统一默认支持工具调用，不提供独立 Function Calling probe、IPC 或配置按钮。
3. Agent Plan 精确模型可执行 `验证 effort（少量消耗）`；只有模型 ID 命中已知矩阵，且在 8 秒总超时内对每个展示档位分别验证、套餐 endpoint 全部接受对应原生值，才持久化完整矩阵。任一档失败、超时或未知模型都不展示 effort；单次 HTTP 200 不能推导全部档位可用，而端点是否语义上采用该值仍需供应商证据。`ark-code-latest` 不展示 effort。
4. 提交先保存凭据，再原子保存非敏感 metadata；成功前 UI 不显示已完成。

effort 验证可能产生少量供应商消耗，不能与普通连接测试合并或静默触发。

## 4. Profile、能力与持久化

`~/.awaken/config/models.json` 当前写入 version 2，version 1 继续兼容读取。每个 profile 的非敏感事实包括：

```text
id / providerId / displayName / modelId
baseURL / protocol / authScheme
enabled / isDefault
advanced.contextWindow / maxTokens / temperature
advanced.endpointId
advanced.supportsVision / supportsNativePDF / supportsVideo
advanced.supportsTools / defaultReasoningEffort
credentialRevision / credentialReference / keyLast4
```

凭据引用分为 `profile_secret(profileId)` 与 `provider_account(providerId, accountId)`。存量 profile 缺少该字段时解释为 `profile_secret`；Agent Plan profile 固定引用 `volcengine-agent-plan-default`，不复制账户 key。

同一 `providerId + normalized modelId` 只允许一个 profile。disabled profile 不能是 default；删除 default 后选择剩余可用项。默认模型只是新会话的初值，不是既有 thread 的强制覆盖。

`defaultReasoningEffort` 继续作为 capability 派生值和存量 schema 兼容字段存在，但 Desktop 设置页不提供编辑入口。用户可见选择只发生在 Composer；没有 thread 覆盖时由内部 profile/capability 默认值兜底。

### 4.1 能力来源与合并

能力顺序为：

```text
静态 MODEL_CAPABILITIES
  -> ~/.awaken/cache/model-capabilities.json
  -> 本次 /models 可解析 metadata
  -> Agent Plan effort 受控验证
```

动态缓存为 v2 scoped cache，严格 identity 至少包含 `provider + normalized Base URL + protocol + profile + credential revision + selector kind + endpoint contract`；相同 provider/model 但不同凭据、代理、自定义 Base URL 或接入点不得复用。v1 的 provider-global 缓存只能当冷缓存忽略，不迁移为新作用域事实。`/models` 只返回 context 时，不能覆盖同作用域内经过验证的 effort。新鲜 observation 在自己的 exact scope 内合并，不投影到其他 profile。

provider catalog 只暴露静态事实，不聚合各 profile 的 scoped cache；Renderer 需要展示或选择能力时优先使用 profile 摘要上的 exact-scope `effectiveCapability`，缺失时才回退静态 catalog。

`default_max_tokens` 是新 profile 和缺省配置的输出预算，`max_output_tokens` 是不可突破的模型上限；Desktop、Desktop 启动的 Core、ACP 和定时任务必须遵守同一优先级与 clamp 规则。

`supportsTools` 字段继续作为存量 schema 和 Core 协议兼容位存在，但当前 Desktop catalog、动态模型和已保存 profile 均归一为 `ready`；旧缓存或旧 profile 中的 `unknown/unsupported` 不再阻止工具 schema。产品不展示该字段，也不通过连接测试改写它。

## 5. Agent Plan 单账户

首期只有固定账户 `volcengine-agent-plan-default`。非敏感 metadata 原子写入 `~/.awaken/config/agent-plan-account.json`，文件为 versioned JSON 和 `0600`。Key 使用 `.env` 中独立的 `AWAKEN_AGENT_PLAN_API_KEY_<accountId>` 命名空间；Renderer 只获得 `hasKey`、掩码、`credentialRevision`、模型 ID 和目录更新时间。

Key 实际变化时 revision 单调递增；metadata 写入失败会恢复旧 key。账户仍被任一 profile 引用时拒绝删除。

保存账户或点击刷新会访问固定 endpoint 的 `/models`：

- 成功时缓存精确模型 ID；
- 失败时保留现有缓存，并至少保留 `ark-code-latest` 与自定义 ID 输入；
- 不把营销名称硬编码成可调用 ID；
- `ark-code-latest` 的实际路由模型不固定，永远不展示 effort。

本阶段只实现 Agent Plan 主模型账户/profile 和 `supportsTools` 基础。图片、视频、搜索、Embedding 等独立工具服务仍是待实现设计，不属于当前支持。

## 6. Reasoning effort

Awaken 的统一用户语义为 `low | high | max`。UI 只显示模型真实支持的档位，并始终使用小写英文。thinking 开关、reasoning effort 和 prompt-cache capability 是三份独立合同，不得因其中一份已知而推导另一份；MiniMax 的 thinking 开关不属于 reasoning effort。Kimi K3 的三档顶层 `reasoning_effort` 以[官方推理强度文档](https://platform.kimi.com/docs/guide/use-reasoning-effort)为准，K2.x/K3 的 thinking 差异以[官方思考模型文档](https://platform.kimi.com/docs/guide/use-thinking-models)为准。

| 接入模型 | UI 档位 | Provider 实际值 | 默认 |
| --- | --- | --- | --- |
| Kimi `kimi-k3` | `low/high/max` | `low/high/max` | `max` |
| Kimi Coding `k3`、`k3-256k` | `low/high/max` | `low/high/max` | `high` |
| MiniMax M3 | 不展示 | 无档位参数 | — |
| GLM `glm-5.2` | `high/max` | `high/max` | `high` |
| Qwen Token `qwen3.8-max-preview` | `low/high/max` | `low/medium/xhigh` | `max` |
| Doubao `doubao-seed-2.1-pro` | `low/high/max` | `low/medium/high` | `high` |
| DeepSeek `deepseek-v4-pro` | `high/max` | `high/max` | `high` |
| Qwen `qwen3.7-max` | 不展示 | 未确认独立档位 | — |

Agent Plan 精确模型只有在受控验证后才获得对应映射。Provider adapter 是原生值映射的唯一 owner；Renderer 和 Agent Core 只处理 Awaken 档位。

保存或迁移 profile 时，不在 capability levels 内的内部默认值会被拒绝。启动 run 的回退顺序固定为 `thread 会话覆盖 -> profile 内部默认 -> capability 默认`。非法、过期或能力变化后的值按该顺序恢复，并在 Renderer 显示一次非阻断提示；这些默认值不会形成第二个用户设置入口。

## 7. Composer 与 thread 选择

Composer 模型与 effort 都是会话级：

```text
RuntimeThread.selectedModelProfileId
RuntimeThread.reasoningEffortByProfile[profileId]
```

当前行为：

- 既有 thread 的 effort 吸附到档位后立即通过 typed IPC/API 持久化；
- 尚未创建 thread 时先保存在 Renderer 草稿，首次 run 与 thread 创建一并写入；
- 支持 effort 的模型从模型列表进入二级面板；卡点轨道与即时保存交互由[输入、斜杠菜单与附件 §3.1](../01_桌面工作台/中间交互区域/输入、斜杠菜单与附件.md)统一定义；
- 不支持档位的模型直接选择，不显示入口或占位；
- 标签显示 `模型名 · max` 等当前有效选择；
- run 期间禁用模型/effort 修改，变化只影响下一次 run；
- thread 已有消息时提示切换会重新建立上下文缓存；
- profile 被禁用、删除或能力变化时忽略失效 preference，回退当前可用 default，不批量改写历史 thread。

模型选择不再调用 `setDefaultModelProfile`。设置页的 default 只决定新会话初值，因此两个 thread 可以稳定使用不同模型和 effort。

thread preference 在写入 metadata 前由 Desktop Main 与 Core 双重校验：profile 必须存在、enabled 且凭据可用，effort 必须位于该 profile exact-scope capability levels 中。已删除、disabled 或不支持档位的请求直接拒绝且不改写 thread；打开旧 thread 时优先按其已保存 profile/effort 重建 snapshot，只在该 profile 不再可运行时回退 default。

## 8. Run 注入和缓存边界

Renderer 启动请求只传 `modelProfileId + reasoningEffort`，不传 Key、Base URL 或完整 profile。Electron Main 重新验证所选 profile enabled/ready，解析 profile/账户凭据、能力和有效 effort，再构造只发往本机 Core 的 `model_profile`。Renderer hints 在 Main 中清除，不进入 Core 的严格 create-run decoder。

Core 将有效选择写入：

- `AgentConfig.ModelConfig`；
- model profile/Agent cache key；
- prompt-cache affinity 与 reasoning policy；
- thread metadata；
- run snapshot 的 `model_profile_id` 与 `reasoning_effort`。

Doubao Ark 等 endpoint-model provider 同时保留两个不可混用的身份：`model_id` 是 provider 请求实际发送的 transport selector（`ep-*`），`capability_model_id` 是用于能力、effort 原生值映射和当前模型展示的 family（如 `doubao-seed-2.1-pro`）。Context Epoch、usage、Agent/profile cache identity 同时包含两者；任意 `ep-*` 不能自动继承某个 family 的 effort 能力，只有当前 profile 的显式 family-endpoint 绑定可用。火山官方文档也将 [Model ID 与 Endpoint ID](https://www.volcengine.com/docs/82379/1298459) 分别作为模型目录身份和推理接入身份。

主 Agent turn 才发送 effort。标题、Memory recall、compact、Dream 等辅助请求不继承 Composer effort，并使用独立 purpose/cache identity。

## 9. 连接、余额与错误

连接测试请求正文、key 和 Authorization 不进入 Renderer、SemanticJournal 或 thread metadata。profile-scoped usage ledger 只保存 request identity、脱敏 shape、nullable usage 和结果。未实现余额的 provider 必须明确返回 unsupported，不能由连接测试推断余额。

| 场景 | 行为 |
| --- | --- |
| 无 enabled profile | run 创建前失败，提示到设置配置 |
| profile/account 无 key | run 创建前失败，不进入 provider transport |
| `.env` 或 metadata 不可读 | fail closed，不覆盖原文件 |
| thread profile 已删除/禁用 | 回退可用 default，并提示一次 |
| thread effort 已失效 | 按 profile/capability 默认恢复，并提示一次 |
| capability sync 失败 | 保留静态和已有缓存 |
| Agent Plan `/models` 失败 | 保留缓存、`ark-code-latest` 与自定义输入 |
| provider 401/403/429/5xx | 作为 provider 错误，不改写成本地凭据文件故障 |
