# 项目生命周期与删除：产品与状态机

## 权威范围

本文唯一拥有“从Awaken移除、删除Awaken历史、移到系统废纸篓”的用户语义和状态机。API/FileStore/outbox/worker见 [API与持久化](API与持久化.md)，验证见 [验收清单](验收清单.md)。

## 三个用户动作

| 动作 | 项目 | Awaken 历史 | 磁盘目录 |
|---|---|---|---|
| 从 Awaken 移除 | `removed`，reason=`detached` | 保留 | 保留 |
| 删除 Awaken 历史 | 保持 `active` | 逻辑删除并后台清理 | 保留 |
| 移到废纸篓 | `trash_pending -> removed/trashed` | 系统废纸篓成功后删除 | 进入系统废纸篓 |

“删除会话”是第四个较小动作：只逻辑删除指定 thread，并后台清理其 FileStore session（metadata、SemanticJournal、runtime-owned attachments），不改变项目和 workspace 目录。

项目状态以 `~/.awaken` 活动 generation 的 lifecycle journal 为唯一真相；`state.json` 只是可重建快照。Thread 的 `workspaceRoot` 只描述历史关联，不能激活 removed 项目。Renderer 不保存或导入第二份 removed 列表。

## 项目状态

- `active`：可创建和运行会话。
- `removed`：从侧栏隐藏；显式重新添加同一路径才允许恢复为active。
- `trash_pending`：禁止新 run，等待 active run 取消、系统废纸篓和 finalize。

只有active project允许新run；未知workspace可在显式upsert时创建。`trash_pending`必须fail closed，不能继续建run或并发开始第二个项目operation。

## Operation状态

Action：`detach|delete_history|trash_and_purge|delete_thread`。

Status：`accepted|running|succeeded|failed|blocked`。

Trash phase：

```text
waiting_for_runs
  -> trash_claimed
  -> trash_staged
  -> trashing
  -> cleaning
  -> completed

failure -> status=failed, phase=failed，并恢复 previous project state
cancel  -> status=failed, phase=cancelled，并恢复 previous project state
```

`status` 与 `phase` 是两个维度：成功收口为 `status=succeeded, phase=completed`；取消不是 status 枚举，而是上述 `failed/cancelled` 组合。所有修改动作必须携带 idempotency key。业务成功以 lifecycle mutation journal-first 提交为准；session 与附件通过 durable cleanup job 重试，不能因为物理清理暂时失败而让 UI 复活。

Renderer收到pending trash operation后持久化tracker并收起项目，不能用固定超时推断结果。只有operation已逻辑提交且project离开 `trash_pending` 才能永久移除；明确失败且project恢复active时立即重新展示并恢复原展开状态。operation查询或项目刷新瞬时失败继续追踪，不能丢tracker或删历史。

## Trash 两阶段与路径身份

Prepare只保存path fingerprint、thread cutoff和operation，不删除历史。active/question/gate run先取消并等到不忙。

每次claim生成新的attempt token，后续attest/stage/begin/complete/fail必须持有当前token，旧worker不能完成新attempt。

Core把原目录原子改名到同卷operation专属staging，并在改名前后复验volume/file identity。目录内普通新增/修改不应误判；同路径被替换成另一个目录必须拒绝。staging保留原文件夹名。

Electron Main只把staging路径交给系统废纸篓，绝不再按原路径删除。`begin-trash` 必须在系统调用前durable记录invocation boundary。只有staging确认消失后，Core才在同一 lifecycle mutation 中 tombstone project、soft-delete cutoff threads 并创建 cleanup jobs。

系统调用明确失败时Core原子恢复原目录和previous project state；若原路径已被另一个目录占用则fail closed，不覆盖、不删除新目录。

## 当前不支持

- 绕过系统Trash/Recycle Bin直接永久删除项目目录；
- 远程/非本机workspace；
- 一次operation跨多个project；
- 在trash_pending继续新run；
- UI固定超时猜成功；
- 用历史thread反向复活removed project。

## 异常恢复

- crash发生在prepare/claim/stage/trashing/finalize/cleanup任一点，重启从durable operation/job继续；
- idempotent重试返回同operation，不重复删；
- active run未停止返回busy并重试，不向用户暴露原始THREAD_BUSY；
- physical cleanup失败不回滚已经提交的逻辑删除，由outbox重试；
- path identity改变或attempt过期必须结构化失败并保全新目录/历史。
