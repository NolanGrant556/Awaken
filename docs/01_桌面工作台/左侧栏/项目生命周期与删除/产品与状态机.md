# 项目生命周期与删除：产品与状态机

## 权威范围

本文唯一拥有项目名称、“一个项目 = 一组文件夹 + 一个主文件夹”的组成语义，以及“从Awaken移除、删除Awaken历史、移到系统废纸篓”的用户语义和状态机。API/FileStore/outbox/worker见 [API与持久化](API与持久化.md)，验证见 [验收清单](验收清单.md)。

## 项目的组成

一个项目持有一个有序文件夹列表，其中恰好一个是主文件夹（primary）。列表顺序由用户决定，Core 只保证「至少一个根、恰好一个 primary」这条不变量。

| 角色 | 承担 |
|---|---|
| 主文件夹 | 新会话 cwd 与 Bash 初始 cwd、相对路径解析基准、项目级 Skill 发现根、项目 Memory 根、broker 工具（`dependency_install` / `git_remote` / MCP artifact bridge） |
| 次文件夹 | 读、写、文件搜索、artifact 输出 |

次文件夹不参与任何项目级发现。所有文件夹都是用户挑选的磁盘目录，role 恒为 `user`，都可切换 primary、可从项目移除、可单独移到废纸篓。Awaken 不再创建 `managed` 角色的文件夹；该枚举值只保留用于解码更早写下的状态。

**项目可以没有任何文件夹。** 项目是一件有名字的活儿，绑文件夹是用户手上有目录时才做的选择。侧栏「+」只要求填项目名称，文件夹可以当场加、也可以永远不加。零文件夹项目照常发起会话：Core 把它解析到该项目自己的 session 工作目录 `<AWAKEN_HOME>/sessions/<project_id>`，产出落在其下的 `output/`，具体契约见 [TaskScope 与路径安全](../../../04_工具权限与审批/TaskScope与路径安全.md)。

加入第一个文件夹后它成为主文件夹。移除或废纸篓掉最后一个文件夹后，项目保留名称、线程和历史，回到零文件夹状态，不会被塞进一个占位目录，也不会因此被删除。

`project_id` 与路径解耦：新项目使用随机 id，已有 path-derived id 原样保留。

项目名称可以在「编辑项目」中重命名。提交时去掉首尾空白，结果为空则拒绝；名称相同是 no-op。重命名只改变稳定 `project_id` 对应项目的 `display_name`，不改变文件夹、primary、状态、侧栏顺序、线程归属或历史。项目处于 `trash_pending` 时拒绝重命名，避免并发改写正在恢复的项目事实。

当前项目名称同时进入新 run 和后续 run 的 `workspace.project_name`，成为模型可见的运行上下文；它只用于让 Agent 说得出自己正在处理哪个项目，不参与路径、权限或项目身份解析。重命名后的下一次 run 使用最新名称并重建对应上下文，既有 transcript 不被批量改写。

**一个磁盘目录可以同时属于多个项目。** 目录参与哪些活儿是用户的判断，Awaken 不替他仲裁，所以创建项目和添加文件夹都不会因为某个目录已经在别的项目里而被拒绝。共享带来的连带效应只有三条，其余动作彼此独立：

| 动作 | 对其他持有者的影响 |
|---|---|
| 从项目移除某个文件夹 | 无。只改这一个项目，磁盘和其他项目都不动 |
| 从 Awaken 移除项目 / 删除 Awaken 历史 | 无。都不碰磁盘，仍有活跃持有者的文件夹在那些项目里照常可用 |
| 把文件夹移到废纸篓 | 磁盘目录真的消失，因此它从**每个**持有它的项目里一并解绑；移动过程中所有持有者都不能在这个文件夹里开新会话，锚在它上面的运行任务先被停掉 |

废纸篓确认弹窗会点名还有哪些项目会因此失去这个文件夹，用户不会在不知情的情况下替另一个项目做决定。

因为目录不再唯一对应项目，路径也就不再能推断项目身份：会话归属由 run 携带的 `project_id` 决定，Desktop 优先采信用户当前选中的项目，只有它并不持有这个根时（例如继续一条旧线程）才回退到按路径查找。

## 三个用户动作

前两个作用于整个项目，第三个作用于单个文件夹：

| 动作 | 作用对象 | 项目 | Awaken 历史 | 磁盘目录 |
|---|---|---|---|---|
| 从 Awaken 移除 | 项目 | `removed`，reason=`detached` | 保留 | 保留 |
| 删除 Awaken 历史 | 项目 | 保持 `active` | 逻辑删除并后台清理 | 保留 |
| 移到废纸篓 | 一个用户文件夹 | `trash_pending -> active`，该文件夹解绑 | 保留 | 该文件夹进入系统废纸篓 |

项目层菜单只提供「添加文件夹」「编辑项目」「从 Awaken 移除」「删除 Awaken 历史」。「编辑项目」可修改名称和已有文件夹组成；文件夹粒度的操作都在创建项目与编辑项目弹窗的文件夹行上，一次只处理一个目录：

- 行只显示文件夹名末段，完整路径挂在原生 `title` 上；
- 主文件夹行显示「主文件夹」徽标，其他行在悬停或键盘聚焦时露出「设为主文件夹」；
- 每行常显 `×`，语义是把文件夹移出这一组，不动磁盘；
- 「移到废纸篓」真的动磁盘，只作为编辑项目弹窗的行内 `⋯` 菜单项出现。创建项目弹窗的文件夹还没挂到项目上，没有这一档，因此那里没有 `⋯`。

「添加文件夹」和创建项目弹窗里的文件夹选择器都支持一次选中多个目录。选中的目录逐个校验，不能加入的（已经在这个项目里、无法访问）各自说明原因并跳过，其余照常加入，不因为其中一个不合格而整批失败。目录已经属于别的项目不是跳过的理由。加入若干目录后只刷新一次项目列表，并给出一条汇总提示。

「从项目移除」只解绑，不碰磁盘，也不产生 operation，仍持有该目录的其他项目不受影响。「移到废纸篓」成功后项目仍然 `active`，只是少了这个文件夹，项目的 Awaken 历史不被删除；被移走的文件夹如果是 primary，剩余文件夹会接任 primary，一个都不剩时项目回到零文件夹状态。其他持有者同样失去这个文件夹，但各自的项目、主文件夹和历史都保留。

“删除会话”是第四个较小动作：只逻辑删除指定 thread，并后台清理其 FileStore session（metadata、SemanticJournal、runtime-owned attachments），不改变项目和文件夹。

项目状态以 `~/.awaken` 活动 generation 的 lifecycle journal 为唯一真相；`state.json` 只是可重建快照。旧快照或旧 journal 没有 `folders` 字段时，读取时合成单个 primary user 文件夹，不需要迁移脚本。Thread 的 `workspaceRoot` 只描述历史关联，不能激活 removed 项目；线程归属项目用 thread 的稳定 `projectId`，不用路径相等匹配。Renderer 不保存或导入第二份 removed 列表。

## 项目状态

- `active`：可创建和运行会话。
- `removed`：从侧栏隐藏；显式重新添加同一路径才允许恢复为active。
- `trash_pending`：禁止新 run，等待 active run 取消、系统废纸篓和 finalize。

只有active project允许新run；未知workspace可在显式upsert时创建。`trash_pending`必须fail closed，不能继续建run或并发开始第二个项目operation。

一个文件夹被多个项目持有时，「这个文件夹还能不能开会话」按整组持有者判定，因为磁盘目录只有一个：任一持有者处于 `trash_pending` 就一起挡住，否则只要有一个 `active` 持有者，这个文件夹就可用。没有任何项目持有的路径不受这道闸门管辖。

## Operation状态

Action：`detach|delete_history|trash_and_purge|delete_thread`。

Status：`accepted|running|succeeded|failed|blocked`。

Trash phase：

```text
waiting_for_runs
  -> trash_claimed
  -> trash_staged
  -> trashing
  -> cleaning
  -> completed

failure -> status=failed, phase=failed，并恢复 previous project state
cancel  -> status=failed, phase=cancelled，并恢复 previous project state
```

`status` 与 `phase` 是两个维度：成功收口为 `status=succeeded, phase=completed`；取消不是 status 枚举，而是上述 `failed/cancelled` 组合。只有创建 operation 的修改动作必须携带 idempotency key；重命名、文件夹挂载/解绑/切主和排序是原子 set，不创建 operation。业务成功以 lifecycle mutation journal-first 提交为准；session 与附件通过 durable cleanup job 重试，不能因为物理清理暂时失败而让 UI 复活。

Renderer收到pending trash operation后持久化tracker并收起项目，不能用固定超时推断结果。只有operation已逻辑提交且project离开 `trash_pending` 才能永久移除；明确失败且project恢复active时立即重新展示并恢复原展开状态。operation查询或项目刷新瞬时失败继续追踪，不能丢tracker或删历史。

## Trash 两阶段与路径身份

作用对象是本次操作指定的那个用户文件夹，两阶段 staging、path fingerprint 复验和系统废纸篓链路与文件夹粒度前完全一致。

Prepare只保存path fingerprint、thread cutoff和operation，不删除历史。active/question/gate run先取消并等到不忙。

每次claim生成新的attempt token，后续attest/stage/begin/complete/fail必须持有当前token，旧worker不能完成新attempt。

Core把原目录原子改名到同卷operation专属staging，并在改名前后复验volume/file identity。目录内普通新增/修改不应误判；同路径被替换成另一个目录必须拒绝。staging保留原文件夹名。

Electron Main只把staging路径交给系统废纸篓，绝不再按原路径删除。`begin-trash` 必须在系统调用前durable记录invocation boundary。只有staging确认消失后，Core才在同一 lifecycle mutation 中把该文件夹从项目解绑并把项目恢复为 previous state。这是项目的最后一个文件夹时，项目回到零文件夹状态。同一条 mutation 里，该文件夹也从其他持有它的项目中解绑：目录已经不存在，别处留着这一行就是一条指向空处的路径。

系统调用明确失败时Core原子恢复原目录和previous project state；若原路径已被另一个目录占用则fail closed，不覆盖、不删除新目录。

## 当前不支持

- 绕过系统Trash/Recycle Bin直接永久删除项目目录；
- 远程/非本机workspace；
- 一次 operation 处理多个文件夹，或由多个项目共同发起：operation 始终归属发起它的那一个项目，废纸篓把目标文件夹从其他持有者移出是这次 operation 的连带结果，不是第二个 operation；
- per-folder 只读权限（所有文件夹的读写能力一致）；
- 在trash_pending继续新run；
- UI固定超时猜成功；
- 用历史thread反向复活removed project。

## 已知缺口

- broker 工具（`dependency_install` / `git_remote` / MCP artifact）仍然只在主文件夹内可用：`WorkspaceExecutionBroker` 是整树复制 staging，并会丢弃 workspace 外的 writable root。次文件夹里的依赖安装和 git 操作没有接通。
- MCP project 配置（`{root}/awaken.mcp.json`）在 Desktop 实际失效，因为 Core 启动时 `AWAKEN_DEFAULT_WORKSPACE=""`；多文件夹没有改变这一点。
- Awaken 只发现当前项目主文件夹的 `.awaken/AGENTS.md` 作为项目运行指令；次文件夹同名文件仍是普通 Markdown。切换主文件夹后从下一次 run 使用新来源，完整契约见 [AGENTS 指令交互](../../AGENTS指令交互.md)。
- 不提供 Codex 的 Git review / PR / worktree。

## 异常恢复

- crash发生在prepare/claim/stage/trashing/finalize/cleanup任一点，重启从durable operation/job继续；
- idempotent重试返回同operation，不重复删；
- 重命名在 journal 提交后即为业务事实；snapshot 缺失或损坏时从 mutation 重放出最新名称，同名重试不推进 version/updated_at；
- active run未停止返回busy并重试，不向用户暴露原始THREAD_BUSY；
- physical cleanup失败不回滚已经提交的逻辑删除，由outbox重试；
- path identity改变或attempt过期必须结构化失败并保全新目录/历史；
- 文件夹级 trash 失败时该文件夹原样挂回项目，项目恢复 active，历史与磁盘都不变；
- session 工作目录缺失时在 run 解析 scope 时重建，不把 run 留在没有 cwd 的状态。
