# 验收

## 1. 自动化

- run 固定 environment/tool availability snapshot，RequestBuilder 与 ToolRuntime 同源；
- registry/PATH 变化不替换当前 run 已固定的 tool schema、runtime/provider identity 和 environment snapshot；MCP adapter 的 live connection/auth state 仍立即改变当前调用结果，model-facing `skill` 调用也按当时 registry 重查定义/正文；
- composer token 校验、inline context、真实 fork child 和 model-facing `skill`；StartRun 到最终 provider request 的合同必须确认当前选择的 Skill ID/source/mode/absolute root/SKILL.md 作为 host-owned block 进入上下文，single/multi/token-only/fork/历史/model-invoked 语义不混同；
- 含 Skill token 的完整 `user_message` 先于预激活耐久化，激活失败保留输入且不写部分/伪 activation，成功执行不重复写入；
- Skill 不改变父 tool snapshot；
- host-owned Memory policy/index/recall block 在请求中保持数据与指令边界，selector 最多 5 条且失败不阻塞主 run，compact 后预算按 11 域复位；原生 child 只继承父已召回的冻结 snapshot，不跑 user-scope selector；
- context estimate/compact、Skill 单包 5k/总计 25k budget、最新 5-of-6 保留、恢复时间顺序和截断块精确 `Read` 源路径提示（`TestCompactInvokedSkillContextEnforcesBudgetsAndKeepsNewest`），以及 tool media storage key、restart 恢复/fork 隔离；
- 低窗口下一批多个媒体 `Read` 只执行剩余预算装得下的前缀，其余合成 `context_admission_exhausted` 且 pairing 仍合法（`TestExecuteToolCallsAdmitsOnlyFittingMediaReads`）；文本 `Read` 不被该入场门拦截；
- 请求投影按当前窗口重算：11 张旧图 + 1 张近尾时本地账仍计媒体，provider clone 只 hydrate 近尾；摘要请求无 image/file payload；14×10 图的超限 tail 被吸收后不再带齐 `DataBase64`；journal replay 只恢复 `storage_key`，重启投影与 live 一致；
- compact 后置条件：摘要成功但重建投影仍高于 auto/block 或未缩 20% 时失败且不切 epoch；三次同类失败才 circuit + `CONTEXT_BLOCKED`；`errors.Is(blocked)` 时 `isPromptTooLongError` 为 false；
- 默认 system prompt 必须把同一任务内已恢复的前序 user/assistant/tool 消息声明为连续历史；“上一个对话”等指代默认落到当前任务最近相关轮次，同时保持供应商 messages 为标准有序 role/content，不下发内部 thread/run/session、时间戳或 message/turn identity；
- root 模型工具池必须暴露 `archived_history` 的 list/read、`thread_id` 寻址、host-managed location 和 untrusted 历史边界；child role 必须隐藏该工具且不继承 service。归档 read 只命中 archived authority，分页/单项上限生效，tool arguments 不返回，当前 journal 只保存无正文读取回执；
- `ContextUsageSnapshot` 七项分类和等于总估算、Memory/Skill 不重复、old record 不补造；provider total/input/output 不覆盖 Core local snapshot；identity 一致的完整主调用 inclusive input 直接驱动 Desktop 当前总输入并与面板输入 Token 相等，provider total/input 与 `sent_estimated_input_tokens` 另驱动 Core 保守阈值并在新 run/旧 thread 的兼容恢复中成对续用；同 epoch 内锚点不得因 pre-epoch admission 与 post-epoch sent estimate 的阶段差异向下回退，必须覆盖 146023/162363/254928/143 这类真实回归并主动压缩；正残差单列“其他/协议开销”，分类显示 reconciliation 后仍与汇总严格相等；缓存与 token/cost 明细紧接分类且没有“上次请求”分界；面板不显示 compact diagnostics 或 failure/invalidation reason，compact 期间保持最后完整快照并仅在成功后的完整 snapshot 原子刷新；失败 compact 后立即检查、完整重启后再检查都必须保持压前值，Journal 中 compact auxiliary usage 后的高位 snapshot 不得在回放中穿透冻结；0 值分类不绘制进度 segment 时，后续 segment 与图例仍按分类语义同色；
- prepare-once exact body、`model_request` fsync-before-send、同 request ID terminal usage、orphan `usage_unknown`、purpose/retry/auxiliary fallback 与 live/replay 聚合；
- DeepSeek/Kimi/火山/custom capability、affinity/credential revision、nullable cached usage、Context Epoch/compact 边界、Kimi provider-opaque state 和大 tool result 首次 admission offload；
- ordinary auto、ask_user、needs_auth/runtime/unsupported，以及消息工具不产生审核 gate；
- cancellation、orphan recovery、partial/unknown retry block 和唯一 terminal；Bash `command+cwd` resource revision 不合并不同恢复命令，已观测 mutation 或成功的 Bash 恢复命令后可重跑验证命令，side effects=none 的无关只读成功不清理失败历史；
- live/replay 相同 semantic projection。
- 主模型响应前连接失败保持 turn 并无限等待网络（`TestRunnerKeepsTurnAliveAcrossConnectionLoss`）；工具流开始前的 stream disconnect 最多 5 次重试并丢弃未耐久文本/思考（`TestRunnerRetriesStreamDisconnectBeforeToolStart`、`TestRunnerGivesUpAfterBoundedStreamDisconnects`）；工具参数流或 tool call 已开始后不重试（`TestRunnerDoesNotRetryAfterToolStreamStarts`）；reconnect detail 不含 URL/host（`TestSafeRetryDetailNeverLeaksURL`）。`ProviderReconnect` 只 live 发出，不写入 SemanticJournal。
- 原生 Subagent 的 tool/model facts 先耐久，`subagent_progress` 再按 tool-call/model-request ID 去重累计；terminal、live/replay 与 Desktop 的工具数、provider-reported token、耗时一致；`wait` 到期返回中性 `retrieval_status=timeout` 与当前 snapshots，不产生失败 Outcome或取消 child；随后耐久的 terminal 在 root 下一模型边界自动交接，且与成功 wait/terminal status 共用一次性消费标记。

## 2. Desktop 验收

按 README 正式入口在真实 Desktop 验证：普通工具回合、多个同类 Skill 下的 composer 当前选择指代、inline/fork Skill、成功/失败压缩、上下文中文面板、主动提问、消息工具直接执行、provider failure、Shell 恢复、取消、切换线程和重开恢复。上下文能力执行 [AC-CU-01～07](提示词缓存与成本治理.md)，并检查 journal/最终 prepared request/wire 与屏幕顺序；旧截图、Gallery、浏览器 renderer 或直接 provider API 不替代本次证据。

当前 macOS 三协议与 MiniMax 低窗口媒体压缩基线已经在真实 Desktop 取得：

- K3（`openai_chat`）写入合法 `context_compacted_v2`，完整请求保守投影低于 10% target，压后继续执行四个新的 PDF `Read`；随后额外任务被供应商 5 小时额度 `403` 阻断，不属于压缩失败；
- kimi-for-coding（`anthropic_messages`）写入合法 `context_compacted_v2`，critical/important coverage 无缺失，压后继续读取三份文本文件和多份 PDF 并正常结束；
- DeepSeek v4 Pro（`openai_responses`）写入合法 `context_compacted_v2`，保守投影低于 10% target，压后继续读取三份新的文本/脚本/Memory 文件；任务约束明确排除 PDF、图片和 PPT，实际工具调用未越过该非多模态边界。
- MiniMax-M3（`openai_chat`，profile 输入窗口 `267307`）在同一既有长会话中读取 12 份 PDF：面板从压缩前 254K/267K（95%）降至压缩完成时 22K/267K（8%）；诊断回执为 10% target 27K、保守压后 18K、mandatory floor 17K。模型保留第 1–8 份 PDF 的路径、页数和发现，从第 9 份继续完成第 9–12 份及三个此前未读文本。首次压缩暴露的 `task checkpoint coverage fact ... is missing` 已由“每类最近 64 条 + 仅显式淘汰 fact 退出 coverage 分母”的滚动契约修复，并在同一会话重启后复验通过。
- 同一 MiniMax thread 已累计 5 个耐久 `context_compacted_v2`。第 3 次在 provider 实报 257K 时由非递减 usage anchor 主动触发，target 26,730、保守压后 26,206、mandatory floor 16,381，UI 从冻结的 257K 一次刷新到 21K，压后完成 Glob 与最终回答；第 4 次 target 26,730、保守压后 26,574、mandatory floor 19,341，UI 从 226K 一次刷新到 24K；第 5 次在 #25 完成后触发，target 26,730、保守压后 20,828、mandatory floor 16,668，Host header 保存“#24 完成、开始 #25”，压后首个 assistant 明确从 #26 继续并顺序完成 #26–#35，没有重读 #1–#25。第 3 次前后及失败 compact 后都执行过完整 Desktop/Core 退出重启；旧值冻结、首请求主动压缩、压后 continuation 均由同一 thread Journal 证明。
- 在上述已压缩 5 次的同一 thread 中，MiniMax `openai_chat` 切换到 kimi-for-coding `anthropic_messages` 后，Kimi 无工具回答了第 5 次 canary、#25/#26、#35 字段和第 4 次 canary，Journal 的输入窗口为 262,144；再切换到 DeepSeek v4 Pro `openai_responses`，DeepSeek 在不读取任何媒体/文件、不调用工具的条件下复述同一事实，输入窗口为 272,000。两个切换都使用各自真实 protocol family 与 provider usage，不复用前一模型 usage anchor。
- mandatory-floor 真实失败使用可恢复的 DeepSeek 测试窗口 32,000 触发：AG-UI 为 `COMPACT_TARGET_UNACHIEVABLE`，projected 13,745、target 3,200、mandatory floor 13,065，run 以 error 结束且 thread 的耐久边界数保持 5；Desktop 对话只显示通用失败文案，上下文面板仍为失败前 106K/272K 且无 reason。验收后 profile 已恢复 272,000。

当前基线已覆盖三种 protocol lowering 的单次压缩、同一 thread 连续 3/5 次压缩、完整退出重启、模型/协议切换和 mandatory-floor 真实失败。OpenAI native 真实账号和 Windows/Linux 实机不属于本次 V2 收口矩阵，未执行时仍不得写成已通过。

低窗口媒体压测本次以 MiniMax 为真实 Desktop 样本，已经按上述基线通过。自定义 API 多 PDF 不属于当前 V2 收口矩阵；custom endpoint 不继承 OpenAI native compaction/opaque state、只使用 provider-neutral bundle 的协议边界仍由自动化门禁。当前低窗口媒体回归合同是：

- 不得再出现「约 19.5K 一次跳到约 30 万，且多次 `compact_succeeded` 后用量继续上涨」；
- 要么入场门截住后续媒体 `Read`（合成 `context_admission_exhausted`，不切 epoch），要么一次压缩后保守投影落到 auto 线以下并能继续追问；
- 真失败保留旧 epoch，重启后可续（AC-CU-07）；`CONTEXT_BLOCKED` 不得再触发 reactive compact。
- 高 provider/local 校准比把 summary budget 压到 1024 时，摘要请求不得生成 analysis/preamble，必须在输出上限内先闭合 13 个 section；真实供应商输出精确触顶后若仍落入 fallback，不得提交 boundary，也不得把失败后的数值刷新到面板。
- 压缩发生在一批工具结果结束、下一次模型续跑之前时，压后消息必须带 host-owned 最近 assistant 进度锚点；例如压前已有“21/24，继续最后三份”且尾部含最后三份结果，压后不得从 #1 重做。
- mandatory-floor 真实失败必须保留 `COMPACT_TARGET_UNACHIEVABLE`、projected/target/floor 在 AG-UI 与 Journal 证据中，但 Desktop 对话、timeline、inspector 和上下文面板只能显示通用失败文案，不能泄漏内部预算原因。

正式入口是 macOS `npm run open:desktop`。Linux Cloud / 无 `Electron.app` 的环境不能用 Core-only、Gallery 或浏览器页面代替该基线。
