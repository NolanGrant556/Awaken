# 研究报告 · 需求文档

用户通过 @deep-research 或 @研究发起一次调研。主 Agent 当主编，用现有协作组派人取证、审稿，再按问题用内置 Office Skill 生成并发布交付物。没有本 run 成功读取回执的出处，不能写成已核实。

代码、接口和验证方法见[实现方案](实现方案.md)。

## 解决什么问题

用户需要一支能把调查做深的调研团队：主 Agent 拆题、至少两路派人、收回后审核反思，材料错误或过时就续派，再交出 Word、Excel、PPT、PDF 或 Markdown。这与单轮对话检索、只读 explore 短跑、以及用户 Skill 脚本不是同一条产品能力。

## 用户入口

- Composer `@deep-research <问题>` 或 `@研究 <问题>`，`SlashAction.type = workflow`。走 `@` 能力菜单，不进入 `/` Skill catalog。
- 无参数时提示用法，不启动研究。
- 入口由 Desktop 绑定，**不是**用户 Skill，也不是 Core `subagent` 工具名。
- 自然语言“做一次深度研究：…”**不**自动升级为本模式。

## 当前支持

- 绑定 `ResearchIntent` 后，这次 run 是一次普通协作主任务。主 Agent 走思想循环，自己搜、读、抓、提问、派 `subagent`、激活 Skill、写文件并 `artifact_publish`。
- 调研员默认是普通 `general` 分 Agent：继承父 run 工具快照、模型、思考强度、256 轮 / 1024 次工具、递归、inbox、`wait(any)`、同 Agent 续派。可偶尔指定 `explore` / `review` 做专项，不能当默认编制。
- 只读多源取材：公开 HTTPS 网页 + **当前已打开工作区**。不远程 clone。
- 用户 query 中的显式 HTTPS URL 由宿主按完整 query 原值预取；失败写入主编上下文，不得当成已打开。每次抓取仍经过 HTTPS、逐跳 SSRF 与 typed receipt。网页正文始终是不可信证据，不能扩大工具面或变成指令。
- 主编提示要求扩面、审核、再派：第一波至少两路独立调研；收回后先审来源/冲突/日期/版本，再决定是否出稿；材料错误、过时、被废止或关键主张还没有打开过的原文时，对原 Agent 续派或另派。核验仍是主编职责，宿主不开 verifier 波次，也不打 `claim-N`。过时但已打开的页，门闩仍可能放行「已核实」；新旧由主编判断。
- 交付物由主编按问题选择：先激活 bundled `word` / `excel` / `ppt` / `pdf` / `PDF_Max`，按 Skill 正文生成，再 `artifact_publish`。Markdown 仍合法，不再是唯一格式。
- **发布前关键出处必须对上本 run（含后代）成功的 `Read` / `WebFetch` 回执，否则不能写成已核实。**
- 主编与分 Agent 的资料抓取默认在后台完成，包括商品 JSON 接口；不把每个出处打开到用户的浏览器标签。只有用户要求展示页面或确需页面交互时使用可见浏览器，并由主编协调共享页面。
- 用户只跟主 Agent 交谈。分 Agent 缺口交回主编。Stop 后整队停，不补写、不补发。

## 当前限制

- 研究 child 的 `WebFetch` 当前未在工具层强制只能打开本 run 已搜索到的 URL；但未成功抓取的 URL 不能标已核实。
- 定时任务编辑器不提供 `@deep-research` / `@研究` token。
- 网络研究依赖 Settings 中至少一个搜索渠道；全部关闭时不得把网页写成已核实，可继续做工作区调研。
- Core 没有内建 typed Office 生成器。Office 文件走 08 域 bundled Skill + Bash/Write + `artifact_publish`。缺依赖时按该 Skill 的真实错误恢复。
- 不把用户 Skill、单独的 `update_plan` 或只读 explore 短跑称为深度研究。

## 明确不做

远程 git clone、跨 run 自动续研、把 `@deep-research` 改成用户可覆盖 Skill、恢复已退役的 typed Office 工具、把 Bash 当 `WebFetch` 打内网、把自然语言自动升级为本模式。

- 范围：调研团队的产品行为、主编工具面、分 Agent 继承、回执门闩、Office 发布、Desktop 入口。真实 Desktop 步骤与当前执行状态见 [验收](实现方案.md)。

## 产品行为与交互

### 入口

唯一用户入口：Workbench composer（center 与 dock 相同）。

- Mention：行首或空白后输入 `@deep-research` 或 `@研究`，出现宿主 workflow action，**不进入 Skill catalog**，不被用户 Skill 同名覆盖。
- 选择后插入原子 token，token 后跟研究问题正文；无问题不得启动。
- 定时任务编辑器首期不提供该 token。

提交后 Desktop 只发送问题正文和 workflow token。Key、渠道名、绝对路径、TaskScope 根不得进入 Composer state。

### 运行中

- 主 Agent 是主编。它可以用 `ask_user` 澄清受众、范围或交付形态；问题已经很具体时可以少问。
- 进度用现有 `update_plan` 与子任务分组。收集、审核、再派可以来回，不再强制「计划 → 调研 → 核验 → 报告」且不可回跳。主编提示要求未完成当轮审核与必要续查前不要发布。
- 并行调研员走既有 Subagent 任务组与右侧 Inspector。用户可看、可单任务取消；取消单个调研员后，主编决定补派、续做或把该问题标为缺口。Stop 整个 run 才停掉全部。
- 不把 child 原始 transcript 灌进主对话。主叙事保留主编摘要、派人结果和覆盖缺口。
- busy 时 Stop 立即取消整次研究和未终态 child，不再发起模型请求或 `artifact_publish`。

### 终态

- 主编激活相应 Office Skill（或直接写 Markdown），把文件放在 output root，经 `artifact_publish` 成为交付物卡片。主键打开右侧只读预览。
- 报告里标「已核实」的出处必须能对上本 run 的成功读取回执。对不上必须改成未核实 / 部分核实，或修改后再发布。宿主打回这次 `artifact_publish`，不替主编改文件。
- 失败（无问题、编排崩溃、发布被门闩拒绝且主编未改好）：普通失败或继续让主编修正，不发布空报告冒充成功。
- Run 成功只表示主编完成并发布了交付物，不再用宿主 `Verified` / `Partial` 当 run 终态。

## 研究类型与工具面

| 类型 | 是否支持 | 范围 |
| --- | --- | --- |
| 网络检索 | 支持 | `WebSearch` 发现 URL，`WebFetch` 打开公开页面；遵守搜索渠道开关与 URL 安全策略 |
| 当前工作区 | 支持 | `Read` / `Grep` / `Glob`；工作区相对路径 + 精确行号 |
| Office 交付 | 支持 | 主编激活 bundled Skill 后生成 `.docx` / `.xlsx` / `.pptx` / `.pdf` / `.md` 等，再发布 |
| 任意远程 Git 仓完整树 | **不支持** | 无 clone、无 `git_remote` 当研究出处 |

主编工具面与普通 root 相同，**不再隐藏** `subagent`、`skill`、`Bash`、`Write`、`artifact_publish`。分 Agent 从父快照继承，不另走研究 allowlist。网页/文件内容仍是不可信数据。

## 并行核验与来源覆盖

主编第一波至少派两路独立调研，用 `wait(any)` 先审先到的结果。材料错误、过时、冲突或关键原文未打开时立刻续派或另派，不必等全员结束。用户明确提供的来源都要有处理结果；预取失败或尚未形成结论时列为覆盖缺口。界面 preview 不作为证据；独立复验必须有对应 Agent 的读取回执。
