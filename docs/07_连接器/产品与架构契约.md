# 产品与架构契约

## 1. 定位

Connector 持有可见名称、说明、类别、provider、auth type、trust/source、MCP config factory/inline config，以及稳定 `providerId`、aggregate capabilities、dependencies 和 provider readiness。连接后仍由 MCP Manager 注册具体 tools/Skills，所有执行经过中央 ToolRuntime。

aggregate capability 用于目录发现和解释“这个 Connector 大体能提供什么”，不能授权具体 tool 的消息发送、删除或其他副作用。per-tool 安全事实只来自 MCP standard annotations、tool `_meta`/schema 和 adapter：明确自洽的 read-only 可不带 Awaken metadata，所有非 read-only 或 annotations 自相矛盾的 tool 缺失/无效 `io.awaken.tool/provider/v1` 时都在 transport 前 fail closed。

## 2. 当前来源

- builtin：七个内建 definition，连接时生成并持久化 user MCP config；
- local：本地定义，连接时通过 `InjectDynamic` 注入当前进程，不持久化 dynamic state。

内建 capability/dependency 目前包括：DingTalk/Lark 聚合 `message.send`，browser connectors 聚合 `browser.interact`，Context7 聚合 `web.search`。这些仍不代表所有子工具都具备对应 per-tool 安全契约。

## 3. UI 状态

Connector 列表显示 source、provider identity、capabilities/dependencies 和当前 readiness。只有当前 MCP server snapshot 可证明 connected/needs_auth/failed；点击过连接或 config 存在都不是 connected 证据。

Desktop 的 MCP/CLI 展示分类是 renderer 规则；Core `ConnectorDefinition.Category` 仍是业务类别。两者不可合并为一个枚举。

## 4. Ownership

| owner | 负责 | 不负责 |
| --- | --- | --- |
| Connector Registry | definition 合并、connect/disconnect、进程内 active owner | MCP transport、per-tool safety |
| MCP Manager | server/session、snapshot、tools/Skills 注册 | Connector 产品分组 |
| Tool Catalog/Runtime | provider snapshot、决策、Outcome | Connector 安装 UI |
| Desktop | 列表、状态和入口 | 直接调用 MCP session |

## 5. 当前缺口

- builtin 连接会覆盖同名 user MCP config，当前没有被覆盖副本/undo；
- Connector active owner 主要在进程内，重启后 user MCP server 可连接但卡片 ownership 可能不一致；
- OAuth/401/WS 边界沿用 06；
- aggregate capabilities 与依赖是声明，readiness 主要来自 MCP connection/auth，不代表本机可执行依赖已探测；
- 有效 per-tool metadata 只让 mutation 进入统一自动决策/专用门禁，不为 provider 执行后的诚信或可撤销性背书；
- 团队/远程 Connector source 如未接入真实 provider，不能以 UI placeholder 写成支持。

## 6. 代码 owner

- `src/connectors/types.go`、`source_builtin.go`、`source_local.go`、`registry.go`。
- `src/mcpclient`：最终 server/tool provider。
