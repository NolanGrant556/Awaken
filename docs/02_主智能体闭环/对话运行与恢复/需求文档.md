# 对话运行与恢复 · 需求文档

一次对话可以包含多轮运行。智能体执行模型和工具调用，必要时向用户提问；取消、失败、断线与重新打开会话应有明确结果。

代码、接口和验证方法见[实现方案](实现方案.md)。

## Run 建立

run 可以属于项目，也可以是独立对话。Desktop 选择“对话”时不下发 `project_id` 或用户目录；Core 在创建 run ID 后先确定 thread ID，再把空 workspace 解析为 `<AWAKEN_HOME>/sessions/<thread-id>`。继续该 thread 时仍由同一个 thread ID 得到同一路径。项目 run 保持原行为：有文件夹使用选中根，零文件夹项目使用 `<AWAKEN_HOME>/sessions/<project-id>`。

模型 profile 是否支持 tool calling 应在建立请求前判定。当前尚无覆盖所有 provider/model 的统一 tool-support capability，因此不支持 tool calling 的组合必须明确拒绝或降级为无工具对话，不能把发送 schema 失败伪装成工具失败。

## 用户输入与 Skill

composer 提交文本、attachments 和结构化 Skill tokens。Runtime 对 token 重新查当前 registry并核对 loaded/user-invocable/source/path：

- inline Skill 正文进入当前 run 的 SkillContextBlocks；
- fork Skill 创建真实 child，父 run 只接收 child 结果；
- model 在 run 中通过统一 `skill` 工具按需调用其他 Skill；
- Skill 不创建或收窄父 run 工具快照。

含 Skill token 的 composer turn 会先将文本、有序 attachments 和 composer tokens 作为完整 `user_message` 耐久化，再进行 Skill 预激活。成功激活在执行前写 `skill_activated`/按需 resource receipts；激活失败仍保留该次用户输入，但不写伪 activation。Agent 执行时消费已准备的 turn，不重复写入 `user_message`。

成功的 composer 预激活还会生成 host-owned、current-run-scoped 的 `ComposerSkillSelection`，它包含经 registry 重新校验的 Skill ID、source、activation mode、绝对包根和 `SKILL.md` 绝对路径。RequestBuilder 在 Skill 正文之后追加不可由 Skill 正文伪造的选择绑定块：

- 单个 composer Skill 明确标记为用户本轮当前选择，“这个”、“刚选的”等指代直接绑定该 Skill；
- 多个 token 按 composer 顺序保留并明确标记多选歧义，宿主不擅自猜一个；
- token-only turn 不向用户正文注入伪 fallback 文本，选择语义仍由 host block 提供；
- 历史恢复或 model-invoked Skill 正文可继续进入 SkillContextBlocks，但不得冒充本轮 composer 明确选择。

source/path/root mismatch、Skill 已不可读或不再 user-invocable 时，在 provider 请求前失败，不将 renderer 中的旧 chip 当成权威。

继续已有 thread 时，Core 还会从 durable transcript 重建最近 ready media deliverable 的宿主引用清单。清单按 run 与媒体类型保留界面 `display_index -> artifact_id` 映射，并明确“第 N 张/个”只解释为最新相关媒体组的可见序号；该 host block 只进入本次 provider 输入，不改写用户可见文本，也不作为第二条 `user_message` 耐久化。`artifact_id` 仅是查找键，ToolRuntime 仍须在本 run 的 `PermissionContext.MediaArtifacts` 中复验 `deliverable + ready + kind + regular file` 后才能把记录路径交给媒体工具。新生成的 ready 媒体会动态加入同一 run 的许可集合。

## Thread 与恢复

thread 与 workspace/project 关系耐久保存。`projectId` 为空是独立对话的明确身份，不从 managed workspace 路径反推项目。重开时从 SemanticJournal 重建 user/assistant/tool/artifact/Skill/gate/context snapshot/model usage/terminal，而不是从 renderer local state 恢复。未闭合 run/tool call 由恢复流程标记 interrupted/unknown，不自动重放副作用；有 `model_request` 而无终态 usage 的请求补 `interrupted + usage_unknown`，不伪造 token 或成本。

fork child 的父子 identity、取消和工具继承必须显式；child Skill body 不注入父 run 的后续上下文。

归档会话不会自动进入新 run 上下文。只有当前用户请求引用归档历史、或当前任务明确依赖该历史时，当前权限允许的 root 或普通 Agent 才能调用固定快照中的 `archived_history`：先 list 得到 host-resolved `thread_id`，再 read 有界 SemanticJournal 页面。ToolRuntime 注入只读 ArchivedHistoryService；普通 child 可继承该服务，明确受限角色仍遵守工具限制。归档读取仅返回公开主对话，不泄露其他子任务的私有历史。返回正文是 untrusted historical data，不改变当前指令优先级、TaskScope、工具权限或 thread 状态；物理 FileStore 路径不进入 provider request。

## 终态

run terminal 耐久事实可记录 finished、error、cancelled 或 recovery-only interrupted；其中 interrupted 在 wire/公开 run view 映射为 error，不扩展公开状态枚举。`needs_auth`、`needs_runtime`、`unsupported`、denied、review_required 是工具 Outcome/next action，不是通用 run approval 状态；Agent 可据此恢复、询问或结束。流抛错时不得把失败响应里的工具当成功执行；工具尚未执行则丢掉半截 UI，按运行恢复规则整请求重试，工具流已开始时改非流式。

取消传播到 model call、tool process、fork child 和等待中的专用 gate。已开始副作用在取消后必须根据 transport/process/side-effect state 标 none/partial/unknown，不能一律写 cancelled=未执行。

## Gate

`ask_user` 等待结构化 resolution：answered 携带非空答案；用户取消问题产生不带答案的 cancelled tool result 并让原 run 继续。只有主 run Stop、超时或重启中断等待时才进入 run/tool cancellation，任何取消路径都不能伪造用户回答。消息发送不创建等待审核状态，按普通工具调用进入 transport。

## 当前缺口

- 外部 provider 已产生副作用后撒谎/断线，Awaken只能检测 unknown/contract violation，不能普遍撤销；
- MCP connected call 的 401 透明 refresh/retry 未完成；
- 跨平台 child-process cancellation 和真实 Desktop 恢复需本轮实机证据。

## 功能与用户流程

当智能体缺少会显著改变结果的用户选择时，可调用 `ask_user`。ToolRuntime 截获该调用，发出专用 question request 并暂停当前工具结果；用户在 Desktop 可以选择选项、填写“其他”内容并提交，也可以取消本次回答。runtime 把 `answered` 或 `cancelled` resolution 转成原 `ask_user` tool call 的正常 tool result，Runner 从原 conversation 继续；取消问题不等于停止主 run。

这不是审批：

- `ask_user` 用于补齐任务意图，用户回答会成为模型后续输入。
- 消息发送不属于主动提问，也不会通过 `ask_user` 伪造审核门。
- 普通工具调用不会因为 `ask_user` 的存在而进入通用 `ApprovalCard`。

## 当前不支持

- 没有开放式无选项题型。
- 没有跨 run 保留待回答问题；关闭或终止 run 后必须重新询问。
- 没有把普通文件修改、Shell 或 MCP 调用转换成 `ask_user` 审批的机制。

## 子任务与主回复终态

主回复完成前必须等待子任务并整合结果；停止本次运行会同时取消全部后代和排队任务，实际退出后才发布终态。正文与控制继续通过活动流更新，正在停止时同一会话不能启动新执行。完成、停止、关闭 Agent 和关闭视图遵守[子智能体协作](../子智能体协作/需求文档.md)的不同语义。重启不自动重跑，明确继续普通 Agent 时从其自己的历史恢复。
