# 提示词缓存、上下文用量与成本治理开发计划

## 1. 文档状态与目标

本文是尚未实现能力的开发计划，负责四个结果：

1. 让 DeepSeek、Kimi 与后续 provider 按各自官方合同使用提示词缓存；
2. 让同一 thread 的 system、tools 和 history 前缀在连续轮次与重启恢复后保持稳定；
3. 用户点击 Composer 的“上下文”后，可以用中文查看当前上下文各组成部分的 Token 估算；
4. 每次主模型与辅助模型调用都留下可恢复的 input、cached、uncached、output 与成本记录。

模型目录、profile 与凭据入口仍由 [05 模型与供应商配置](../05_模型与供应商配置/索引.md) 拥有；上下文压缩与恢复由 [上下文窗口与压缩](上下文窗口与压缩.md) 拥有；Workbench 容器、overlay 和 composer 交互由 [01 中间交互区域](../01_桌面工作台/中间交互区域/架构契约.md) 拥有。

实现完成后，本文必须删除阶段顺序和调研快照，只保留已经由代码、测试和真实 Desktop 证明的当前合同。

## 2. 当前状态

| 能力 | 当前事实 | 缺口 |
| --- | --- | --- |
| Composer 上下文指标 | dock 模式显示 `context windows`、进度条和汇总值 | 不可点击，没有中文分项 |
| 指标语义 | 无 provider usage 时使用本地启发式估算 | 有 usage 时前端优先使用最近响应 `totalTokens`，其中包含 output，不能代表当前上下文占用 |
| 分类估算 | `ContextEnvelope` 可见 system、messages、attachments 和 tools | 事件只有汇总值；Memory/Skill 还会因平行 debug projection 被重复估算 |
| Provider prompt cache | profile wire 存在 `prompt_cache_key` | 字段没有进入 `src/llm` 请求或最终 HTTP body |
| 稳定前缀 | run tool snapshot 已排序并冻结 | 秒级时间、异步 Memory 与运行期 Skill 会重写 system 前缀 |
| Provider usage | `llm.Usage` 只有 input/output/total | 不解析 cached/read/write；流式 OpenAI Chat 没有主动请求 usage |
| 成本账本 | run terminal 能保存终态 | 没有逐请求 `model_usage`，主 Agent、标题、Memory、compact、Dream 无法拆账 |
| Kimi 连续推理 | 当次响应能解析 `reasoning_content` | 没有跨 turn、resume 的 provider-opaque state |

直接结论：当前指标只能作为粗略风险提示，不能解释“哪些内容占用了上下文”，也不能解释“额度为何消耗”。前端展开面板必须建立在新的分类估算合同上，不能从现有总数反推百分比分摊。

## 3. Provider 决策

下表是本计划采用的合同基线。实现和发布当天必须重新打开所列官方文档核验；字段、endpoint 或计费身份变化时，先更新 capability 与测试 fixture，再改 transport。

| Awaken provider | 官方缓存合同 | 本计划行为 |
| --- | --- | --- |
| DeepSeek | [自动前缀缓存](https://api-docs.deepseek.com/guides/kv_cache/)；usage 返回 hit/miss | 不发送私有 cache key；稳定前缀并解析 hit/miss |
| Kimi CN | [自动上下文缓存](https://platform.kimi.com/docs/guide/use-context-caching-feature-of-kimi-api)；支持稳定 `prompt_cache_key` 与 `cached_tokens` | thread 级 affinity key；流式请求主动索取 usage |
| Kimi Coding Plan | [Chat API](https://platform.kimi.com/docs/api/chat) 要求 Code Plan 提供稳定 key；模型/effort 切换是冷边界 | 自动发送 key；cached usage 只做字段探测，不臆造套餐换算 |
| 火山 Coding Plan | `/api/coding/v3` 官方未确认缓存字段 | 不发送普通方舟 Context/Responses 字段；只做稳定前缀和响应探测 |

普通方舟 Context API、Responses、Anthropic breakpoint、Bedrock Converse 或 Gemini CachedContent 必须作为独立 endpoint contract 接入，不能因为都兼容某种 SDK 就共用请求字段。

从 Codex、Claude Code、OpenCode 源码只保留以下设计结论：

- Codex：session-stable key、精确历史重放、append-only context delta；
- Claude Code：协议级 cache breakpoint、稳定 tool schema、按 5m/1h 拆分 cache write、cache break 诊断；
- OpenCode：provider option 与最终 wire adapter 分层、持久化 Context Epoch、typed source snapshot、集中式 tool-output offload；
- 不照搬：OpenCode V2 只把 key 放在 `openai` namespace、Chat 不 lower key、缺失 usage 折 0、成本写 0、按固定比例估算 cache hit，以及把中途 system delta 降为 user message。

## 4. 目标产品行为

### 4.1 Composer 入口

- dock Composer 的元信息由 `context windows` 改为“上下文”；center 空态没有上下文时不显示假 0；
- 汇总值固定表示 **当前下一次 provider request 的本地输入估算占可用输入窗口的比例**，其中 `可用输入窗口 = 模型总窗口 - 输出预留`，格式为 `约 92.1K / 240K 可用输入`；
- 汇总值不再被最近响应的 input/output/total usage 覆盖；
- 指标是 button，支持鼠标点击、键盘 Enter/Space，并带 `aria-haspopup="dialog"` 与 `aria-expanded`；
- warning、auto compact、blocked 继续使用 Core 阈值，前端不自行判断。

| `subagent_definitions` | 子智能体定义（条件项） | 仅计入最终请求实际包含的 model-visible child/agent definitions；当前没有时整行隐藏 |

各行只在 Token 大于 0 时显示；`subagent_definitions` 是未来兼容类别，不得据此写成 Awaken 当前已有正式 subagent。

### 4.4 面板交互与布局

- `App.tsx` 拥有 open state、数据和 overlay 编排；Design System 组件只接收 props/callbacks；
- 面板进入现有 `RunStage.overlay`，不进入 `ExecutionFeed`，也不放进 `composer-dock-stack`；
- overlay 外层 pointer-through，面板本体 pointer-auto；打开面板不改变 ComposerDock 高度、safe area、native tail、marker 或 return-to-latest 位置；
- 面板底部使用现有 composer inset 定位，宽度不超过内容列；窄窗口时保留 16px 安全边距并在面板内部滚动；
- Escape、关闭按钮、点击面板外部均可关闭；关闭后焦点返回触发按钮；
- 打开/关闭不改变 draft、IME composition、follow/paused、active turn 或 thread identity；
- 颜色只辅助区分，类别名称和数值必须始终可见；亮色/暗色均使用 Design System token；
- 数据更新时原位更新，不抢焦点、不重新打开已关闭面板。

## 5. 数据与架构合同

### 5.1 上下文分类快照

Core 在最终 provider-visible request projection 完成后生成：

```text
ContextUsageSnapshot
  schema_version / snapshot_id / estimator_id
  basis: current_projection | sent_request
  request_id_optional / request_sequence_optional
  model_id / protocol_family / request_shape_digest
  model_window_tokens
  output_reserve_tokens
  effective_input_window_tokens
  estimated_input_tokens
  warning_threshold_tokens
  auto_compact_threshold_tokens
  compact_target_tokens
  contributions[]:
    kind / estimated_tokens / source_count
  generated_at
```

不变量：

1. `sum(contributions.estimated_tokens) == estimated_input_tokens`；
2. 只计算最终会发给 provider 的内容，不计算 debug-only projection；
3. Memory/Skill、附件和 tool result 每份内容只能由一个 contribution owner 计入一次；
4. category 由 Core 的 typed source 决定，Renderer 不按字符串、tool name 或 message 文本猜测；
5. 估算算法版本化；算法变化不伪装成真实上下文突然增减；
6. 老 transcript 没有 breakdown 时只显示汇总和“暂无分类明细”，不按比例补造；
7. `ContextActualTokens`/最近响应 `totalTokens` 不再参与当前窗口占用计算。

为保证类别来自真实来源而不是字符串猜测，需要同时补齐：

- `src/prompt` 输出带稳定 ID 的 typed prompt sections，使系统提示词与规则可区分；
- `src/context` message 保留 host-owned origin、turn/message identity，区分 history、current input、tool result、compact summary 与 synthetic continuation；
- model-visible tool schema 保留不发给 provider 的 source/provider/registration provenance；
- provider adapter 完成 protocol lowering 后，把额外插入的恢复指令、多模态 block 与协议开销回报给 composition；
- Runtime 在每次真实模型请求前，用 request ID 耐久写入脱敏 `model_request` composition，response 的 `model_usage` 复用同一 ID。

持久化和 wire 只发送恢复与展示所需的脱敏字段：schema/snapshot/estimator 版本、basis、request identity、模型与协议 identity、窗口和阈值、request shape digest、各类别 Token/item count 与生成时间。不能包含 prompt、规则正文、路径、tool 参数、Memory、API key 或 reasoning。Go `AwakenEvent`、AG-UI wire、TypeScript shared type、runtime reducer 与 replay 同步增加 typed contributions；中文 label 只在 Renderer/Design System 映射，Core 不发送本地化文案。

### 5.2 Provider capability

`src/llm` 建立唯一 provider manifest：

```text
PromptCacheCapability
  protocol_family
  endpoint_contract_id
  mode: automatic_prefix | affinity | breakpoint | explicit_context | undocumented
  affinity_key: unsupported | recommended | required
  wire_strategy
  usage_normalizer_id
  token_identity_contract
  streaming_usage
  reasoning_replay
  pricing_snapshot
```

只有标准化 Base URL 匹配已核验 endpoint contract 时才能发送厂商私有字段。自定义兼容 endpoint 一律降级，只发送协议通用字段并做响应探测。

### 5.3 Cache key 生命周期

需要 affinity 的 provider 使用 host 自动生成的非敏感 key：

```text
aw1_ + base64url(SHA-256(
  provider_id + profile_id + credential_scope_revision
  + endpoint_contract_id + agent_tree_root_thread_id
  + model_id + reasoning_policy + prompt_schema_version
))
```

- 同一 root thread 连续 turn 与 restart/resume 保持一致；
- 新 root thread、credential、endpoint、model、effort 或 prompt schema 产生新 key；
- child 默认继承 root affinity；明确隔离的一次性任务派生 purpose key；
- title、Memory、compact、Dream 使用独立 purpose key，不污染主 Agent；
- key、日志与 telemetry 不包含 API key、路径、用户名、prompt 或 thread title。

### 5.4 稳定前缀与 Context Epoch

```text
ContextEpoch
  epoch_id / thread_id / baseline_sequence
  exact_baseline_text / baseline_digest / prompt_schema_version
  source_snapshots[]:
    source_key / codec_version / value_digest / applied_sequence / state
```

`state` 至少包含 `unchanged | updated | unavailable | removed | incompatible`。相同 epoch 在重启后重用原 baseline bytes；临时 unavailable 保留上一准入值；明确 removed 才发 removal delta；初始化或 incompatible 缺少完整 source 时不建立残缺 baseline。

日期只保留到日；Memory、Skill、MCP 与 runtime 变化在安全 provider-turn boundary 形成 host-owned delta。provider 无法在 tail 保持 system/developer authority 时，建立显式新 epoch，绝不能降成普通 user message。只有成功 compaction、workspace move、prompt/tool schema 不兼容或 provider authority 编码不兼容才能换代；失败或中断保留旧 epoch。

tools 在 epoch 初始按稳定类别和名称排序。动态 tools 进入耐久 trailing partition，只按首次发现顺序追加；更新、删除或无法 append-only 表达的变化形成 typed tool-schema boundary。

Kimi `reasoning_content` 作为 provider-opaque state 持久化，只在 provider、credential scope、model、protocol family 与 endpoint contract 全部匹配时重放，不进入普通正文、Memory 或 telemetry。

### 5.5 逐请求模型用量账本

`ContextUsageSnapshot` 是当前下一次请求的本地估算；`ModelUsageRecord` 是某一次已完成 provider 请求的 usage 真相，两者必须分开：

```text
ModelUsageRecord
  thread_id / run_id / turn_id / request_id / sequence
  provider_id / profile_id / credential_scope_revision / model_id
  protocol_family / endpoint_contract_id / purpose / retry_index
  cache_mode / cache_key_applied / prefix_digests / invalidation_reason
  raw_typed_usage
  input / cached_input / uncached_input / cache_write / output
  usage_complete / calculated_cost / pricing_snapshot / currency
  provider_request_id / latency / status
```

purpose 至少区分 `agent_turn | thread_title | memory_recall | compact_summary | memory_maintenance | connection_test`。provider 缺失字段保持 unknown；严禁用固定百分比估算缓存命中并回填 provider usage。

## 6. 开发阶段

### 阶段一：修正上下文指标语义

主要 owner：`src/agentcore/context_window.go`、`context_envelope.go`、`request_builder.go`、事件 mapper、Desktop reducer。

交付：

- 从最终 provider-visible projection 生成 `ContextUsageSnapshot`；
- 为 prompt section、message 和 tool schema 增加只用于归因的 typed provenance；
- 修复 Memory/Skill 重复估算；
- 将 tools 按来源分类，messages 拆分 history/tool result/current input；
- `ContextActualTokens` 不再覆盖当前估算；最近 provider input 迁入独立 usage 字段；
- 每次 request 的 `model_request` composition 与 `model_usage` 用同一 request ID 关联；
- live、replay 与 restart 恢复相同 breakdown。

完成门槛：分类和等于总估算；旧记录不伪造分类；Go mapper、TS type、reducer/replay 测试通过。

### 阶段二：实现中文上下文面板

主要 owner：`App.tsx`、`AwakenContextUsagePanel`、Workbench overlay 样式、Design System states/demo/tests。

交付：

- Composer 指标改为中文并可点击；
- 实现分类进度条、中文行、估算标记、输出预留和压缩阈值；
- provider usage 已可用时显示独立“最近一次模型调用”；
- 完成键盘、焦点、暗色/亮色、窄窗口和无 breakdown 降级。

完成门槛：面板不参与 composer 测量，不破坏 RunStage 滚动/follow/marker/return，Gallery 与真实 Desktop 都有当前证据。

### 阶段三：接通 provider 缓存与 usage

主要 owner：`src/llm` provider manifest、OpenAI Chat adapter、model profile/run snapshot。

交付：

- DeepSeek 解析 hit/miss，不发送未知 cache 字段；
- Kimi/Kimi Coding Plan 发送稳定 key 与 `stream_options.include_usage`；
- 火山 Coding Plan 保持未确认降级；
- custom Base URL 不继承官方 endpoint 私有字段；
- raw typed usage 与 normalized usage 一起进入 `model_usage`。

完成门槛：mock server 断言最终 HTTP body；unknown 不折 0；同 thread resume key 稳定，新 scope 明确冷启动。

### 阶段四：稳定前缀与 Context Epoch

主要 owner：`src/agentcore` request builder/context engine、journal/store/replay、tool snapshot。

交付：

- 删除秒级 system 时间；跨日只追加 typed delta；
- Memory、Skill、MCP 与 runtime 变化不再重写旧前缀；
- exact baseline 与 typed source snapshot 耐久化；
- tool schema canonicalization、动态 trailing partition 与 cache boundary 诊断；
- Kimi provider state 跨 tool turn 与 resume 安全重放。

完成门槛：连续三个 full-replay tool turn 保持 canonical prefix；重启重用 baseline bytes；unsupported Chat 不发生 host instruction 降权。

### 阶段五：调用次数与成本治理

主要 owner：RunService、SemanticJournal、主/辅助调用入口、Desktop usage projection。

交付：

- main、title、Memory、compact、Dream、retry 全部按 purpose 记账；
- title 优先本地规则，辅助调用使用独立小模型/预算；
- compact summary 使用独立 purpose/key，成功后才切 epoch；
- tool result 在首次 model admission 前完成稳定 offload；事后 replacement 记录冷边界；
- 提供每 run 的主/辅助请求数、uncached input、cache hit、output 与成本汇总。

完成门槛：live/replay 聚合一致；取消、失败和 retry 不漏账；任何估算都不冒充 provider 报告。

### 阶段六：真实 provider canary 与发布

- 固定 `prompt-cache-three-turn-v1` fixture：相同账号、区域、model/effort、tools、workspace 和三轮工具输入；
- 每个已确认支持并报告缓存用量的 endpoint 在 30 分钟内完成 5 组配对试验：稳定组在同一 thread 连续三轮，冷对照组每轮更换等长的早期前缀并派生新 key；每组共 6 次调用；
- 保存每次 request shape digest、key 是否应用、input/cached/uncached/output、provider request ID、状态和延迟；比较两组中位数，不保存 prompt 正文；
- transport 合同、key 生命周期、usage identity 和账本关联必须 30/30 正确；稳定组 10 个 warm turn 中至少出现一次非零 cached read，否则停止发布并进入 prefix/key/provider 路由诊断；
- 官方未承诺或未返回缓存用量的 endpoint 只验证降级与 unknown 语义，不以缓存命中为发布声明；不预先承诺节省百分比。

### 总完成门槛

只有同时满足以下条件，才能宣布本计划完成：

1. 阶段一至五的局部门槛全部通过，阶段六 canary 留下本次可追溯记录；
2. 第 7 节自动化与第 8 节真实 Desktop 旅程均在当前工作区通过；
3. 当前估算、provider usage、缓存用量和成本四种口径在 live、replay、restart 后仍一致且不互相覆盖；
4. 所有 provider 的 supported/unsupported/unknown 均有明确合同，没有把缺失字段折 0；
5. 唯一权威文档已更新为实际代码和 Desktop 行为，本文按第 1 节要求移除阶段顺序与静态调研快照。

## 7. 自动化验收

必须覆盖：

1. `ContextUsageSnapshot` 分类求和、无重复、空类别隐藏、old record 降级；
2. system/tools/history/tool result/attachments/current input 的 typed attribution；
3. `AWAKEN_CONTEXT_ESTIMATED` breakdown 经 Go mapper、JSON、TS、reducer、replay 不丢失；
4. Composer 指标始终使用 local estimate，最近 provider total/output 不覆盖；
5. 面板中文标签、进度条、估算标记、最近调用 unknown 状态；
6. 点击、Enter/Space、Escape、点击外部、焦点返回与 `aria`；
7. panel 打开时 composer height、safe area、native tail、follow、marker、return 和 IME 不变；
