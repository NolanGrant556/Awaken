# Awaken Tool Layer v2 架构设计

更新时间：2026-07-11

文档状态：设计已实施；自动化与 live runtime contract 验收完成，真实 LLM tool-selection smoke 的凭据层阻断见 `验收记录.md`。

适用范围：Tool interface、registry、definition/schema、execution result、error model、tool documentation 与现有工具迁移。

非范围：Agent Loop 重写、Planning、Memory、Model Provider、Workbench UI 重构。

## 1. 目标

Tool Layer v2 要同时满足四类消费者：

1. LLM：准确选择工具、构造参数、理解结果并规划下一步。
2. Runtime：执行前校验 capability/permission/schema，执行后保留真实状态。
3. Journal/UI：可靠重放同一语义事实，不从人类文本猜状态。
4. Tool author：用一个可 lint、可测试的定义描述能力和结果。

完成标准不是字段数量，而是：

- 工具职责边界可从 definition 独立理解；
- 非法输入尽量在执行前拒绝；
- 结果能区分调用、操作、进程和副作用状态；
- 失败能明确是否可重试、是否已有副作用、下一步需要什么；
- 未观察到的环境状态明确标记 unknown，不伪造完整性；
- legacy/MCP/Skill 工具也进入同一 canonical result；
- model、journal、AG-UI 与 audit 都从同一事实派生。

## 2. 设计原则

### 2.1 单一事实源

`ToolDefinition v2` 是能力事实，`ExecutionOutcome v2` 是执行事实。`Description()`、provider schema、UI tool info、audit metadata 都是派生视图。

### 2.2 Additive migration

保留现有：

- `tool.Tool`
- legacy `Execute(ctx,input) (string,error)`
- `OutcomeTool`
- snake_case Outcome JSON
- AG-UI lowerCamelCase 映射
- ToolCall/ToolResult pairing
- transcript adapter
- FailureSupervisor 依赖字段

所有 v2 字段 additive；不原地重写旧 transcript。

### 2.3 高信号而非全量快照

结果默认返回 operation delta 和明确 observation scope。只有工具真实观察过 git/process/env 时才返回对应状态。禁止每次工具调用无条件运行全量 `git status`、`ps` 或导出环境变量。

### 2.4 声明不等于授权

`permissions` 与 `side_effects` 帮助模型和 registry 理解工具，不取代 `ToolRuntime`、TaskScope、profile、executor、sandbox 或 mass-message review gate。

### 2.5 统一 envelope，保留专属 details

所有工具共享状态、错误、变化和下一步字段；每种工具仍可在 `details` 中返回 typed payload，例如 shell stdout/stderr、Edit structured patch、Glob truncation cursor。对 v2/`OutcomeTool`，`content` 只保留兼容性的人类可读文本，永不作为状态、错误或资源变化的事实源；只有 legacy result adapter 可为了兼容旧返回而保守推断变化，且必须标记 `ChangeInferred`。当 `details` 与 `content` 冲突时，以 canonical typed fields 和 `details` 为准。

## 4. Tool Definition Schema v2

### 4.1 Authoring contract

每个 resolved Tool 必须具备：

```yaml
schema_version: 2
name:
display_name:
source:
description:
purpose:
when_to_use: []
when_not_to_use: []
input_schema: {}
output_schema: {}
side_effects: []
permissions: {}
examples: []
failure_modes: []
annotations: {}
```

用户要求的字段全部是 resolved definition 的必备字段形状。为兼容外部/legacy 工具，raw definition 可以缺字段，但注册 adapter 必须补齐并标记 provenance/quality；30 个可执行静态 builtin 已全部通过 `strict_builtin` 注册，运行时注入的 `skill_install` 也使用同一严格门禁，固定一方 `skill_resource_read` 使用 `strict_all`。`GET /v1/tools` 对每个工具都返回全部 resolved fields；动态外部工具没有可验证的元数据时，`examples` / `failureModes` 仍存在且为空数组，缺口由 `quality` / `warnings` 如实表达。

### 4.2 Go 类型

目标类型：

```go
type ToolDefinition struct {
    SchemaVersion int                  `json:"schema_version"`
    Name          string               `json:"name"`
    DisplayName   string               `json:"display_name"`
    Source        ToolSource           `json:"source"`
    Description   string               `json:"description"` // compact summary
    Purpose       string               `json:"purpose"`
    WhenToUse     []string             `json:"when_to_use"`
    WhenNotToUse  []string             `json:"when_not_to_use"`
    InputSchema   ToolParametersSchema `json:"input_schema"`
    OutputSchema  ToolParam            `json:"output_schema"` // tool-specific details schema
    SideEffects   []ToolSideEffect     `json:"side_effects"`
    Permissions   ToolPermissionSpec   `json:"permissions"`
    Examples      []ToolExample        `json:"examples"`
    FailureModes  []ToolFailureMode    `json:"failure_modes"`
    Annotations   ToolAnnotations      `json:"annotations"`
    Policy        PermissionPolicy     `json:"policy,omitempty"`
}
```

辅助类型：

```go
type ToolSideEffect struct {
    Kind        string   `json:"kind"`
    Resources   []string `json:"resources,omitempty"`
    Description string   `json:"description"`
    Reversibility string `json:"reversibility"` // reversible/conditional/irreversible/unknown
}

type ToolPermissionSpec struct {
    CapabilityClass CapabilityClass `json:"capability_class,omitempty"`
    WorkspaceScope  string          `json:"workspace_scope,omitempty"`
    FileBridgeScope FileBridgeScope `json:"file_bridge_scope,omitempty"`
    NetworkScope    NetworkScope    `json:"network_scope,omitempty"`
    RequiresAuth    bool            `json:"requires_auth"`
    RequiresReview  string          `json:"requires_review,omitempty"`
}

type ToolExample struct {
    Scenario string         `json:"scenario"`
    Input    map[string]any `json:"input"`
    Outcome  string         `json:"outcome,omitempty"`
}

type ToolFailureMode struct {
    Code        string   `json:"code"`
    Cause       string   `json:"cause"`
    Retryable   bool     `json:"retryable"`
    Recovery    []string `json:"recovery,omitempty"`
}
```

实现时允许为避免重复而调整具体字段承载文件，但不得删除用户要求的语义。

### 4.3 Resolution 与兼容

新增 `ResolveDefinition(t Tool) ToolDefinition`：

1. 读取 `t.Definition()`。
2. 校验 `Definition.Name == t.Name()`。
3. 以 `ResolveInputSchema(t)` 填充 canonical input schema。
4. `ExecutionOutcome v2` 是所有工具固定的 canonical envelope；`output_schema` 只描述 envelope 内 tool-specific `details`。没有 typed details 时使用空 object schema。
5. 从 annotations 派生 permission facts，但不把声明当授权。
6. legacy/MCP/Skill 缺失字段由 source-specific adapter 补齐；无法诚实推断的值显式标记 `unknown`，不得生成虚假 example/failure mode。
7. 分别记录 origin（builtin/MCP/Skill）与 quality（strict/adapted/incomplete），供 lint/audit 使用，不发送给模型。

兼容周期内：

- `Description()` 和 `Parameters()` 仍可用；resolved definition 的字段优先级是 explicit v2 > source adapter > legacy method。
- RequestBuilder 改为从 resolved definition 编译；
- `description` 仅是 purpose 的短摘要，模型长描述由 purpose/when/not/effects/returns 编译；builtin 逐步删除 legacy 重复源；
- 外部 MCP 若 metadata 不足，使用保守 side-effects/permission defaults，并按能力风险选择告警、降级或隐藏。

## 5. Description Engineering

### 5.1 Naming convention

- builtin：小写 `snake_case`，动作和资源清晰，例如 `read_file`、`text_edit`。
- 外部 namespace：`mcp__server__tool`，不得丢失 server identity。
- Skill：`skill__id`。
- 避免 `do_task`、`query`、`process` 等无资源语义名称。
- 展示名不参与模型调用、permission rule 或 hook identity。
- 同一 canonical name 必须贯穿 registry、model schema、audit 和 result operation。

### 5.2 Description source template

Author 不直接维护一大段易漂移文案。模型描述由字段编译：

```text
<description>
Use when: <when_to_use>.
Do not use when: <when_not_to_use>; use <alternative> instead.
Effects: <side effects and reversibility>.
Returns: <high-signal result and continuation fields>.
```

编译器要求：

- 第一行说明唯一目的，不写营销语言。
- 用 when 区分相邻工具，不只重复 what。
- when-not 必须给可行动替代工具或停止条件。
- 只描述真实实现，不把未来能力写入 description。
- 不重复 input schema 已明确的字段名清单。
- 高风险 caveat 与不可逆行为必须出现。
- 结果说明重点写模型下一步能用的字段。
- provider 可配置长度预算；截断不能删除 when-not 或安全边界。

### 5.3 Parameter description guideline

每个参数说明至少回答：

1. 语义对象是什么。
2. 格式/单位/路径基准是什么。
3. 默认值和边界是什么。
4. 与其他参数是否互斥或依赖。
5. 参数如何改变副作用。
6. 错误时返回什么 code。

禁止：

- `path: file path` 这类同义反复；
- 在 string 中再次包装可由递归 schema 表达的 JSON；
- 用自由文本代替 enum；
- 未声明 `additionalProperties`；
- description 声称支持但 executor 忽略的字段。

### 5.4 Description lint

Registry/CI 至少检查：

- name identity 与命名格式；
- purpose/when/when-not 非空；
- parameter description 非空；
- example 能通过同一 input validator；
- failure mode code 不重复；
- read-only 与 mutation side effect 不矛盾；
- destructive 工具声明可逆性；
- requires-auth/network 与 annotations 一致；
- output schema 只声明 tool-specific details，且不得重复或覆盖 canonical envelope fields；
- description 不包含不存在的替代工具。

### 6.1 扩展现有 ExecutionOutcome

### 6.3 状态组合与副作用确定性

固定枚举：

- `not_started`：input/policy/auth/precondition 阶段即停止。
- `none`：操作已执行，且已确认没有副作用。
- `applied`：声明的变化已观察并成功提交。
- `partial`：部分变化已提交，另一些失败。
- `unknown`：进程中断、外部系统超时等导致最终状态未知。

每个 `changes[]` 可带 `certainty: observed/inferred/unknown` 与 `reversibility: reversible/conditional/irreversible/unknown`；顶层 side-effect state 是保守汇总，因此 `partial + unknown resource` 可以同时表达。失败并不等于“什么都没发生”。

Normalization 必须满足：

| canonical status | transport | semantic | side effect | 合法含义 |
|-|-|-|-|-|
| succeeded | completed | success/neutral | none/applied/unknown | 调用完成；声明可变更但未观察到 delta 时必须保守为 unknown；neutral 表示无成败业务语义 |
| failed | not_started/completed/failed | failure | not_started/none/partial/unknown | 已知失败，副作用独立表达 |
| denied/needs_auth/needs_runtime/unsupported/review_required | not_started | failure/neutral | not_started | 控制面在工具运行前阻断；`needs_auth` / `needs_runtime` 通过 next action 指向授权或运行时恢复 |
| cancelled/interrupted | not_started/cancelled/completed/failed/unknown | failure/neutral | not_started/none/partial/unknown | 根据中断发生阶段保留已知 transport；已观察变化为 partial，未能确认终态为 unknown |

进程型工具另以 `process_status=exited/timed_out/signaled/spawn_failed/unknown/not_applicable` 表达本次调用的终态；长期运行 session 的 running 状态属于独立 process/session observation。任何矛盾组合由 finalizer 拒绝或保守降级为 `failed + unknown`。

### 6.4 Projection rules

Canonical Outcome 包含完整事实；不同消费者使用明确的读取或持久化边界：

- model：status、summary、operation、changes、compact environment、errors、next actions、tool-specific details；按字段敏感级别去敏并限长。
- journal：当前仍持久化 canonical Outcome，保留执行事实以支持恢复；字段级 sensitivity、去敏、retention 与 access policy 尚未落地，是后续安全项，不能用 model projection 的去敏行为代表 journal 持久化策略。
- AG-UI：现有状态字段 + 需要展示的 summary/change/error；UI 不反向推断。
- audit：definition identity、decision、outcome status、side-effect state、affected resources。
- telemetry：只记录去敏 preview、duration、category、code，不记录 secrets/content 全文。

## 7. Error Feedback Design

### 7.1 现有字段继续是快速索引

保留：

- `error_code`
- `error_category`
- `error_message`
- `retryable`
- `recovery_options`
- `diagnostic`

新增 `errors[]` 是面向 Agent 的结构化解释，不取代索引字段。第一个 error 必须与顶层 code/category 一致。

### 7.2 Error stage

工具执行 Outcome 固定 stage：

- `input_validation`
- `policy`
- `authorization`
- `precondition`
- `execution`
- `verification`

`persistence` 与 `projection` 是 Outcome 交付阶段，不可能可靠写回已经失败的同一条工具 Outcome；它们进入独立 `OutcomeDeliveryError`/telemetry，并引用相同 correlation id。

### 7.3 Retry strategy

固定策略语义：

- `do_not_retry`
- `retry_same_input`
- `retry_after_backoff`
- `refresh_state_then_retry`
- `change_input_then_retry`
- `request_authorization`
- `prepare_runtime`
- `switch_tool`
- `manual_recovery_required`

`retryable=true` 不能单独出现，必须有 retry strategy 或 next action。`retryable=false` 禁止 FailureSupervisor 重新执行相同 signature；validation 失败仍应给出 `change_input_then_retry`，它表示修正参数后构建新 signature，不是重放同参调用。

定义声称 `requires_review` 时，执行路径必须实际进入可达的 review gate；如当前只有特定业务 review 通道，其他高风险动作必须 fail-closed，不能只在 metadata 中写“需审批”而实际被 capability lane 自动放行。

### 7.4 示例

```json

  "semantic_status": "failure",
  "error_code": "stale_file_revision",
  "error_category": "domain",
  "retryable": true,
  "operation": {
    "type": "text_edit",
    "target": "src/example.go",
    "side_effect_state": "none"
  },
  "errors": [
    {
      "type": "stale_file_revision",
      "category": "domain",
      "stage": "precondition",
      "cause": "File changed after it was read",
      "context": "expected sha256 differs from current sha256",
      "possible_fixes": ["Read the file again"],
```

## 8. Tool State Awareness

### 8.1 Baseline + delta

Runtime snapshot 继续提供 baseline：workspace、cwd、scope、platform、tool pool。Tool result 只返回本次操作观察到的 delta。

### 8.2 文件状态

文件读取：

- path、sha256、size、mtime；
- returned range、total lines；
- partial/truncated 与 continuation hint。

文件修改：

- created/updated/appended/moved/trashed；
- before/after digest；
- additions/deletions 或 replacement count；
- unified diff summary；
- recoverability；
- actual affected path，不使用 permission prediction 冒充已完成变化。

### 8.3 Git 状态

Git 状态是可选 observation：

- 只有工具或 runtime 明确执行过 git inspection 时才返回；
- 必须带 observation time/scope；
- 不将启动时 snapshot 冒充当前状态；
- 普通 file tool 默认返回 changed resources，不强制跑 git。

所有 observation 共用 `observation/observed_at/scope/source` provenance；未观察维度进入 `unobserved[]`，不得用零值暗示“干净”或“不存在”。

### 8.4 进程状态

Shell/long-running tool 可返回：

- process/session id；
- running/exited/timed-out/signaled；
- exit code；
- cwd；
- stdout/stderr truncation；
- continuation tool/id；
- env persistence contract。

### 8.5 环境变量

只返回变量名和变化类型，不返回 secret value。默认把未观察 env 标为 unobserved。

## 9. Registry 与 Interface

### 9.1 注册单元

目标是 Definition 与 Runtime 不能分开注册。兼容期仍接收 `Tool`，registry 立即生成 `RegisteredTool`：

```go
type RegisteredTool struct {
    Runtime    Tool
    Definition ToolDefinition
    Quality    DefinitionQuality
}
```

### 9.2 验证模式

- `compat`：legacy/external 可经 adapter 注册，记录 warning。
- `strict_builtin`：builtin 缺任一 v2 contract 直接失败。
- `strict_all`：未来用于受控插件/官方 MCP；第三方 MCP 仍允许 conservative adapter。

### 9.3 Output normalization

ToolRuntime 在唯一 finalize 点执行：

1. 使用 registry snapshot 中与模型展示相同的 input schema 做执行前校验，并保持 v2/MCP JSON object shape；仅显式 legacy 单值工具允许解包。
2. 统一 timing/truncation。
3. 合并真实 affected paths、artifacts、trash result。
4. 填充 schema version、operation、side-effect certainty；声明可变更但未观察到 delta 的成功结果必须是 `unknown`，不能猜成 `none`。
5. 对 strict definition 的 tool-specific `details` 执行 output schema verification；不匹配返回 `tool_output_schema_mismatch`，stage=`verification`，并保留已经发生的 partial/unknown side effects。

strict verification 必须位于终态发布门之前。直接调用与 transform 调用都必须遵循 `execute -> normalize/verify -> terminal progress -> artifact events -> audit`；任何 verification failure 只能发布 failed 终态，禁止先发 completed/ready artifact 再在最终 ToolResult 改口为 failed。
6. 从顶层 error/recovery 生成 `errors/next_actions`。
7. 添加带时间、scope 和 source 的 workspace/cwd partial observation。
8. 去重 changes 与 next actions。
9. 验证 envelope 不变量。

模型投影必须先深拷贝 canonical Outcome，避免 projection/normalization 改写 runtime truth；任意 typed map/slice 递归脱敏，结构化字段采用确定预算，超限返回仍可解析的 JSON truncation envelope。provider 原生 output-schema 功能与 Awaken runtime 的 details verification 是两层能力，不得混写。

Tool-specific `OutcomeEnricher` 可以增加精确 change/details，但不得覆盖真实 status/error。

## 10. Existing Tools Migration

### 10.1 第一批：协议真相

- MCP `IsError` 转为 failed Outcome。
- runtime truncation 同步 canonical Outcome。
- `needs_auth/needs_runtime` retryability 一致。
- permission/result affected paths 合并回 Outcome。
- v2/`OutcomeTool` 的 trash result 直接结构化，不解析 `content`；legacy adapter 仅为旧返回保守推断变化并标记 `ChangeInferred`。

### 10.2 第二批：Definition v2

优先显式迁移：

- `read_file / read_artifact`
- `list_files / grep_search / web_search`
- `text_edit / text_file_create / apply_patch / trash_file`
- `shell`
- `artifact_publish`
- `ask_user`

typed artifact tools 使用共享 catalog metadata 生成完整 definition 与经 validator 验证的 examples，并与其他静态 builtin 一样以 `strict_builtin` 注册；不可执行的 `execute=nil` stub 不注册、不暴露。

MCP：保留 raw input schema，映射 annotations；side effects/failure modes 无可靠 metadata 时标记 unknown，不编造事实。

Skill：when-to-use 进入 purpose/when；tool policy/requirements 进入 permissions；执行结果进入 Outcome adapter。

### 10.3 第三批：legacy result

9 个 legacy builtin 分批实现 OutcomeTool 或 Tool-specific error classifier。动态工具使用 source adapter，不能继续把业务失败当成功。

### 10.4 暂不做

- 不在本轮删除 legacy Execute。
- 不改用户历史 transcript。
- 不把空 artifact executor 宣称为已实现；本轮已将三个 `execute=nil` stub 从 catalog 隐藏。
- 不合并 artifact 工具名称，除非真实 transcript eval 证明必要。

## 11. 测试与评估

### 11.1 Static contract tests

- 所有 builtin resolved definition 完整。
- examples 通过 input validator。
- input schema 与 canonical output/details schema 可 JSON round-trip。
- annotation/side-effect/permission 无矛盾。
- model description 包含 purpose、use/not-use、effects、returns。
- 相邻工具边界测试：read file vs artifact、list vs grep、edit vs create vs patch vs trash、local vs web search。

### 11.2 Result golden tests

至少覆盖：

- success with no side effects；
- mutation applied；
- validation failed before start；
- permission denied；
- process nonzero；
- timeout；
- interrupted with unknown effects；
- partial mutation；
- MCP is_error；
- truncation/continuation；
- needs_auth/runtime；
- trash/change/artifact。

### 11.3 Cross-layer tests

- model/AG-UI 从同一 canonical Outcome 做受控投影，journal 当前持久化 canonical Outcome；各消费路径共有字段的事实值一致。
- model 只允许按声明的字段白名单省略、截断或脱敏；不得改变 status/error/side-effect 语义。
- journal restore 后 Outcome v2 不丢字段。
- AG-UI mapping 不从 content 猜状态。
- legacy v1/v2 transcript 仍可读。
- FailureSupervisor 继续使用 code/retry/recovery。

### 11.4 Tool selection eval

按 effective tool pool/feature flag 生成固定 prompt matrix；固定 model/provider、sampling 参数和 workspace fixture，每个 case 重复运行并保存 transcript：

| Prompt | 期望工具 | 禁止误选 |
|---|---|---|
| 读取 Go 文件片段 | read_file | read_artifact、shell |
| 预览 xlsx | read_artifact | read_file |
| 找出所有 Go 文件名 | list_files | grep_search |
| 搜索函数定义文本 | grep_search | list_files、web_search |
| 修改唯一字符串 | text_edit | apply_patch、shell |
| 新建 Markdown | text_file_create | text_edit |
| 多文件移动/高级 diff | apply_patch（仅当本次 tool pool 暴露） | text_edit |
| 删除文件 | trash_file | shell rm |
| 运行测试 | shell | local file tools |
| 查询当前公开信息 | web_search | grep_search |

评估记录 tool calls、参数合法率、无必要调用数、恢复路径和最终完成率。验收阈值为：确定性 contract cases 100% 参数合法；每个 selection case 至少 5 次、首选工具正确率 >= 80%、禁止工具误选率 <= 10%、失败恢复完成率 >= 80%。样本不足时只报告 smoke，不宣称 statistically proven。不能只以 description 字数判定成功。

### 11.5 真实 Desktop

必须按根 README：

```bash
npm run close:desktop
npm run open:desktop
```

在 Awaken Desktop UI 中执行选择矩阵的最小 smoke，并验证：

- 工具选择正确；
- 模型结果能看到 operation/change/error/next action；
- 成功、失败、neutral、needs-runtime 不混淆；
- 失败后模型换策略而非原样重试；
- 重启后 ToolResult 语义不漂移。
