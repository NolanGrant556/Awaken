# 项目生命周期与删除：产品与状态机

## 三个动作

| 动作 | 项目 | Awaken 历史 | 磁盘目录 |
|---|---|---|---|
| 从 Awaken 移除 | `removed/detached` | 保留 | 保留 |
| 删除 Awaken 历史 | 保持 `active` | 逻辑删除并后台清理 | 保留 |
| 移到废纸篓 | `trash_pending -> removed/trashed` | 系统废纸篓成功后删除 | 进入系统废纸篓 |

项目状态以 Desktop 全局 SQLite 为唯一真相。Thread 的 `workspaceRoot` 只描述历史关联，不能激活 tombstone 项目。

## 删除状态机

- `active`：可创建和运行会话。
- `removed`：从侧栏隐藏；重新添加同一路径才允许显式恢复。
- `trash_pending`：禁止新 run，等待 active run 取消、系统废纸篓和 finalize。

所有修改动作必须幂等。业务成功以逻辑事务提交为准；JSONL 和附件通过 durable cleanup job 重试，不能因为物理清理暂时失败而让 UI 复活。

Renderer 收到 `trash_and_purge` operation 后不得用固定超时推断结果。未终态 operation ID 会持久化到本地 tracker，并在后台低频轮询 durable operation：只有成功且项目已离开 `trash_pending` 时才保持移除；明确失败且项目已恢复 `active` 时必须立即重新展示项目并恢复原有展开状态。operation 查询或项目刷新暂时失败时继续跟踪，不能丢弃 tracker，也不能删除或隐藏历史。

## Trash 两阶段约束

Prepare 阶段只保存 path fingerprint、thread cutoff 和 operation，不删除历史。运行停止后，Core 先把原目录原子改名到同盘 operation 专属 staging，并在改名后再次复验文件身份；staging 中仍保留原文件夹名。Electron Main 只把这个 staging 路径交给系统废纸篓，绝不再按原路径删除。`begin-trash` 在系统调用前持久化当前 attempt；只有 staging 确认消失后才能在同一事务中 tombstone 项目、soft-delete cutoff threads 并创建清理任务。系统调用明确失败时 Core 原子恢复原目录，项目与历史保持不变；若原路径已被另一个目录占用则 fail closed，不覆盖、不删除新目录。
