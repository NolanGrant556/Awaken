# 模型配置与调用

## 1. 权威范围

本文是 Awaken 当前模型配置与调用链的权威说明，负责：

- Desktop 中供应商和模型 profile 的用户入口；
- provider catalog、profile 唯一性、默认/启用状态；
- 模型能力的静态值、动态覆盖和运行参数归一化；
- 连接测试与余额查询；
- Desktop 创建 run 时如何把 profile 注入本机 Core；
- provider 错误分类与敏感信息边界；
- 当前支持、不支持、异常恢复和验收。

API key 密文格式、safeStorage 状态机与恢复契约由 [安全凭据存储与恢复契约](./安全凭据存储与恢复/架构与恢复契约.md) 唯一拥有。Agent 的上下文与 thread 生命周期由 [主智能体闭环](../02_主智能体闭环/索引.md) 定义；本文只说明模型配置如何进入一次 run。

## 2. 用户入口与产品流程

### 2.1 配置模型

正式入口为 Desktop 设置中的 `Models`：

1. 用户打开设置并进入模型配置。
2. Desktop 主进程返回当前 provider catalog 和已保存 profiles。
3. 用户展开一个 provider，选择或填写 model ID、Base URL 和 API key。
4. `测试连接` 只验证当前表单/既有凭据能否访问 provider，不等于保存。
5. `提交` 先完成安全加密，再原子写入 profile store；只有两步都成功，UI 才显示“模型配置已安全保存”。
6. 已配置模型页负责启用/禁用、默认模型、上下文长度和输出上限。

新增同一 `providerId + modelId` 的第二个 profile 会失败；携带同一 profile `id` 的提交是更新。为同一 provider 新增其他 model 时，可以通过 `templateProfileId` 复用已保存凭据，Renderer 不读取该凭据明文。

### 2.2 使用模型

用户从 workbench 提交 prompt 时：

```text
Composer
  -> Renderer RuntimeClient.startRun
  -> Preload bridge
  -> Electron Main IPC awaken:start-run
  -> ModelProfileStore.resolveDefaultRunProfile
       -> 选择 enabled default，或首个 enabled profile
       -> async safeStorage 解密
       -> 归一化 provider/model/advanced 参数
  -> run 创建 API（method/path 见 09 协议域），body.model_profile 携带当次运行配置
  -> Go RunService
  -> AgentConfig.ModelConfig
  -> LLM transport
```

如果没有可用 profile，Desktop 在创建 run 前返回“请先在设置 > 模型中配置可用模型”。如果 profile 没有 key，返回“请先在设置 > 模型中配置 API key”。凭据暂不可用或不可读时，由 Desktop 结构化操作错误承载恢复动作，run 不会进入 provider transport。

这里存在一条必须显式记录的传播边界：Desktop 和 Go 的 `model_profile` wire 能接收 `prompt_cache_key`、`supports_vision` 和 `supports_video`，但 `cmd/awaken-core/main.go` 的 `modelConfigFromProfile` 当前只把 API key、Base URL、model、protocol、temperature、max tokens、auth scheme 和 context window 写入 `AgentConfig.ModelConfig`。因此：

- `temperature`、`maxTokens` 和 `contextWindow` 已进入当前 Agent/LLM 配置；
- `promptCacheKey` 当前只参与 thread 的 profile cache identity，没有进入 LLM transport；
- `supportsVision` / `supportsVideo` 当前是 Desktop 侧保存、展示和能力同步元数据，没有进入 Core 的模型能力 gate。

不得仅根据 wire 字段存在，就宣称后三项已经端到端生效。

### 2.3 查看余额

Workbench 顶部的余额入口调用主进程统一查询。当前：

- DeepSeek：读取 `/user/balance`，展示金额及赠送/充值拆分。
- Kimi Coding Plan：读取 `/usages`，展示周额度与可识别的 5 小时窗口。
- Kimi CN、火山 Coding Plan：明确返回“不支持查询该供应商余额”。

余额按 provider 复用一次解密结果和一次请求，再投影到该 provider 的各个 enabled profile。当前实现具体选择同 provider 的第一个 enabled profile 的 credential 与 Base URL；同 provider 其他 profile 即使保存了不同 key 或 Base URL，也不会单独查询，而会收到首项结果。这是已知限制，当前没有数据不变量阻止这种配置。凭据层故障会折叠成一个全局恢复提示，不能伪装成 provider `401`。

## 3. 当前支持与不支持

### 3.1 当前 provider catalog

Desktop 产品路径的 catalog owner 是 `apps/desktop/src/main/model-profile-store.ts`。Go 的 `src/modelprofile/registry.go` 还为 Core API 提供一份非敏感目录；两处目前没有共享生成源或完整 parity test，不能宣称完全同步。已知漂移是 `volcengine`：Go 当前为 `CodingPreset=true`，Desktop catalog 没有 `coding_preset`，归一化后为 false。修改任一目录时都必须显式比较两份定义。

| Provider ID | 展示名 | 默认 Base URL | 默认模型 | 模型输入 | 连接测试 | 余额 |
| --- | --- | --- | --- | --- | --- | --- |
| `deepseek` | DeepSeek | `https://api.deepseek.com` | `deepseek-v4-pro` | 目录选择 | `GET /models` | 支持 |
| `kimi-cn` | Kimi CN | `https://api.moonshot.cn/v1` | `kimi-k2.6` | 目录选择 | `GET /models` | 不支持 |
| `kimi-coding-plan` | Kimi Coding Plan | `https://api.kimi.com/coding/v1` | `kimi-for-coding` | 固定目录 | 最小 `POST /chat/completions` | 支持 |
| `volcengine` | 火山 Coding Plan | `https://ark.cn-beijing.volces.com/api/coding/v3` | `ark-code-latest` | 建议列表并允许自定义 ID | 最小 `POST /chat/completions` | 不支持 |

四个 provider 当前都使用 `openai_chat` 与 bearer auth。目录中的 API key 环境变量名只用于表单提示和兼容配置语义，Desktop 保存路径仍是全局安全凭据 store。

### 3.2 Profile 能力

Profile store 与 Desktop UI 当前支持：

- 同一 provider 配置多个不同 model；
- 一个全局默认 profile；
- enabled/disabled；
- 自定义 Base URL；
- 保存和编辑 `temperature`、`maxTokens`、`contextWindow`、`promptCacheKey`；
- 保存、展示和动态同步 `supportsVision`、`supportsVideo` 能力元数据；
- 静态能力目录与 provider `/models` 返回的动态覆盖；
- provider/model 规范化与上下文/输出上限 clamp；
- 读取时对旧 profile 的 Base URL 与能力默认值做兼容归一化。

只有 `temperature`、`maxTokens` 和 `contextWindow` 已从上述 advanced 字段继续传播到 `AgentConfig.ModelConfig`。`promptCacheKey` 和两个输入能力位的端到端缺口见 2.2；读取时归一化也不等于自动把新默认值持久化回文件。

当前不支持：

- 同一 `provider + model` 存在多个 profile；
- workspace 或 thread 私有的 API key；
- 运行中热切换当前 thread 的 profile；
- 在 input composer 中上传视频。`supportsVideo` 当前只保存能力位；
- 用 `supportsVision` / `supportsVideo` 在 Core 或 composer 形成可靠的端到端输入 gate；
- 把 `promptCacheKey` 传给 provider transport；
- 为所有 provider 查询余额；
- 通过 Renderer 直接读取、导出或复制已保存 API key；
- 把连接测试成功当作完整真实 Agent run 验收。

## 4. 数据模型与持久化

### 4.1 Profile 与能力文件

Desktop 通过 `ModelProfileStore` 持久化 profile，并单独持久化模型能力覆盖。稳定 userData 身份、profile 文件位置和 credential envelope 只由 [安全凭据存储与恢复契约](安全凭据存储与恢复/架构与恢复契约.md) 定义；本文只拥有非敏感 profile schema、规范化和调用语义。

`model-profiles.json` 顶层 schema 为 version 1。每个 profile 包含：

```text
id
providerId
displayName
modelId
baseURL
protocol
authScheme
enabled
isDefault
advanced
credential          # 仅密文 envelope
```

`ModelProfileStore` 使用临时文件加 rename 原子替换；损坏 JSON 会向上报错，不会被当作空 store 覆盖。所有写操作经进程内 mutation queue 串行化。

### 4.2 Profile 规范化

每次读取和写入都会：

1. 以 `providerId + normalized modelId` 去重；对既有重复项保留靠后的 profile，并从旧项补齐 credential/default 等有效字段。
2. 保证至多一个 default；默认 profile 被删除时，剩余首项成为 default。
3. disabled profile 不能保持 default。
4. provider 不允许自定义 model 时，未知 model 回落到 provider default。
5. Kimi Coding Plan 旧 Base URL `https://api.kimi.com/coding` 归一为 `/coding/v1`。
6. 火山旧 `/api/v3` 归一为 `/api/coding/v3`。

去重逻辑是兼容既有数据的读取策略，不授权 UI 新建重复 profile。

### 4.3 Renderer 可见摘要

Renderer 只接收非敏感摘要：

- profile 基本字段与 advanced；
- `has_key`；
- `masked_key`（当前实现来自密文 envelope 的 `last4`）；
- `profile_status`。

`profile_status` 的枚举、转移与恢复动作只由 [安全凭据存储与恢复契约](安全凭据存储与恢复/架构与恢复契约.md) 定义。本文只规定调用链消费非敏感摘要，不重新定义凭据状态机。

## 5. 模型能力与运行参数

### 5.1 能力来源

能力合并顺序为：

```text
内置 MODEL_CAPABILITIES
  -> 已持久化 model-capability-overrides.json
  -> 本次 provider /models 返回的可解析字段
```

动态覆盖支持解析：

- `context_window` / `max_context_length` / `context_length` / `num_ctx`
- `max_output_tokens` / `max_tokens`
- `default_max_tokens`
- `default_temperature` / `temperature`
- `supports_vision`
- `supports_video`

打开模型设置时，UI 先使用静态/既有数据，再 best-effort 同步 provider 能力。单 provider 失败或返回未知 schema 不阻断设置页；已保存覆盖继续可用。

### 5.2 参数归一化

`normalizeAdvancedWithModelCapability` 负责：

- 用用户显式值覆盖目录默认；
- 缺省时填充 context/output/temperature/输入能力；
- 将 context 和 max output clamp 到已知上限；
- 独立合并 `supportsVision` 和 `supportsVideo`；主进程当前不强制 video 依赖 vision；
- 火山自定义 model 使用保守默认：256,000 context、32,000 output。

Renderer 的设置表单会在用户交互层阻止“video=true 且 vision=false”，但这不是 store/Core 不变量，直接或遗留数据仍可能形成该组合。当前代表性默认由各自代码和测试锁定；文档不复制完整 model 清单，以避免形成第三套定义。修改目录时必须同时更新 `model-capabilities.test.ts`、`registry_test.go`，并补做 TS/Go catalog parity 核对。

## 6. 连接测试、能力同步和余额

### 6.1 连接测试

连接测试使用表单输入的 key；未输入时可读取正在编辑的 profile 或同 provider template profile 的既有凭据。超时为 8 秒。

- DeepSeek/Kimi CN：`GET <baseURL>/models`；成功后尝试解析并持久化能力覆盖。
- Kimi Coding Plan/火山 Coding Plan：发送 `max_tokens=1` 的最小 chat completion；Kimi 固定 `temperature=1`。

错误只返回按 HTTP status 分类的中文提示或统一网络/超时提示，不向 Renderer 透传 Authorization header 或 provider 原始 body。

### 6.2 余额

余额请求超时为 8 秒，支持外部取消信号。状态为：

```text
available | unavailable | missing_key | error | unsupported
```

`credential_issue` 只允许：

```text
temporarily_unavailable | unreadable
```

余额组件优先展示全局凭据恢复，再展示各 profile 金额、额度或业务错误。

同 provider 的查询当前不按 credential/Base URL 分组，而是使用第一个 enabled profile 代表整个 provider。需要逐 profile 精确余额前，必须先修改这一实现和测试。

## 7. Provider 调用与错误边界

### 7.1 RuntimeInfo

Core runtime info 动作（method/path 见 09 协议域）只暴露：

- configured model；
- protocol；
- `has_api_key` boolean；
- provider host；
- runtime/API version 与默认 workspace。

它不返回完整 Base URL 或 API key。Desktop 产品路径会用当前默认 profile 摘要补充显示；Core 的 wire authority 见 09 域。

### 7.2 Run 错误

Agent Core 将：

- `llm.ErrMissingAPIKey` 映射为 `PROVIDER_AUTH_MISSING`；
- `llm.ErrRequestFailed` 映射为 `PROVIDER_REQUEST_FAILED`。

LLM transport 对错误做以下处理：

- transport error 和 request-build error 使用固定脱敏文案，不包含 URL；
- non-2xx 最多读取 4 KiB body；JSON 尝试提取 `error`、`message` 或 `error_description`，非 JSON 则保留截断后的纯文本再做启发式脱敏；
- Authorization、bearer、API key、token、secret 及 `sk-`/`ak-` 模式会被替换为 `[redacted]`；
- UI 可显示 status 与已脱敏 message，但不能显示完整 provider body。

错误脱敏是纵深防御，不等于可以把任意下游响应当作安全日志。新增 provider 格式时必须先补泄密回归测试。

## 9. 异常与恢复

| 场景 | 当前行为 | 恢复 |
| --- | --- | --- |
| 无 enabled profile | run 创建前失败 | 到 Models 启用/新增 profile |
| profile 无 key | run 创建前失败 | 在 Awaken 内输入并安全保存 |
| safeStorage 临时不可用 | 保留密文，结构化 `credential_temporarily_unavailable` | 受控 relaunch |
| 密文无效/不可读 | `unreadable`，不删除旧记录 | 在 Awaken 内重新录入；macOS 系统认证异常先按凭据契约分类 |
| provider 401/403/429/5xx | 凭据已解密并已进入 provider 层 | 按连接测试、余额或 run 的 provider 错误处理 |
| capability sync 失败 | 保留静态/既有覆盖 | 后续打开设置重试；不阻断配置 |
| store JSON 损坏 | 读取/写入失败，原文件保留 | 停止写入并修复数据；不得当作空配置 |
| 更新 key 加密失败 | 新 key 不写盘，旧 profile 字节保持 | 处理安全存储状态后重新提交 |

## 10. 验证

### 10.1 自动化

最小相关测试：

```bash
npm --workspace @awaken/desktop run test -- src/main/model-profile-store.test.ts src/main/model-capabilities.test.ts src/main/model-balance-fetchers.test.ts src/main/secure-credential-store.test.ts src/main/desktop-operation.test.ts
go test ./src/modelprofile/... ./src/llm/... ./src/agentcore/... ./src/server/... ./src/runtime/... ./cmd/awaken-core
npm run typecheck:desktop
```

必须覆盖：

- 两份 catalog 的各自默认值，以及 TS/Go 显式 parity；当前 `volcengine.coding_preset` 漂移在修复前必须作为失败项报告；
- duplicate、default、disabled、template credential；
- 原子保存、损坏 store 保全、并发迁移不覆盖新 key；
- capability 默认值、clamp、动态解析，以及 advanced 字段到 Core/AgentConfig 的实际传播边界；
- DeepSeek/Kimi 余额解析、错误及“同 provider 首个 enabled profile”复用限制；
- run error code 与 URL/body/secret 脱敏。

### 10.2 真实 Desktop

从根 README 正式入口启动，只使用专用测试 profile：

1. 打开 Models，确认四个 provider 与已配置列表。
2. 新增或更新测试 profile；先测试连接，再提交。
3. 完整重启 Desktop，确认 profile/default/enable/能力仍在。
4. 对支持 provider 查看余额；对不支持 provider 确认明确“不支持”。
5. 发送最小真实 prompt，确认请求越过凭据层并收到 provider 结果。
6. 检查 Renderer、运行日志和 transcript 不含 key、密文、完整 Base URL 或 Authorization。

故障注入与 macOS Keychain lock/unlock 不属于日常 smoke，必须按 [安全凭据存储与恢复契约](./安全凭据存储与恢复/架构与恢复契约.md) 和专用 QA 案例执行。
