## Awaken 当前接入

- 普通 API：provider ID `minimax`；Token Plan：`minimax-token-plan`。
- 中国区 OpenAI Base：`https://api.minimaxi.com/v1`；Messages Base：`https://api.minimaxi.com/anthropic`。
- 两个入口当前都公开 Chat、Responses、Messages；Key 与计费入口分开。
- 默认模型从 Awaken provider catalog 读取；目录从中国区 `/v1/models` best effort 同步。

## 三协议兼容矩阵

| 协议 | 官方合同 | Awaken 当前 | 结论 |
| --- | --- | --- | --- |
| Chat Completions | 有 | API 与 Token Plan 已接入 | 支持 |
| Responses | 有 | API 与 Token Plan 已接入 | 支持；继续核对当前官方 schema |
| Messages | 有 Anthropic 兼容 | API 与 Token Plan 已接入 | 支持；Base 和 auth scheme 与 OpenAI 路径不同 |

## 鉴权、端点与模型

- Chat/Responses 使用 Bearer；Messages 在 Awaken 当前 route 使用 `x-api-key`。
- 中国区与国际区 endpoint、Key、模型和套餐不保证互通；当前内置入口固定中国区。
- Chat `POST /v1/chat/completions`；Responses `POST /v1/responses`；Messages `POST /anthropic/v1/messages`。
- 目录条目出现不代表三协议和全部多模态都支持；按模型/API 页收窄。

## 上下文、多模态与工具

- MiniMax-M3 官方 Chat/Message 示例包含图片，模型页还说明视频和长上下文；Awaken 必须逐协议核对 lowering。
- 当前 Chat adapter 发送 `reasoning_split:true`，把 `reasoning_details` 或前导 `<think>` 统一为 reasoning delta。
- Messages 的 thinking block/signature、tools 和 stream 由 Anthropic adapter 处理。
- 原生 PDF 只有官方 exact protocol 明确支持 document/PDF block 时才可标记；图片能力不等于 PDF。

## 提示词缓存

- OpenAI 兼容路径有官方 Prompt 缓存文档，usage 可返回 `prompt_tokens_details.cached_tokens`。
- Messages 路径有 Anthropic 兼容的 `cache_control` 和 cache read/creation usage。
- 当前 Awaken exact prompt-cache registry 尚未为 MiniMax 内置入口建立专属合同；即使 profile capability 声明支持，也需验证请求字段和 usage 后才能宣称当前完整支持。
- API 与 Token Plan 的缓存 identity 必须分开，不能复用同模型前缀。

## 推理开启关闭

- MiniMax-M3 使用 `thinking.type`，省略时可能默认 adaptive；M2.x 的关闭能力不同。
- `reasoning_split` 只改变输出分离格式，不负责开启/关闭 thinking。
- 当前 Awaken 把 MiniMax thinking 开关视为独立能力，不在 Composer 伪造成 effort 档位。

## 推理强度

- 当前官方 M3 Chat 文档以 thinking 模式为主，未建立可映射成 Awaken `low | high | max` 的稳定三档参数。
- 因此 Awaken 当前 MiniMax M3 不展示 reasoning effort；不要把 adaptive/disabled 映射成 low/high/max。
- 官方若新增 effort，需按 Chat、Responses、Messages 分别验证位置、默认值和 stream 行为。

## 用量、余额、限流与套餐

### 用量查询合同

- A 类：per-request usage、缓存 token 和 service tier 按对应 API 页解析。

#### 普通 MiniMax API

- 用户入口与身份：用户在“MiniMax API”卡片填写普通按量 API Key，Awaken identity 为 `provider_id=minimax`。推理按实际 token 消耗开放平台账户余额。
- A 类数据：Chat、Responses、Messages 的响应 usage 只描述单次请求的 input/output/cached 等 token，不等于账户余额或套餐剩余量。
- B 类候选：MiniMax 官方 CLI 对 `sk-api-` 普通 API Key 请求 `{api-region-base}/account/query_balance`，Bearer 鉴权，读取 `available_amount` 及现金、代金券、授信和欠款等字段。该路径来自厂商一方实现，尚未形成与 Token Plan FAQ 同等级的公开 API reference；Awaken 接入前必须用真实中国区/国际区账户固化响应 schema、币种、空值和错误语义。
- Awaken 当前状态：尚未自动调用普通 API 的账户余额查询。因此 UI 可以显示已记录的逐次 usage，但不能显示 5 小时/周额度；余额区应说明当前未接入并提供开放平台余额/账单入口。

#### MiniMax Token Plan / Coding Plan

- 用户入口与身份：用户在“MiniMax Token Plan”卡片填写订阅 Key，Awaken identity 为 `provider_id=minimax-token-plan`。官方明确说明订阅 Key 与普通按量 API Key 相互独立、不能混用。
- B 类合同：`GET /v1/token_plan/remains` 使用 Token Plan subscription key 和 Bearer 鉴权；官方 FAQ 明确公开，返回当前窗口、周窗口、重置时间及可选积分/boost 等套餐指标。
- 查询 host：中国区官方示例为 `https://www.minimaxi.com/v1/token_plan/remains`，国际区为 `https://www.minimax.io/v1/token_plan/remains`。这是管理查询合同，不从推理 Base URL 自动拼接。
- Awaken 当前状态：已接入，复用用户保存的套餐 Key 解析 `model_remains`。文字模型 profile 只读取 `model_name=general`，展示“5 小时额度”和“周额度”；`video` 等非文本资源桶留给媒体工具自己的用量入口。计数型窗口显示 usage/total，时间型窗口使用官方 remaining-percent 字段，避免把 `0 / 0` 误报成零额度。2026-08-11 中国区真实账户返回 `current_interval_status=1`、`current_weekly_status=3`，且控制台对应显示 5 小时有限、周额度无限；Awaken 因此把 `status=3` 保留为无限语义。

#### 路由与错误不变量

- 先按 `provider_id + access_type + region + credential_scope` 选择查询合同；不能从模型名、推理协议、Base URL 或一次连接测试结果猜测 Key 类型。
- `minimax` 不请求 `/v1/token_plan/remains`；`minimax-token-plan` 不请求 `/account/query_balance`。一个端点失败时不得拿同一 Key 自动试另一个端点。
- 401/403/404 优先表达凭据类别、区域、权限或套餐不匹配，不能显示成余额或额度为 0；429 保留查询限流语义。
- 旧 profile 无法确定凭据类型时让用户重新选择入口，不只依赖官方 CLI 的 `sk-api-` 前缀识别。
- 普通 API 余额与 Token Plan 套餐窗口使用独立缓存 identity；不能把套餐快照投影到普通 API 卡片。

- `service_tier=priority` 可能改变准入和价格；没有显式产品需求时不要偷偷开启。
- Token Plan 的周期、额度、并发和支持工具/模型以当前计划页与 FAQ 为准；不能按 API token 价格折算。
- 中国区与国际区价格、Key 和余额不混用；易变数字只在带日期的验收记录中引用。

## Awaken 落地规则

- `minimax` 与 `minimax-token-plan` 是两个 credential/计费 identity，即使 Base URL 相同也不共享 profile cache。
- 继续保留三协议独立连接测试；一个协议成功不能证明另两个。
- Chat reasoning 分离需要覆盖跨 SSE chunk 的 `<think>` 状态机和 `reasoning_details` 去重。
- Responses 官方页不可达或 schema 变化时标为待复核，不能只靠 Chat 的兼容性推断。
