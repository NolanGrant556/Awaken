# 定时任务设计契约

## 1. 文档状态与目标

本文是 Awaken 定时任务的设计契约与当前实现依据。首版已按切片 A–E 落地。

**当前支持（首版）：** 左侧一级入口、循环/日程任务、10 个内置模板、创建/编辑/启停/删除/立即执行/取消、专属线程、最近 50 条执行历史、Core 内调度器与 misfire 恢复、Agent 与固定提醒两类任务。固定提醒以 `AWAKEN_SCHEDULED_NOTICE` 进入专属线程并在 Desktop 运行时触发原生通知，不伪装成模型回复。

**已确认并已在首版实现的目标：**

1. 左侧一级导航在“技能”正下方增加“定时任务”，顺序固定为“连接器 → 技能 → 定时任务”。
2. 支持五段式 Cron 循环任务和指定时间的日程任务；日程任务可以不重复、按天重复到截止时间或按次数结束。
3. 支持创建、编辑、启停、删除、立即执行、取消当前执行和查看最近执行记录。
4. 复刻 Qwenpaw 的“从模板创建”主流程与 10 个内置模板：选模板只预填编辑器，用户确认保存后才创建任务。
5. Agent 任务复用 Awaken 当前 RunService、模型 profile、TaskScope、工具/Skill、SemanticJournal 和项目线程；不建立第二套 Agent loop。
6. 固定提醒不调用模型，不伪造成 assistant 回复；它以 host-owned 定时提醒事件进入专属线程，并在 Desktop 运行时触发原生通知。

## 2. Qwenpaw 参考结论与 Awaken 适配

参考代码位于 `/Users/frank/Documents/project/Qwenpaw`。核心实现包括：

- `src/qwenpaw/app/crons/models.py`：任务、调度、投递、运行参数、状态和执行记录；
- `manager.py`：调度器生命周期、启停、立即执行、misfire、并发和历史；
- `executor.py`：固定文本和 Agent 两类执行；
- `repo/json_repo.py`：`jobs.json` 与每任务历史；
- `api.py`：CRUD、pause/resume/run/state/history；
- `console/src/pages/Control/CronJobs/`：列表、日历、编辑抽屉、模板选择与 10 个内置模板。

复用的是产品行为和边界，不复制 Python/React 实现。两边概念映射如下：

| Qwenpaw | Awaken 目标 |
|---|---|
| APScheduler | Core 内 `src/scheduledtask` 调度服务；Cron 解析采用 Go 依赖 |
| agent/channel/user/session | project + 每任务稳定专属 thread |
| console/inbox | 专属 thread + 独立执行历史；提醒额外发 Desktop 原生通知 |
| `jobs.json` | 当前 FileStore generation 下的 journal-first authority |
| 前端模板返回 API payload | Renderer 拥有内置产品模板，转换为受控编辑表单；Core 重新校验全部字段 |
| request 中携带运行参数 | 任务只保存 profile ID、project ID 和用户配置；凭据及真实 workspace 在每次触发时由 Core 解析 |
| `tool_safety` 可关闭审批 | Awaken 沿用当前零审批工具合同；需要用户交互的无人值守调用 fail fast |
| `share_session` | 初版固定为每任务一个稳定专属线程，同一任务历次执行共享、不同任务隔离 |

不能直接搬用的行为：

- Awaken 没有 Qwenpaw 的 channel/inbox authority，不能把 `channel/user_id/session_id` 硬塞进 Renderer 或 Connector。
- Awaken 的模型凭据由 `~/.awaken/config/models.json` 与 `~/.awaken/.env` 管理，定时任务定义不得保存 API key、Base URL 快照或完整模型配置。
- Awaken 的 workspace/项目边界由 Core FileStore 解析，定时任务不得保存可绕过项目变更的旧路径权限快照。
- Awaken 的 Desktop 关闭时 Core 也停止；首版不承诺应用退出后由操作系统唤醒执行。

## 3. 产品范围

### 3.1 首个可交付版本

首版必须同时交付：

- 左侧一级入口；
- 空状态、任务列表和状态汇总；
- 普通创建与从模板创建；
- 循环/日程表单；
- 项目、任务类型、内容、时区、profile、超时和漏跑宽限配置；
- CRUD、启停、立即执行、取消当前执行；
- 最近 50 条执行记录；
- 每任务稳定专属线程和从执行记录打开线程；
- Core 重启恢复、misfire、单任务防重入和全局并发上限；
- Agent 与固定提醒两种任务；
- 10 个模板及动态未来时间默认值；
- 自动化测试和真实 Desktop 视觉证据。

### 3.2 首版明确不支持

- Desktop 完全退出后由 launchd、Task Scheduler 或其他 OS 后台服务唤醒；
- 多设备、云端或团队同步；
- 秒级 Cron、Quartz 特殊字符、自然语言直接生成表达式；
- 同一任务并发执行多个 Agent run；
- 用户保存自定义模板、模板市场、模板导入导出；
- 任意 Connector/channel 作为直接投递目标；
- 把现有普通线程选为写入目标；
- 对漏掉的多个周期逐条补跑；
- 未经独立安全设计的“忽略工具边界”“自动回答 ask_user”或自动完成外部授权。

### 3.3 后续增强

列表和模板闭环验收通过后，可以增加 Qwenpaw 同类的月历视图。月历只投影 `calendar` 日程任务的未来 occurrence，点击项目仍打开同一编辑器；它不是第二份任务 authority。该增强不阻塞首版“从模板创建”。

## 4. Desktop 产品行为

### 4.1 入口与页面

`apps/desktop/src/renderer/App.tsx` 的一级导航目标顺序：

```text
连接器
技能
定时任务
```

“定时任务”使用图标库的 `calendar-clock` 图标，`activeNavId="scheduled-tasks"`。选择后中间内容区显示独立 `ScheduledTasksView`；它与 `ExtensionsView` 平级，不塞入 Connector 或 Skill section。切换页面不得改变当前项目、活动 thread 或进行中的 run。

页面顶部：

- 标题“定时任务”；
- 说明“按计划自动执行提醒或 Agent 任务；Awaken 退出期间不会运行”；
- 主按钮“创建任务”；
- 次按钮“从模板创建”；
- “刷新”动作。

列表每项至少显示：

- 名称、类型（提醒/Agent）、所属项目；
- 人类可读计划和时区；
- 启用状态；
- 下次执行时间；
- 最近一次状态和时间；
- “立即执行”“执行记录”“编辑”“删除”；
- 运行中时显示“取消执行”，而不是再次运行。

空状态必须同时提供普通创建和模板创建，不展示静态假任务。

### 4.2 普通创建

编辑器按以下顺序组织：

1. **基本信息**：名称、启用；
2. **运行位置**：通过单一下拉选择器选择一个 active project，候选项目在弹层内可搜索、可滚动，不随项目数量扩展表单高度；零文件夹项目允许选择；
3. **调度**：
   - 循环任务：每小时、每天、每周、自定义五段 Cron；
   - 日程任务：开始时间、是否重复、每 N 天、永不结束/截止时间/限定次数；
   - IANA 时区，默认读取系统时区；UI 使用自有中文可搜索选择器，主文案和列表不直接暴露 IANA ID，按计划日期计算中文偏移，但保存值仍是原 IANA ID；
   - 日程日期时间使用 Design System 自有中文日历与小时/分钟控件，draft 仍输出 `YYYY-MM-DDTHH:mm`，不得回退为 Chromium 原生 `datetime-local` 弹层；
4. **任务内容**：
   - `reminder`：固定提醒正文；
   - `agent`：给 Awaken Agent 的 prompt；输入框复用首页 Composer 的 `/` Skill 目录、筛选、键盘选择和结构化 token 展示，目录仍只展示所选项目范围内 `loaded && userInvocable != false` 的 Skill；
   - Slash 选择保存结构化 Skill identity，不把 Skill 名称扁平化进 prompt；提醒正文不显示 Slash 菜单，也不能保存 Composer token；
5. **模型**：任务可保存一个显式 profile ID；留空时按“`scheduled_task` 用途 profile → 当前默认 ready profile”在每次触发时重新解析。候选项消费与 Composer/设置相同的 enabled/ready 目录，前端只显示实际 model ID，不附加 Chat、Responses 或 Messages 等协议文案；选择值仍使用 opaque profile ID，因此展示简化不会改变任务绑定和协议执行。选择器复用 Design System 的视口自适应规则；
6. **高级选项**：超时秒数、misfire 宽限秒数；
7. **提交**：“取消”“保存任务”。

视觉层级使用单一滚动 body、细分隔线和固定 footer；任务内容是主要编辑区，模型与高级选项默认折叠。Design System 只改变表现和 draft 交互，不改变 Core schedule、Renderer RFC3339 转换或保存协议。

首版每任务最大并发固定为 1，不在 UI 暴露伪可配的 `max_concurrency > 1`。全局最多同时执行 2 个 Agent 定时任务；额外到期项进入有界队列，超过其 misfire 宽限后记为 skipped。

### 4.3 从模板创建

点击“从模板创建”打开宽度约 860px 的模板窗口：

- 顶部文案“先选内置模板，再在编辑器里微调关键参数后保存”；
- 分类只包含“循环任务”和“日程任务”；
- 模板卡展示名称、说明、频率和“使用模板”；
- 选择模板后关闭模板窗口，打开与普通创建相同的编辑器；
- 模板只预填字段，绝不自动调用创建 API；
- 用户可以修改名称、时间、项目、profile 和正文；
- 新任务保存 `template_origin`，后续编辑不再受模板变更覆盖。

Qwenpaw 的固定 2026 年 1 月日期在当前时间已经可能过期，Awaken 不能照抄成不可执行数据。Awaken 保留模板形态和内容，但在用户每次选择时基于所选时区生成严格晚于当前时间的默认值。

### 4.4 编辑、启停、删除和立即执行

- 启停使用 version CAS；乐观 UI 失败后回滚 Core 返回的真实状态。
- 编辑只影响后续触发；已经开始的 execution 使用开始时快照。
- 任务运行中禁止删除；先取消或等待结束。删除需要确认并创建 tombstone，UI 立即从 active 列表移除。
- “立即执行”需要二次确认，允许对暂停任务执行，不消耗日程任务的重复次数。
- 同一任务已经运行时，新的 idempotency key 返回 `TASK_ALREADY_RUNNING`，不能悄悄排第二次；相同 key 的网络重试返回原 execution，即使 worker 仍在收尾也不得随机冲突。
- 打开执行记录显示最近 50 条，按 `scheduled_for/started_at` 倒序；错误只显示清洗后的 code/message。

### 4.5 专属线程

- 每个任务第一次执行时由 Core 建立稳定专属 thread，`source="scheduled_task"`，项目归属为任务的 `project_id`。
- `StartScheduledRun` 一旦返回真实 `run_id/thread_id`，executor 必须在等待 terminal 之前报告启动身份；Scheduler 立即绑定 task ↔ thread、以同一 execution ID 追加 running-with-identity 记录并发布携带 `project_id/run_id/thread_id` 的 `execution_started`。
- 专属 thread 名称使用任务名；任务重命名后同步 thread 标题，但用户后来手工改过标题时不覆盖。
- 同一任务历次执行继续同一 thread，以便 Agent 使用该任务自己的历史；不同任务不能共享。
- 用户显式删除专属 thread 但保留任务时，下一次执行必须创建新的专属 thread，并仅在任务仍绑定被删除 ID 时以 CAS 更新绑定；不得永久失败，也不得覆盖并发形成的其他有效绑定。
- 普通用户 run 与定时执行同时命中该 thread 时，定时 execution 记为 `skipped/TASK_THREAD_BUSY`，不把内容写到其他 thread。
- 任务删除不自动删除 thread；thread 历史继续遵守现有用户显式删除语义，避免级联丢失交付物。

## 6. 数据模型

### 6.1 定义

目标 Go/JSON 结构：

```json
{
  "task_id": "sched_...",
  "version": 3,
  "name": "工作日科技新闻早报",
  "enabled": true,
  "project_id": "project_...",
  "thread_id": "thread_...",
  "schedule": {
    "kind": "cron",
    "cron": "30 9 * * 1-5",
    "timezone": "Asia/Shanghai"
  },
  "action": {
    "kind": "agent",
    "content": "整理今天最值得关注的科技新闻……",
    "composer_tokens": [
      {
        "id": "skill:daily-news:project",
        "type": "skill",
        "label": "daily-news",
        "payload": {
          "skillId": "daily-news",
          "sourceOrigin": "project",
          "skillFilePath": "/当前项目/.awaken/skills/daily-news/SKILL.md",
          "rootDir": "/当前项目/.awaken/skills/daily-news"
        }
      }
    ]
  },
  "execution": {
    "profile_id": "",
    "timeout_seconds": 600,
    "misfire_grace_seconds": 600
  },
  "template_origin": {
    "template_id": "daily_tech_news_brief",
    "source": "builtin"
  },
  "created_at": "2026-07-26T10:00:00Z",
  "updated_at": "2026-07-26T10:00:00Z"
}
```

日程 `schedule`：

```json
{
  "kind": "calendar",
  "run_at": "2026-07-27T08:00:00+08:00",
  "timezone": "Asia/Shanghai",
  "repeat_every_days": 1,
  "repeat_end": {
    "kind": "count",
    "count": 14
  }
}
```

`repeat_end.kind` 为 `never | until | count`；不重复时不出现 `repeat_every_days/repeat_end`。`until` 必须晚于 `run_at`。`count` 范围为 1–10,000。

### 6.2 状态与执行记录

任务 materialized state：

```text
enabled | paused | running | completed | invalid
```

执行状态：

```text
queued | running | success | error | skipped | cancelled | interrupted
```

执行记录至少包含：

```json
{
  "execution_id": "exec_...",
  "task_id": "sched_...",
  "task_version": 3,
  "trigger": "scheduled",
  "scheduled_for": "2026-07-27T00:00:00Z",
  "started_at": "2026-07-27T00:00:01Z",
  "finished_at": "2026-07-27T00:01:20Z",
  "status": "success",
  "run_id": "run_...",
  "thread_id": "thread_...",
  "error_code": "",
  "error_message": ""
}
```

`trigger` 为 `scheduled | manual | misfire`。运行次数限制只消费 scheduled/misfire 的 occurrence，手动执行不消费。失败或 skipped 的已到期 occurrence 也计入限定次数，避免失败后无限延长日程。

### 6.3 校验

Core 是唯一校验 owner：

- 名称 1–120 个 Unicode 字符；
- reminder content 非空且不允许 Composer token；Agent 必须至少有 content 或一个 Composer token；
- Agent `composer_tokens` 当前最多 24 个且只接受结构化 Skill token，token ID 唯一；可见 prompt 由各 token 的 `leadingText` 与末尾 content 组成，总计最大 32 KiB，token metadata 总计最大 16 KiB；
- Cron 必须是五段“分 时 日 月 周”，不接受秒；数字周日 `0/7` 规范化为 `sun`，并支持英文 `sun..sat`；
- IANA 时区必须由 Go `time.LoadLocation` 成功加载；
- 自定义 Cron 必须能计算出未来 occurrence；
- project 必须存在且为 active；
- profile ID 只保存 opaque ID；创建时若显式 profile 不 ready 则拒绝；
- 超时 30–3,600 秒，misfire grace 0–86,400 秒；
- client 提供的 task/thread/execution ID、状态、next run 和时间戳均不可信，由 Core 生成。

## 7. 持久化与 authority

定时任务属于全局业务数据，进入当前 FileStore generation：

```text
~/.awaken/
└── store-generations/<CURRENT>/
    └── scheduled-tasks/
        ├── mutations.jsonl
        ├── state.json
        └── executions/
            └── <task-id>.jsonl
```

- `mutations.jsonl` 是定义、版本、启停、thread 绑定、完成/tombstone 的 authority。
- `state.json` 是可重建快照，损坏时从 journal 重建。
- execution 文件是每任务追加历史，最多向 API 投影最近 50 条；中段损坏 fail closed，尾部半条按 FileStore committed offset 截断。
- 所有目录 `0700`、文件 `0600`，写入使用 `src/filestore` 的 atomic/journal 原语。
- mutation 与项目 lifecycle 共享 `locks/store.lock` 或同等级的 generation 级锁，不能出现两个 Core 同时写定义。
- task prompt/content 是用户业务数据，不进入日志、错误 message、Desktop 偏好或 Renderer localStorage。
- API key、Authorization、完整 resolved profile 和工具快照不进入任务定义。
- 删除写 tombstone 并停止调度；用户可见定义和执行历史立即消失。物理 journal 压缩遵守未来 FileStore generation compaction，不用危险的原地改写伪装硬删除。

## 8. 调度语义

### 8.1 Core 生命周期

调度器由 `cmd/awaken-core` 随 RunService 启动并在 HTTP ready 前完成：

1. 打开 repository 并恢复任务；
2. 把遗留 `running/queued` execution 封口为 `interrupted`；
3. 校验每条 enabled 定义；
4. 单条无效任务标记 `invalid` 并从调度器移除，不阻止其他任务/Core 启动；
5. 计算 next occurrence 和启动期 misfire；
6. 启动调度 loop；
7. HTTP 才开始对外 ready。

shutdown 顺序：

1. 停止接收新 occurrence；
2. 标记队列中未开始项 cancelled；
3. 请求取消活动 scheduled run；
4. 等待现有 Core graceful shutdown 上限；
5. 未闭合 execution 由重启恢复为 interrupted。

### 8.2 Desktop 关闭边界

首版调度器只在受管 Core 存活时运行。Desktop 完全退出期间：

- 不运行任务；
- 不使用 OS crontab、launchd 或 Windows Task Scheduler；
- 再次启动时只按 misfire 规则最多合并补一次；
- UI 必须始终展示这一限制，不能用“后台运行”误导用户。

如果未来要求关掉窗口仍执行，应先单独设计 Desktop close-to-tray 或受 lease 管理的 headless Core；不能在本功能里偷偷留下孤儿 Core。

### 8.3 misfire、时区和 DST

- 每条任务记录最近已处理 occurrence，重启后从该点和当前时间计算。
- 若最新到期点距离当前时间不超过 `misfire_grace_seconds`，合并为一次 `trigger=misfire`；多个漏点不逐个补跑。
- 超过宽限时写 `skipped/MISFIRE_GRACE_EXCEEDED`，再计算下一次。
- 一次性日程超过宽限后写 skipped 并进入 completed。
- DST 不存在的本地时间跳到调度库计算的下一个合法 occurrence；重复的本地时间每个表达式 occurrence 只执行一次。测试必须固定 location 和 clock，不能依赖 CI 机器时区。
- scheduler 使用可注入 Clock 和 Timer，单元测试不得真实等待分钟。

### 8.4 并发与幂等

- 每任务 semaphore=1，全局 Agent semaphore=2；reminder 不占 Agent semaphore。
- `(task_id, scheduled_for)` 形成 occurrence 幂等键；同一到期点在重启、定时器迟到或 API 重试中只能创建一个 execution，`scheduled` 与 `misfire` 共享该键。
- “立即执行”必须携带 idempotency key；Main/Renderer 网络重试不能创建两次。
- definition version 在 execution 开始时冻结；执行过程中编辑不会改变其 prompt/profile/project。

## 9. 执行、线程与无人值守边界

### 9.1 项目与 TaskScope

触发时用 `project_id` 重新读取当前 active project：

- cwd 为当前 primary folder；
- readable/writable/output roots 为当前全部 folders；
- 零文件夹项目使用现有 session workspace；
- 项目 removed、删除操作中或路径失效时不猜旧路径，execution 记为 `PROJECT_UNAVAILABLE` 或现有 project conflict code；
- 定义中不保存创建时的绝对 roots 快照。

### 9.2 模型 profile

- `profile_id=""`：每次触发通过 `src/modelprofile.UserStore.Resolve("")` 解析当时默认 ready profile；
- 显式 ID：每次触发重新 resolve；已禁用、缺 key 或删除时 execution 失败为 `MODEL_PROFILE_UNAVAILABLE`；
- resolved API key 只在内存中转换为 `runtime.ModelProfileConfig`，沿用 ACP control route 已有转换模式；
- 不静默切换显式选择的付费 provider。

### 9.3 Agent 任务

新增 host-only `RunService.StartScheduledRun`，不向普通 renderer HTTP client开放伪造 source 的旁路。它负责：

1. 解析/建立该任务稳定 thread；
2. 构造 `ClientInfo{EntryPoint:"scheduled_task", Source:"scheduled_task", RequestID:execution_id}`；
3. 使用现有 `StartRun` 的 journal、上下文、工具快照、Composer token 预激活和恢复路径；计划触发时按当前 Skill Registry 重新核对 Skill ID、来源、包根和 `SKILL.md`，Renderer 保存的路径不是授权来源；
4. 禁止普通 LLM 标题生成，任务名是 thread 初始标题；
5. 订阅 run 直至 terminal 或超时；
6. 超时调用 `CancelRun`，等待终态后记录 execution。

定时 Agent 不获得额外工具、不绕过 TaskScope、不自动安装额外 Connector、不改变零审批合同。

定时任务保存的是用户当时的结构化 Skill 选择，不缓存 Skill 正文。每次触发都把这些 token 作为该次 run 的 `invocation=user_composer` 选择重新预激活；Skill 被删除、禁用用户调用或来源/锚定路径变化时，该次 execution 按普通 Composer token 失败路径终止，不静默改选同名 Skill。

无人值守 run 不能无限等待：

- `ask_user`、外部授权、ACP permission 等交互一旦出现，立即以 `SCHEDULED_INTERACTION_REQUIRED` 取消并失败；
- 错误记录只保存 gate 类型和安全错误，不保存 token、二维码、原始 stdout/stderr；
- 用户可从执行记录打开 thread，在普通交互 run 中处理依赖后再手动重试。

### 9.4 固定提醒

`reminder` 不调用模型。新增 `RunService.PublishScheduledNotice`：

- 建立/复用同一专属 thread；
- 写 `run_started -> scheduled_notice -> run_terminal(success)` 的 host-owned SemanticJournal 记录；
- 新语义 kind 为 `scheduled_notice`，payload 只含 task/execution identity、任务名和固定正文；
- 09 域映射为 `AWAKEN_SCHEDULED_NOTICE`；
- Workbench 投影专用“定时提醒”卡，不伪装为 user 或 assistant 文本；
- Main 收到 live 事件时使用 Electron `Notification`，点击后聚焦主窗口并打开对应 thread；
- replay 只还原卡片，不重复发系统通知。

### 9.5 结果与交付物

Agent 的文本、工具、文件变化和 artifact 沿用普通 run。执行记录只引用 run/thread，不复制 assistant 正文或 artifact 路径。任务历史页跳转 thread 查看完整过程，避免形成第二份 transcript。

## 10. HTTP、IPC 与事件

目标 HTTP：

```text
GET    /v1/scheduled-tasks
POST   /v1/scheduled-tasks
GET    /v1/scheduled-tasks/{task_id}
PATCH  /v1/scheduled-tasks/{task_id}
DELETE /v1/scheduled-tasks/{task_id}
POST   /v1/scheduled-tasks/{task_id}/pause
POST   /v1/scheduled-tasks/{task_id}/resume
POST   /v1/scheduled-tasks/{task_id}/run
POST   /v1/scheduled-tasks/{task_id}/cancel
GET    /v1/scheduled-tasks/{task_id}/executions
```

- write 请求统一携带 `expected_version`；run/delete 携带 idempotency key。
- create 返回 201，异步 run 返回 202；字段错误 422；版本冲突 409；不存在 404。
- Renderer 不直接持有 loopback URL，通过 preload/Main typed bridge。
- `apps/desktop/src/shared/runtime.ts` 定义 wire/camelCase 转换；不得在 `ScheduledTasksView` 手写 snake_case payload。
- Main 订阅 scheduled task 状态/notice 并转为受控 IPC event，用于实时刷新、原生通知和点击定位；Renderer 页面未挂载也不能丢失 Core durable 状态。
- `execution_started` wire/camelCase 事件携带 `project_id/projectId`、`run_id/runId` 和 `thread_id/threadId`。顶层 `App` 常驻订阅 started/finished：有 thread identity 时立即从 thread authority 对账侧栏，但不切页面、不激活 thread、不抢焦点；`ScheduledTasksView` 只刷新任务列表，不拥有全局 thread 可见性。

新增公开 AG-UI-compatible 事件仅限 thread 内可重放事实：

```text
AWAKEN_SCHEDULED_NOTICE
```

任务 CRUD、next run 和全局队列状态不是 thread 叙事，不塞进 AG-UI；由 scheduled-task HTTP/IPC surface 读取。

## 11. Ownership

| 层 | 目标 owner | 负责 | 不负责 |
|---|---|---|---|
| 定义/触发/状态 | `src/scheduledtask` | schema、Cron/日程计算、repository、scheduler、execution、misfire、幂等 | UI、模型实现、工具执行 |
| Agent/提醒线程 | `src/runtime` | 专属 thread、普通 run 复用、scheduled notice、取消/终态 | 定时表达式解析 |
| 模型配置 | `src/modelprofile` | 触发时按 opaque ID 解析 ready profile | 保存到任务定义的 credential |
| HTTP | `src/server/handlers_scheduled_tasks.go`、`router.go` | typed route、状态码、错误映射 | 调度状态 authority |
| Core 装配 | `cmd/awaken-core/main.go` | repository/service 注入、start/stop 顺序 | 第二套 scheduler |
| Main/preload/shared | `apps/desktop/src/main`、`preload`、`shared/runtime.ts` | typed bridge、通知、窗口聚焦、wire normalize | 任务 authority、Cron 校验 |
| Renderer | `ScheduledTasksView.tsx`、`scheduled-tasks/*` | 页面数据适配、模板目录、表单和乐观状态 | 定时器、凭据、FileStore |
| Design System | `AwakenScheduledTasks*` | UI-only 列表、模板窗口、编辑器、历史窗口和状态 | API、Electron、模板业务 payload |
| 协议/Workbench | `src/protocol/agui`、renderer projector | notice live/replay 映射与卡片 | 全局任务管理 |

实现不得把 `setInterval` 当成任务调度器放进 Renderer，也不得复用 Desktop Main 的 Memory Dream scheduler store 作为定时任务 authority。Dream 是单一内部维护策略；用户定时任务需要 Core 级定义、历史和 run ownership。

## 13. 风险与明确决策

1. **退出后不运行：** 这是 Desktop 生命周期的真实限制，不靠文案掩盖。OS 唤醒是独立后续项目。
2. **固定提醒语义：** 用 host-owned notice，不花模型 token，也不冒充模型回复。
3. **专属线程：** 避免后台任务污染用户任意活动 thread，也自然复用当前 journal/artifact。
4. **profile 只存 ID：** 避免凭据过期与 secret 复制；每次触发重新验证。
5. **项目只存 ID：** 避免项目文件夹编辑后继续使用陈旧权限根。
6. **单任务并发 1：** 当前 RunService 的 thread busy 语义决定同一专属 thread 不能安全并行。
7. **Qwenpaw 日期动态化：** 保留模板意图，不复制已经过期的演示日期。
