# Awaken Desktop Workbench 产品需求

## 1. 背景

Awaken Desktop 的中间工作区是用户把任务交给 Agent，并持续阅读执行过程、工具使用、审批请求、最终回答和上下文状态的地方。它不是普通聊天窗口，也不是日志面板，而是执行中的任务叙事空间。

过去多轮修复暴露出一个核心问题：中间区域的视觉与交互已经被用户确认是想要的方向，但滚动、锚定、sticky prompt、composer 避让、latest-output follow 等算法仍不够系统。单点修复容易出现“修一个功能，破坏另一个已确认行为”的情况。

本 PRD 固化 Workbench 中间区域的产品行为，为后续重构 `useRunStageScrollController`、turn/feed 渲染层和验收护栏提供产品依据。2026-07-05 的失败线程已独立沉淀到 [2026-07-05 失败复盘与反模式](2026-07-05失败复盘与反模式.md)。

## 2. 目标

1. 固化 Workbench 中间区域的产品行为，而不是只描述当前代码结构。
2. 明确 prompt bubble、turn、ExecutionFeed、dock composer、turn marker、scroll/follow 之间的交互关系。
3. 为后续算法重构提供可验收的需求边界。
4. 明确哪些行为必须通过真实 Awaken Desktop + Computer Use 验证。
5. 降低后续重构破坏现有设计的概率。

## 3. 非目标

- 不要求立刻重写 Workbench 前端。
- 不改变 `RunStage / ExecutionFeed / ComposerDock` 的 DOM 契约。
- 不新增第三种 composer variant。
- 不把 Desktop renderer 的 scroll/follow 策略下沉到 `@awaken/design-system`。
- 不引入 Playwright 或浏览器自动化作为动态交互验收手段。
- 不解决 markdown / assistant message 渲染质量问题，除非它直接影响中间区域布局和滚动。

## 4. 用户与场景

主要用户是本地使用 Awaken Desktop、需要连续向 Agent 发起多轮任务、会在执行中阅读历史、暂停自动 follow、回到底部继续观察的人。

核心场景：

- 用户在空态从 center composer 发起第一条任务。
- Agent 进入运行态后，composer 变为 dock 形态，ExecutionFeed 展示 turn。
- 用户连续发送多轮 prompt，每轮 prompt bubble 成为该 turn 的视觉锚点。
- 用户在输出过程中向上滚动阅读历史，系统不强行拉回底部。
- 用户向下滚回最新输出区域后，latest-output follow 可恢复。
- 多 turn 后，turn marker rail 提供跳转和当前 turn 位置反馈。
- approval prompt、runtime panel、composer 高度变化时，输出区域不被 dock composer 覆盖。

## 5. 产品原则

### 5.1 中间区现有设计是产品契约

空态 center composer、运行态 dock composer、ExecutionFeed turn 分组、sticky prompt header、turn marker、latest-output follow、用户滚动暂停/恢复，都是产品意图，不是临时实现。

### 5.2 Prompt 属于 Turn

用户 prompt bubble 必须位于对应 turn section 内，并与该 turn 的 Thought、工具轨迹、审批卡、文件变更、assistant answer 形成完整叙事单元。不能把 prompt header 拆成外部同步层或独立悬浮副本。

### 5.3 RunStage 是唯一中间区域容器

中间区域的滚动、定位、overlay、composer 都必须通过 `RunStage` 承载。`ExecutionFeed` 只展示 narrative / turn；composer 只通过 `RunStage` 的 composer slot 挂载。

### 5.4 用户意图优先于被动布局变化

用户主动滚动、触摸、点击 marker 时，系统必须尊重用户正在阅读历史的意图。ThoughtTrace 增高、markdown 渲染完成、composer 高度变化等被动布局变化，不能被误判为用户想恢复 auto-follow。

### 5.5 真实运行优先于静态等价

DOM 等价、静态截图、纯函数测试都只是辅助。凡是涉及 scroll、anchor、sticky、follow、composer 避让的改动，必须通过真实 Awaken Desktop + Computer Use 交互验收。

## 6. 信息架构与结构契约

```text
AppShell
  -> WorkbenchShell
    -> RunStage
      -> ExecutionFeed
        -> execution-turn-section
          -> execution-turn-header
            -> UserPromptBlock
          -> execution-turn-body
            -> narrative items
      -> ComposerDock
      -> turn marker rail overlay
      -> return-to-latest overlay
```

| 层级 | 代表 | 责任 |
|------|------|------|
| Design System | `AwakenRunStage`、`ComposerBar`、`UserPromptBlock` | 结构壳、视觉 token、可复用 UI |
| Desktop Renderer | `App.tsx`、`useRunStageScrollController.ts` | runtime 编排、DOM scroll、anchor、follow、用户意图、composer 生命周期 |
| Pure Decisions | `workbenchPresentation.ts` | 可测试的纯判断函数 |
| Acceptance | `capture-workbench-*`、Computer Use | 真实窗口截图和动态交互证据 |

## 7. 功能需求

### P0-1 空态 Center Composer

无 narrative 且无 active run 时显示 center composer。center composer 位于视觉中心偏上位置，并与 `TaskWelcome` 共同构成空态。此状态不显示 dock composer、ExecutionFeed、turn marker rail。

验收：`npm run open:desktop` 后窗口 ready，center composer 可输入、可发送，center 截图非白屏。

### P0-2 第一轮 Prompt 锚定

第一条 prompt 提交后，center composer 切换为 dock composer；最新 turn 的 prompt bubble 锚定到 RunStage 顶部；prompt 下方显示该 turn 的 Thought / narrative / answer；dock composer 不遮挡 prompt 或 answer。

验收：真实 Desktop 中输入并发送第一条短 prompt，发送后 prompt bubble 位于中间区顶部，输入框进入运行态 stop mode，结束后恢复可编辑。

### P0-3 多轮 Prompt 锚定与 Sticky 交接

新 run 开始时，sticky ownership 必须从旧 active turn 交接到 latest turn。第二条 prompt 提交后，第二 turn 的 prompt bubble 应锚定到顶部。第一 turn 的 prompt header 不得覆盖第一 turn 自己的 answer，也不得遮挡第二 turn 的内容。

已知失败：连续发送两条相同多行 prompt 后，旧 prompt bubble 仍 sticky 在顶部，导致新 turn 置顶失效；多行 prompt 会让旧 sticky header 更高，遮挡更明显。

验收：连续发送两条多行 prompt，第二条发送后最新 prompt bubble 位于顶部锚点，旧 turn header 不覆盖旧 turn answer，上下滚动后 active marker 与 sticky header 一致。

### P0-4 Latest Output Follow

当用户没有主动阅读历史时，latest turn 输出持续增长应自动保持可见。follow 的目标是助手最终输出内容底部，不是 turn section 整体底部、padding 底部或预留高度底部。run 完成后，最终输出与 dock composer 之间保持稳定可读间距。

验收：运行会产生多段 Thought / 工具输出 / final answer 的任务，输出过程中助手最终输出内容底部保持在可视区域，完成后 final answer 不被 dock composer 覆盖。

### P0-5 用户滚动暂停 Follow

wheel 向上、touch 向历史方向、pointer 操作、点击旧 marker 都视为用户主动阅读历史。用户暂停 follow 后，后续 ThoughtTrace / markdown / tool output 增高不得自动恢复 follow。passive layout scroll 不得被误判为用户恢复 follow。

如果 latest run 仍在输出，系统应提供显式“回到最新输出” affordance；用户触发该 affordance 或明确滚回 tail 后，才允许恢复 follow。按钮专项要求见 [回到最新输出按钮需求](回到最新输出按钮需求.md)。

验收：run 过程中向上滚动后，输出继续增长时视图停留在用户阅读位置；只有用户明确点击“回到最新输出”或向下滚回 tail 后，follow 才恢复。

### P0-6 Dock Composer 避让

RunStage 内容底部必须为 dock composer 预留稳定 safe area。composer 高度变化时，RunStage inset 同步更新。runtime panel、approval prompt、model pill、输入框高度变化都不能破坏输出避让。output tail、scroll bottom、composer inset 必须使用同一个布局事实，不能各算各的。

已知失败：final output 卡进输入框区域，无法通过滚动恢复正常间距；滚动条视觉突破 composer dock。

验收：完成长输出任务后，final answer 与 composer dock 之间有稳定可读间距，右侧滚动条停在 composer 上方，不穿过输入框区域。

### P0-7 Turn Marker Rail

turn 数达到阈值后显示 marker rail。marker rail 位于 RunStage overlay 内，不影响 ExecutionFeed 布局。active marker 与当前 sticky / active turn 一致。点击 marker 后跳转到对应 prompt anchor，并暂停 latest follow。

验收：连续发送至少三轮 prompt，marker rail 出现；点击旧 marker 后跳转到对应 turn，sticky header 与 marker 同步，latest follow 暂停。

### P1-1 Prompt Bubble 长文本与折叠

超过行数或长度阈值的 prompt bubble 默认折叠为 3 行。用户展开后最多显示 9 行；超过 9 行的剩余内容在 prompt bubble 内部滚动查看。折叠高度、展开高度和内部滚动区域都必须参与 sticky / anchor / follow 算法。

验收：折叠态显示 3 行；展开态最多显示 9 行；折叠、展开、内部滚动、再次折叠后 sticky / anchor / follow 都正常。

### P1-2 Runtime Panel 与 Approval Prompt

runtime panels / approval prompt 位于 composer stack 内。出现或消失时，composer bottom inset 应稳定同步。approval card 不应出现在 ExecutionFeed 中作为非 narrative 控件；历史 approval narrative 可作为 narrative item 展示。

### P1-3 Tool / Work Packet 叙事

长任务读取大量文件或运行工具时，用户应看到“正在做什么”，但不被低层日志淹没。很长的工具调用、文件变更、执行日志必须合并为可展开的 collapsed work packet，而不是把低层事件全部平铺到 feed。

### P1-4 响应式 Workbench

窗口宽度变化、sidebar/inspector 折叠展开时，中间区域仍可稳定使用。sidebar / inspector 折叠或展开不应让 RunStage 出现异常空白；composer model pill、按钮、输入框不应错位；prompt bubble、turn body、dock composer 在窄窗口保持可读。

### P2-1 自动化 VRT

保留 center / dock / marker baseline。`npm run capture:workbench:vrt` 可产出 manifest。VRT 可作为 PR 级对比截图护栏，但不得取代真实交互验收。

### P2-2 结构性重构

`App.tsx` 后续可继续治理，但每一刀都必须可回滚、可验收。重构顺序优先治理 scroll / anchor 算法，再做渲染层拆分。抽 hook / view 时不得改变 DOM key、wrapper、approval handler、ExecutionFeed 边界。

## 8. 关键状态模型需求

后续算法设计应至少显式建模以下状态，而不是散落在多个 ref / CSS 变量 / effect 中：

1. `currentTurn`：当前视觉上被 sticky / active marker 代表的 turn。
2. `latestTurn`：最新提交的 prompt 所属 turn。
3. `pendingPromptAnchor`：新 prompt 等待锚定到顶部。
4. `followLatestOutput`：系统是否正在自动跟随 latest output。
5. `pausedByUser`：用户是否主动退出 follow。
6. `resumeIntent`：用户是否明确表达恢复 follow。
7. `composerInset`：dock composer 实际占用和 safe area。
8. `promptBubbleMode`：prompt bubble 折叠 / 展开 / 多行高度状态。
9. `programmaticScroll`：系统主动滚动，避免被误判为用户滚动。
10. `returnToLatestAffordance`：用户暂停 follow 后，是否需要显示“回到最新输出”的显式恢复入口。
11. `workPacketMode`：长工具调用 / 文件变更 / 执行日志是否处于折叠、展开、内部滚动或摘要状态。

## 10. 已确认产品决策

1. 多行 prompt bubble 保持当前视觉方向：默认折叠为 3 行；展开后最多显示 9 行；超过 9 行的剩余内容在 prompt bubble 内部滚动查看。
2. latest turn 自动 follow 的 tail 明确定义为助手最终输出内容的底部，不是 turn section bottom。
3. 点击旧 marker 或用户主动阅读历史后，latest follow 暂停；如果最新 run 仍在输出，应显示“回到最新输出”的显式 affordance，用户触发后才恢复 follow。
4. 很长的工具调用、文件变更、执行日志必须合并为可展开的 collapsed work packet。
5. Workbench 交互验收必须保存录屏或关键帧证据到固定目录：`docs/01_桌面工作台/中间交互区域/验收文件夹/`。
