# 工具定义与暴露

## 1. 权威范围

本文唯一定义 Tool Definition Schema v2、authoring 到 resolved definition 的解析、registry 质量元数据、模型可见性和当前热替换边界。它不授予执行权限：TaskScope、路径与 executor 强制见 [TaskScope 与路径安全](TaskScope与路径安全.md)，canonical 执行结果见 [工具决策、Outcome 与失败监督](工具决策、Outcome与失败监督.md)，wire 上的工具列表动作见 [09 接口契约](../09_AGUI与A2UI协议/HTTP与SSE接口契约.md)。

## 2. Tool Definition v2

Go authority 是 [`src/tool/tool.go`](../../src/tool/tool.go)、[`src/tool/definition.go`](../../src/tool/definition.go) 与 [`src/tool/definition_validation.go`](../../src/tool/definition_validation.go)。`ToolDefinition` 把三类不同事实分开：

| 类别 | 字段 | 当前语义 |
| --- | --- | --- |
| 身份与选择 | `schema_version/name/display_name/source/description/purpose/when_to_use/when_not_to_use` | 说明“这是什么、何时用、何时不用”；`source` 为 `builtin/mcp/connector/skill/plugin` |
| 可执行合同 | `input_schema/output_schema/examples/failure_modes` | 输入验证、`details` 的 typed 结构、能通过同一 schema 的示例和稳定失败边界 |
| 安全事实 | `side_effects/permissions/annotations/policy` | `annotations` 会进入 fallback permission decision；`side_effects/permissions` 是声明与诊断事实；`policy` 当前未接线 |

`name` 是 model call、registry、permission 和 audit 共用的 canonical 全局身份。strict builtin 使用 lower snake case；MCP/Skill adapter 按约定生成 `mcp__...` / `skill__...` 前缀，但 registry 只校验安全字符形式，不校验 `Source` 与前缀的绑定，`RegisterToolForce` 也能替换任意同名注册。因此命名空间是 adapter 约定，不是 registry 的强制隔离不变量。`display_name` 只用于 UI，不能参与调用、权限或审计身份判定。`description` 是短摘要，`purpose/when_to_use/when_not_to_use` 才定义选择语义和与相邻工具的边界。

`side_effects` 的每项包含 `kind/resources/description/reversibility`。当前 kind 为 `none/read/create/update/delete/execute/network/unknown`；reversibility 为 `not_applicable/reversible/conditional/irreversible/unknown`。`permissions` 明列 `capability_class/workspace_scope/file_bridge_scope/network_scope/requires_auth/requires_review`。当前枚举是：

| 维度 | 值 |
| --- | --- |
| capability | `unknown/artifact_read/artifact_write/connector_read/connector_write/browser_read/browser_interaction/local_transform/mass_message_send/external_publish/system_operation` |
| workspace scope | `none/workspace_read/workspace_write/task_scope/unknown` |
| file bridge | `none/task_scope_read/task_scope_write` |
| network | `none/restricted/open` |
| trusted origin | `builtin/official_hosted/official_connector/third_party_mcp/local_skill` |

annotations 的完整事实面为 `readOnly/destructive/openWorld/requiresAuth/serverName/toolName/capabilityClass/trustedOrigin/fileBridgeScope/networkScope/massMessage`。`massMessage` 的 review metadata 包含 `reviewId/channel/recipientScope/recipientCount/bodyPreview/templatePreview/attachments/sendingAccount/sourceTool`。permissions 必须与 annotation 的 capability、file bridge、network、auth、read-only/destructive 相容；静态 annotation 不能代替单次 input-aware 决策。

`PermissionPolicy` 类型声明了 `always_allow/always_deny`，但 `ToolDefinition.Policy` 当前没有 runtime consumer，不进入工具列表或 audit，strict lint 也不验证其值。`DecideWithOverride` 读取的是独立 override map，ToolRuntime 的 annotation fallback 路径传入 `nil`，不会读取 Definition 上的 `policy`。因此它只是未接线 authoring 字段，不得作为当前默认授权姿态，更不能扩大 TaskScope 或取代 runtime permission check。

`output_schema` 只定义 canonical `ExecutionOutcome.details` 中的工具专属字段。`status/errors/changes/environment/next_actions` 等顶层字段属于 Outcome authority，工具不得在 details 内重新定义。没有专属 details 的 builtin 使用封闭空 object，不另造 success/error envelope。

## 3. Authoring、解析与质量

运行时 Tool 提供的原始 authoring 定义不等于 registry 最终使用的 resolved definition。`ResolveDefinitionReport` 按以下优先级形成 v2 snapshot：

```text
显式 v2 字段
  -> 从 runtime parameter/annotation 生成的保守 compatibility adapter
  -> 旧 Name/Description/Parameters method 的最小恢复
```

无论原定义版本如何，resolved snapshot 都标记 schema v2。逐项 fallback 与质量变化如下：

- name 只能从 runtime method 恢复，一旦恢复就标记 `incomplete`；display name 缺失时使用 name，标记 `adapted`；
- source 缺失直接标记 `incomplete`；description 可从 legacy method 恢复，purpose 可从 description 恢复；
- when-to-use / when-not-to-use 缺失时只生成保守兼容边界，不生成业务承诺；
- input schema 优先取 `InputSchemaProvider`，否则从 legacy parameters 适配；output schema 缺失时为封闭空 details object；
- side effects 缺失时由 annotations 保守推导；仍是 `unknown` 时质量为 `incomplete`；permission scope 补全后仍不确定也是 `incomplete`；
- examples/failure modes 缺失只降为 `adapted` 并记 warning，绝不编造；
- 若解析后仍暂标 `strict` 但完整 lint 失败，最终质量改为 `incomplete` 并保留原因。

解析结果同时保存：

- `Origin`：工具来自 builtin、MCP、connector、Skill 还是 plugin；
- `Quality`：`strict`、`adapted` 或 `incomplete`；
- `Warnings`：哪些事实由兼容层补全或仍不完整。

Origin 和 Quality 必须分离：“来自 builtin”不自动证明定义完整，“来自外部”也不必然意味着质量低。Warnings 是 registry 和 `GET /v1/tools` 工具列表的诊断元数据，当前不直接发给模型，也没有进入 `ToolAuditRecord` / `writeAudit`。

## 4. 验证模式与 strict lint

`ValidateToolWithMode` 有三个迁移门禁：

| mode | 当前行为 |
| --- | --- |
| `compat` | 验证稳定 Tool 接口、名称、来源和基本描述；允许 adapted/incomplete 外部或旧工具迁移 |
| `strict_builtin` | builtin 必须完整通过 v2 lint；MCP/Skill 等外部工具仍可按 compat 注册 |
| `strict_all` | 所有来源都必须是 strict v2 |

所有 mode 都先执行最小门禁：runtime 不为 nil；runtime name 符合受支持的安全名称；legacy parameter 名和 JSON Schema type 合法；原 `ToolDefinition.Name` 必填并与 runtime name 相等；Source 和 Description 必填。strict mode 才在此基础上要求完整 v2 authoring。

strict definition 至少必须满足：

- `ToolDefinition.Name` 与 runtime name 一致；builtin 名称为 lower snake case；source 已知；
- purpose、when-to-use 和 when-not-to-use 都有可操作内容；
- input 和 output-details 根均为 object；object 明确声明 `additionalProperties`；required 字段真实存在；array 有 items；
- input schema 的嵌套参数都有 description；output-details 不复制 canonical Outcome 字段；
- side effects 有非空 kind、description 和已知 reversibility，且不与 `read_only/destructive` 冲突；当前 lint 不验证 kind 是否属于声明的完整枚举；
- permission scope 非空且与已填 annotations 一致；destructive 工具声明 review 边界；当前 lint 不校验 capability、workspace/file/network scope、trusted origin 或 policy 的完整枚举；
- 每个 example 的 input 经过同一 runtime schema validator，不允许只是无法执行的文案；
- failure mode code 唯一，且有原因；
- permission 和 annotation 引用的 capability、file bridge、network、auth 事实相互一致。

strict lint 只能证明当前校验器覆盖的结构和内部一致性；不证明未校验枚举值合法，不证明 executor 真实实现了声明行为，也不授权执行。

共用 recursive validator 当前支持 object/array/string/number/integer/boolean/null/any、required、enum、精确一个分支成立的 `oneOf`、`additionalProperties`、字符串/数组/数值边界和精确 JSON path 错误。它不因 definition 是 external 就跳过执行前 input validation。

当前自动化对 builtin 的实际保证是：所有注册 builtin 都通过 strict contract，都声明 examples 和 failure modes；除 `ask_user` 外均实现 `OutcomeTool`。这一保证按能力和名称测试，不依赖固定工具数量。

## 5. 模型描述

`ModelDescriptionWithBudget` 从 resolved definition 编译模型可见描述，默认硬上限为 1,800 runes。summary、“Do not use”、side effects 和 permission boundary 被标记为 required segment；若合计超预算，每个 required segment 也会分配预算并裁剪，不保证完整保留原文。可选段的插入优先级是 Use when → Purpose → Returns。外部工具的长描述不能无上限膨胀每轮请求。

input schema 不内嵌在这 1,800 runes 中；RequestBuilder 将 resolved `InputSchema` 作为 provider tool parameters 单独发送。因此 description budget 不能代替 schema 校验，也不应用自然语言重复全部字段。

该描述用于工具选择，不是执行权限，也不是 Outcome 的自然语言替代。

## 6. Registry snapshot 与当前 TOCTOU

[`src/tool/registry.go`](../../src/tool/registry.go) 的每个 `RegisteredTool` snapshot 同时保存 executable runtime、resolved definition、Origin、Quality、Warnings 和 `PreserveInputObject`。原始 definition 为 v2 或 runtime 实现 `InputSchemaProvider` 时，该值为 true 并保留完整 JSON object；显式 `LegacySingleValueInput.UnwrapSingleParameterInput()=true` 可将其强制改为 false。其他非 v2、无 provider 的 legacy tool 默认为 false：仍先用 registered schema 验证，然后进入旧 `Parameters()` shaping；单参数 object 会展开为该值，多参数才重新序列化整个 object。`GetRegisteredTool` / `ListRegisteredTools` 返回 definition 和 warning 的单次 clone snapshot，不让读者直接改写 registry 内容。builtin 由 [`src/tools/tools.go`](../../src/tools/tools.go) 装配；新 builtin 必须同时提供 strict definition、schema 正反例、canonical Outcome/错误、测试和对应功能域文档。

但当前没有在“模型请求构建→实际执行”之间锁定同一 snapshot identity：

```text
RequestBuilder 读取当时 resolved definition
  -> AgentConfig.ResolvedToolPool 只记工具名集合
  -> ToolRuntime 执行时按名重新 lookup
```

MCP 刷新和测试使用的 `RegisterToolForce` 可以在中间替换同名 runtime/definition，导致模型看到旧合同却执行新实现的 TOCTOU。`GetRegisteredTool` / `ListRegisteredTools` 返回的单次 clone 不等于跨阶段冻结；当前不存在独立 `Snapshot()` API。修复前不得在 active run 中依赖同名 force replacement 的原子隔离，也不得将“模型与 executor 必定使用同一定义快照”写成当前保证。

## 7. 模型暴露与双 gate

[`src/tool/exposure.go`](../../src/tool/exposure.go) 和 02 的 RequestBuilder 构造每轮可见工具池：

- 普通 provider 默认隐藏 raw `apply_patch`，优先提供低风险 typed 编辑工具；
- compat/grammar/all 模式可以显式暴露 `apply_patch`；
- `ExtraVisible` 会强制扩大/保留指定名称，`ExtraHidden` 会移除指定名称，二者之后才应用 mode；08 的 Skill activation 再将可见池与 Skill policy 求交；
- ToolRuntime 执行前再检查 call 是否仍在 resolved name pool 内，防止模型或重放直接调用池外工具。

当前代码实际优先级是 `ExtraVisible > ExtraHidden > mode`：同名同时列入 visible 和 hidden 时仍会暴露。这与 `ExtraHidden names are always removed` 的代码注释冲突，且当前没有专门冲突测试。这是暴露策略缺口，不得把 ExtraHidden 当作能压过 ExtraVisible 的安全不变量。

因此：

```text
已注册 ≠ 本轮模型可见 ≠ 本次获准执行
```

RequestBuilder 的实际构造顺序是 exposure filter → 可选 `ResolvedToolPool` 名称交集 → 按名读取当时 registry definition → `ModelDescription + exact InputSchema`。09 的工具列表动作只用于诊断，不是绕过 exposure/policy 的执行入口。

### 7.1 工具列表诊断面

[`src/server/handlers_tools.go`](../../src/server/handlers_tools.go) 的当前工具列表返回 schema/name/display/source/quality/warnings/description/modelDescription/purpose/when-to-use/when-not-to-use/input/output/sideEffects/permissions/examples/failureModes，以及 readOnly/destructive/openWorld/requiresAuth/serverName/toolName/capabilityClass/trustedOrigin/fileBridgeScope 这些选定 annotation 投影。

它不返回 `Definition.Policy`、`annotation.MassMessage` 或独立 annotation NetworkScope（network 仍可在 permissions 中看到）。MCP adapter 的 `OutputSchemaWarnings()` 当前也没有消费者将其并入 registry warnings/列表结果；这是外部 output schema 诊断缺口。

## 8. 当前不支持与限制

- 不承诺 registry 中所有工具每轮都暴露给模型。
- 不支持通过 Definition 扩大 TaskScope、execution profile 或绕过 executor。
- adapted/incomplete 不是 strict；warning 可诊断，但不是模型可信的隐式能力保证。
- MCP input schema 只能保留 `ToolParametersSchema/ToolParam` 可表示的子集；`pattern`、`format`、`$ref` 等不支持的 keyword 可被 `json.Unmarshal` 静默丢弃。整体反序列化失败时回退到 flat parameters；非 object root 不会包装，而是在 arguments 必须为 object 的执行前验证中失败。这些路径不保证 warning。
- MCP output schema 同样只保留可表示子集；整体反序列化失败会产生 warning，非 object root 会包在 `mcp_value`，canonical Outcome 字段冲突会整包放入 `mcp_payload`。未知 keyword 仍可静默丢弃，不保证拒绝或 warning。
- 工具数量不是产品合同；文档和测试应按名称/能力验证，不用固定总数代替。
- 当前不支持跨 request/execution 的 definition/executor identity pinning；同名热替换隔离尚未实现。
- ExtraVisible/ExtraHidden 同名冲突当前由 ExtraVisible 获胜，和注释不一致；不得依赖 hidden 必定优先。
- MCP output-schema adapter warning 当前不会自动进入 registry warning 和工具列表诊断。
