# 2026-07-05 失败复盘与反模式

## 1. 结论

2026-07-05 的 `codex/workbench-prd-full-implementation` 分支尝试把 Workbench PRD 一次性全量落地，最终在真实 Awaken Desktop 中确认破坏了中间区域整体滚动效果。该分支已关闭 Awaken 后删除，不能作为后续修复基础。

本次失败不是单个按钮样式问题，而是 Workbench 中间区域滚动、composer、overlay、sticky 和 follow 状态被跨阶段联动修改后，缺少逐刀真实验收导致的系统性回归。

## 2. 线程 Plan 摘要

本次实现计划原本被拆成五个 gated phases：

1. sticky / anchor 状态模型。
2. latest-output follow 与 composer 避让。
3. return-to-latest 恢复入口。
4. old transcript replay 定位。
5. collapsed work packet。

计划同时要求：

- 保留 `RunStage -> ExecutionFeed -> ComposerDock` 契约。
- 不新增第三种 composer variant。
- 不使用 browser-only 验收。
- 将 `useRunStageScrollController.ts` 重构为 reducer-owned Workbench scroll state。

这个方向本身仍可作为长期目标，但不能再以同一分支、同一批改动一次性推进。

## 3. 实际执行过的改动类型

`codex/workbench-prd-full-implementation` 分支中曾实际尝试过以下类型的改动：

- 在 `useRunStageScrollController.ts` 中新增 reducer-owned scroll state，建模 `activeTurnId`、`latestTurnId`、`pendingAnchorTurnId`、`followLatestOutput`、`pausedByUser`、`resumeIntent`、`returnToLatestVisible`、`programmaticScroll` 等状态。
- 修改 latest prompt / active sticky turn 的归属，尝试修复连续多行 prompt 后旧 prompt 继续 sticky 的问题。
- 修改 latest-output tail follow 和 composer avoidance，尝试让 final output 与 dock composer 保持可读间距。
- 新增 return-to-latest affordance，并多次调整其视觉与位置：从带文字按钮改为白色圆形下箭头，再尝试放到输入框上方。
- 为了让按钮位于输入框附近，曾把按钮实现耦合进 composer 区域，并尝试通过 wheel 事件处理补救滚动。
- 新增 collapsed work packet 的 narrative 类型、projector 聚合和 design-system 展示组件。
- 增加多项单元测试、typecheck、design-system smoke 和截图证据。

这些改动中，若单独拆开看，部分可以通过静态测试或局部截图；但它们叠加后改变了中间区域滚动事实和 composer 事实，真实 Desktop 中出现了 P0 回归。

## 4. 用户反馈与失败信号

用户通过真实 Awaken Desktop 截图连续指出：

- 发送短文本 / 多行 prompt 后，旧 prompt 或重复 prompt 仍可能出现在错误位置，sticky/anchor 行为没有稳定。
- return-to-latest 入口最初的视觉不符合要求：应为白色圆形下箭头，不应显示“回到最新输出”文字。
- 按钮应在输入框上方中轴，并随输入框多行高度变化上移；实际实现中按钮位置不稳定，甚至落入输入框区域或离输入框过远。
- 按钮周围的层不应阻挡内容，文字应能视觉穿过；实际实现引入了新的遮挡或布局占位风险。
- 为按钮调整布局后，本项目原有输出内容与输入框之间的间距被破坏。
- 更严重的是，中间区域滚动效果整体失效，用户明确确认“原先的滚动设计被破坏了”。

最终用户要求关闭 Awaken 并删除 `codex/workbench-prd-full-implementation` 分支。

## 5. 反模式

- **AP-001：一次性全量实现 Workbench PRD。** sticky/anchor、latest follow、return affordance、transcript replay、work packet 都是高耦合交互域，不得在同一分支一次性改完后再靠静态测试兜底。
- **AP-002：在真实滚动失败后继续叠补丁。** 一旦真实 Desktop 确认中间区域滚动被破坏，应先撤回导致破坏的实现，再重新切小阶段；不能继续在坏状态上调整样式或事件。
- **AP-003：把 return affordance 当作 ComposerDock 内容。** “回到最新输出”按钮不得作为 `ComposerDock` 的普通直接子元素参与 flex 布局、子项宽度规则、composer 高度测量或 `composerContentInset` 计算。
- **AP-004：用 wheel 转发修复 overlay / composer 造成的滚动问题。** 中间区域滚动事件链应保持在 `RunStage` 滚动容器内；按钮浮层只能让按钮本体响应点击，不能拦截、代理或改写 scroll / wheel。
- **AP-005：为了放置按钮改变 output tail / composer inset。** return affordance 是视觉恢复入口，不是新的布局事实；不得通过改变输出与输入框间距、safe area 或 scroll tail 来给按钮腾位置。
- **AP-006：把截图脚本或单测通过当作动态验收。** Workbench 中间区域的真实滚动手感、按钮跟随多行输入框、sticky 交接、用户暂停 follow，只能由真实 Awaken Desktop 的交互验收最终判定。
- **AP-007：把视觉需求和状态机重构绑在一刀里。** 按钮样式、位置和点击行为必须单独实现、单独验收；不得与 reducer 状态模型、transcript replay 或 work packet 聚合混在同一刀。

## 7. 下次重启实现的最小前置条件

再次实现本 PRD 前，必须先满足：

1. 基于 `main` 新开分支，不复用已删除的 `codex/workbench-prd-full-implementation`。
2. 每个阶段开始前写明只触碰哪些文件、只改变哪个行为轴。
3. 每个阶段结束后立即运行静态检查，并在真实 Awaken Desktop 中完成对应 AC 验收。
4. return-to-latest 按钮实现前，先画清楚挂载层级：必须属于 `RunStage overlay` 视觉层，不属于 `ComposerDock` 内容层，不属于 `ExecutionFeed` narrative 层。
5. 只要用户在真实窗口确认中间区域滚动被破坏，该阶段立即回滚。
