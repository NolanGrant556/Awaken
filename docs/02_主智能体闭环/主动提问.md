# 主动提问

## 权威范围

本文唯一定义 `ask_user` 的问题合同、等待/回答生命周期与主循环恢复。问题卡在 Workbench 中的布局和 composer 复用属于 [01 中间交互区域产品契约](../01_桌面工作台/中间交互区域/产品与交互契约.md)；事件 route 和字段属于 09。

## 功能与用户流程

当智能体缺少会显著改变结果的用户选择时，可调用 `ask_user`。ToolRuntime 截获该调用，发出专用 question request 并暂停当前工具结果；用户在 Desktop 选择选项、可填写“其他”内容并提交后，runtime 把回答转成一个正常的 tool result，Runner 从原 conversation 继续。

这不是审批：

- `ask_user` 用于补齐任务意图，用户回答会成为模型后续输入。
- 群发消息审核属于 04 的专用安全 gate。
- 普通工具调用不会因为 `ask_user` 的存在而进入通用 `ApprovalCard`。

## 输入合同

新模型调用使用结构化 `questions`：

- 一次 1–3 个问题；
- 每题 2–4 个明确选项，默认单选；`multi_select=true` 时允许多选；
- `question`、选项 `label` 必填；
- `header`、选项 `description`、`multi_select` 可选；
- Desktop 可以提供“其他”自由文本，但当前没有“只有自由文本、没有选项”的独立题型。

`questions_json` 和裸数组解析仅用于历史兼容，不应继续出现在新 prompt、示例或调用代码中。JSON schema 是新调用的限制来源；兼容解析器对旧载体较宽松，不代表产品合同放宽。

代码 owner：[`src/tools/ask_user/ask_user.go`](../../src/tools/ask_user/ask_user.go)。

## 状态与事件流

1. 模型产生 `ask_user` tool call。
2. ToolRuntime 不调用普通 executor，而是构造 question request。
3. [`src/runtime/session.go`](../../src/runtime/session.go) 登记 pending question，并等待 answer、cancel 或 terminal。
4. Desktop 通过 09 协议域定义的 question answer 动作提交非空回答。
5. Session 校验 run/question identity，完成等待；ToolRuntime 生成含 `answer_text` 与 `question_count` 的 canonical outcome。
6. 该结果按普通 tool result 进入 journal 和模型续轮。

若 sink 不支持等待、run 取消、question identity 不匹配或回答为空，runtime 不执行任何替代副作用；pending question 被清理并形成明确失败/取消结果。

## 不变量与边界

- 同一个 pending question 只能完成一次；迟到回答不得复活已终止 run。
- question request 与 resolved 必须携带同一 run/question identity。
- 用户回答必须作为 tool result 回到原 tool call，不能额外伪造 user message 破坏 pairing。
- Workbench 必须使用既有 `RunStage`/composer ownership；不得为问答卡新增第二个滚动容器或输入系统。
- 问题不得承载密码、API key 等敏感凭据收集；凭据入口属于 05 模型配置。

## 当前不支持

- 没有开放式无选项题型。
- 没有跨 run 保留待回答问题；关闭或终止 run 后必须重新询问。
- 没有把普通文件修改、Shell 或 MCP 调用转换成 `ask_user` 审批的机制。
