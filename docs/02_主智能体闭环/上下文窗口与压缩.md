# 上下文窗口与压缩

## 权威范围

本文唯一定义主智能体的上下文组装、token 估算、warning/compact/blocking 阈值、压缩结构与恢复策略。它不拥有 provider profile 字段（见 05 模型域），也不拥有消息的磁盘格式（见 03）。

## 当前能力

每次模型请求都从 `ContextEnvelope` 重建上下文，而不是把 renderer 的可见文本直接拼成 prompt。当前 envelope 包含：系统块、用户与系统上下文项、附件、工具 schema、runtime snapshot、窗口状态、cache keys/deltas、conversation messages 与 compact model 配置。

[`src/agentcore/request_builder.go`](../../src/agentcore/request_builder.go) 是请求组装 owner；[`src/agentcore/context_window.go`](../../src/agentcore/context_window.go) 负责估算和阈值；[`src/agentcore/context_compactor.go`](../../src/agentcore/context_compactor.go) 负责压缩；[`src/agentcore/runner.go`](../../src/agentcore/runner.go) 负责在 loop 中触发 warning、compact 和 reactive retry。

## 窗口模型与阈值

默认模型窗口为 128,000 tokens，预留输出 16,000；有效输入窗口为模型窗口减输出预留。当前默认阈值：

| 阶段 | 默认值 | 行为 |
| --- | --- | --- |
| warning | 有效窗口的 85% | 发出上下文警告，run 可继续 |
| automatic compact | 有效窗口的 90% | 在下一次模型调用前压缩；profile 可覆盖，但不能超过有效窗口 |
| compact target | 有效窗口的 30% | 摘要后保留尾部消息，目标降到该占用附近 |
| blocking | 有效窗口减 4,000 | 无法安全压缩时拒绝继续请求 |

这些是当前代码常量，不是 provider 精确 tokenizer 的承诺。估算器用本地启发式方法计算系统内容、上下文项、附件、消息和工具 schema；真实 provider usage 另行保留，不能用回传 usage 倒改此前的本地估算。

## 压缩流程

1. RequestBuilder 计算 `ContextWindowState` 并发出 warning/compact 建议。
2. 到达自动阈值时，Runner 调用 compact service；已经在最近边界之后的必要尾部消息保留。
3. 历史按语义组分割。assistant tool call 与紧邻 tool result 是不可拆分单元，不能为节省 token 破坏配对。
4. 大型工具结果先形成结构摘要；当前结构摘要阈值为 256 tokens。
5. compact model 生成摘要，摘要以带 `CompactBoundaryID` 的 user message 进入 conversation，随后拼接保留尾部。
6. 摘要默认最大输出 8,192 tokens。若摘要请求自身过长，可最多做两次裁剪重试。

摘要不是完整 transcript，也不能替代 SemanticJournal。磁盘仍保留原始语义事实；compact 只改变后续模型看到的 conversation 视图。

## 降级与恢复

压缩层有确定性 fallback：配对失败、空摘要、信息量过低、模型调用失败或重试耗尽时，生成带原因标记的结构化 fallback，而不是静默丢弃全部历史。

连续三次 compact 失败后打开 compact circuit。若仍低于 blocking 阈值，run 可以继续并保留警告；若已经到 blocking 区域，终止为 `context_blocked`。provider 返回 prompt-too-long 时，每个 run 最多触发一次 reactive compact retry，避免无限“压缩—重试”循环。

`context_warning` 和 `compact_failed` 也是终态枚举成员，但日常 warning 或一次 compact fallback 不必然结束 run；是否终止取决于窗口是否仍可安全请求和 circuit 状态。

## 当前不支持

- `CompactModeManual` 类型存在，但 Desktop 没有正式的手动 compact route 或用户入口。
- 不使用 provider 的精确 tokenizer 作为统一估算真相。
- 不支持 provider 托管的隐式 compact 取代本地语义边界。
- 不允许通过删除 tool result、附件事实或最近用户目标来强行跨过 blocking 阈值。

## 依赖与不变量

- 工具池必须先经 08 的 Skill activation 与 04 的可见性过滤，再进入 token 估算；不能估算一套 schema、实际发送另一套。
- compact 前后 tool pairing 必须成立；校验 authority 见 [04 工具决策、Outcome 与失败监督](../04_工具权限与审批/工具决策、Outcome与失败监督.md)。
- 摘要中的文件、artifact 和失败结论只能来自 canonical facts，不能根据 UI 文案推断。
- blocking 必须显式终止，不可在用户不知情时丢掉关键上下文继续执行副作用工具。
