# Awaken Tool Layer 深度调研与差距分析

更新时间：2026-07-11

研究口径：Awaken 当前工作区、OpenAI Codex 官方源码与文档、Anthropic Claude Code 官方文档与官方 SDK 类型。

仓库基线：`main` / `d85ece10a584871bde2d6ca351471478768cf1e2`

文档状态：Phase 1 完成；本文件只记录本轮修改前的调研基线与差距，不把后续已实施状态回写为调研起点。实施后事实以 `迁移说明.md` 和 `验收记录.md` 为准。

## 1. 执行摘要

用户背景中“Awaken 工具只返回 `success + message`”已经不是当前源码事实。2026-07-11 的工作区已经具备：

- 递归 JSON Schema 与执行前校验；
- canonical `tool.ExecutionOutcome`；
- transport、semantic、process 三层状态；
- 结构化 error code/category/retryability/recovery options；
- affected paths、patch summary、artifact、digest、timing、truncation字段；
- ToolCall/ToolResult 耐久语义账本；
- live/replay 共用 projector；
- permission/profile/executor router；
- FailureSupervisor 重复失败预算。

因此，本轮不应另造一套平行 Tool Layer。真正问题是现有能力处于“双轨迁移态”：

1. `ToolDefinition` 仍只描述基础元数据，不能作为完整能力契约。
2. 模型实际看到的是 `Description() + input schema`，并非完整 definition。
3. 33 个静态 builtin 中仍有 9 个走 legacy `string,error`；MCP、Skill 动态工具也未进入结构化结果主路径。
4. 现有 Outcome 有底层事实，但缺少统一的 `summary / operation / changes / environment / warnings / errors / next_actions` 语义层。
5. 一些事实在 UI、journal、模型结果之间没有完全收口，存在状态误判或字段丢失。

推荐方向不是简单加字段，而是建立两条单一事实链：

```text
ToolDefinition v2
  -> registry validation
  -> provider-specific compact schema/description
  -> permission/exposure/audit views

ExecutionOutcome v2
  +-> model compact payload
  +-> semantic journal projection
  +-> AG-UI/Desktop projection
  +-> audit/hooks/telemetry projections
```

第二条是从 canonical fact 并行派生多个受控视图，不是 model payload 继续流入 journal 或 UI。

## 3. Awaken 当前架构

### 3.1 注册与模型暴露

```text
Builtin init / dynamic MCP / Skill
        |
        v
src/tool global registry
        |
        +--> ToolExposurePolicy
        +--> ResolvedToolPool
        |
        v
RequestBuilder
  -> t.Description()
  -> ResolveInputSchema(t)
        |
        v
ToolSchema{name, description, parameters}
        |
        +--> OpenAI adapter
        +--> Anthropic adapter
```

当前关键事实：

- `tool.Tool` 同时要求 `Description()`、`Parameters()`、`Definition()` 与 legacy `Execute()`。
- `ToolDefinition` 只含 name、display name、source、description、annotations、policy。
- RequestBuilder 使用 `t.Description()`，不使用完整 `ToolDefinition`。
- `ResolveInputSchema` 支持递归 schema，但多数工具仍由扁平 `[]ToolParameter` 生成浅 object。
- raw `apply_patch` 默认被 exposure policy 隐藏；Skill effective pool 同时在模型侧与执行侧收窄。

### 3.2 执行链

```text
LLM ToolCall
  -> durable ToolCall record
  -> FailureSupervisor.BeforeCall
  -> ToolRuntime
       -> effective pool gate
       -> registry lookup
       -> schema validation / legacy normalization
       -> ExecutionIntent
       -> subagent / guardian boundary
       -> permission / auto policy
       -> executor router
       -> OutcomeTool or LegacyOutcomeAdapter
  -> FailureSupervisor.AfterOutcome
  -> durable ToolResult + Artifact batch
  -> Outcome.ModelPayload() for next LLM turn
  -> shared semantic projector for live/replay
```

这条链已经具备正确的扩展点，不需要重写 Agent Loop。

### 3.3 当前 Definition 能力

已有能力：

- tool source；
- read-only、destructive、open-world、requires-auth；
- capability class、trusted origin、file bridge、network scope、mass-message metadata；
- recursive schema 与 pre-execution validator；
- source-specific exposure 与 permission routing。

主要缺口：

- 没有 `purpose`、`when_to_use`、`when_not_to_use`；
- 没有 canonical `input_schema` 和 `output_schema`；
- 没有 side-effect contract、permission contract、examples、failure modes；
- registry 只检查 Name、Source、Description，未检查 name identity、annotations consistency、schema contract；
- `Description()` 与 `Definition().Description` 可漂移，当前已有实际不一致；
- MCP 保存 raw input schema，却未用 `InputSchemaProvider` 把它传给模型/validator；
- `ask_user` 把嵌套对象再次编码进 `questions_json` 字符串；
- artifact 工具存在相近名称和空 executor stub，增加错误选择概率。

### 3.4 当前 Result 能力

`ExecutionOutcome` 已经包含：

```text
status
transport_status
semantic_status
process_status
exit_code / signal / timed_out
error_code / error_category / error_message
retryable / recovery_options
diagnostic
affected_paths / patch_summary / artifacts
started_at / finished_at / duration_ms
truncated
```

这是本轮应继续扩展的 canonical 类型。

主要缺口与真实 bug：

1. 9 个静态 builtin 仍未实现 `OutcomeTool`：`artifact_publish`、`ask_user`、`calculator`、`grep_search`、`list_files`、`read_artifact`、`text_file_create`、`trash_file`、`web_search`。
2. MCP `CallToolResult.IsError=true` 目前被格式化成人类文本，但 Go error 为 nil，legacy adapter 会把它标为 succeeded。
3. legacy adapter 把所有 Go error 统一归类为 retryable `tool_execution_failed`，丢失 validation、not-found、permission 和 domain 语义。
4. ToolRuntime 截断兼容 `Content` 时没有同步 canonical `Outcome.Content/Truncated`，模型与 UI 可能看到不同长度的结果。
5. permission metadata 的 affected paths 不一定回写 Outcome，legacy mutation 的路径可能进入事件却不进入下一轮模型。
6. `needs_auth` / `needs_runtime` 的 retryability 在 decision 与 synthesized outcome 之间不一致。
7. `ModelPayload` 没有 artifacts、operation、actual changes、state observation、warnings 和 next actions。
8. trash/change 仍有从人类文本反解析中文 marker 的路径，不能作为机器协议长期保留。

### 3.5 当前状态反馈

已有：

- 初始 runtime snapshot：cwd、workspace、scope roots、attachments、tool/skill summary；
- read digest：sha256、size、mtime；
- text edit：before/after digest、replacement count、diff；
- shell：command、cwd、stdout、stderr、exit、timeout；
- mutation：affected paths、patch summary、artifact、file-change record、turn diff。

缺口：

- 没有统一的 observation scope/provenance；
- 没有统一区分“已观察到的变化”“可能发生的副作用”“未知状态”；
- 没有统一 git/process/environment delta；
- 各工具自由写 `Diagnostic`，字段不可发现、不可 lint；
- Artifact 既可在 Outcome 中出现，也可由独立 producer/event 生成，尚未完全收口。

结论：不应在每次结果中无条件跑全量 `git status + process list + env`。正确方案是“baseline context + operation delta + explicit observation scope + on-demand snapshot”。

## 4. OpenAI Codex Tool Architecture

### 4.1 结构

Codex 当前结构可概括为：

```text
ToolSpec / ToolExecutor
  -> exposure / namespace / deferred loading
  -> ToolRegistry
  -> hooks + dispatch
  -> handler parse / environment resolution
  -> ToolOrchestrator
       approval -> sandbox -> first attempt -> escalation -> retry
  -> ToolRuntime
  -> ToolOutput adapters
       model / code mode / UI / hooks / telemetry
```

官方源码：

- [`codex-rs/tools/README.md`](https://github.com/openai/codex/blob/a328f30172c606cfdc150c009790a3f05bfb4d22/codex-rs/tools/README.md)
- [`ToolExecutor`](https://github.com/openai/codex/blob/a328f30172c606cfdc150c009790a3f05bfb4d22/codex-rs/tools/src/tool_executor.rs)
- [`ToolSpec`](https://github.com/openai/codex/blob/a328f30172c606cfdc150c009790a3f05bfb4d22/codex-rs/tools/src/tool_spec.rs)
- [`ToolRegistry`](https://github.com/openai/codex/blob/a328f30172c606cfdc150c009790a3f05bfb4d22/codex-rs/core/src/tools/registry.rs)
- [`ToolOrchestrator`](https://github.com/openai/codex/blob/a328f30172c606cfdc150c009790a3f05bfb4d22/codex-rs/core/src/tools/orchestrator.rs)

### 4.2 值得引入

- Definition/spec 与 runtime executor 绑定为一个注册单元，减少声明与实现漂移。
- Direct、Deferred、DirectModelOnly、Hidden exposure，适合大工具集按需加载。
- namespace 与 tool search 让模型先选能力域，再加载完整 schema。
- shell 的 PTY/session/chunk/truncation contract 清晰。
- approval policy 与 sandbox capability 分层，支持最小额外权限与 escalation retry。
- apply_patch 使用 Lark grammar freeform tool，不把 DSL 再包进脆弱 JSON string。
- UI lifecycle、partial patch delta、duration、sandbox metadata 很完整。
- 环境采用 baseline/snapshot/diff，而不是每次重复全量状态。

### 4.3 不足

- Provider-facing function schema 仍主要是 name、description、input；内部 `output_schema` 不会序列化到普通 Responses 请求。
- 工具短 description 与全局 prompt 分开维护，边界可能漂移。
- 大多数 tool strict=false。
- 普通 direct exec 给模型格式化文本，code mode 才给 JSON；UI 又有更丰富的第三种 shape。
- apply_patch 在 code mode 的结果甚至是空 object。
- 高层 `FunctionCallError` 只有 `RespondToModel(String)` / `Fatal(String)`，底层 typed error 在模型边界被压成字符串。
- unified exec 的 logging success 与非零 exit 的 operation failure 没有统一命名。
- 本地读取、目录和 grep/glob 主要依赖 shell/rg；不适合 Awaken 降低 shell 误用的目标。

- [`ResponsesApiTool`](https://github.com/openai/codex/blob/a328f30172c606cfdc150c009790a3f05bfb4d22/codex-rs/tools/src/responses_api.rs)

## 5. Claude Code Tool Architecture

### 5.1 公开可验证结构

Claude Code 的公开契约是四层协作：

1. `tool_use_id + name + typed input` 与对应 `tool_result`。
2. 工具专属强类型结果。
3. permission、sandbox、hooks、task/checkpoint 独立控制平面。
4. read-before-edit、stale-write、exact-match、partial/truncated 等可恢复不变量。

官方证据：

- [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- [Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- [Agent SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript)
- [Claude Code tools reference](https://code.claude.com/docs/en/tools-reference)
- [Configure permissions](https://code.claude.com/docs/en/permissions)
- [Configure the sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing)
- [Hooks reference](https://code.claude.com/docs/en/hooks)
- [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

### 5.2 值得引入

- Description 必须说明 what、when、when-not、参数影响、限制和不返回什么。
- 复杂输入提供 schema-valid examples；职责相近工具必须从“何时用”区分。
- Tool name 同时作为模型、permission、hooks、subagent、skill 的 canonical identity。
- Edit 的 read-before-edit、stale detection、exact match 和 uniqueness 是执行器不变量，不靠提示词。
- Edit/Write 返回 structured patch 与可选 git diff。
- Glob 返回 `truncated`，Read 返回 partial/continuation，Bash 大输出落盘并给路径。
- Bash stdout/stderr 分离，后台任务返回稳定 task id。
- deny、ask、allow 与 OS sandbox 分层；prompt 不改变真实权限。
- tools 被裸 deny 时可从模型上下文移除。
- hooks 可在执行前修改/阻断，也可在失败后补充 additional context 或 retry 信号。
- 大工具集采用 tool search，避免同时加载 30–50 个完整 schema。

### 5.3 不足

- 公开主协议只有 `is_error`，没有统一、稳定的 error taxonomy。
- 没有统一 `next_actions[]`；恢复依赖工具专属错误、hooks 和模型推理。
- 启动 git snapshot 与后续状态可能漂移。
- Bash 副作用不天然形成完整文件变更清单，也不受 file checkpoint 完整保护。
- tool permission 字符串匹配不能替代 OS sandbox。
- SDK/hook structured output 与真正 model-facing serialization 是两层，容易被误读为同一结果。

## 7. 推荐引入与明确不引入

### 7.1 引入

1. Definition 与 runtime executor 绑定。
2. 富内部定义、provider-specific compact adapter。
3. purpose/when/not/examples/failure modes 单一事实源。
4. 统一版本化 Result Envelope，保留工具专属 details。
5. invocation/transport、operation/semantic、process 三层状态继续分开。
6. baseline + delta + observation provenance。
7. Read-before-edit、stale revision、partial/truncated continuation 等执行器不变量。
8. Direct/Deferred/Hidden exposure 与大工具集检索。
9. error code/category/stage/retry/partial effects/possible fixes。
10. contract lint、golden payload、真实 transcript tool-selection eval。

### 7.2 不引入

1. 不另造与 `ExecutionOutcome` 平行的第二结果类型。
2. 不把完整 YAML 原样塞进所有 provider 的 description。
3. 不把每次调用都变成全量 git/process/env 扫描。
4. 不把权限声明当真实安全边界。
5. 不依赖全局 prompt 修补工具职责。
6. 不把本地 read/search 全部退回 shell。
7. 不用字符串解析恢复错误、状态或 trash path。
8. 不在本任务重写 Agent Loop、Planner、Memory、Provider 或 UI。

## 8. 改造优先级

1. 修复协议真相错误：MCP IsError、Outcome truncation、retryability、affected paths、trash result。
2. 建立 `ToolDefinition v2 + ResolveDefinition` 单一事实源。
3. Registry 分阶段启用 contract validation。
4. RequestBuilder 从 resolved definition 编译 model description/input schema。
5. 在现有 `ExecutionOutcome` 上添加 Result Envelope v2 语义字段。
6. legacy builtin、MCP、Skill 进入同一 Outcome adapter；高风险工具显式迁移。
7. 增加 contract/eval/compat tests。
8. 按 README 从真实 Awaken Desktop 做工具选择、成功、失败和恢复 smoke。

详细架构与迁移门禁见同目录 `架构设计.md`。
