# MCP 工具接入与技能桥接

## 1. 权威范围

本文档是 MCP tool 动态注册、schema/annotation 映射、调用结果和 MCP prompt/resource 到 Skill 桥接的权威。Skill 的本地包格式、激活计划和执行模式由 [08 技能](../08_技能/索引.md) 持有。

## 2. MCP tool 注册与名称

server 进入 `connected` 后，Manager 调用 `tools/list`，对每个工具建立 `McpToolAdapter`，并以下列名称强制注册到中央 registry：

```text
mcp__{serverName}__{toolName}
```

server 断开、失败、停用或被删除时，按 `mcp__{serverName}__` 前缀反注册。`tools/list_changed` 刷新同一 server 的全部工具，不影响其他 server。

## 3. schema、annotation 与权限边界

- Adapter 保留 MCP server 给出的递归 input JSON Schema；无法安全解码时才回退到扁平 `ToolParameter`。
- output schema 被收纳为 `ExecutionOutcome.Details` 合同；与 Awaken outcome envelope 冲突的字段会包装，不覆盖 canonical status/error。
- 有 MCP annotations 时使用 `readOnlyHint`、`destructiveHint`、`openWorldHint`；缺失时默认 `readOnly=false`、`destructive=true`、`openWorld=true`。
- Adapter 会根据 server/tool 名和 trusted origin 进一步推断 connector/browser capability。只有 official connector/hosted origin 可获得 task-scope read file bridge；普通第三方 server 默认 `FileBridgeNone`。
- MCP 工具仍经过统一 `tool.Decide` 和 ToolRuntime，不得因为 server 自报 read-only 就绕过 TaskScope、网络边界或审计。

## 4. 调用结果

`Manager.CallTool` 从带前缀名称解出 server 和原 tool name，再调用 MCP `tools/call`。Adapter 将结果区分为：

- transport/protocol error：Go error + 结构化 failed outcome。
- MCP `CallToolResult.IsError=true`：transport 已完成，但业务语义为失败，使用 `mcp_tool_reported_error`。
- 成功：文本内容进入 model payload，`structuredContent` 在符合 output contract 时进入 `Details`。

输出长度和结构由 `McpToolAdapter` 和通用 outcome 合同限制；不得将 server 原始返回无限制透传到模型或 UI。

## 5. MCP Prompt/Resource 到 Skill 的当前链路

`src/skills/mcp_bridge.go` 订阅 Manager 事件：

```text
Connected / PromptsListChanged / ResourcesListChanged
  -> 每 server 300ms debounce
  -> prompts/list + resources/list
  -> reconcile SkillRegistry

Disconnected / Disabled
  -> 立即删除 mcp__{server}__* Skills
  -> 将该 server 标为不可用
```

映射规则：

| MCP 输入 | Skill 结果 |
| --- | --- |
| prompt | ID `mcp__{server}__{normalizedPrompt}`，参数统一映射为 string |
| `text/x-prompt` resource | ID 取 URI 末段，binding kind 为 `resource` |
| 其他 resource | 不桥接 |

单 server 最多注册 100 个 prompt + resource Skill，超出按 server 返回顺序截断并 warning。所有桥接 Skill 都带 `requiredMcpServers=[server]`；只有 dynamic connector server 在 snapshot 中带 `sourceConnectorId` 时才同时带 `requiredConnectors`。

## 6. Skill bridge 已确认缺口

桥接的发现和注册已存在，但执行不是完整闭环：

1. `FetchPromptBody` 调用 `prompts/get` 时把 `Arguments` 固定为 `nil`，Skill tool 收到的参数没有传给 MCP prompt。
2. 该函数只返回 `GetPromptResult.Description`，没有投影 `messages` 中的 prompt content。
3. resource binding 也复用同一 `FetchPromptBody`，仍调用 `prompts/get`，未调用 `resources/read`；binding kind 没有进入执行分支。
4. resource映射只保留URI末段作为binding reference，完整URI已经丢失；即使把调用改成 `resources/read` 也缺少可靠定位值。
5. bridge 没有独立的 60 秒执行 timeout 包装；实际取决于上层 context/transport。
6. 已连接的 server 如果没有可桥接 prompt/resource，`syncForServer` 会将 `mcpServers[server]` 标为不可用；这会让仅声明 `requiredMcpServers` 的本地 Skill 被误判为不可用。
7. 启动顺序是Manager先异步 `Start`、bridge后订阅事件；`Bridge.Start` 不做首次Manager snapshot reconcile。连接事件若在订阅前完成，重启后动态Skill可能一直不出现。
8. 当前测试锁定了prompt/resource转换和registry操作，但没有启动竞态或从MCP arguments/messages/resource read到真实Skill执行的端到端测试。

因此当前文档和 UI 可称其为“MCP 动态 Skill 发现”，不能称为“prompt/resource 完整执行闭环”。

## 7. 依赖和不变量

- MCP bridge 是单向 `mcpclient.Manager -> skills.Bridge -> SkillRegistry`，Skill 不反向控制 server lifecycle。
- `mcp__` 是桥接 Skill 保留前缀；本地 Skill 使用同前缀时不得与 bridge 竞争。
- server 离线时必须同时卸载 MCP tools 和桥接 Skills，不得留下可选但必然失败的模型工具。
- 对上述已知缺口，只能在修改代码并增加自动化/真实 Desktop 验收后更新为“支持”。
