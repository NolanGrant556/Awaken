## 2. 为什么压后约 30%

当前容量数学在 [context_window.go](/Users/nolangrant/Awaken/src/agentcore/context_window.go:99)：

```text
EffectiveWindow = ModelWindow - OutputReserve
WarningThreshold = EffectiveWindow × 85%
AutoCompactThreshold = EffectiveWindow × 90%
CompactTarget = EffectiveWindow × 30%
```

`CompactTarget` 明确写成 30%，见 [context_window.go](/Users/nolangrant/Awaken/src/agentcore/context_window.go:126)。

Governor 会从完整请求目标中扣除稳定前缀和固定 8192 summary reserve，再把余额交给 conversation tail，见 [context_engine.go](/Users/nolangrant/Awaken/src/agentcore/context_engine.go:381)。这说明当前目标已尝试覆盖完整请求，而不是只计算 tail。

但成功后置条件没有要求 `post <= CompactTarget`。当前只要求：

- 非 fallback summary；
- summary 非空；
- tool pairing 合法；
- post 低于 auto threshold；
- post 低于 block threshold；
- 可压历史足够大时，message tokens 至少减少 20%。

实现见 [context_engine.go](/Users/nolangrant/Awaken/src/agentcore/context_engine.go:336)。因此压后仍高于 30% 也可能被判成功。

## 3. 压缩事务只持久化 conversation messages

`persistContextCompacted` 当前 payload 主要包含：

```text
compact_boundary_id
mode
messages
pre_estimate_tokens
post_estimate_tokens
```

见 [runner.go](/Users/nolangrant/Awaken/src/agentcore/runner.go:156)。它没有原子携带：

- Memory recall snapshot；
- 压后的 Skill blocks；
- RunPlan version；
- tool/dynamic tool snapshot digest；
- 未消费 Subagent handoff；
- Instruction snapshot digest；
- transcript sequence locator；
- critical-fact coverage receipt。

结果是 conversation compact 成功不等于整个模型上下文状态完成了一次原子切换。

## 4. Memory 在成功压缩后被清空

压缩持久化并替换消息后，Runner 会调用 `MemoryRecallReset`，见 [runner.go](/Users/nolangrant/Awaken/src/agentcore/runner.go:75)。`ResetAfterCompaction` 清空已召回记录、pending 和 session budget，见 [recall.go](/Users/nolangrant/Awaken/src/memory/recall.go:332)。

当前 summary 请求只总结 conversation messages，并不确定性包含刚才已召回的 Memory block。压缩后的立即 rebuild 也不等同于重新执行一次新用户 turn 的 Memory selector。

风险：同一 run 压缩后，刚刚影响任务判断的 Memory 可能同时不在 summary 和新请求中。

## 5. Skill live 与 replay 不是同一 source of truth

成功压缩后，Skill 单独按每个 5K、总计 25K token 裁剪，见 [skill_context.go](/Users/nolangrant/Awaken/src/agentcore/skill_context.go:12)。裁剪后的 blocks 没有写入 `context_compacted` bundle。

重启恢复又会从 `skill_activated` records 重建 Skill context。当前风险是：

- live 压后看到裁剪后的 Skill；
- restart/replay 可能重新看到原始 Skill 内容；
- 两者 provider-visible context 不一致。

## 6. Summary 质量门是栏目级，不是事实级

当前 quality gate 只确认若干 section 中至少一个有意义，见 [context_summary_prompt.go](/Users/nolangrant/Awaken/src/agentcore/context_summary_prompt.go:159)。它不验证：

- 用户纠正是否逐项保留；
- pending ask 是否完整；
- 精确数字、路径、命令、错误是否匹配；
- 工具结果 ID、Artifact ID、Subagent task ID 是否存在；
- 上一次 summary 中仍活跃的事实是否迁移。

因此模型可以输出看起来结构完整、但丢失关键事实的摘要并通过质量门。

## 7. Recent tail 不是完整 turn 合同

当前 compactor 主要按安全 message group 和 token 从尾部回填。普通 user 与 assistant 并不天然组成一个不可拆分的完整 turn。风险包括：

- 保留 assistant 回答但压掉其 user 问题；
- 保留工具 exchange，但压掉触发该 exchange 的任务上下文；
- 最近用户意图只通过截断后的 summary anchor 存活。

V2 必须把“最近完整 turn”提升为宿主结构，而不是继续依赖 message 粒度。

## 8. Subagent terminal handoff 是一次性交付

Root 把 terminal child state 投影成 synthetic host notification；Manager 的 `DrainTerminalNotifications` 对每个结果最多交付一次，见 [manager.go](/Users/nolangrant/Awaken/src/subagentruntime/manager.go:485)。

如果该 notification 被压进 prefix，而 summary 没保留，Manager 不会自动重投。V2 必须让未被 root 确认消费的 handoff 成为 bundle 的 durable item。

## 9. 完整历史仍在，但模型缺少当前线程精确恢复入口

Awaken 已有 append-only SemanticJournal 和 archived thread 只读桥，但当前开发上下文没有发现一个面向当前 thread、按 compact boundary/sequence 有界回读旧原文的 root-only 工具。

V2 不应默认把全历史重新放回上下文，而应提供：

```text
thread_history_read(boundary, sequence range, query, limit)
```

实现前重新搜索当前 HEAD；若已有等价能力，复用 owner，不新建第二套历史 API。

## 10. 问题本质

当前失忆不是单一模型质量问题，而是压缩边界覆盖不完整：

```text
conversation 被替换
Memory 被 reset
Skill 被另一条链裁剪
Subagent handoff 被消费
Plan/Instruction/Tool 由其他 owner 重建
```

这些状态没有被同一个 journal-first transaction 绑定。只把 30% 改为 10%，会让上述断层更频繁、更确定。
