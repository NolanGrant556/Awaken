# 运行终止与失败编排

## 权威范围

本文唯一定义 Runner 主循环、transition、取消和 run 级 terminal reason。单个工具的 canonical `ToolOutcome`、重试指纹与 `FailureSupervisor` 数值预算由 [04 工具决策、Outcome 与失败监督](../04_工具权限与审批/工具决策、Outcome与失败监督.md) 定义，本文只说明它们如何驱动 run。

## 主循环

[`src/agentcore/runner.go`](../../src/agentcore/runner.go) 的 `RunStreamWithEvents` 是正式路径：

1. 正常Agent路径写入 `run_started` 与用户输入；composer Skill预激活失败会绕过这段主循环并走runtime专用终态，当前可能没有 `user_message`。
2. 构建上下文和可见工具池，校验现有消息配对。
3. 调用模型并流式发布文本/工具增量。
4. 将完整 assistant message 写入语义账本。
5. 对每个 tool call 先持久化调用事实，再经过 04 的 permission/policy/executor/finalizer。
6. 以完整 tool result 继续下一轮模型请求。
7. 没有工具调用且输出有效时完成；失败、取消、预算或上下文边界形成显式终态。

正式 transition：`initial`、`tool_result_continuation`、`xml_fallback_continuation`、`reactive_compact_retry`、`max_output_continuation`。模型输出达到上限时只允许一次 continuation；再次达到上限终止为 `max_output_reached`。

## TerminalReason

[`src/agentcore/turn_state.go`](../../src/agentcore/turn_state.go) 拥有Runner的typed canonical枚举：

| 分类 | reason |
| --- | --- |
| 正常 | `completed` |
| 用户或宿主取消 | `cancelled`、`aborted_streaming`、`aborted_tools` |
| 预算 | `max_turns`、`max_output_reached`、`repeated_tool_failure` |
| 上下文 | `context_warning`、`context_blocked`、`prompt_too_long`、`compact_failed` |
| 模型/消息 | `model_error`、`tool_pairing_error`、`empty_response` |
| 工具策略 | `tool_policy_abort` |
| 耐久性 | `persistence_error` |

生产路径当前还会写出两个没有进入上述typed枚举的runtime-injected reason：

- composer Skill预激活失败：`skill_activation_failed`；
- 重启恢复封口：`process_restarted`。

它们是当前真实journal/replay事实，也构成类型漂移。新增或收口reason必须同时更新Go类型、runtime写入、journal/AGUI映射、Desktop reducer和重放测试；在修复前不能把 `turn_state.go` 表格称为完整生产全集。

枚举存在不等于每次警告都终止。例如 context warning 通常只发事件；最终是否进入 terminal 由窗口、compact circuit 和请求结果决定。

## 取消语义

- 流式模型请求中取消：终态 `aborted_streaming`。
- 工具批次中取消：尚未执行或未产生结果的调用得到合成 cancelled/interrupted tool result，终态 `aborted_tools`。
- 两轮之间取消：终态 `cancelled`。

无论位置如何，下一条非工具消息出现前，所有已经声明的 tool call 必须各有一个 result。不得为了更快退出而留下孤儿调用。

## 失败监督协作

ToolRuntime 把每个 outcome 交给 `FailureSupervisor`。supervisor 可以：允许继续、要求下一轮改变策略、阻止重复调用，或把 run 终止为 `repeated_tool_failure` / `max_turns`。数值预算、fingerprint 与 recovery directive 的唯一说明在 04；Runner 只消费决策并把 recovery directive 注入下一次 system context。

不相关工具的一次成功不会自动证明原失败已恢复。只有 supervisor 认定资源或同工具的恢复条件满足时，directive 才清除。

## 异常与恢复

- 模型临时错误：按 provider/runner 已定义的有限重试处理，耗尽后 `model_error`。
- provider prompt too long：每 run 最多一次 reactive compact retry；仍失败则 `prompt_too_long`。
- 空响应：没有有效文本和工具调用时 `empty_response`，不能伪造成成功。
- pairing 错误：在发下一次请求前失败为 `tool_pairing_error`，不把坏历史继续提交给模型。
- persistence error：立即进入 fail-stop；不得再启动新的副作用工具。耐久层恢复细节见 03。
- 进程重启：不继续原 run；03 对开放工具调用保守封口，结果未知且禁止自动重执行。

## 不变量与当前不支持

- 每个 LLM 请求前都必须验证消息配对。
- 任何 deny、cancel、policy block、重复失败 block 都产生 terminal tool result，而不是丢弃调用。
- 终态只在所需语义事实写入并按 03 的 durability 边界 flush 后对外确认。
- 不支持无限自动重试、无限 max-output continuation 或重启后盲目续跑。
- 不存在“看起来完成但最后一个工具失败”的隐式成功；run 叙事必须区分交付物已存在与尾随工具失败。

## 测试与 Desktop 验收

自动化 owner：[`src/agentcore/runner_test.go`](../../src/agentcore/runner_test.go)、[`src/agentcore/agent_test.go`](../../src/agentcore/agent_test.go)、[`src/agentcore/failure_supervisor_test.go`](../../src/agentcore/failure_supervisor_test.go) 以及 03 的 journal failure/recovery 测试。

真实 Desktop 验收至少观察：普通完成、模型流中取消、工具执行中取消、一次可恢复工具失败、重复同类失败被阻断、重启后 interrupted 历史。UI 必须显示真实终态；不能因已有 artifact 就覆盖尾随失败，也不能因诊断工具返回“未命中”就误报整轮失败。
