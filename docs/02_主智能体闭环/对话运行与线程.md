# 对话运行与线程

## 权威范围

本文是 run/thread 产品语义与运行服务协作的唯一权威。它负责创建和继续线程、workspace 绑定、同线程并发、run 生命周期与跨重启产品语义；输入文件、metadata 与 journal 的精确持久化顺序由 03 域拥有。

本文不定义：SQLite/JSONL 格式（见 [03 全局数据与会话存储](../03_运行时与本地服务/全局数据与会话存储.md)）、事件字段（见 [09 协议域](../09_AGUI与A2UI协议/索引.md)）、线程列表 UI（见 [01 桌面工作台索引](../01_桌面工作台/索引.md)）。

## 用户入口与当前行为

用户从 Awaken Desktop 的 composer 提交文本、附件或 composer token。运行服务拒绝三者都为空的请求；仅有附件或 token 的请求是有效输入。

- 不传 `thread_id`：创建新线程并返回服务端生成的标识。
- 传入已知 `thread_id`：恢复或复用该线程的 conversation，并把本轮追加到同一历史。
- 传入未知 `thread_id`：返回未找到，不隐式创建同名线程。
- 同一线程已有活动 run：返回 HTTP 409 与 `THREAD_BUSY`。
- 线程已在当前 `RunService` 内存中时，请求 workspace 不一致会返回 `THREAD_WORKSPACE_MISMATCH`。
- **冷恢复缺口**：线程不在内存、需从持久层恢复时，当前代码没有比较 `restoredMeta.Snapshot.Workspace` 与请求 workspace；它会用请求 workspace重建Agent、灌入旧消息并覆盖thread metadata。这会静默跨项目改绑旧历史，是当前严重identity/隔离缺口，不能宣称所有路径都已阻断。
- 同一线程的模型 profile 或 TaskScope 改变：运行服务重建 Agent，但复制既有 conversation；线程身份和历史不变。

`THREAD_BUSY` 是同线程互斥，不是全应用并发上限。当前代码没有主智能体全局并发计数器；Desktop 当前可见入口是否允许同时发起多个线程，属于 Desktop UI 约束而非后端合同。

## 启动顺序与所有权

一次 run 的确定性顺序是：

1. HTTP 层解析输入；运行服务校验输入和内存态线程的workspace。冷恢复workspace校验当前缺失。
2. 运行服务从内存或持久层取得线程；不存在时创建新 conversation。
3. 运行服务按 03 域的存储与 journal 合同准备输入，再登记 active run 与 cancel function 并启动 Agent goroutine。
4. composer Skill 预激活、Agent 主循环和 Runner 继续执行；当前“预激活失败时 replayable user message 可能缺失”的精确时序与 payload 缺口只查 [03 SemanticJournal](../03_运行时与本地服务/SemanticJournal与重放.md)。
5. 终态清理 active run。线程 conversation 继续保留，可由下一轮复用。

conversation 的事实所有权在 runtime，不在 renderer。renderer 可以投影、缓存和选择线程，但不能用本地组件 state 作为恢复真相。

## 状态与终态

运行服务对外状态只有：`running`、`cancelling`、`finished`、`error`、`cancelled`。不存在通用 `awaiting_approval` run 状态。

取消请求先把活动 run 标为 `cancelling` 并触发 context cancel。Runner 根据取消发生位置，形成 `cancelled`、`aborted_streaming` 或 `aborted_tools` 等语义；任何已经向模型声明但尚无结果的 tool call 都必须先补合成 tool result，再进入终态。完整规则见 [运行终止与失败编排](运行终止与失败编排.md)。

## 跨重启语义

重启后，线程 metadata、用户/助手消息、工具事实和终态由全局 SQLite + per-thread SemanticJournal 恢复。当前不恢复重启前的 goroutine、网络 stream 或子进程；未闭合工具调用会被标记为“进程重启，结果未知”，且不会自动重执行。详见 [03 SemanticJournal 与重放](../03_运行时与本地服务/SemanticJournal与重放.md)。

运行服务最多把 100 个非活动线程保留在内存缓存中；这个数字只是内存淘汰阈值，不是持久线程保留上限，也不是并发上限。被淘汰线程仍可从全局存储恢复。

## 不变量与禁止绕过

- 一个 `thread_id` 应永远绑定一个 workspace identity；当前冷恢复分支违反该不变量，修复前不得把它标为已满足。
- 同一线程只有一个 active run；不得仅在 renderer 侧规避 `THREAD_BUSY`。
- 用户输入必须在模型/工具副作用前进入耐久层；当前 journal 输入时序的缺口以 03 SemanticJournal 为唯一说明，02 不能另定义一套记录顺序。
- 线程历史必须从 runtime 恢复，不能重新引入 workspace `.awaken/transcripts` 扫描。
- 取消、拒绝、失败和重启恢复都必须维持 tool-call/tool-result 配对。
- 普通 run 不进入通用审批卡；只有 `ask_user` 和群发消息审核是各自专用 gate。

## 当前不支持与已知限制

- 不支持同一线程并发执行两个 run。
- 不支持自动恢复进程重启前的执行；只恢复可确认的语义历史并保守封口。
- 不支持跨 workspace 移动同一 thread identity。
- 不存在正式的全局最大并发合同；需要全局排队时必须先新增产品与运行时设计。
- 冷恢复workspace mismatch当前未阻断；不得以“不支持跨workspace移动”的产品规则掩盖实现缺口。
- Skill预激活失败的v2 run可能没有durable用户消息；附件关联也不能从当前v2 journal完整重放。

自动化至少覆盖：

- [`src/runtime/run_service_test.go`](../../src/runtime/run_service_test.go)：创建、继续、busy、恢复和取消；现有workspace mismatch只覆盖同一service内存态，必须补冷恢复反例。

- Desktop runtime client/reducer 测试：请求携带 thread identity，重连不重建历史。

真实 Desktop 验收：新建线程发送一轮，再在同一线程发送第二轮并确认上下文连续；运行中尝试同线程重复提交应被阻止；关闭并重新打开 Desktop 后选择该线程，历史应由 runtime 重放且不出现重复消息。不得通过直接 provider 调用替代这条产品链路。
