# 安全凭据存储与恢复契约

## 1. 权威范围

本文唯一拥有模型 API key 的持久化身份、密文 envelope、当前错误与恢复状态、迁移不变量，以及已经确认但尚未实现的恢复设计。

本文不负责 provider catalog、余额或模型调用参数；见 [模型配置与调用](../模型配置与调用.md)。真实 macOS 登录钥匙串事故的诊断和人工恢复见 [macOS 登录钥匙串认证状态失效 QA 案例](./macOS登录钥匙串认证状态失效QA案例.md)。

文中使用两种明确标签：

- **当前实现**：能在当前代码、测试与 Desktop 行为中找到。
- **已确认待实现契约**：当前事故或安全边界已经证明必须满足，但代码、IPC、状态枚举或 UI 尚未闭环。

后一类不能写成当前产品能力。

## 2. 目标与安全不变量

Awaken 在 macOS、Windows 与后续支持的平台上使用同一产品语义保存全局模型 API key：优先自动恢复；无法恢复时在 Awaken 内给出受控动作；不把系统钥匙串、凭据管理器或终端操作暴露为普通用户步骤。

下列不变量同时约束当前实现和后续修改：

1. 模型 API key 是 Desktop 全局配置，不提供 session-only、workspace 级或明文环境变量回写降级。
2. 明文只允许存在于可信本机 Electron 主进程和 `awaken-core` 完成运行所需的内存生命周期。
3. 明文、密文、Authorization header 与底层系统错误不得进入 Renderer 持久状态、日志、错误事件或 transcript。
4. 落盘只允许系统安全存储保护的密文；禁止 `setUsePlainTextEncryption(true)`。
5. 不以 `isAsyncEncryptionAvailable()` 作为操作前置条件；直接执行 async encrypt/decrypt，再按结果分类。
6. 临时不可用、解密失败或迁移失败时保留旧密文，禁止自动清空、覆盖或生成替代密钥。
7. 新密文成功生成并原子持久化后，才允许替换旧密文。
8. app name、application ID、bundle/signing identity 与 `userData` namespace 是持久化凭据身份，不是可随展示文案修改的 UI 字段。
9. Renderer 只接收非敏感摘要和结构化恢复动作。
10. provider 拒绝、网络错误和本地解密失败必须分层，不能共用一个“key 无效”结论。

## 3. 当前持久化身份

当前代码按 launch mode 固定两套互不共享的身份：

| 身份 | 安装版 | 源码开发版 | Owner |
| --- | --- | --- | --- |
| Application ID | `com.awaken.desktop` | `com.awaken.desktop.dev` | `apps/desktop/src/main/desktop-instance.ts` |
| macOS safeStorage app name | `Awaken` | `Awaken Dev` | 同上；在 Electron ready 前由 `app.setName` 设置 |
| userData namespace | `@awaken/desktop` | `@awaken-dev/desktop` | 同上；主进程显式调用 `app.setPath("userData", ...)` |
| profile 文件 | `<userData>/config/model-profiles.json` | `<userData>/config/model-profiles.json` | `ModelProfileStore` |
| capability override | `<userData>/config/model-capability-overrides.json` | `<userData>/config/model-capability-overrides.json` | capability sync |

两种 launch mode 可以同时运行，也共同复用操作系统、用户、项目与 Skill 中的工作工具，但模型 profile、API key、会话和其他 userData 不跨模式读取。开发者需要在 `Awaken Dev` 中单独配置开发凭据；安装版升级继续沿用 `Awaken` 身份和原有凭据。

历史上曾存在 `@awaken/desktop Safe Storage` 与当前 `Awaken Safe Storage` 两个 macOS service namespace。它是迁移风险，但不是每次解密失败的默认根因。

`desktop-instance.test.ts` 当前以字面量锁定两种 mode 的 app name、userData namespace 与 application ID；尚未自动检查安装版 identity 与 `electron-builder.yml` 的 appId parity。任何安装版身份修改都必须先补 parity 测试，并具备凭据兼容迁移、回滚和真实升级验收，不能直接重命名。开发版 identity 独立，不得通过回退到安装版 userData 来复用凭据。

## 4. 当前实现链路

### 4.1 保存

```text
Renderer Models 表单
  -> Preload bridge
  -> IPC awaken:save-model-profile
  -> runDesktopOperation
  -> ModelProfileStore.saveProfile
  -> ElectronSecureCredentialStore.encrypt
  -> safeStorage.encryptStringAsync
  -> v2 credential envelope
  -> profile temp file + rename
  -> Renderer 收到成功摘要
```

安全加密发生在任何 profile 写入之前。加密失败时，新的表单 key 不进入 `model-profiles.json`；更新既有 profile 时，原文件保持不变。

### 4.2 读取与运行

```text
Desktop start-run / connection test / balance / capability sync
  -> ModelProfileStore.decryptProfileCredential
  -> safeStorage.decryptStringAsync
  -> plaintext
  -> 可选 lazy replacement
  -> 当次调用或 ModelProfileRunConfig
  -> localhost awaken-core
```

成功读取后，如果 legacy envelope 或 Electron 返回 `shouldReEncrypt=true`，凭据层生成 replacement。`ModelProfileStore` 只在磁盘中仍是同一旧 credential 时写回，避免 lazy migration 覆盖并发保存的新 key；迁移写回失败会被吞掉，本次可用明文仍可继续，旧密文保留供后续重试。

### 4.3 当前明文内存边界

当前真实实现中，明文会：

1. 在 Electron 主进程解密调用栈和 `ModelProfileRunConfig` 中出现；
2. 通过 localhost run request 交给 `awaken-core`；
3. 进入 `AgentConfig.ModelConfig`；
4. 因 `RunService` 按 thread 缓存 Agent 而持续到 profile 重建、thread 淘汰或进程退出。

当前没有显式 zeroization，也没有覆盖 profile 变更、thread 淘汰和退出清理的完整安全生命周期测试。这是已确认缺口；文档不能缩窄为“只在 Electron 主进程短暂存在”，也不能据此允许持久化或日志记录。

## 5. 密文 envelope 与迁移

`model-profiles.json` 顶层仍是 version 1；每个 credential 独立版本：

```json
{
  "encryptedApiKey": "base64 ciphertext",
  "last4": "1234",
  "version": 2,
  "scheme": "electron-safe-storage"
}
```

当前读取规则：

- 缺少 `version`，或 `version=1` 的记录，按 legacy v1 读取；legacy 记录可以没有 scheme。
- `version=2` 必须显式使用 `electron-safe-storage` scheme；缺失或不一致都会在调用 safeStorage 前按 `unsupported_version` 拒绝。
- 其他 version 拒绝。
- base64 必须非空、格式严格且 round-trip 一致。
- legacy v1 或 `shouldReEncrypt=true` 触发 lazy replacement；无效的 v2 scheme 不解密，也不触发 replacement。
- replacement encrypt 失败时，不丢弃已解出的本次 plaintext，也不修改原 envelope。
- replacement persist 使用 compare-and-swap 语义；并发用户保存优先。

当前 envelope 暴露 `last4` 给 Renderer 用于掩码展示。它不是认证数据；QA 证据和日志不应记录实际尾号。

## 6. 当前状态与结构化恢复

### 6.1 底层错误

`SecureCredentialErrorCode` 当前只有：

```text
temporarily_unavailable
invalid_ciphertext
unsupported_version
encrypt_failed
decrypt_failed
```

Electron 原始异常只在主进程用于分类，不跨 IPC。`temporarily unavailable` 的字符串模式被归一为 retryable 的 `temporarily_unavailable`；其他 encrypt/decrypt 异常使用安全中文文案。

### 6.2 Profile 状态

`ModelCredentialStatus` 当前只有：

```text
ready
missing_key
disabled
temporarily_unavailable
unreadable
```

状态转移是进程内观察结果：

```text
no credential -> missing_key
disabled -> disabled
credential present, no observed failure -> ready

ready
  -> decrypt temporary failure -> temporarily_unavailable
  -> invalid/unsupported/decrypt failure -> unreadable
  -> decrypt success -> ready

missing_key
  -> secure encrypt + atomic profile write -> ready

ready/unreadable/temporarily_unavailable
  -> secure replacement save succeeds -> ready
```

`ready` 表示存在密文且本进程尚无失败观察，不保证当前系统一定可以解密；只有真实 decrypt 成功才能证明当次可用。

### 6.3 Desktop 操作错误

跨 IPC 的 `DesktopOperationIssue` 当前为：

| Code | 当前动作 | 语义 |
| --- | --- | --- |
| `credential_temporarily_unavailable` | `relaunch` | 保留密文；同进程重试没有价值 |
| `credential_unreadable` | `reenter` | 当前实现把 invalid/version/decrypt failure 归为重新录入 |
| `credential_save_failed` | `relaunch` | 新值未保存；原值保留 |
| `operation_failed` | `retry` | 非凭据或未分类失败；未知下游文案被脱敏 |

Renderer 支持 `retry / relaunch / reenter` 三种动作。`relaunch` 在 macOS 开发态调用仓库托管 helper 重建完整 Desktop；打包态使用 Electron relaunch。

### 6.4 当前恢复限制

Electron async encryptor 会在同一进程复用 provider；临时空密钥初始化后，循环 decrypt 通常不会重新查询 Keychain/DPAPI，所以当前正确的第一恢复动作是受控 relaunch。

但当前实现无法识别“同类错误已经跨进程持续”。relaunch 后若仍失败，代码会继续落回 `temporarily_unavailable` 或 `unreadable`，没有持久化尝试次数，也没有 `system_reauthentication_required`。

## 7. 已确认但尚未实现的恢复契约

2026-07-11 的真实 macOS 事故证明：Awaken relaunch 后仍不可读的原密文，可能在用户完成系统重新认证后恢复，无需重录。因此以下是已确认待实现契约：

```text
relaunch_required
  -> controlled_relaunch
  -> ready
     | system_reauthentication_required
     | reentry_required

system_reauthentication_required
  -> user_system_reauthentication
  -> ready | reentry_required
```

完成实现必须同时具备：

1. 能跨进程识别同类失败，而不是无限提示 relaunch。
2. 新增明确 wire/UI 状态；当前枚举中不存在该状态。
3. 继续保留旧密文，不自动删除、覆盖或要求重录。
4. 将系统层、应用 identity/envelope 层与 provider 层分类。
5. 普通用户只看到 Awaken 内的安全引导；系统认证必须由 OS UI 或用户交互完成。
6. 只有确认永久不可恢复且当前安全写入可用时，才进入重新录入。
7. 有不含秘密的 `credential_decrypted`、`transport_started`、`provider_response_received` 与 credential write attempt 证据。
8. 为明文在 Electron/Core/Agent thread 中的存活与清理补齐实现和自动化。

在这些条件落地前，`system_reauthentication_required` 只能出现在“已确认待实现”章节和 QA 分类中，不能列入当前产品状态表。

## 8. 平台边界

### macOS

- Electron safeStorage 依赖 Keychain。
- app name、签名、bundle identity、登录钥匙串认证状态和历史 namespace 都可能影响读取。
- Keychain 条目能枚举不等于秘密值可读。
- lock/unlock 只允许工程/QA 在用户知情和交互式参与下按专用案例执行。

### Windows

- Electron safeStorage 依赖 DPAPI。
- 当前用户身份、管理员重置密码、跨用户/跨机器复制和 userData/Local State 丢失可能导致不可恢复。
- 产品状态与数据保护不变量应与 macOS 一致；具体人工处置不能复制 macOS 命令。

### 通用结论

操作系统永久拒绝或丢失主密钥时，应用无法安全还原旧 key。正确路径是保留非敏感 profile，在 Awaken 内重新录入，并只在安全写入成功后替换；不是明文 fallback。

## 9. 产品行为

当前 Desktop：

- 临时不可用：显示“模型密钥暂不可用”，提供“重新启动 Awaken”。
- unreadable：提供“在 Awaken 中恢复”，先打开 Models 的已配置列表；用户仍需再选择具体 profile 才进入编辑。
- 保存失败：不显示成功，新的 key 不写入 store。
- 余额页将多个 profile 的相同凭据故障折叠为一个恢复状态。
- 设置页用 profile status 区分 ready、missing、disabled、temporary、unreadable。

当前不具备：

- relaunch 次数持久化与跨进程故障升级；
- `system_reauthentication_required` UI；
- OS 原生系统重新认证引导；
- 可信内存主动清理/zeroization；
- 完整 macOS/Windows 故障注入 contract suite。

## 10. 异常保护

| 异常 | 必须保持 | 当前恢复 |
| --- | --- | --- |
| encrypt temporary/generic failure | 新明文不落盘；旧 profile 文件不变 | relaunch/重试 |
| decrypt temporary failure | 旧密文、profile 与 masked summary 保留 | relaunch |
| invalid base64/version/scheme | 原记录保留，不调用 safeStorage（格式前置失败） | 当前 reenter；系统事故先分类 |
| decrypt generic failure | 原记录保留，底层文案不跨 IPC | 当前 reenter |
| lazy re-encrypt failure | 本次读取继续；原密文保留 | 后续读取重试 |
| lazy persist 与用户保存并发 | 不覆盖用户新 credential | compare-and-swap |
| profile store JSON 损坏 | 不当作空 store 覆盖 | 停止写入并人工修复 |
| provider 401 | 不改凭据层状态为 Keychain 故障 | provider 错误路径 |

## 11. 验证

### 自动化最低集合

```bash
npm --workspace @awaken/desktop run test -- src/main/secure-credential-store.test.ts src/main/model-profile-store.test.ts src/main/desktop-operation.test.ts src/renderer/runtime/client.test.ts src/renderer/useComposerLifecycle.test.ts src/renderer/ProfileBalancePopover.test.tsx src/main/desktop-instance.test.ts
npm run typecheck:desktop
```

关键断言：

- 只调用 async safeStorage，不调用同步接口、availability gate 或 plaintext fallback。
- legacy 与 `shouldReEncrypt` 先成功生成 replacement，再安全写回。
- v2 缺失/错误 scheme 在调用 safeStorage 前拒绝；当前还缺少专门锁定 missing/wrong scheme 的测试。
- migration failure 和并发保存不损坏旧/新 credential。
- 临时错误每次操作只调用一次 safeStorage，并映射 relaunch。
- Renderer 只接收结构化安全文案和动作。
- app name、userData namespace 固定；application ID 还需字面量与 builder parity 测试。

### 真实 Desktop

日常验收：

1. 在 Models 保存专用测试 profile。
2. 完整重启 Desktop，确认原 profile 可读取。
3. 查询支持的余额入口。
4. 用原 profile 发送最小真实 prompt。
5. 检查 UI、日志和 transcript 不含秘密。

故障验收：

- temporary、legacy、rotation 和 write failure 优先用注入测试。
- macOS 登录钥匙串 lock/unlock 不进入普通 smoke，只按 [专用 QA 案例](./macOS登录钥匙串认证状态失效QA案例.md) 在隔离条件执行。
- 已确认待实现的状态必须标记为未通过/缺口，不能用文档勾选代替代码证据。
