# 上下文窗口与压缩

## 1. Request envelope

模型上下文由稳定 system prompt、结构化历史、attachments、inline SkillContextBlocks、runtime snapshot 和 tool schemas 组成。runtime snapshot 记录 workspace/cwd、模型、tool snapshot ID、environment ID 和 Skill summary；tool schemas 来自本 run 固定可用性快照。工具渐进披露启用时，未激活的延迟定义（内建辅助组或 MCP）不进入该投影，由 [04 工具定义与暴露](../04_工具权限与审批/工具定义与暴露.md#31-工具渐进披露) 唯一拥有；被激活的工具按 Context Epoch 的 dynamic tools append-only 语义进入后续请求，激活集合经 `deferred_tools_activated` 语义记录耐久（恢复兼容旧 `mcp_tools_activated`），压缩与重启不丢失。

runtime snapshot 有宿主侧与模型侧两个投影，只有后者进入 provider 请求。宿主侧 `runtime_snapshot` context item 记录全部 scope 字段（project ID、scope_id、三组 roots、protected roots、temporary work root 等），用于 journal 与用量核算；模型侧由 `prompt.FormatRuntimeInfo` 渲染结构化 `<environment_context>`，当前分开包含项目 ID/名称、工作目录、逐项保留的精确 `workspace_roots`、unrestricted permission profile、日期、模型、入口、工具与 Skill 摘要和已授权附件。多个 roots 不折叠为共同父目录。零文件夹项目与独立对话分别标明其 project/conversation scope 和 Awaken 管理的 session 目录，不伪造成用户选择的项目文件夹。项目重命名不改写已经运行中的请求快照；Desktop 从项目 authority 刷新后，下一次 run/follow-up 携带新名称，`sameTaskScope` 与 runtime snapshot identity 都把名称变化视为需要重建模型上下文。Windows drive/UNC 根在 Renderer 项目归属阶段按本机大小写不敏感和分隔符等价语义比较，不能因盘符大小写或 `\\`/`/` 表现差异丢掉 `project_name`。往宿主侧加字段不等于模型能看到，两侧要分别确认。

RequestBuilder 在 system prompt 的最后追加稳定、host-owned `conversation_continuity` 块：最终请求中当前 user 输入之前的 user/assistant/tool 消息都是当前同一个 Awaken 任务的历史轮次；跨日期、Desktop/Core 关闭、重启或重新打开不会把这些已恢复历史变成另一个独立会话。只要当前输入之前存在消息，用户使用“上一个对话”“上一轮”“刚才”或“之前”等指代，模型必须默认解析到当前任务中最近的相关历史并直接回答，不得声称系统未提供；只有用户明确说另一个任务/独立会话时才按跨任务不可见处理。该块不复制历史正文，不把数量、thread/run/session ID、时间戳、message origin 或内部 message/turn identity 下发为供应商私有字段，也不允许模型声称看到了请求之外的其他任务或编造未提供的时间。它的 Context Epoch 与缓存身份由[提示词缓存、上下文用量与成本治理](提示词缓存与成本治理.md)统一定义。

Skill 不在估算前与 tools 求交。目录只暴露统一 `skill` 工具及有预算的 Skill catalog；调用后的 inline 正文才进入上下文。

## 2. 预算

Awaken 模型 profile 的 `ContextWindow` 就是用户配置的可用输入容量，也是 Desktop 上下文用量的分母；它不是还要再扣输出的总窗口。`MaxTokens` 是独立的单次输出上限，不得从 `ContextWindow` 中扣减。若存在更小的明确 `MaxInputTokens`，它作为硬输入上限约束配置容量。Core 的 `ModelWindowTokens` 与 `EffectiveInputWindowTokens` 都保持这一配置后的输入容量，`OutputReserveTokens` 只独立记录输出上限；warning/auto-compact threshold 和 compact target 均以输入容量为基数。当前 `awaken_leaf_v4` 从 provider-visible projection 生成 `ContextUsageSnapshot`，按 typed prompt/message/tool provenance 统计分类并保证分类和等于总估算。它仍是版本化本地估算，不是 provider tokenizer 的精确输入量。

`ContextActualTokens`、最近响应的 input/output/total 和 cached usage 都不能改写 Core 的本地 snapshot。每次主请求会把最终 `sent_request` 的 `estimated_input_tokens` 一并写入 `ModelUsageRecord`。Desktop 的当前总输入直接显示最近一次兼容、成功且完整的主请求 inclusive input，不加入 output，也不叠加当前本地变化量；缺少兼容 input 时回退 v4 snapshot，并把与七项 typed 分类（系统、内置工具、MCP、技能、记忆、任务检查点、对话）之间的正残差列为“其他/协议开销”。Core 的 warning/auto-compact/block 仍独立用 provider total/input 与本地变化得到锚定投影，并取该投影与本地估算中的更保守值；同一 context epoch 内 provider 锚点不得因“压缩判断前投影”与“Context Epoch lowering 后 sent request”处于不同阶段而向下回退，只有成功 compact 或 model identity 不兼容边界可清除它。新的 run 或旧 thread 恢复时会从最后兼容硬边界之后成对恢复最近成功完整主请求的 provider total/input 与发送时估算，使首个请求也使用同一保守锚点。打开旧 thread 时，Desktop 仍以当前可运行 profile 从耐久历史与当前工具/Skill/Memory/checkpoint 重建 v4 snapshot；provider/model/protocol/effort、compact 等不兼容边界不复用旧实报，source/tool 重建边界只允许继续展示最近请求 input。无法重建且旧记录没有 breakdown 时才显示已有汇总和“暂无分类明细”。完整口径见 [提示词缓存、上下文用量与成本治理](提示词缓存与成本治理.md)。

Skill catalog 预算约窗口 1%。compact 前已激活 inline Skill 仍使用完整正文；compact 成功后不再使用互相独立的单 Skill 5K/合计 25K 配额，而是把每个 active Skill 降为包含 Skill ID、正文 digest 和精确 `SKILL.md` 路径的有界引用。后续再次应用该 Skill 前必须用 `Read` 重载原始路径；active Skill 不因数量排序被静默删除。Skill 引用与其他输入统一进入完整请求 10% 分配器。

## 3. 压缩与耐久边界

一批 tool call 仍按现有顺序执行（失败监督、Hook、journal 顺序不变），但每条结果 persist/offload 之后，用与 `PrepareRequest` 同一套保守投影计算 `remaining = blockingThreshold - ConservativeProjectedTokens - 本批已执行结果`。下一条媒体类 `Read`（图片或 PDF）按参数预估：图片 2000 token，PDF 为页数 × 2000，省略 `pages` 的 PDF 按 10 页。`estimated > remaining` 时该调用不执行，写入合成失败 `error_code=context_admission_exhausted`，说明剩余 token 并建议减少页数/条数或等下一轮压缩；同批后续调用同样不再执行。入场拒绝不切 Context Epoch，也不是 compact 成功。文本 `Read` 预估为 0，不受该门限拦截。

每次 `Build` / replay 按**当前** `ContextWindow` 重算 provider 可见投影，不把某次大窗口留下的整组原图写成永久 tail：

- 近尾 1 个安全组内的媒体可以 hydrate，但受剩余窗口夹紧；
- 更早 Read/图/PDF 页去掉 `DataBase64`，正文加 stub（路径/页码，可再 Read）；durable `storage_key` / `ByteSize` 仍计入本地账，避免轻量投影后假瘦；
- 已 offload 的大文本不再全量灌回模型，请求只保留 stub；
- 摘要请求全部去掉 image/file payload；`structurallyCompactMessage` 同时清空 `ModelContent`；
- 最后一组自身超过 `CompactTarget`（或 `block - summary预算`）时，先组内轻量投影；仍超限则整组进入 prefix 摘要，tail 只留最新 user 与未闭合 pairing。单条不可投影 remainder 拒绝压缩，不写假成功。

`CompactTarget` 的语义是压缩后**完整 provider-visible input** 的硬目标：`floor(EffectiveInput × 10%)`。通常 `EffectiveInput = ContextWindow`；仅当明确的 `MaxInputTokens` 更小时才取该上限。`MaxTokens` 不参与扣减。该目标不是“触发后剩余窗口”或只保留消息尾部的预算。只有 profile 提供明确 `ContextWindow` 或 `MaxInputTokens` 时才宣称硬门禁成立；未知上限不会拿 128K 默认值伪造达标 receipt。governor 把目标换算成交给 `splitCompactGroups` 的对话尾部预算：供应商实报大于发送时本地估算时先按该比值通缩，再扣除稳定前缀、动态摘要预算和压后 checkpoint provider projection reserve。摘要预算也先使用同一校准目标，再按剩余预算 35% 计算并夹在 1024–4096 tokens；不能一边按 provider ratio 缩小 tail、一边仍保留未校准的 4096 summary 配额。摘要请求必须把这个硬输出预算显式交给模型，禁止先输出 analysis/reasoning/preamble，并要求先完成全部 13 个 section 与 `</summary>` 再增加第二条 bullet，避免 1024 紧预算在结构未闭合前被供应商截断。Host 还会把被压缩 prefix 中最后一条非空 assistant 进度压成有界、确定性的 `Latest compacted assistant progress` header；它不依赖模型摘要是否主动注意到“21/24、继续最后三份”之类断点，并与受保护尾部共同恢复精确续跑位置。若供应商忽略摘要请求的 `MaxTokens`，Host 会在 section 归一化后再次按同一预算裁剪：优先保留 Active Task、Pending Asks、约束、进行中/阻塞/剩余工作与 Critical Context，supporting bullets 延迟到 TaskCheckpoint/Journal；Host 自身 summary header 预留独立计入。checkpoint reserve 取 `CompactTarget / 8` 并同样夹在 1024–4096 tokens。两者都是 global allocator 的入场保留额，最终仍以 exact prepared body receipt 为准；尾部预算只缩小、不放大，最低夹到 1 token。compactor 对“最后一个安全组是否过大”的判定使用 `min(分配后 tail budget, CompactTarget)`，不得再用较大的整体 10% 目标把 allocator 已决定延迟的工具结果强行留在 tail；完整 pairing 先进 summary/checkpoint/Journal，未闭合 pairing 仍 fail closed。

压缩提交前会用 proposed messages、TaskCheckpoint、Memory/Skill refs、Instruction、RunPlan、Hook、Tool/MCP schemas 和 attachments 重新构造完整请求，再调用与正式发送相同的 `llm.PrepareRequest` 完成 Chat、Responses 或 Messages lowering；预算以最终 prepared JSON body 为兜底并写 `CompactBudgetReceipt`。draft 会模拟提交后的 Memory 状态：已 compact 的正文不再由 `MemoryContextProvider` 重复注入，只保留 bundle/checkpoint 中的 identity refs。压缩边界后的上下文敏感工具描述和 Skill catalog 按 `CompactTarget` 重新编译，不沿用按完整模型窗口生成的目录预算；这只缩短可检索目录/描述，不改变 pinned tool implementation、暴露策略或已激活 Skill identity。若 mandatory floor 可达但完整 projection 只因 compacted active-Skill reference block 超额，allocator 可以延迟该 system block；bundle/checkpoint 仍保留 Skill ID、路径和 digest，模型可通过 Skill catalog/Read 按需重载，live 与 restart 使用同一空 projection。成功条件是 `ConservativeProjected <= CompactTarget`；provider-actual/local-estimate 比值只会把结果向更保守方向校准。压缩后的 provider opaque reasoning/thinking 不进入 provider-neutral conversation 或 RecentTurns，避免跨模型误重放与未计量输入。若连 system/instructions/tools/checkpoint/summary mandatory floor 都超过 10%，返回带 `category_breakdown` 的 `COMPACT_TARGET_UNACHIEVABLE` 与 lower-snake-case reason，不通过删除 critical facts 伪造成功。

压缩保留最新用户意图、未完成工具配对、active gate、canonical tool outcome、artifact/change identity 和必要恢复事实。`PostCompactContextBundleV2` 同时保存宿主生成的 `TaskCheckpointV2`、最近最多三个已闭合的完整 user-task turns、Instruction/Memory/RunPlan/Skill/Tool/Hook/Subagent/Artifact refs、当前 thread Journal locator、coverage 与预算 receipt。完整 checkpoint 的 fact digest、record ID、sequence 和 coverage 只属于宿主耐久校验，不原样重复发给模型；provider-visible 投影只携带去重后的语义值、各类耐久 fact 数量和 Journal locator。单个长语义值在 provider projection 中保留有界头尾，避免多轮重复 follow-up 把耐久事实复制成新的 mandatory floor；完整值仍留在 typed checkpoint。critical/当前状态保留语义投影；relevant file、command 和 tool finding 属于 `supporting` 可检索事实，不进入 critical/important coverage 分母。每个 checkpoint 事实类别保留最近 64 条；只有被该滚动上限明确淘汰的旧 fact ID 才退出 coverage 分母，并继续由同一 `TranscriptLocator + thread_history_read` 精确回读，其他任何非预期缺失仍硬失败。completed actions 和 relevant files 只投影最新少量值，commands/tool findings 的精确值默认只通过耐久 fact 数量与 Journal locator 延迟读取，被延迟的事实仍在同一 bundle/Journal 中由 `thread_history_read` 找回。Glob 工具返回的批量清单保留为有界 tool finding 与 Journal 原文，不把其中上百条尚未使用的路径全部升级为 active `relevant_file`；用户点名、Read 参数/结果或其他工具实际使用的路径仍正常进入 checkpoint。tool result 的 error/blocker 抽取以 canonical `IsError` 为准；成功 outcome 即使正文或 JSON key 含 `error/failed` 也不升级为 critical 失败，真实失败仍同时保留 error 与 blocker。当前尚未闭合的任务由最新 user anchor、semantic summary 与 typed checkpoint 承载，不把已在当前轮中的工具历史整轮重复注入 RecentTurns。已闭合 RecentTurns 在全局 10% 预算中仍属可延迟检索层：超预算时按从旧到新移出 provider-visible projection，精确内容仍由 `TranscriptLocator + thread_history_read` 找回，不删除 checkpoint 滚动窗口内的 critical facts。Checkpoint 通过 range-bounded Journal projection。

压缩成功必须同时满足：pairing 合法、summary 非空（fallback 不算成功）、可压量足够时对话至少缩 20%、typed checkpoint/section/digest/coverage 全部合法、完整请求硬 10% receipt 合法，并低于 auto/block。任一门禁失败都不 append、不换内存、不切 epoch、不清 usage 锚点。主动压缩在可压量小于约 5000 token 时直接 `not enough compactable history`。`CONTEXT_BLOCKED` 不能再触发 reactive；mandatory floor 已超过 target 的 `compact_target_unachievable` 会立即打开熔断；仅完整投影超 target、但 mandatory floor 仍可达时允许一次更轻 tail 重试。其余情况连续三次落在同一失败族（例如 `insufficient_reduction` / `still_above_*` 这类预算未解）也会熔断，不要求三次完全相同的具体 reason。

压缩成功产生唯一 `compact_boundary_id` 和一个原子 `PostCompactContextBundleV2`。Runner 的提交顺序固定为：

```text
计算 summary/tail + TaskCheckpoint + refs + coverage/budget
  -> validate/seal bundle digest
  -> append context_compacted_v2
  -> flush journal
  -> 一次安装 conversation / checkpoint / Memory refs / Skill refs
  -> 发出 compact finished
```

V2 使用 journal 的 transactional `AppendFlushed`：先把现有合法 records 与新 boundary 编码为完整 JSONL，再通过同目录 temp、temp fsync、atomic rename、parent fsync 一次替换 authority，不在原文件尾部写入后再 truncate 回滚。rename 前失败时旧文件保持完整；若底层在 rename 已完成后才返回错误，Journal 会比较 target 与本次精确 transaction bytes，把已经完整提交的 boundary 认作成功，不能让调用方保留旧内存而重启又读到新 boundary。live record 只在该事务确认提交后发布。因此失败 boundary 不会在后续 flush/restart 复活。Memory 不清空 identity：V2 bundle 保留旧 identity/revision/content-digest refs，但提交后会从当前 Runner snapshot 和 RecallManager 的后续注入集合移除这些旧正文，child 也不能重新继承；压缩后 selector 新召回的未压缩正文仍可合并。Skill 不改写，Subagent terminal handoff 不消费。服务重建按最后一个合法 v1/v2 boundary 选择 authority；V2 后出现合法 v1 会清除旧 V2 checkpoint/Memory/Skill refs，v1 后出现 V2 则恢复最新 V2，不能拼成混合状态。旧 v1 transcript thread 仍写并读取 `context_compacted.messages`，直到 journal 迁移。Skill 使用 bundle 内压后投影。`AWAKEN_CONTEXT_COMPACTION_V2=false` 可显式回退写 v1 record；semantic journal thread 默认启用 V2。

完整 thread Journal 始终保留。root Agent 可按 bundle 的 sequence/boundary locator 调用延迟披露的 `thread_history_read`，只读当前 thread 的有界 query/sequence 页面；该工具不接受其他 thread ID，不返回物理 store 路径、provider opaque state 或原始 tool arguments，并遮蔽 bearer/basic、常见 API/token 前缀、`client_secret`、AWS secret access key、passphrase/private key/credential 等命名敏感值，包括带空格的引号值。默认每项最多 2,000 字符、单次正文合计最多 12,000 字符；可调硬上限分别为 4,000/24,000，耐久 tool result 只保存无正文 receipt。

fork body 属于 child 上下文，不纳入父压缩；父只保留 child result/identity。child 自己的 compaction record 带 agent identity。attachments 与 tool result media 通过 runtime storage key 恢复，不重复持久化 image/PDF base64。

## 4. 主动与被动压缩

- 接近 auto-compact threshold 时执行 proactive compact；
- 除此之外，`ContextWindowState.ShouldAutoCompactByActualUsage` 作为并行主动触发：`LastAPIUsageTokens > 0` 时以 provider 实报为同 epoch 的非递减下界，再叠加 `max(EstimatedDeltaTokens, EstimatedTokens - LastSentEstimatedInputTokens, 0)`；这既保留同基准下真实增长，也阻止压缩判断前投影与 Context Epoch lowering 后 sent request 的阶段差异被误当成负增长。它与 v4 `EstimatedTokens` 触发是 OR 关系，不修改 `awaken_leaf_v4` snapshot。`LastAPIUsageTokens` 在同一 run 的连续请求以及新 run/旧 thread 的兼容恢复中优先取 provider `total_tokens`，provider 未返回 total 时回退 `input_tokens`；warning 和 block 同样取该锚定投影与本地估算的较大值，避免显示已接近窗口但安全门仍过晚。恢复只接受成功、完整、同 identity 的主请求，并要求成对存在发送时估算；成功 compact 与 provider/model/credential/protocol/reasoning 等硬边界清除或拒绝旧锚点。算术溢出按越过阈值处理。成功压缩后 governor 同时清零 provider 实报与发送时估算锚点，因为 compact 后的新 prefix 已不再对应上一请求；
- provider 返回上下文过长且仍可安全重试时执行 reactive compact；
- 同一 governor 的失败计数和 circuit breaker 防止无限压缩循环；同一次 compact 的 postcondition 最多允许 1 次更轻 tail 重试（即摘要模型总调用最多 2 次）。fallback summary、`insufficient_reduction`、以及 mandatory floor 已超过 hard target 的 `compact_target_unachievable` 属当轮终态，不再继续请求同一摘要模型；其余失败 reason 为 `still_above_auto_threshold` / `still_above_block_threshold` / `oversized_protected_tail`；
- summary 请求使用 `compact_summary` purpose、独立 affinity 和动态 1024–4096 token 上限；默认继承 thread profile，Host 内部存在有效 route 时可先解析该 route，并按所选模型能力进一步限制输出；Renderer 不提供独立用途模型选择器；
- summary model 失败可使用明确标记的本地 fallback，失败或中断不切 epoch；
- 无法安全裁剪 tool pair 或最新用户意图时 block，而不是静默丢失。

provider/tool snapshot 只保存 ID/摘要；压缩后不能重新选择当前 registry implementation。Skill 正文截断必须提示重读锚定路径。

## 5. 当前不支持与缺口

- 供应商目录未提供的 per-model tool-support 仍会显示 unknown，只有官方/API 事实或用户纠正后才下发工具；连接测试本身不证明工具能力；
- catalog/Skill token 预算是估算，不是 provider tokenizer 精确值；
- bare unit Runner 没有 recorder 时只做内存压缩；产品 `RunService` 路径必须始终持久化；
- OpenAI official Responses 的 native opaque adapter 已按 exact provider/base/protocol/model capability 接入，并保持 `store:false`、不依赖 `previous_response_id`；native output 只有通过相同完整请求硬 10% receipt 才随 V2 boundary 原子安装，失败或超限回落 provider-neutral checkpoint。当前证据为 mock/自动化，本机没有 ready OpenAI profile；真实 OpenAI 账号调用不属于本次 V2 收口要求。custom endpoint、OpenAI Chat 与 Anthropic Messages 不得继承；
- Windows/Linux 的大路径、非 ASCII attachments 与真实重开压缩尚无本轮实机证据，也不属于本次 V2 收口矩阵；因此不能宣称这些平台已实机通过，但它们不阻塞当前功能收口；
- MiniMax-M3（当前 profile `267307` 输入窗口）的低窗口多 PDF 已在 macOS 真实 Desktop 通过：压缩前 254K，10% 目标 27K，保守压后 18K、mandatory floor 17K，压缩完成时面板为 22K/267K（8%）；模型从压缩前第 8 份 PDF 断点继续完成第 9–12 份并读取新文本。自定义 API 的独立低窗口媒体样本仍未取得，不能由 MiniMax、`go test` 或 Gallery 代替；
- 当前没有多个 Core 实例并发写同一 thread 的产品级 session lease。
