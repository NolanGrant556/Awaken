## 1. 本方案解决什么

本方案处理一次真实 PPT 会话暴露出的八类问题，并把修复收敛为一套稳定的执行控制面，而不是逐个修补错误文本、某个 Skill 或某台机器上的 wrapper。

最终目标是：

1. 模型可以犯错，但错误必须在执行前被约束，或在执行后被结构化识别。
2. 工具活动由宿主直接展示，不依赖模型主动口述。
3. Skill 的主文、必读资源、工具池和 runtime 要求由宿主确定性激活。
4. Office/PDF 等 Artifact 工作默认走平台拥有的受控引擎与验证流程。
5. ToolCall、ToolResult、Artifact、恢复决策和终态在重启后可以完整重放。
6. 相同错误达到阈值后必须换策略或终止，不能无限消耗模型轮次。
7. Awaken runtime 的所有权、版本、探测、修复和回滚均由 Awaken 管理。

本方案不是一次 UI 重写，也不是删除 shell。它是在保留当前 Desktop、Workbench、AUTO 工具策略和本机执行能力的前提下，修正执行事实、能力路由和持久化底座。

## 3. 实施前基线事实与问题定性

本节冻结 2026-07-10 开工前的事故与源码事实，用于解释方案来源；它不是 Phase 8 后的当前实现说明。当前实现以根 README、对应功能域“当前规范”和验收证据为准。

### 3.1 真实会话证据

对外加工成本风险分析会话的持久化记录做结构化核对后，确认：

- JSONL 中有 74 条 message 和 1037 条 event。
- event 记录只有文本、上下文、TurnFinished、RunFinished 等类型，没有 ToolCall、ToolResult 或 Artifact。
- message 记录中实际完整存在 6 次 apply_patch 和 12 次 shell 调用。
- 6 次 apply_patch 不是同一种错误：2 次属于 patch 语法错误，4 次属于 context mismatch；其中存在两组完全相同 payload 被原样重复提交。
- 12 次 shell 中有 6 次 exit_code=1，但 ToolRuntime 将这些调用标记为成功。

因此，需要纠正两个容易误导实施的说法：

1. 不是六次 apply_patch 全部属于输入格式错误；语法错误和目标上下文不匹配都存在。
2. 历史并非完全没有保存工具事实；conversation message 保存了事实，但历史 API 和 UI 重放没有投影出来。

### 3.2 八类问题与当前根因

| 编号 | 表现 | 实施前源码事实 | 根因归属 |
|---|---|---|---|
| P1 | pip 安装没有模型口述，用户难以理解发生了什么 | Runner 只发通用 Executing tool；ToolCall 参数和 CommandOutput 分散；没有宿主生成的活动描述 | 运行时和 UI 可观测性设计 |
| P2 | CJK XML helper 写错并复制到多个函数 | 平台已有 presentation_create，但用户 Skill 明确要求 pip、动态生成 Python、shell 执行；正确 reference 没有被加载 | 首次为 LLM coding 错；扩散为 Skill、能力路由和 Artifact 引擎问题 |
| P3 | apply_patch 连续失败 | apply_patch 只暴露一个 string 类型 patch 参数；严格 parser 在执行时才校验；当前 provider 工具层没有 grammar constrained decoding | 工具接口过于脆弱，模型错误缺少执行前约束 |
| P4 | PPT Skill 与 Awaken 工具契约冲突 | Skill allowedTools 被复制到 InlineExecutor，但 InlineExecutor 完全不使用；RequestBuilder 和 ToolRuntime仍使用全局工具池 | 平台缺少真实 Capability Contract |
| P5 | 会话没有调用 skill_resource_read | 主 SKILL.md 已由 loader 读入并在 SkillTool 执行后返回；辅助 references 只靠提示模型主动读取 | 主文调用次数不是问题；缺少 required resource preload 和 receipt 才是问题 |
| P6 | 错误已返回，模型仍重复相同策略 | ToolExecutionResult 已有 Status 和 ErrorCode，但 ToolResult event 没携带；shell 非零退出不标错；MaxThoughts=0 可无限；无 failure fingerprint | 错误事实在层间丢失，且无失败监督器 |
| P7 | LibreOffice、Poppler wrapper 失效 | prepare 默认搜索 Codex cache，并在 macOS 生成指向外部绝对路径的 wrapper；已有 wrapper 只看文件存在；Go preflight 主要 os.Stat | Runtime 生命周期所有权错误和 readiness 假阳性 |
| P8 | 重启后工具过程消失 | JSONL message 有 tool calls/results；recoverable event 白名单只包含文本、上下文和终态；历史 API只返回 events；flush 错误被忽略 | 双重事实模型、重放投影缺失、持久化失败静默 |

### 3.3 当前已有能力，禁止重复建设

以下基础已经存在，应扩展而不是另起炉灶：

- Runner 多轮工具闭环。
- ToolRuntime、ExecutionProfile、AUTO policy、executor router。
- ToolExecutionResult 的 Status、ErrorCode、Duration、AffectedPaths。
- shell 的 exit_code、stdout、stderr、timeout 和流式 CommandOutput。
- apply_patch 的严格 parser、workspace 边界、Trash、artifact 和 patch preview。
- presentation_create、presentation_edit、presentation_render 等 typed artifact 工具。
- Skill package、SkillTool、skill_resource_read、project/user source。
- Desktop 全局 threads.sqlite 与 thread JSONL。
- Run Narrative projector、runtime reducer、thread transcript replay helper。
- RuntimePrepare、RuntimeReady、RuntimeMissing 等事件类型。

## 4. 不可妥协的不变量

所有阶段必须同时遵守以下不变量：

1. 不依赖模型口述工具行为。
2. 不恢复通用 ApprovalCard、awaiting_approval 或通用人工审批主路径。
3. 不删除 shell；只把普通文本编辑、Artifact 和 runtime 安装从 shell 主路径中移出。
4. Skill 不得扩大父 run 的 ToolPool、TaskScope、网络或写权限。
5. 模型侧工具过滤和执行侧工具拒绝必须同时存在。
6. primary-runtime 不得持久依赖 Codex cache、其他产品 cache或可被清理的外部 wrapper target。
7. ToolCall、ToolResult、Artifact 和 terminal semantic record 必须耐久。
8. 高频 stdout delta、spinner、token tick 可以是临时事件，不要求全部写入会话账本。
9. 直播和重放必须使用同一套语义 projector；不得在 Desktop 另写一套历史专用猜测逻辑。
10. ToolResult 状态不能从 content 是否为空、字符串中是否含 error 等方式推断。
11. 每个错误必须有机器可读 code、category、retryable 和 recovery options。
12. Artifact Skill 缺 runtime 时必须 needs_runtime 或 fail closed，不得自动改走 pip、shell 或手写 ZIP/XML。
13. 旧 transcript 必须可读；迁移采用读取适配，不做破坏性批量重写。
14. 每个阶段独立可构建、可测试、可回滚。

## 5. 参考产品验证与目标架构

### 5.1 采用的设计原则

对 Claude Code 与 Codex 的源码和产品路径对照，本方案只吸收已经能映射到 Awaken 根因的工程原则：

- Claude Code 方向：Skill/Agent 定义可以约束可用工具、运行上下文和适用条件；权限、工具能力和子任务继承是宿主控制面，不靠模型自律。
- Codex 方向：文档、表格、PPT、PDF 使用平台拥有的 typed runtime 与 render/inspect/verify 闭环；模型表达语义意图，宿主负责依赖、执行和验证。
- 两者共同的有效做法：工具调用是协议对象，宿主维护执行状态和错误事实；失败反馈必须机器可读；能力边界和执行预算由 runtime 决定；会话恢复重放语义事实，而不是只重放最终文本。

Awaken 不照搬参考产品的 UI、审批模式或私有实现。具体取舍固定为：保留现有 Skill、AUTO 和本机执行能力，引入 typed outcome、双重 capability gate、受控 Artifact runtime、耐久语义账本和失败监督器。这样解决的是 Awaken 当前八类根因，而不是把参考产品名称写进 prompt。

## 6. 核心协议一：ToolOutcome

### 6.1 唯一结果模型

本文把协议概念称为 ToolOutcome，Go 中唯一 canonical 类型固定为 tool.ExecutionOutcome。它作为工具和 executor 返回给 ToolRuntime 的唯一结构化结果。原来的 string output + error 保留兼容适配，但新工具和 shell 必须使用结构化接口。

固定字段如下；允许追加向后兼容字段，但不得改名、复用或删除这些字段：

~~~go
type ExecutionOutcome struct {
    Content          string
    Status           string
    TransportStatus  string
    SemanticStatus   string
    ProcessStatus    string
    ExitCode         *int
    Signal           string
    TimedOut         bool
    ErrorCode        string
    ErrorCategory    string
    ErrorMessage     string
    Retryable        bool
    RecoveryOptions  []string
    Diagnostic       map[string]any
    AffectedPaths    []string
    PatchSummary     string
    Artifacts        []ArtifactDescriptor
    StartedAt        time.Time
    FinishedAt       time.Time
    DurationMs       int64
    Truncated        bool
}
~~~

持久化与模型侧 JSON 字段固定为 snake_case：content、status、transport_status、semantic_status、process_status、exit_code、signal、timed_out、error_code、error_category、error_message、retryable、recovery_options、diagnostic、affected_paths、patch_summary、artifacts、started_at、finished_at、duration_ms、truncated。时间使用 RFC3339Nano UTC。AG-UI/TypeScript 边界只做一次明确的 lowerCamelCase 映射，不得各层自行改名。

Status 枚举固定为：

- succeeded
- failed
- denied
- cancelled
- interrupted
- needs_auth
- needs_runtime
- unsupported
- review_required

TransportStatus 枚举固定为：

- not_started
- completed
- failed
- cancelled
- unknown

SemanticStatus 枚举固定为：

- success
- failure
- neutral
- unknown

ProcessStatus 枚举固定为：

- not_applicable
- exited
- timed_out
- signaled
- spawn_failed
- unknown

ErrorCategory 枚举固定为：

- validation
- policy
- authorization
- runtime
- process
- tool
- persistence
- unsupported
- cancelled
- domain

常见结果映射固定为：

| 场景 | Status | TransportStatus | SemanticStatus | ProcessStatus |
|---|---|---|---|---|
| 成功完成 | succeeded | completed | success | not_applicable 或 exited |
| 成功但无匹配/无差异 | succeeded | completed | neutral | exited |
| 输入校验失败 | failed | not_started | failure | not_applicable |
| policy/Skill gate 拒绝 | denied | not_started | failure | not_applicable |
| 缺授权 | needs_auth | not_started | unknown | not_applicable |
| 缺 runtime | needs_runtime | not_started | unknown | not_applicable |
| 普通进程非零 | failed | completed | failure | exited |
| 进程无法启动 | failed | failed | failure | spawn_failed |
| 执行中取消 | cancelled | cancelled | unknown | not_applicable 或 signaled |
| 进程重启且副作用结果未知 | interrupted | unknown | unknown | unknown |
| 工具领域校验失败 | failed | completed | failure | not_applicable |

### 6.2 兼容字段

现有 ToolExecutionResult.IsError 保留一个兼容周期，但必须由 Outcome 派生：

~~~text
IsError =
  Status in failed, denied, cancelled, interrupted, needs_auth, needs_runtime, unsupported
  OR SemanticStatus == failure
~~~

禁止反向用 IsError 推导完整 Outcome。

Desktop 必须保留 canonical toolStatus，并将工具卡显示状态固定映射为：

| ExecutionOutcome.Status | ToolDisplayState |
|---|---|
| succeeded | done |
| failed | error |
| denied | denied |
| cancelled | cancelled |
| interrupted | interrupted |
| needs_auth | blocked |
| needs_runtime | blocked |
| unsupported | unsupported |
| review_required | blocked |

ToolDisplayState 类型固定为 active、done、error、denied、cancelled、interrupted、blocked、unsupported；active 只用于已有 ToolCall 但尚无 ToolResult。Inspector 和 badge 始终显示原始 toolStatus，不能仅保留投影后的颜色状态。

### 6.3 Shell 语义

Shell 必须区分：

- spawn 失败：TransportStatus=failed，ProcessStatus=spawn_failed。
- timeout：Status=failed，ProcessStatus=timed_out。
- 普通 exit 0：Status=succeeded，SemanticStatus=success。
- 普通非零：Status=failed，SemanticStatus=failure，ErrorCode=process_exit_nonzero。
- rg/grep 单一查询命令 exit 1：Status=succeeded，SemanticStatus=neutral，ErrorCode 为空，Diagnostic.reason=no_match。
- diff 单一命令 exit 1：Status=succeeded，SemanticStatus=neutral，Diagnostic.reason=different。
- test 或方括号条件命令 exit 1：Status=succeeded，SemanticStatus=neutral，Diagnostic.reason=false_condition。

对复合 shell 命令无法可靠识别语义时，按最终非零退出失败处理，不做猜测。

shell 输出中必须保留 command、cwd、exitCode、stdout、stderr、duration、truncated。ToolResult event 和历史记录必须携带这些结构化字段。

### 6.4 工具活动描述

新增宿主侧 ToolActivity：

~~~go
type ToolActivity struct {
    Stage  string
    Title  string
    Detail string
}
~~~

工具可以实现 ActivityDescribingTool。ToolRuntime 在参数 normalize 后、执行前生成活动描述并发 ToolProgress，不再由 Runner 统一发 Executing tool。

至少覆盖：

- pip/npm/pnpm/yarn/brew/winget install：正在安装依赖，并展示包名或命令摘要。
- text_edit/apply_patch：正在修改文件。
- presentation_create：正在生成演示文稿。
- presentation_render：正在渲染并验证演示文稿。
- runtime repair：正在准备或修复本地运行时。

## 7. 核心协议二：语义执行账本

### 7.1 账本记录

新增 schema_version=2 的 agentcore.SemanticRecord，作为内存、持久化和 projector 的唯一 canonical record 类型。稳定 kind 固定为：

- thread
- run_started
- user_message
- assistant_message
- tool_call
- tool_result
- artifact
- file_change
- turn_diff
- permission_decision
- skill_activated
- resource_receipt
- runtime_notice
- recovery_decision
- turn_boundary
- run_terminal
- persistence_warning

每条记录至少包含：

~~~text
schema_version
record_id
seq
session_id
thread_id
run_id
turn_id
parent_id
kind
timestamp
payload
~~~

### 7.2 耐久与临时事件边界

必须写入：

- 用户消息和每次 LLM turn 的完整可见 assistant message；不得持久化私有 reasoning/token delta。
- ToolCall 的 name、arguments、skill_id、call_id 和宿主生成的 activity descriptor。
- ToolResult 的完整 ToolOutcome。
- Artifact 的 id、kind、path、status、关联 ToolCall。
- 文件变更的 planned/applied phase、tool_call_id、summary、affected_paths、最终 unified diff 和 truncated 标记。
- turn 结束时最终 TurnDiff；单条 unified diff 最大 50,000 字符，超出后保留前后片段并设置 truncated=true。
- Skill 激活、资源 receipt、能力冲突。
- runtime prepare/ready/missing/repair failed。
- recovery decision 和重复失败阻断。
- turn/run 终态。

默认不写入：

- stdout/stderr 的每个 delta。
- reasoning token delta。
- spinner、百分比 tick。
- tool args streaming delta。

临时 delta 的最终结果必须汇总进 tool_result 或 assistant_message。

### 7.3 写入顺序

持久化和直播使用两个明确接口：agentcore.SemanticRecorder 负责可返回 error 的耐久 Append/AppendBatch/Flush；现有 EventSink.Emit 保持无返回，只负责成功落盘后的直播广播。runtime.ExecutionJournal 实现 SemanticRecorder，并由 RunService 按 thread 注入 Agent/Runner。禁止让 EventSink 暗中承担持久化后再用 cancel 猜测写入是否成功。

~~~go
type SemanticRecorder interface {
    Append(context.Context, SemanticRecord) error
    AppendBatch(context.Context, []SemanticRecord) error
    Flush(context.Context) error
}
~~~

正式 StartRun 缺少 recorder 时必须返回 persistence_unavailable，不得使用 noop；noop recorder 只允许在不执行副作用的纯单元测试中显式注入。

1. run_started 和 user_message 必须在首次 LLM 调用前写入成功。
2. tool_call 必须在真实工具执行前写入成功。
3. tool_result 与其 artifacts 使用同一 AppendBatch 写入。
4. run_terminal 写入后必须 Flush，并等待确认。
5. Runner 先调用 SemanticRecorder，成功后才调用 EventSink 广播对应 live semantic event。
6. Ephemeral delta 可以直接广播。

### 7.4 写入故障

- run_started、user_message 或 tool_call 写入失败：立即取消 run，真实工具不得执行。
- tool_result、artifact 或 terminal 在副作用发生后写入失败：保留待写 batch 并按固定策略重试；重试耗尽后立即 fail-stop，停止新的副作用，并尝试写入用户可见的 `persistence_error` terminal。
- terminal flush 在重试后仍失败：run 终态必须明确为 persistence_error，不能假装完整保存。
- canonical SemanticRecorder 的 Append/AppendBatch/Flush 错误不得忽略。v2 journal 是唯一执行事实；RunService 对 SQLite thread metadata 与 legacy v1 mirror 的收尾同步是兼容层，不得反向成为重放真相。

AppendBatch 和 terminal Flush 的固定重试策略为：首次失败后分别等待 50ms、200ms 再重试，共最多 3 次实际尝试；ctx 已取消、磁盘空间不足、只读文件系统和编码错误直接标记为不可重试。每次失败保留原 pending batch，成功后才移除。

### 7.5 文件一致性

- 每个 thread 使用一个串行 writer。
- 一批记录先编码到内存，再单次 append。
- terminal 时执行 file.Sync。
- reader 只允许忽略最后一条未完成的尾行；中间损坏必须返回明确错误。
- record_id 和 seq 去重。
- 旧 v1 JSONL 通过 LegacyTranscriptAdapter 读取，不原地重写。

### 7.6 重放

服务端将 agentcore.SemanticRecord 通过唯一的 SemanticProjector 转为 AG-UI event。实时路径和 transcript API 均调用该 projector。

Desktop 的 actionsForThreadTranscript 只负责按顺序 dispatch，不得再依据 run.result 猜测丢失的 ToolCall 或 ToolResult。

live/replay 等价测试只允许忽略：

- 接收时间。
- 流式 delta 游标。
- 纯动画状态。

Narrative、Tool Inspector、Artifacts 和 terminal state 必须完全一致。

启动时发现 run_started 后没有 run_terminal 的 orphan run，先为无结果 tool_call 追加 synthetic tool_result：Status=interrupted、TransportStatus=unknown、SemanticStatus=unknown、ProcessStatus=unknown、ErrorCode=process_restarted_outcome_unknown、ErrorCategory=persistence、Retryable=false、Diagnostic.side_effect_state=unknown；再追加 run_terminal(status=interrupted, reason=process_restarted)。不得自动重放该工具调用。

## 8. 核心协议三：结构化文本编辑

### 8.1 新增 text_edit

新增 text_edit，默认用于单文件精确替换：

~~~json
{
  "path": "src/example.ts",
  "old_string": "old text",
  "new_string": "new text",
  "replace_all": false,
  "expected_sha256": "optional digest returned by read_file"
}
~~~

规则：

1. path 必须通过现有 PermissionContext 和 writable roots 校验。
2. old_string 与 new_string 完全相同则 validation 失败。
3. old_string 不存在返回 text_not_found。
4. 匹配多处且 replace_all=false 返回 text_not_unique。
5. expected_sha256 存在但不匹配返回 stale_file_revision。
6. 在同目录写临时文件、fsync、原子 rename。
7. 失败不得破坏原文件。
8. 输出 affected path、replacement count、before/after digest 和统一 diff。
9. 实现 ArtifactProducingTool 和 PatchPreviewingTool。

### 8.2 read_file 配合

read_file 的结构化结果增加 sha256、size、mtime。显示内容保持兼容，但 ToolOutcome.Diagnostic 中必须有这些字段。

### 8.3 apply_patch 定位

- apply_patch 保留，用于多文件、移动、删除和高级 patch。
- 普通单文件修改优先 text_edit。
- text_file_create 继续负责新建普通文本。
- trash_file 继续负责显式删除。
- Office/PDF 文件使用 typed artifact 工具。

当前 provider 均可使用 text_edit 的普通 JSON Schema。只有当 provider transport 真正支持 grammar custom tool 时，apply_patch 才启用 grammar constrained 版本；不允许只在 prompt 中声称已经受 grammar 约束。

## 9. 核心协议四：SkillActivationPlan

### 9.1 新增前置产物

每次 Skill 激活必须编译为：

~~~go
type SkillActivationPlan struct {
    SkillID                   string
    SkillVersion              string
    EffectiveTools            []string
    RequiredTools             []string
    RequiredCapabilities      []tool.CapabilityClass
    RequiredRuntimeComponents []string
    ResourceReceipts          []SkillResourceReceipt
    CompatibilityStatus       string
    CompatibilityErrors       []SkillCompatibilityError
}

type SkillResourceReceipt struct {
    SkillID      string
    SkillVersion string
    Resource     string
    Source       string
    SHA256       string
    Size         int64
    Mode         string
    LoadedAt     time.Time
}
~~~

Resource 固定为 Skill 包内相对路径；Source 固定为 project 或 user，不写入包外绝对路径。LoadedAt 使用 RFC3339Nano UTC。
持久化 JSON 字段固定为 skill_id、skill_version、resource、source、sha256、size、mode、loaded_at；AG-UI 边界映射为 lowerCamelCase。

### 9.2 Frontmatter v2

~~~yaml
toolPolicy:
  mode: intersect
  allow:
    - presentation_create
    - presentation_render
    - runtime_preflight
  deny:
    - shell
    - apply_patch

requiredTools:
  - presentation_create
  - presentation_render

requiredCapabilities:
  - artifact_write

requiredRuntimeComponents:
  - python
  - libreoffice
  - poppler

requiredResources:
  - path: references/presentation_recipes.md
    mode: preload
    required: true
    maxBytes: 131072
    sha256: optional-64-char-lowercase-hex
~~~

sha256 是可选的发布者锁定值：填写时必须是 64 位小写十六进制并与实际内容一致，否则激活失败；未填写时仍计算实际 SHA256 写入 receipt，但不做预期 hash 比对。required resource 缺失、越界、超过 maxBytes、不是 UTF-8 或指定 hash 不匹配时，必须在首次 LLM 请求前 fail closed。

旧 allowedTools 作为 toolPolicy.allow 的兼容别名，并输出 deprecated warning。

### 9.3 工具池规则

~~~text
effectiveTools =
  parentRunToolPool
  intersect 每个 active Skill 的非空 allow 集合
  minus 所有 deny 集合
~~~

- allow 为空表示继承父 pool，不表示全局开放。
- requiredTools 必须存在于 effectiveTools。
- requiredCapabilities 必须能由 effectiveTools 中至少一个工具满足。
- Skill 不得把父 pool 之外的工具加回来。
- RequestBuilder 只暴露 effectiveTools。
- ToolRuntime 在执行入口再次验证 effectiveTools。
- 未允许调用返回 skill_tool_not_allowed。

### 9.4 显式 Skill token

Composer 中显式选择 Skill 时：

1. RunService 在首次 LLM 请求前解析 token。
2. SkillActivator 读取主 SKILL.md。
3. 预加载 requiredResources。
4. 生成 receipts。
5. 检查 required tools、capabilities 和 runtime。
6. 把 SkillActivationPlan 和已加载内容加入 typed context block。
7. 首次请求直接使用 effectiveTools。

禁止继续只插入一段让模型调用 skill__xxx 的文字。

### 9.5 隐式 Skill 调用

模型调用 skill__xxx 时，宿主执行相同的 SkillActivator：

- 主文由宿主加载，不要求 skill_resource_read。
- required/preload resource 由宿主加载。
- optional resource 才通过 skill_resource_read 按需读取。
- 激活结果必须记录 skill_activated 和 resource_receipt。

### 9.6 Legacy Skill 兼容编译

对没有 v2 契约的 Skill 执行静态检查。Artifact Skill出现下列模式时，不允许直接运行：

- pip install、npm install、pnpm add、yarn add。
- 动态生成 generate.py 或同类临时引擎。
- 直接 shell 调用 soffice、pdftoppm。
- 手写 pptx/docx/xlsx ZIP/XML。
- 声明或要求当前不存在的工具。

此类 Skill标记 unavailable：

~~~text
error_code = skill_platform_contract_conflict
~~~

不能通过追加 system prompt 来覆盖冲突。

## 10. 核心协议五：Artifact 引擎

### 10.1 Typed schema

新增递归 InputSchemaProvider，支持：

- properties
- items
- required
- enum
- additionalProperties
- minItems/maxItems
- minLength/maxLength
- minimum/maximum
- oneOf

RequestBuilder 发送给模型的 schema 与 ToolRuntime 执行前校验必须使用同一份定义。

presentation_create 的 slides 不得继续只有 type=array。嵌套错误必须返回 JSON path，例如：

~~~text
$.slides[2].images[0].width expected number, got string
~~~

### 10.2 PPT 引擎所有权

将当前 artifact_runtime.go 中的长 Python 字符串拆为：

~~~text
src/tools/artifact_runtime/engines/presentation_engine.py
~~~

使用 go:embed 随 awaken-core 发布。

引擎必须集中提供：

- set_run_font
- add_text_box
- add_bullets
- add_image
- add_notes
- validate_overflow
- save_and_validate_package

CJK 字体 XML helper 只能有一个实现，并以中文标题、正文、项目符号的 PPTX XML 测试保护。模型只提交 semantic slide spec，不提交 XML/helper 源码。

### 10.3 布局和编辑

第一版 layout enum 固定为：

- title
- section
- bullets
- two_column
- image_right
- comparison
- metrics
- timeline
- closing

presentation_edit 必须接受 source_path 和结构化 edits；在做到真正增量编辑前，不允许把全量重写继续描述成 edit。

### 10.4 验证等级

返回 verification_level：

- package
- pdf
- png
- visual

verified=true 至少要求：

1. PPTX package 可重新打开。
2. LibreOffice 转 PDF 成功。
3. Poppler 全部页转 PNG 成功。
4. slide count、PDF page count、PNG count 一致。

render_preview=false 只表示不保留预览文件，不能跳过技术验证。Poppler 失败不得仍返回 verified=true。

### 10.5 深度 Skill 扩展

未来需要自带脚本的高深度 Skill 使用受控 skill_script_run：

- 只能执行 Skill 包内 manifest 声明的脚本。
- interpreter 只能来自 Awaken RuntimeManager。
- cwd、output roots、网络和超时由 activation plan 固定。
- 不接受任意 shell command。
- 依赖在安装或 RuntimeManager 阶段解析，不能在用户任务中 pip/npm。

skill_script_run 不属于本轮第一批阻断项；只有当真实 Skill 无法通过 typed tool 表达时再实施。

## 11. 核心协议六：RuntimeManager v2

### 11.1 所有权

生产环境唯一根目录为 AWAKEN_USER_DATA_DIR 下的 runtimes 目录：

~~~text
<AWAKEN_USER_DATA_DIR>/runtimes/primary-runtime/
├── versions/<bundle-version>/<os>-<arch>/
├── staging/
├── current.json
└── state.json
~~~

当前 Desktop 已把 AWAKEN_USER_DATA_DIR 传给 awaken-core。npm prepare/check 在 Electron 尚未启动时使用与 app.setPath 相同的共享 resolver：优先 AWAKEN_USER_DATA_DIR；否则 macOS 使用 ~/Library/Application Support/@awaken/desktop，Windows 使用 %APPDATA%\@awaken\desktop，Linux 使用 ${XDG_CONFIG_HOME:-~/.config}/@awaken/desktop。禁止各脚本分别推导目录或回退到 ~/.cache。

典型路径为：

- macOS：~/Library/Application Support/@awaken/desktop/runtimes/primary-runtime/
- Windows：%APPDATA%\@awaken\desktop\runtimes\primary-runtime\

current.json 固定记录当前和上一 known-good version key，跨平台均使用临时文件写入、file sync、原子 rename；不使用平台语义不同的目录 symlink 作为激活指针。

正式解析顺序：

1. 显式测试/开发 override。
2. 共享 userData resolver 中 current.json 指向的 Awaken managed known-good runtime。

应用包内 Awaken bundled runtime、显式 seed 和系统安装只能作为 prepare 的复制来源；探测通过并发布到 managed root 前不得直接作为正式执行路径。

默认路径不得包含：

- ~/.cache/codex-runtimes
- 其他产品 cache
- 任意 PATH fallback

prepare 阶段可以使用显式 AWAKEN_PRIMARY_RUNTIME_SEED_DIR 作为来源，但必须复制进 Awaken-owned staging，并在发布前探测；不得生成指向 seed 的 wrapper 或 symlink。

一次性迁移规则固定为：仅当 current.json 不存在时，允许把旧 ~/.cache/awaken-runtimes/primary-runtime 作为 migration source；先拒绝越界 symlink、指向外部目录的 wrapper 和无法 probe 的组件，再把通过的真实组件复制进新 staging。不得扫描 ~/.cache/codex-runtimes。成功或失败都在 AWAKEN_USER_DATA_DIR/data/migrations/primary-runtime-v2.json 记录结果，后续启动不重复迁移。旧 AWAKEN_PRIMARY_RUNTIME_CACHE_DIR 只作为一次性迁移别名读取，并输出 deprecated warning，不参与正式解析。

### 11.2 Manifest v2

模板和激活状态分离。激活状态至少记录：

~~~json
{
  "schemaVersion": 2,
  "runtimeName": "primary-runtime",
  "bundleVersion": "0.2.0",
  "platform": "darwin",
  "arch": "arm64",
  "components": [
    {
      "name": "libreoffice",
      "version": "detected-version",
      "source": "awaken_bundle",
      "relativePath": "libreoffice/LibreOffice.app",
      "sha256": "optional-for-file",
      "probe": {
        "args": ["--version"],
        "acceptedExitCodes": [0]
      }
    }
  ]
}
~~~

### 11.3 生命周期

~~~text
discover
-> stage temporary directory
-> copy/install into staging
-> probe every required component
-> write resolved state
-> atomic rename to version directory
-> atomically update current.json
-> retain previous known-good
~~~

- 文件存在不等于 ready。
- wrapper target 或 symlink 必须 resolve 后仍在 Awaken-owned root 内。
- prepare 中途失败不得破坏 current。
- repair 失败回滚 known-good。
- Node check 与 Go runtime_preflight 必须读取同一 resolved state，并返回相同 readiness。
- Go 关键 probe 使用短 TTL cache，但 Artifact 工具调用前必须确认未过期。

### 11.4 可见恢复

RuntimeManager 产生：

- RuntimePrepareStarted
- RuntimePrepareProgress
- RuntimeReady
- RuntimeRepairFailed

Desktop 直接展示这些宿主事件。RuntimeManager 内部安装 Python 包也必须通过这些事件可见，但不得伪装成模型主动 pip。

## 12. 核心协议七：FailureSupervisor

### 12.1 追踪维度

每个 run 维护：

- call_signature = toolName + canonical arguments hash。
- failure_fingerprint = toolName + errorCode + normalized primary diagnostic。
- same_call_attempts。
- same_failure_attempts。
- total_tool_failures_in_turn。

canonical arguments 必须对 JSON key 排序；patch 内容保留语义行但规范化换行和尾部空白。

normalized diagnostic 必须移除时间戳、临时目录、随机 ID 和绝对 workspace 前缀，保留错误 code、行号类别和核心原因。

### 12.2 固定阈值

- retryable=false 的失败 call_signature 只允许真实执行 1 次；第二次相同调用在执行前阻断。
- retryable=true 的失败 call_signature 最多真实执行 2 次；第三次相同调用在执行前阻断。
- 同一 tool、resource revision、error class 组合最多真实失败 3 次；此后必须换工具、刷新 resource revision 或终止。
- 同一 failure_fingerprint 连续出现 2 次后，下一轮必须携带 recovery_required。
- 单 turn 工具失败总数达到 6，终止该 turn。
- 单 run 工具失败总数达到 12，终止 run。
- 产品默认 MaxAgentTurns=128、MaxToolExecutions=512；配置 0 表示使用产品默认值，不再表示无限。

成功调用会重置同一工具的 consecutive failure，但不清除 run 累计失败数。

### 12.3 固定恢复映射

| 错误类别 | 恢复要求 |
|---|---|
| invalid_patch_format | 切换 text_edit、text_file_create 或重新读取文件；禁止原样 patch |
| patch_context_mismatch | 重新 read_file，再使用 text_edit；禁止直接重放 |
| text_not_unique | 扩大 old_string context 或显式 replace_all |
| process_exit_nonzero | 先解释 exit code/stderr，再改变命令或停止 |
| needs_runtime | 调用宿主 RuntimeManager；Artifact Skill不得 shell 安装 |
| skill_tool_not_allowed | 重新编译 activation plan；不得换壳调用同一能力 |
| skill_platform_contract_conflict | 停止并退出该 Skill；后续只能由新的显式恢复规划在 Skill scope 外调用平台 typed tool，不得自动改写或路由原 Skill |
| persistence_error | 停止新副作用，等待 journal 恢复或终止 |
| retryable=false | 不允许自动重复相同 call |

### 12.4 事件与终态

新增语义事件：

- ToolRecoveryRequired
- ToolRetryBlocked

新增 TerminalReason：

- repeated_tool_failure
- persistence_error

UI 必须显示被阻断的工具、重复次数、错误 code 和允许的下一步，不能只显示达到最大思考次数。

## 13. 分阶段实施顺序

| 阶段 | 目标 | 解锁条件 |
|---|---|---|
| 0 | 锁定基线、补当前规范、加入事故 fixtures | 当前测试和真实问题样本可重复 |
| 1 | ToolOutcome 全链路和宿主活动描述 | shell 非零、validation、deny、runtime 状态可正确投影 |
| 2 | SemanticJournal v2 与 live/replay 等价 | 重启后 ToolCall/Result/Artifact 完整 |
| 3 | text_edit、read digest、apply_patch 降级 | 普通编辑不再依赖 patch mini-language |
| 4 | SkillActivationPlan、资源 receipt、双侧工具池 gate | Skill 冲突在执行前失败 |
| 5 | 深化 typed schema 和 PPT engine | 中文 PPT 不再依赖模型生成 helper |
| 6 | RuntimeManager v2 | 不依赖 Codex cache，false-ready 消失 |
| 7 | FailureSupervisor | 同错重复有预算和恢复策略 |
| 8 | 全量回归、真实 Desktop、macOS/Windows 证据 | 达到完成定义 |

阶段顺序不得交换：

- FailureSupervisor 不能先于 ToolOutcome，否则 fingerprint 只能继续解析字符串。
- 历史重放不能先于 ToolOutcome 字段贯通，否则会固化错误数据模型。
- Skill gate 不能只做模型侧过滤，必须同阶段完成执行侧拒绝。
- RuntimeManager 未就绪前，不得把 PPT Skill验收标记为完成。

## 14. 兼容与迁移

### 14.1 Tool API

- 新字段全部 additive。
- Desktop 对未知字段保持容忍。
- 一个兼容周期后再删除 IsError 推断和旧 string-only executor。

### 14.2 Transcript

- 新 thread 写 v2。
- v1 使用 adapter 读取。
- v1 message 中已有 ToolCall/ToolResult 时，adapter 必须投影为语义 item。
- v1 缺失 Artifact 时不伪造。
- 不批量改写用户历史。

### 14.3 Skill

- 旧 allowedTools 映射为新 allow。
- 无 v2 metadata 的普通知识型 Skill继续可用。
- 有明确 Artifact 冲突的 legacy Skill标记 unavailable，不静默降级。

### 14.4 Runtime

- 旧 wrapper 只用于识别并报告 stale，不作为 ready。
- 首次启动只按 11.1 的一次性迁移规则复制旧 Awaken runtime；不迁移 Codex cache 或越界 wrapper。
- 迁移后 current.json 只能引用 Awaken root 内的 version key。

## 15. 明确非目标

- 不在本轮实现完整多 Agent 团队编排。
- 不实现所有 Office layout。
- 不把每个流式 delta 永久存储。
- 不让 Skill 自定义权限系统。
- 不移除 MCP、shell、apply_patch。
- 不用 prompt 覆盖代替宿主 gate。
- 不在历史持久化阶段重写 Workbench 布局。
- 不把当前用户 pptx Skill 的手工修补当作完成。

## 16. 风险与回滚

### 16.1 最大风险

- ToolOutcome 字段在 Go、AG-UI、Electron shared type、reducer 间漂移。
- v2 journal 与旧 conversation message 发生重复投影。
- Skill 工具池收窄导致 legacy Skill突然不可用。
- Runtime 自含复制增加打包体积。
- PPT engine 拆分后打包遗漏 go:embed 资源。

### 16.2 控制措施

- 每个协议建立 golden fixture。
- live/replay 使用同一 fixture 做等价测试。
- 工具池同时记录 base、allow、deny、effective，便于诊断。
- Runtime state 记录 provenance 和 probe 结果。
- 旧路径保留读取 adapter，不保留双写。
- 每阶段独立提交；失败时回滚该阶段，不跨阶段挑改。

## 17. 完成定义

只有同时满足以下条件，才允许宣告整体完成：

1. shell exit 7 在模型、事件、历史和 UI 中都显示失败、exitCode=7。
2. rg 无匹配不会被误报为系统故障。
3. 工具活动无需模型口述即可在 UI 显示。
4. 新文本编辑任务默认使用 text_edit；历史坏 patch fixture 不再形成无限循环。
5. 显式 Skill 在首次 LLM 前完成主文、required resource 和 capability 激活。
6. required resource 有 SHA256 receipt；缺失时执行前失败。
7. Skill 未允许的 shell 即使被模型直接调用也被 ToolRuntime拒绝。
8. PPT Skill缺 runtime 时返回 needs_runtime，不得 pip 或动态写 generate.py。
9. 中文 PPT 的 CJK helper 只有一个实现，XML 和 render 测试通过。
10. LibreOffice、Poppler 真实 probe 通过才可 ready。
11. 删除或不存在的 Codex cache 不影响 Awaken 已激活 runtime。
12. 执行 shell、text_edit、presentation_create 后重启 Desktop，工具卡、结果、Artifact 和终态完整恢复。
13. journal 写入失败不会被静默吞掉。
14. retryable=false 的相同失败调用第二次被阻断；retryable=true 的相同失败调用第三次被阻断，并给出 recovery options。
15. macOS 与 Windows 构建/路径 fixture 通过。
16. 按根 README 从真实 Awaken Desktop 完成最终验收并保存截图或录屏。

具体任务和命令见任务.md、检查清单.md。
